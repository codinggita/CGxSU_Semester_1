# 18. State Management

State management in Next.js — local state, server state, TanStack Query, Zustand, and Redux Toolkit.

---

## 1. State Management in Next.js

```text
State
├── Local State      → useState / useReducer
├── Server State     → Server Component fetch / TanStack Query
└── Client / Global  → Zustand / Redux Toolkit
```

Do not start by picking a library. Ask: **where does this state belong?**

---

## 2. Local State

Local state belongs to a component or small subtree — modal open, dropdown, tab, input, toggle.

```tsx
"use client";

import { useState } from "react";

export function Counter() {
	const [count, setCount] = useState(0);
	return <button onClick={() => setCount(count + 1)}>Count: {count}</button>;
}
```

If only one component needs the state, keep it local. Do not move everything into Redux/Zustand.

---

## 3. Server State

**Server state** is the formal term (popularized by TanStack Query) for remote data owned by the backend/database — users, products, orders. In any REST-backed application, the database is the source of truth and the browser holds a possibly stale copy.

Characteristics:

```text
Remote · Asynchronous · Shared · Backend-owned · Potentially stale · Cacheable · Refetchable
```

In Next.js, server data can come from a **Server Component `fetch()`** (Next.js cache) or **`useQuery()`** in a Client Component (TanStack Query cache). For `fetch()`, revalidation, and caching details, see **Data Fetching** and **Caching & Revalidation**.

---

## 4. Client State

Client state lives in the browser/UI — theme, sidebar, modal, temporary filters. It is not automatically global:

```tsx
const [isOpen, setIsOpen] = useState(false); // client state, but local
```

Use global stores only when multiple client subtrees genuinely share the same state.

---

## 5. Local vs Server vs Global

| Type          | Example                | Typical Approach                  |
| ------------- | ---------------------- | --------------------------------- |
| Local         | Modal open             | `useState`                        |
| Server        | Products, orders       | Server Component / TanStack Query |
| Global client | Theme, complex cart UI | Zustand / Redux Toolkit           |

---

## 6. Next.js Cache vs TanStack Query Cache

These are **different caching systems**:

### Next.js server-side cache

```text
Server Component → fetch() → Next.js caching
```

### TanStack Query cache

```text
Client Component → useQuery() → TanStack Query cache
```

Do not treat them as the same cache. Configuring `staleTime` in TanStack Query does not configure Next.js ISR.

---

## 7. Axios vs `fetch` in Next.js

Axios (common in Express/React applications) works in Next.js too:

```ts
import axios from "axios";

const response = await axios.get("https://api.example.com/products");
```

However:

> **Next.js provides special caching/revalidation integration around server-side `fetch()`.**

A normal Axios request does not automatically participate in that same Next.js `fetch` caching behavior.

### When to prefer `fetch()`

```ts
await axios.get("https://api.example.com/products");
```

does not automatically mean:

```text
Next.js Data Cache + ISR
```

Axios makes the HTTP request. Next.js must provide the caching layer separately.

For server-side caching in Next.js, prefer `fetch()` — its caching and revalidation behavior is built into the framework.

### When Axios still makes sense

Axios is still appropriate when you already have:

```text
Axios interceptors
Shared API client
Custom HTTP configuration
Existing backend/client abstraction
Common request/response handling
```

### Quick rule

```text
Axios         → HTTP client
Next.js cache → Caching/revalidation mechanism
```

Axios itself does not provide Next.js ISR.

## 8. TanStack Query

TanStack Query is primarily a **server-state management library** for the client:

```text
Queries · Mutations · Query cache · Refetching · Invalidation
Loading/error states · Pagination · Optimistic updates
```

```tsx
"use client";

import { useQuery } from "@tanstack/react-query";

export function Products() {
	const { data, isPending, error } = useQuery({
		queryKey: ["products"],
		queryFn: getProducts,
	});

	if (isPending) return <p>Loading...</p>;
	if (error) return <p>Something went wrong</p>;
	return <ProductList products={data} />;
}
```

### 8.1 Query

A query represents a request for server state:

```tsx
const { data, isPending, error } = useQuery({
	queryKey: ["products"],
	queryFn: getProducts,
});
```

```text
queryKey + queryFn → TanStack Query → Server Data
```

### 8.2 Query Key

A query key identifies cached server state:

```ts
["products"][("products", productId)][("products", { category: "laptop" })];
```

TanStack Query uses the key to identify, cache, and invalidate queries.

### 8.3 Query Function

```ts
async function getProducts() {
	const response = await fetch("https://api.example.com/products");

	if (!response.ok) {
		throw new Error("Failed to fetch products");
	}

	return response.json();
}
```

```tsx
useQuery({ queryKey: ["products"], queryFn: getProducts });
```

### 8.4 Query Cache

```text
Component A ──┐
              ▼
        Query Cache  ← shared by same queryKey
              ▲
Component B ──┘
```

If Component A fetches `["products"]`, Component B can reuse the cached result per configuration.

### 8.5 `staleTime`

`staleTime` controls how long data is considered fresh:

```tsx
useQuery({
	queryKey: ["products"],
	queryFn: getProducts,
	staleTime: 60 * 1000,
});
```

```text
Data fetched → Fresh for 60s → Becomes stale
```

> **Stale does not mean deleted.** Cached data can remain available after becoming stale.

### 8.6 `gcTime`

`gcTime` controls how long **unused** query data stays in cache before garbage collection:

```text
Query used → Component unmounts → Unused → After gcTime → Removed
```

Check version-specific docs for defaults.

### 8.7 `staleTime` vs `gcTime`

```text
staleTime → how long data is considered fresh
gcTime    → how long unused cached data can remain
```

```ts
useQuery({
	queryKey: ["products"],
	queryFn: getProducts,
	staleTime: 60_000,
	gcTime: 5 * 60_000,
});
```

### 8.8 Queries vs Mutations

**Query** — retrieve server state (typically GET):

```text
Products · Users · Orders · Profile
```

**Mutation** — change server state (POST / PUT / PATCH / DELETE):

```text
Create product · Update profile · Delete order
```

### 8.9 Mutation Example

```tsx
"use client";

import { useMutation } from "@tanstack/react-query";

export function CreateProduct() {
	const mutation = useMutation({ mutationFn: createProduct });

	return (
		<button onClick={() => mutation.mutate({ name: "Laptop" })}>
			Create
		</button>
	);
}
```

```text
Button → Mutation → Node.js API → Database
```

### 8.10 Query Invalidation

After creating a product, invalidate stale cache:

```tsx
queryClient.invalidateQueries({ queryKey: ["products"] });
```

```text
Create Product → DB changes → Invalidate ["products"] → Refetch → UI updates
```

### 8.11 With a Separate Node.js Backend

```text
Browser → Client Component → TanStack Query → Node.js API → Database
```

```ts
async function getProducts() {
	const response = await fetch("https://api.example.com/products");
	if (!response.ok) throw new Error("Failed to fetch products");
	return response.json();
}
```

```tsx
useQuery({ queryKey: ["products"], queryFn: getProducts });
```

This is separate from the Next.js server cache — **Next.js Cache vs TanStack Query Cache** explains the difference.

### 8.12 Combined with Next.js

Combine server rendering with client-side server-state management:

```text
                 Next.js Server
                       │
                Initial Data
                       ▼
                 Node.js API → Database

                       ▼
                    Browser
                       │
                TanStack Query → Query Cache
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
     Refetch        Mutation       Invalidate
```

Use when you need server-side initial data **and** client-side refetching, mutations, or invalidation.

### 8.13 Hydration

Server prefetch + client hydration:

```text
Next.js Server → Prefetch Query → Dehydrate → Browser → Hydrate → TanStack Query
```

This is an advanced topic — learn it after you are comfortable with queries, mutations, and caching basics.

### 8.14 When to Use TanStack Query

Good use cases:

```text
Client-side server data · Frequent refetching · Polling · Pagination
Infinite scrolling · Mutations · Optimistic updates · Query invalidation
```

Examples: admin dashboard, order management, infinite search, complex filtering.

### 8.15 When TanStack Query Is Not Required

Do not reach for TanStack Query by default. A Server Component fetch is often enough.

**With revalidation:**

```tsx
export default async function ProductsPage() {
	const response = await fetch("https://api.example.com/products", {
		next: { revalidate: 3600 },
	});

	const products = await response.json();
	return <ProductList products={products} />;
}
```

**Simple static page:**

```tsx
export default async function AboutPage() {
	const data = await getData();
	return <About data={data} />;
}
```

Use TanStack Query when the **browser** needs richer server-state management — refetching, caching across client components, mutations, invalidation — not for every server fetch.

## 9. Global State

Global state is client-side state shared across multiple components:

```text
Theme · Shopping cart UI · Multi-step workflow · Global UI preferences
```

Common tools: **Zustand**, **Redux Toolkit**.

---

## 10. Zustand

Zustand is a lightweight library for global **client** state.

### 10.1 Basic Store

```ts
import { create } from "zustand";

type CartStore = {
	count: number;
	addItem: () => void;
};

export const useCartStore = create<CartStore>((set) => ({
	count: 0,
	addItem: () => set((state) => ({ count: state.count + 1 })),
}));
```

```tsx
"use client";

const count = useCartStore((state) => state.count);
const addItem = useCartStore((state) => state.addItem);
```

### 10.2 No Provider in the App Router

A store created with `create()` is a module-level hook — import and use it in any Client Component. Zustand's docs state: _"Use the hook anywhere, no providers are needed."_

This is a practical App Router advantage over Redux: Redux's `<Provider>` uses React Context and must live inside a Client Component boundary (**Provider Must Be a Client Component**). Zustand skips that wrapping step for the default `create()` pattern.

(Context + `createStore()` from `zustand/vanilla` is optional for per-tree or prop-initialized stores — not the default path.)

### 10.3 When Zustand Is Useful

```text
Small/medium global client state · Low boilerplate · Theme · Sidebar · Cart UI · Multi-step wizard
```

Zustand is **not** a replacement for server-state management.

---

## 11. Redux Toolkit

Redux Toolkit is the modern Redux API for complex global **client** state.

### 11.1 Basic Slice

```ts
import { createSlice } from "@reduxjs/toolkit";

const cartSlice = createSlice({
	name: "cart",
	initialState: { count: 0 },
	reducers: {
		addItem(state) {
			state.count += 1;
		},
	},
});

export const { addItem } = cartSlice.actions;
export default cartSlice.reducer;
```

### 11.2 Provider Must Be a Client Component

In the App Router, `app/layout.tsx` is a **Server Component by default**. Redux's `<Provider>` uses React Context — Context providers require `"use client"`. Placing `<Provider>` directly in `layout.tsx` will break.

Per the [Redux Next.js guide](https://redux.js.org/usage/nextjs): _"Any component that interacts with the Redux store … needs to be a client component … because accessing the store requires React context."_

**Fix — dedicated providers wrapper:**

```tsx
// app/providers.tsx
"use client";

import { Provider } from "react-redux";
import { store } from "./store";

export function Providers({ children }: { children: React.ReactNode }) {
	return <Provider store={store}>{children}</Provider>;
}
```

```tsx
// app/layout.tsx — stays a Server Component
import { Providers } from "./providers";

export default function RootLayout({
	children,
}: {
	children: React.ReactNode;
}) {
	return (
		<html lang='en'>
			<body>
				<Providers>{children}</Providers>
			</body>
		</html>
	);
}
```

For per-request store creation in SSR apps, use a `makeStore()` factory inside the provider with `useRef` — see the official Redux Next.js docs.

### 11.3 When Redux Toolkit Is Useful

Appropriate when client state is large and cross-cutting:

```text
Complex multi-feature client workflows · Predictable state transitions · DevTools · Existing Redux codebase
```

In Next.js, the main extra cost vs Zustand is the **Provider Client Component wrapper** in the App Router — justified when Redux's structure and tooling match your needs.

---

## 12. Zustand vs Redux Toolkit

| Feature            | Zustand                         | Redux Toolkit                          |
| ------------------ | ------------------------------- | -------------------------------------- |
| Boilerplate        | Low                             | Higher                                 |
| App Router setup   | No Provider needed (`create()`) | Requires Client Component `<Provider>` |
| Small/medium state | Excellent                       | Can be overkill                        |
| Large applications | Best                            | Excellent                              |
| DevTools           | Available                       | Excellent                              |

---

## 13. TanStack Query vs Zustand vs Redux Toolkit

| Library        | Best for                                                    |
| -------------- | ----------------------------------------------------------- |
| TanStack Query | Server state (products, orders, users)                      |
| Zustand        | Simple/medium global client state (theme, sidebar, cart UI) |
| Redux Toolkit  | Complex global client state (large workflows, many teams)   |

These are not direct replacements for one another.

---

## 14. Do Not Store All Server State in Global State

Avoid routing every API response through Redux:

```text
API → Redux → products, orders, users
```

You would manually handle loading, errors, caching, refetching, invalidation, and pagination — work TanStack Query already provides.

Better separation:

```text
Server data     → TanStack Query (or Server Component fetch)
Global client   → Zustand / Redux Toolkit
```

---

## 15. Example: E-Commerce State Architecture

```text
Products / Orders  → Server Component or TanStack Query
Theme / Cart UI    → Zustand
Complex checkout   → Zustand or Redux Toolkit
```

## 16. Shopping Cart Example

A cart spans multiple state types:

**Client cart/UI** — selected items, quantity UI, drawer open/closed → Zustand

**Server cart** — persisted cart, inventory, prices, checkout → TanStack Query + backend API

```text
Cart ≠ automatically global state
```

## 17. State Management Decision Guide

Use this process — start with the simplest option:

```text
1. Is it temporary UI state?
       ↓
   useState / useReducer

2. Is it server-owned data needed during rendering?
       ↓
   Server Component + fetch

3. Does the browser need advanced server-state management?
       ↓
   TanStack Query

4. Do multiple client components need shared state?
       ↓
   Zustand / Redux Toolkit
```

```text
What kind of state is this?
             │
      ┌──────┴──────┐
      │             │
    Local         Server
      │             │
   useState     Server Component
                  or TanStack Query
      │
      └─────────────────────
                │
       Multiple client components?
                │ Yes
                ▼
         Global Client State
                │
          ┌─────┴─────┐
          │           │
       Zustand     Redux Toolkit
```

Quick reference:

> **Local state** — owned by a component (`useState`).
>
> **Server state** — remote data owned by the backend (Server Component fetch or TanStack Query).
>
> **Client/global state** — shared browser state (Zustand / Redux Toolkit).
>
> **TanStack Query** — client-side server-state management, not Next.js ISR.
>
> **Next.js `fetch()` cache** — separate from TanStack Query cache.
>
> **Redux Provider** — must be in a Client Component in the App Router.
>
> **Zustand `create()`** — no Provider wrapper needed.

---

## 18. Common Mistakes

- **Redux for every API response** — server data is server state, not global client state
- **TanStack Query for modal open** — use `useState`
- **Zustand as a server cache** — use TanStack Query or Server Component fetch for products/orders/users
- **Everything in one global store** — keep state as local as practical
- **Assuming TanStack Query provides ISR** — it does not; Next.js server cache is separate

---

## 19. App Router Architecture

```text
Server Component
      │
      ├── fetch server data
      └── render initial UI
                │
                ▼
         Client Component
                │
         ┌──────┴──────┐
         ▼             ▼
    TanStack Query   Global State
                      │
                Zustand / Redux
```

Different approaches coexist in one application.

---

## 20. Pages Router Consideration

TanStack Query, Zustand, and Redux Toolkit work with both App Router and Pages Router.

The App Router adds the Server/Client Component model. Pages Router uses traditional client React with `getServerSideProps` / `getStaticProps` for server data.

```text
TanStack Query ≠ Server Components — they solve different problems
```

---

## 21. Recommended Architecture

For a Next.js frontend with a separate Node.js backend:

```text
                         Browser
                            │
              ┌─────────────┴─────────────┐
              │                           │
       Server-rendered UI            Client UI
              │                           │
        Next.js Server             TanStack Query
              │                     Query Cache
              └─────────────┬─────────────┘
                            ▼
                       Node.js API → Database

Client UI → Zustand / Redux Toolkit (global client state only)
```

Four separate systems — do not conflate them:

```text
Next.js Server Cache  ≠  TanStack Query Cache  ≠  Zustand Store  ≠  Redux Store
```
