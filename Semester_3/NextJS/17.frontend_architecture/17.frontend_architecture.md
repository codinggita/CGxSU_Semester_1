# 17. Frontend Architecture

Production Next.js frontend structure — folder layout, feature organization, and Server/Client Component boundaries. Next.js changes frontend architecture through the App Router, Server Components, and colocation compared to a typical React component tree.

---

## 1. Frontend Architecture in Next.js

In a typical Express + React stack, the React app and Express API are separate. In Next.js, routes, UI, and server logic live in one project. A practical layering:

```text
app/           → routing + page composition
features/      → business UI, actions, types per domain
components/    → shared generic UI + layout
lib/           → auth, db, utilities
```

```text
Route → Feature components → Shared UI
```

Keep components focused. Avoid one page component that fetches data, manages auth, handles payments, and renders the entire layout.

---

## 2. Folder Organization

### Type-based vs feature-based

Small apps can use flat folders (`components/`, `hooks/`, `services/`). As the app grows, feature-based grouping scales better:

```text
src/
├── app/
├── components/
│   ├── ui/          ← Button, Input, Modal, Table
│   └── layout/      ← Navbar, Sidebar, Footer
├── features/
│   ├── products/
│   │   ├── components/
│   │   ├── actions/
│   │   └── types.ts
│   ├── cart/
│   └── orders/
└── lib/
```

**UI vs business components:**

| Layer      | Examples                      | Location                         |
| ---------- | ----------------------------- | -------------------------------- |
| Generic UI | `Button`, `Card`, `Modal`     | `components/ui/`                 |
| Layout     | `Navbar`, `Footer`            | `components/layout/`             |
| Business   | `ProductCard`, `CheckoutForm` | `features/<feature>/components/` |

### Route structure vs feature structure

The App Router owns URLs:

```text
app/products/page.tsx
app/products/[id]/page.tsx
```

Business code does **not** have to live inside `app/`. Keep `app/` thin — compose from `features/`:

```text
app/        → routing + route composition
features/   → business UI and logic
components/ → shared UI
lib/        → infrastructure
```

### Colocation

Components used by **one route only** can stay next to that route:

```text
app/products/[id]/
├── page.tsx
├── ProductGallery.tsx
├── ProductInfo.tsx
└── ProductReviews.tsx
```

Move to `features/products/components/` when reused across `/products`, `/search`, `/home`, etc. Extract based on **actual reuse**, not prematurely.

## 3. Server and Client Components

The main App Router difference from CRA/ Vite React: components are **Server Components by default** unless marked `"use client"`.

|                                 | Server Component | Client Component         |
| ------------------------------- | ---------------- | ------------------------ |
| Default in App Router           | Yes              | Only with `"use client"` |
| Can `async` / fetch on server   | Yes              | No                       |
| `useState`, `useEffect`, events | No               | Yes                      |
| Browser APIs                    | No               | Yes                      |

Server/Client describes **where code runs**. It is not the same as SSR/SSG/ISR/CSR — those describe **rendering strategy**. A Server Component ≠ SSR; a Client Component ≠ CSR.

### Decision rule

```text
Start as Server Component
        ↓
Needs useState, useEffect, events, or browser APIs?
     No → stay Server
     Yes → mark that component "use client"
```

Do not add `"use client"` just because a component renders UI.

### Push client boundaries down

```text
ProductPage        → Server
ProductInfo        → Server
ProductImage       → Server
QuantitySelector   → Client
AddToCartButton    → Client
ProductReviews     → Server
```

Avoid making the entire page a Client Component because one button needs interactivity.

### Server → Client data flow

Server Components fetch data; pass **serializable props** to Client Components:

```tsx
// app/products/[id]/page.tsx — Server
export default async function ProductPage({
	params,
}: {
	params: Promise<{ id: string }>;
}) {
	const { id } = await params;
	const product = await getProduct(Number(id));

	return (
		<>
			<ProductInfo product={product} />
			<AddToCartButton productId={product.id} />
		</>
	);
}
```

```tsx
// features/cart/components/AddToCartButton.tsx — Client
"use client";

export function AddToCartButton({ productId }: { productId: number }) {
	return <button>Add {productId}</button>;
}
```

Never pass secrets to Client Components — props reach browser-side code. Call third-party APIs from Server Actions or Route Handlers instead.

### Shared components are not automatically Client

A presentational `Card` or `Button` without hooks can remain server-compatible. Only add `"use client"` when the component needs client capabilities (e.g. an interactive dropdown).

### State ownership

- **Server state** — products, orders, users (fetch on server; don't copy everything into global client state)
- **Client state** — modal open, selected tab, form input, dropdown (keep local unless multiple client subtrees need it)

```tsx
// Server fetch + client filter when interaction is needed
export default async function ProductsPage() {
	const products = await getProducts();
	return <ProductList products={products} />;
}
```

```tsx
"use client";

export function ProductList({ products }: { products: Product[] }) {
	const [filter, setFilter] = useState("");
	// filter client-side only when interactivity requires it
}
```

## 4. Where to Put a Component

```text
Generic UI (Button, Input)?
  → components/ui/

Used across multiple features?
  → components/ or shared feature export

Belongs to one business domain?
  → features/<feature>/components/

Only used by one route?
  → colocate under app/.../ until reused
```

Then separately:

```text
Needs useState / useEffect / events / browser APIs?
  No → Server-compatible
  Yes → "use client"
```

---

## 5. Dependency Direction

```text
app/products/page.tsx
       ↓
features/products/components/ProductList
       ↓
components/ui/Card
```

Generic UI must **not** import from `features/products` — that creates coupling. Features and routes depend on shared UI, not the reverse.

---

## 6. App Router vs Pages Router

These concepts apply to both routers:

- Reusable and feature components
- Shared UI vs business components
- Feature-based organization

**App Router adds** the Server/Client Component model. Pages Router uses the traditional all-client React model unless you fetch in `getServerSideProps` / `getStaticProps` and pass props down.

```text
App Router:     app/products/page.tsx  + Server/Client split
Pages Router:   pages/products/index.tsx + features/ + components/
```

Same `features/` and `components/` layout works for both; only the routing folder and server/client boundaries differ.

## 7. Example Architecture

```text
src/
├── app/
│   ├── products/
│   │   ├── page.tsx
│   │   └── [id]/
│   │       ├── page.tsx
│   │       ├── ProductGallery.tsx
│   │       └── QuantitySelector.tsx   ← Client
│   ├── cart/page.tsx
│   └── orders/page.tsx
│
├── components/
│   ├── ui/
│   └── layout/
│
├── features/
│   ├── products/
│   │   ├── components/
│   │   ├── actions/
│   │   └── types.ts
│   ├── cart/
│   └── orders/
│
└── lib/
```

```text
Next.js routes → route composition → feature layer (Server + Client) → shared UI
```

**Bad:** one `"use client"` page that fetches, manages cart, auth, modals, filters, and renders everything.

**Good:** thin server page composing `ProductFilters` (client), `ProductList` (server), `AddToCartButton` (client), and shared layout.

---

## 8. Common Mistakes

- **`"use client"` on every file** — keep the client boundary narrow
- **Extracting abstractions too early** — colocate until reuse is real
- **Giant props APIs** — prefer composition (`children`, slot props) over dozens of boolean flags
- **Global state for all UI state** — modals/tabs/inputs stay local when possible
- **Copying all server data into Redux/Zustand** — fetch on server; hydrate client state only when needed
- **Secrets in Client Component props**
- **Business logic inside generic `components/ui`**
- **Putting all business code inside `app/`** — use `features/`

---

## 9. Quick Reference

| Rule                  | Location / action                           |
| --------------------- | ------------------------------------------- |
| Generic UI            | `components/ui/`                            |
| App layout            | `components/layout/`                        |
| Business UI           | `features/<feature>/components/`            |
| Route-only UI         | colocate under `app/.../`                   |
| Default in App Router | Server Component                            |
| Client boundary       | smallest component that needs interactivity |
| Data fetching         | Server Component or Route Handler           |
| Interactivity         | Client Component with props from server     |

> **Not every component needs to be reusable or a Client Component.**
>
> **Keep `app/` thin; put business code in `features/`.**
>
> **Server/Client = execution boundary. SSR/SSG/ISR/CSR = rendering strategy.**
