````markdown
# 25. Logging & Monitoring in Next.js

## 1. Introduction

Logging and monitoring help us understand how an application behaves after it is deployed. Testing locally cannot reveal every issue that users may encounter in production.

They help us:

- Detect application errors and failures.
- Understand when and where an error occurred.
- Monitor API and page performance.
- Identify slow database queries and external services.
- Track application availability.
- Investigate issues reported by users.

Monitoring is not only about collecting logs. It also involves tracking errors, performance, availability, and application health.

## 2. Logging

Logging records important events that occur while the application is running. Logs can help developers investigate unexpected behavior and understand what happened before a failure.

In Next.js, we can use standard JavaScript logging methods on the server and in the browser. In production, server logs are typically collected by the hosting platform, while client logs appear in the browser's developer console unless sent to a monitoring service.

### Log levels

| Level   | Purpose                                                           |
| ------- | ----------------------------------------------------------------- |
| `debug` | Detailed information useful during development or troubleshooting |
| `info`  | Expected application events or milestones                         |
| `warn`  | Unexpected situations that may not have caused a failure          |
| `error` | Failures that require investigation                               |

Log meaningful events such as failed database operations, external API failures, authentication events, or important business actions. Avoid logging every routine operation without a clear reason.

### Structured log information

When logging, include useful context where appropriate, such as an event name, request ID, resource ID, timestamp, and duration. Structured information makes logs easier to search and filter in a logging platform.

```ts
console.info({
	event: "product.created",
	productId: "prod_123",
	userId: "user_456",
	timestamp: new Date().toISOString(),
});
```
````

Never log passwords, session tokens, cookies, API keys, payment details, or other sensitive information.

## 3. Error Handling vs. Error Monitoring

Error handling and error monitoring serve different purposes.

- **Error handling** determines how the application responds when something goes wrong.
- **Error monitoring** records and reports failures so developers can investigate them.

For example, an API can catch a database failure and return a safe response to the user. Error monitoring can separately capture the exception, stack trace, environment, and relevant context for debugging.

A user-friendly error response does not mean the error has been monitored. Similarly, recording an error does not replace handling it appropriately.

## 4. Error Boundaries in Next.js

Next.js provides error boundary files to handle errors during rendering and show a fallback UI instead of leaving the user with a broken page.

### `error.tsx`

An `error.tsx` file creates a route-segment error boundary. It must be a Client Component and receives the error and a `reset` function.

```tsx
"use client";

export default function Error({
	error,
	reset,
}: {
	error: Error & { digest?: string };
	reset: () => void;
}) {
	return (
		<div>
			<h2>Something went wrong.</h2>
			<button onClick={reset}>Try again</button>
		</div>
	);
}
```

The `reset` function attempts to recover by re-rendering the affected segment.

An error boundary is a user-interface recovery mechanism. It does not automatically provide a complete production error-monitoring system.

## 5. Production Error Monitoring

In production, developers need to know when errors happen even if users do not report them. Error monitoring tools collect exceptions and provide details that help diagnose failures.

A monitoring service may capture:

- Error message and stack trace.
- Which page, action, or request failed.
- Browser, device, and environment information.
- Error frequency and affected users.
- Related breadcrumbs or events leading up to the error.
- Release or deployment version where the error occurred.

### Error monitoring with Sentry

Sentry is an example of an error-monitoring platform that can be integrated with Next.js to capture errors from server-side and client-side code.

It can help answer:

- What error occurred?
- Where did it occur?
- How often is it happening?
- Which users or sessions are affected?
- Did it begin after a recent deployment?

Monitoring SDKs should be configured according to the official Next.js integration instructions. Avoid manually reporting the same error multiple times if it is already automatically captured by the SDK.

## 6. Next.js Instrumentation

Next.js supports instrumentation for initializing monitoring and observability integrations.

### `instrumentation.ts`

The `instrumentation.ts` file is located at the root of the application (or inside `src`, if the project uses that directory structure). It is used to initialize code that should run when the Next.js server starts.

A common use case is initializing a monitoring SDK.

```ts
// instrumentation.ts
export async function register() {
	// Initialize server-side monitoring here.
}
```

The `register` function is called when the server instance starts. Monitoring SDK initialization is commonly placed here or in SDK-specific configuration files, depending on the integration.

Next.js also exposes an `onRequestError` instrumentation hook that monitoring integrations can use to capture server request errors.

Instrumentation is not a replacement for handling errors in application code. It provides a place to initialize and connect monitoring capabilities.

## 7. Request Tracking and Correlation IDs

A request ID is a unique identifier associated with an incoming request. It can help correlate logs or error reports related to the same request.

When a request fails, including its request ID in a response or log entry can help support and developers locate the relevant information.

Request IDs are especially useful when several requests are processed at the same time. Keep request tracking simple for this project; do not build a complex distributed tracing system.

## 8. Performance Monitoring

Performance monitoring helps identify slow pages, APIs, database operations, and external services.

Useful measurements include:

- **Response duration:** how long a request takes to complete.
- **Throughput:** how many requests the application handles over a period.
- **Error rate:** how frequently requests fail.
- **Database duration:** how long database operations take.
- **External service duration:** time spent waiting for third-party APIs.
- **Resource usage:** CPU, memory, and other server resource consumption, often provided by the hosting platform.

These measurements help determine whether the application is slow, overloaded, or experiencing failures.

### Investigating slow requests

When a request is consistently slow, investigate its main dependencies:

1. Database queries taking too long.
2. External APIs responding slowly.
3. Unnecessary sequential requests.
4. Large amounts of data being fetched or processed.
5. Expensive server-side computation.
6. Excessive client-side JavaScript or rendering work.

Do not optimize based on assumptions. Use measurements to identify the bottleneck first.

## 9. Core Web Vitals

Core Web Vitals are user-focused metrics used to understand the real-world experience of a web page.

| Metric                          | What it measures                                           | Good target         |
| ------------------------------- | ---------------------------------------------------------- | ------------------- |
| LCP (Largest Contentful Paint)  | Loading performance; when the main content becomes visible | 2.5 seconds or less |
| INP (Interaction to Next Paint) | Responsiveness to user interactions                        | 200 ms or less      |
| CLS (Cumulative Layout Shift)   | Unexpected visual layout movement                          | 0.1 or less         |

These thresholds are evaluated at the 75th percentile of page visits, separated for mobile and desktop when assessing real-user data.

Core Web Vitals can help identify problems such as slow hero images, heavy client-side code, delayed interaction responses, and layout shifts caused by content loading.

## 10. Health Checks and Availability Monitoring

A health check is a simple endpoint or check that indicates whether an application is running or able to serve requests.

For example, a basic Route Handler can expose an application health endpoint:

```ts
// app/api/health/route.ts
export async function GET() {
	return Response.json({ status: "ok" });
}
```

External uptime monitoring services can periodically request this endpoint and alert the team if the application stops responding.

A basic health endpoint only confirms that the endpoint responds. If the application depends on a database or other critical service, a separate readiness check may also verify those dependencies. Do not make a health check unnecessarily expensive.

### Health, liveness, and readiness

- **Health check:** provides a general indication of application health.
- **Liveness:** indicates that the process is running and should not be restarted.
- **Readiness:** indicates that the application is ready to handle traffic, including required dependencies when appropriate.

For a small deployment, a simple health endpoint and hosting-platform uptime checks may be sufficient.

## 11. Monitoring Client and Server Errors

Next.js applications can fail in both server-side and browser-side code.

| Area           | Examples                                                | Monitoring focus                                           |
| -------------- | ------------------------------------------------------- | ---------------------------------------------------------- |
| Server         | Server Components, Route Handlers, Server Actions       | Exceptions, request failures, database errors, latency     |
| Client         | Client Components, event handlers, browser interactions | Runtime errors, failed interactions, browser compatibility |
| Infrastructure | Hosting platform, server process, database              | Availability, resource usage, service failures             |

A production monitoring setup should capture relevant errors across these areas. Browser monitoring should be configured carefully to avoid collecting sensitive user data.

## 12. Logs, Errors, Metrics, and Availability

These are complementary parts of observability:

| Type                    | Main question it answers        | Example                                         |
| ----------------------- | ------------------------------- | ----------------------------------------------- |
| Logs                    | What happened?                  | An order creation request failed                |
| Error monitoring        | What failed, and where?         | Exception with stack trace and affected release |
| Metrics / performance   | How is the app behaving?        | API latency increased or error rate spiked      |
| Availability monitoring | Is the app reachable and ready? | Health endpoint check failed                    |

A monitoring tool may provide more than one of these capabilities. The important thing is to know which signals are available and how to use them during an investigation.

## 13. Common Mistakes

- Relying only on local testing to discover production problems.
- Showing an error UI without recording the underlying failure.
- Logging sensitive information.
- Logging excessive noise that makes important events difficult to find.
- Returning internal stack traces or database details to users.
- Monitoring only the server and ignoring client-side errors.
- Measuring performance without investigating the underlying bottleneck.
- Treating a successful health endpoint response as proof that every dependency is working.
- Adding monitoring tools without configuring alerts or knowing how to review the reports.

## 14. Key Takeaways

- Logging records meaningful events and provides context for troubleshooting.
- Error handling protects the user experience; error monitoring helps developers investigate failures.
- `error.tsx` provides a route-segment fallback UI but is not a complete monitoring solution.
- Production error-monitoring tools can capture server and client errors.
- Next.js instrumentation provides hooks for initializing monitoring integrations.
- Performance monitoring helps identify slow requests, database operations, and external dependencies.
- Core Web Vitals measure important aspects of the real user experience.
- Health checks and uptime monitoring help detect availability problems.
- Logs, errors, performance metrics, and health checks work together to provide visibility into a production application.
