# 24. Testing in Next.js

Testing a Next.js application at every level — unit, integration, API, database, authentication, and end-to-end browser workflows — for **both App Router and Pages Router**. Vitest and Playwright are configured per the official Next.js docs, with a complete admin-only product-creation walkthrough and runnable tests at each layer. The objective is confidence that important behavior works correctly, not writing the maximum number of tests.

---

## 1. What Is Testing and Why It Matters

Testing is the process of automatically verifying that application behavior matches expected behavior.

An application may include:

```text
Registration
Login
Products
Cart
Checkout
Admin Dashboard
```

Manual testing becomes repetitive:

```text
Open browser
   ↓
Login
   ↓
Open products
   ↓
Add product
   ↓
Open cart
   ↓
Checkout
```

Automated tests allow these behaviors to be verified repeatedly without opening a browser every time you change code.

Testing provides:

- **Confidence** — you know a feature works before shipping
- **Regression protection** — a refactor cannot silently break login or checkout
- **Safer refactoring** — change internals without fear when tests assert behavior
- **Faster development** — catch bugs in seconds instead of minutes of manual clicking
- **Living documentation** — tests describe what the system is supposed to do

---

## 2. What to Test and the Testing Pyramid

Test **observable behavior** — what the user or API consumer sees — not internal implementation.

| Layer | Test the behavior | Not the implementation |
| ----- | ----------------- | ---------------------- |
| Unit | `calculateDiscount(1000)` returns `100` | Whether it uses `if` vs a lookup table |
| Server Action | Invalid product name returns error | Whether `revalidatePath` was called |
| Route Handler | `POST /api/products` without session → `401` | Which middleware function ran first |
| Component | Submit button shows "Saving…" while pending | Whether `useState` flipped to `true` |
| E2E | After login, dashboard shows the user's name | Which React hook triggered the render |

**Priority areas in a Next.js app:**

```text
Validation logic       → unit tests
Service + database     → integration tests
Route Handlers / APIs  → API tests (status, body, auth)
Server Actions         → unit or integration (with mocked storage)
Critical user flows    → Playwright E2E (login, checkout, admin)
```

If a refactor breaks a test but the behavior is still correct, the test was tied to implementation — rewrite it to assert the outcome instead.

### 2.1 The Testing Pyramid

A useful mental model is:

```text
                 E2E Tests
               /           \
              /             \
        Integration Tests
          /             \
         /               \
       Unit Tests
```

Generally:

```text
Many unit tests
Some integration/API tests
Fewer E2E tests
```

Unit tests are usually faster and cheaper. E2E tests are slower and can be more fragile. Use each level for the right purpose.

---

## 3. Testing Levels Overview

Testing concepts group into two categories — scope/isolation and target/concern:

**Test scope** (how much of the app is involved):

```text
1. Unit Testing
2. Integration Testing
3. End-to-End Testing
```

**Test target / concern** (what behavior you verify):

```text
API behavior
Database behavior
Authentication        → "Who are you?"
Authorization         → "Are you allowed to do this?"
Components
Server Actions
```

These are **not** six independent formal testing levels. A single test can belong to more than one category — for example, an API test is often also an integration test, and an authentication test can be unit, integration, API, or E2E depending on what you verify.

| Label | Describes | Example |
| ----- | --------- | ------- |
| Unit | Scope | `validateProduct()` in isolation |
| Integration | Scope | `createProduct()` + Prisma test DB |
| API | Subject | `POST /api/admin/products` → `401` |
| Database | Subject | Unique slug constraint enforced |
| Auth | Subject | Expired session → redirect |
| E2E | Scope + subject | Login → create product → visible in list |

Vitest and Jest are both valid test runners for Next.js — these examples standardize on **Vitest**, but the concepts apply regardless of runner.

| MERN / Express | Next.js | Notes |
| -------------- | ------- | ----- |
| Express route | Route Handler / Pages API Route | HTTP boundary testing is similar |
| Express controller | Route Handler / Server Action / Service | Keep business logic in services |
| Service layer | Service layer | Same testing approach |
| React component | Client Component / Server Component | RTL for client UI; data functions for server |
| SSR data fetching | Server Component / `getServerSideProps` | Test data functions, not framework internals |
| Static data fetching | Static Server Component / `getStaticProps` | Test returned props/data |
| Express middleware | Next.js auth / proxy mechanisms | Test observable outcomes |
| MongoDB test DB | PostgreSQL + Prisma test DB | Always use a dedicated test database |
| Jest | Vitest / Jest | Either works; these examples use Vitest |
| Supertest-style API test | Route Handler / API Route test | Mock `Request`/`Response` or `req`/`res` |
| Cypress / Playwright | Playwright | Cross-browser E2E |

Next.js changes **where** code executes, but the core testing principles remain the same. These are **conceptual mappings**, not exact one-to-one replacements.

## 4. Unit Testing

Unit testing verifies a small, isolated piece of code.

Good candidates include:

```text
Functions
Validators
Formatters
Calculations
Business rules
Data transformations
Utilities
```

### 4.1 Unit Test Characteristics

A good unit test is generally:

```text
Independent
Fast
Deterministic
Focused
Easy to understand
```

Ideally it does not require a real database, network, browser, or payment provider unless those dependencies are specifically what the test is intended to verify.

### 4.2 Arrange, Act, Assert

A common unit-test pattern is:

```text
Arrange
   ↓
Act
   ↓
Assert
```

Example:

```ts
it("applies 10 percent discount at 1000", () => {
	// Arrange
	const total = 1000;

	// Act
	const discount = calculateDiscount(total);

	// Assert
	expect(discount).toBe(100);
});
```

This structure makes tests easier to read.

### 4.3 Test Suites and Test Cases

A test suite groups related tests:

```ts
describe("calculateDiscount", () => {
	it("does not apply discount below 1000", () => {
		// ...
	});

	it("applies 10 percent discount at 1000", () => {
		// ...
	});

	it("handles zero total", () => {
		// ...
	});
});
```

Conceptually:

```text
describe
   ↓
Test Suite
   ├── Test Case
   ├── Test Case
   └── Test Case
```

### 4.4 Positive, Negative, and Edge Cases

Do not test only successful scenarios.

**Positive case** — valid input → expected result

**Negative case** — invalid input → expected error

**Edge case** — boundary or unusual input → expected behavior

Examples of edge inputs:

```text
0
1
Negative value
Very large value
Empty string
Null
Undefined
Empty array
Duplicate value
Invalid format
```

### 4.5 Example — `calculateDiscount`

One business-logic example for unit testing. The admin create-product walkthrough uses `validateProduct` at every layer.

```ts
// lib/pricing.ts
export function calculateDiscount(total: number): number {
	if (total >= 1000) {
		return total * 0.1;
	}
	return 0;
}
```

```ts
// lib/pricing.test.ts
import { describe, expect, it } from "vitest";
import { calculateDiscount } from "./pricing";

describe("calculateDiscount", () => {
	it("does not apply discount below 1000", () => {
		expect(calculateDiscount(500)).toBe(0);
	});

	it("applies 10 percent discount at 1000", () => {
		expect(calculateDiscount(1000)).toBe(100);
	});

	it("returns 0 for zero total", () => {
		expect(calculateDiscount(0)).toBe(0);
	});
});
```

The test focuses only on the function — no database, no HTTP, no React.

## 5. Integration Testing and Mocking

Integration testing verifies that multiple parts work together.

Examples:

```text
Service
   ↓
Repository
   ↓
Database
```

or:

```text
Route Handler
   ↓
Service
   ↓
Repository
   ↓
Database
```

Unlike a unit test, integration testing intentionally includes multiple components.

### 5.1 Unit vs Integration

**Unit** — does this individual piece work?

```text
Function → Result
```

**Integration** — do these pieces work correctly together?

```text
Service → Repository → Database → Result
```

### 5.2 Integration Example

Suppose:

```ts
async function createUser(data: CreateUserInput) {
	const hashedPassword = await hashPassword(data.password);
	return userRepository.create({ ...data, password: hashedPassword });
}
```

An integration test verifies:

```text
createUser()
    ↓
Password hashing
    ↓
Repository
    ↓
Database
    ↓
User exists
```

This is more realistic than mocking every internal dependency.

### 5.3 Mocks

A mock replaces a dependency with a controlled fake implementation.

```text
Application
   ↓
Mock Payment Service   (instead of real Payment Service)
```

Mocks are useful when:

- A real service is expensive or slow
- A service is unavailable in CI
- A side effect is dangerous (charging a card, sending email)
- A deterministic response is required
- The dependency is outside your system

### 5.4 When Not to Mock

Over-mocking can make tests unrealistic:

```text
Mock database
Mock repository
Mock service
Mock authentication
```

The test may pass even though the real components do not work together.

A useful rule:

> Mock external systems when necessary, but allow important internal components to integrate when the integration itself is what you want to verify.

## 6. Vitest vs Jest

Both Vitest and Jest are JavaScript test runners. Developers familiar with Jest will find the syntax nearly identical — `describe`, `it`, `expect` work the same way.

| | Jest | Vitest |
| --- | --- | --- |
| Config | `jest.config.js` | `vitest.config.mts` |
| Speed | Good | Often fast in Vite-based projects |
| ESM / TypeScript | Supported with configuration | Built around the Vite ecosystem; strong TypeScript/ESM support |
| Next.js official guide | Older community examples | [Official Vitest guide](https://nextjs.org/docs/app/guides/testing/vitest) |

**These examples standardize on Vitest** per the [Next.js Vitest guide](https://nextjs.org/docs/app/guides/testing/vitest). The [with-vitest example](https://github.com/vercel/next.js/tree/canary/examples/with-vitest) is a ready-made starting point:

```bash
npx create-next-app@latest --example with-vitest with-vitest-app
```

> **Good to know:** Since `async` Server Components are new to the React ecosystem, Vitest currently does **not** support them. While unit tests still work for synchronous Server and Client Components, Next.js recommends **E2E tests** for async components. Async Server Components cannot be rendered directly in Vitest — test data functions in isolation and use E2E for the rendered page.

## 7. Vitest Configuration

Install Vitest and related packages as dev dependencies (from the official guide):

```bash
npm install -D vitest @vitejs/plugin-react jsdom @testing-library/react @testing-library/dom @testing-library/jest-dom @testing-library/user-event vite-tsconfig-paths dotenv-cli
```

The `test:integration:local` script uses `dotenv-cli` to load `.env.test`. Vitest runs as a standalone process outside Next.js's own env-loading pipeline — unlike `next dev` or `next build`, which load `.env.*` files automatically — so the test database URL must be injected explicitly for local integration runs. In CI, set `DATABASE_URL` directly as an environment variable.

Create `vitest.config.mts` in the project root:

```ts
// vitest.config.mts
import { defineConfig } from "vitest/config";
import react from "@vitejs/plugin-react";
import tsconfigPaths from "vite-tsconfig-paths";

export default defineConfig({
	plugins: [tsconfigPaths(), react()],
	test: {
		environment: "jsdom",
		setupFiles: ["./vitest.setup.ts"],
	},
});
```

Add a test script to `package.json`:

```json
{
	"scripts": {
		"dev": "next dev",
		"build": "next build",
		"start": "next start",
		"test": "vitest",
		"test:run": "vitest run",
		"test:integration": "vitest run --config vitest.integration.config.mts",
		"test:integration:local": "dotenv -e .env.test -- npm run test:integration"
	}
}
```

- `npm run test` — watch mode (re-runs on file changes)
- `npm run test:run` — single run (use in CI for unit/component tests)
- `npm run test:integration:local` — integration tests locally (loads `.env.test` via `dotenv-cli`)
- `npm run test:integration` — integration tests when `DATABASE_URL` is already set (CI)

For integration tests that need a real database, use a separate config file (`vitest.integration.config.mts`) that sets `test.fileParallelism: false`. Prisma Test Database covers database setup. In CI, set `DATABASE_URL` as an environment variable — no `.env.test` file is required on the runner.

## 8. React Testing Library

React Testing Library (RTL) tests components the way users interact with them — by role, label, and text — not by implementation details.

Create `vitest.setup.ts`:

```ts
// vitest.setup.ts
import "@testing-library/jest-dom/vitest";
```

The `@testing-library/jest-dom` matchers extend Vitest's `expect`:

```ts
expect(element).toBeVisible();
expect(element).toHaveTextContent("Saved");
expect(button).toBeDisabled();
```

### 8.1 Smoke Test

Verify the setup works with a simple component test (from the official guide):

```tsx
// app/page.tsx
import Link from "next/link";

export default function Page() {
	return (
		<div>
			<h1>Home</h1>
			<Link href="/about">About</Link>
		</div>
	);
}
```

```tsx
// __tests__/page.test.tsx
import { expect, test } from "vitest";
import { render, screen } from "@testing-library/react";
import Page from "../app/page";

test("Page renders heading", () => {
	render(<Page />);
	expect(screen.getByRole("heading", { level: 1, name: "Home" })).toBeDefined();
});
```

Run:

```bash
npm run test
```

Test files can live in `__tests__/` or be colocated next to the component inside `app/`.

## 9. Playwright

Playwright automates Chromium, Firefox, and WebKit with a single API. Use it for **End-to-End (E2E)** testing — complete user journeys through a real browser.

Install Playwright (from the [official Next.js guide](https://nextjs.org/docs/app/guides/testing/playwright)):

```bash
npm init playwright
```

This creates a `playwright.config.ts` and a `tests/` folder.

### 9.1 `playwright.config.ts` with `webServer`

The `webServer` option starts your Next.js app before tests run:

```ts
// playwright.config.ts
import { defineConfig, devices } from "@playwright/test";

export default defineConfig({
	testDir: "./tests",
	fullyParallel: true,
	forbidOnly: !!process.env.CI,
	retries: process.env.CI ? 2 : 0,
	workers: process.env.CI ? 1 : undefined,
	reporter: "html",
	use: {
		baseURL: "http://localhost:3000",
		trace: "on-first-retry",
	},
	projects: [
		{ name: "chromium", use: { ...devices["Desktop Chrome"] } },
		// Uncomment for full cross-browser coverage (slower — run nightly or
		// pre-release rather than on every PR):
		// { name: "firefox", use: { ...devices["Desktop Firefox"] } },
		// { name: "webkit", use: { ...devices["Desktop Safari"] } },
	],
	webServer: {
		command: "npm run start",
		url: "http://localhost:3000",
		reuseExistingServer: !process.env.CI,
	},
});
```

### 9.2 Dev vs Production for CI

The official guide recommends running Playwright against **production** code to more closely resemble real behavior:

```bash
npm run build
npm run start
npx playwright test
```

In CI, the `webServer` block in `playwright.config.ts` runs `npm run start` after you build. Locally during development you can temporarily change the command to `npm run dev` for faster iteration, but CI should use `build` + `start`.

For CI browser dependencies:

```bash
npx playwright install --with-deps
```

Prefer accessible locators:

```ts
page.getByRole("button", { name: "Login" });
page.getByLabel("Email");
```

Avoid fragile CSS selectors like `.btn-primary:nth-child(2)`.

## 10. App Router vs Pages Router — What Changes in Testing

Testing tools such as Vitest, React Testing Library, and Playwright remain mostly the same. What changes is the Next.js execution model and the API being tested.

| App Router | Pages Router | What is tested |
| ---------- | ------------ | ------------ |
| Server Component | Page Component | Rendered behavior / data functions |
| Route Handler | API Route | HTTP behavior (status, body, auth) |
| Server Action | No direct equivalent | Action logic, validation, returned state |
| Server-side data function | `getServerSideProps` | Returned props / redirect behavior |
| Static data function | `getStaticProps` | Returned props / `notFound` |
| Client Component | Client Component | UI behavior |

App Router Server Components can call server-side application code (service/repository) **directly** — they do not need to HTTP-fetch their own API. Pages Router pages typically receive data via props from `getServerSideProps` / `getStaticProps` or fetch on the client.

### 10.1 Pages Router API Route Example

Same business logic as the App Router Route Handler — different request/response shape:

```ts
// pages/api/admin/products.ts
import type { NextApiRequest, NextApiResponse } from "next";
import { getCurrentUser } from "@/lib/auth/session";
import { validateProduct } from "@/features/products/product.validation";
import { createProduct } from "@/features/products/product.service";

export default async function handler(
	req: NextApiRequest,
	res: NextApiResponse,
) {
	if (req.method !== "POST") {
		return res.status(405).json({ error: "Method not allowed" });
	}

	const user = await getCurrentUser(req);
	if (!user) {
		return res.status(401).json({ error: "Unauthorized" });
	}
	if (user.role !== "admin") {
		return res.status(403).json({ error: "Forbidden" });
	}

	const result = validateProduct(req.body);
	if (!result.success) {
		return res.status(400).json({ errors: result.errors });
	}

	const product = await createProduct(result.data);
	return res.status(201).json(product);
}
```

Test the HTTP boundary with mock `req` / `res` objects (similar to Supertest in Express):

```ts
// pages/api/admin/products.test.ts
import { describe, expect, it, vi, beforeEach } from "vitest";
import type { NextApiRequest, NextApiResponse } from "next";
import handler from "./products";

vi.mock("@/lib/auth/session", () => ({
	getCurrentUser: vi.fn(),
}));

vi.mock("@/features/products/product.service", () => ({
	createProduct: vi.fn().mockResolvedValue({
		id: 1,
		name: "Test Product",
		slug: "test-product",
		price: "19.99",
		categoryId: 1,
	}),
}));

import { getCurrentUser } from "@/lib/auth/session";

function createMockRes() {
	const res: Partial<NextApiResponse> & { statusCode?: number; body?: unknown } = {};
	res.status = vi.fn((code: number) => {
		res.statusCode = code;
		return res as NextApiResponse;
	});
	res.json = vi.fn((data: unknown) => {
		res.body = data;
		return res as NextApiResponse;
	});
	return res as NextApiResponse & { statusCode?: number; body?: unknown };
}

describe("POST /api/admin/products (Pages Router)", () => {
	beforeEach(() => vi.clearAllMocks());

	it("returns 401 when not authenticated", async () => {
		vi.mocked(getCurrentUser).mockResolvedValue(null);

		const req = {
			method: "POST",
			body: { name: "Item", price: 10, categoryId: 1 },
		} as NextApiRequest;
		const res = createMockRes();

		await handler(req, res);

		expect(res.status).toHaveBeenCalledWith(401);
		expect(res.body).toMatchObject({ error: "Unauthorized" });
	});

	it("returns 201 for admin with valid body", async () => {
		vi.mocked(getCurrentUser).mockResolvedValue({
			id: "1",
			email: "admin@example.com",
			role: "admin",
		});

		const req = {
			method: "POST",
			body: { name: "New Item", price: 25, categoryId: 1 },
		} as NextApiRequest;
		const res = createMockRes();

		await handler(req, res);

		expect(res.status).toHaveBeenCalledWith(201);
		expect(res.body).toMatchObject({ name: "Test Product" });
	});
});
```

The service is mocked here because this test focuses on the **HTTP boundary** — auth, validation, status codes, and response body. Service + database integration is tested separately in Integration Tests for `createProduct`.

### 10.2 Testing `getServerSideProps` and `getStaticProps`

Test the **returned result** from the data-fetching function — not Next.js internals:

```ts
// pages/admin/products.tsx
export async function getServerSideProps(context) {
	const user = await getCurrentUser(context.req);
	if (!user || user.role !== "admin") {
		return { redirect: { destination: "/login", permanent: false } };
	}

	const products = await getProducts();

	return { props: { products } };
}
```

```ts
// pages/admin/products.test.ts
import { describe, expect, it, vi } from "vitest";
import { getServerSideProps } from "./products";

vi.mock("@/lib/auth/session", () => ({ getCurrentUser: vi.fn() }));
vi.mock("@/features/products/product.service", () => ({
	getProducts: vi.fn().mockResolvedValue([
		{ id: 1, name: "Mouse", price: "29.99" },
	]),
}));

import { getCurrentUser } from "@/lib/auth/session";

describe("getServerSideProps — admin products", () => {
	it("redirects unauthenticated users to login", async () => {
		vi.mocked(getCurrentUser).mockResolvedValue(null);

		const result = await getServerSideProps({
			req: {} as import("next").NextApiRequest,
		});

		expect(result).toEqual({
			redirect: { destination: "/login", permanent: false },
		});
	});

	it("returns products for admin", async () => {
		vi.mocked(getCurrentUser).mockResolvedValue({
			id: "1",
			role: "admin",
		});

		const result = await getServerSideProps({
			req: {} as import("next").NextApiRequest,
		});

		expect(result).toEqual({
			props: {
				products: [{ id: 1, name: "Mouse", price: "29.99" }],
			},
		});
	});
});
```

The same pattern applies to `getStaticProps`:

```ts
const result = await getStaticProps(context);
expect(result).toEqual({ props: { products: [...] } });
```

You are testing your application's data-fetching logic and observable output — not how Next.js renders the page.

## 11. Prisma Test Database

Integration and API tests that touch the database must use a **separate test database** — never production.

### 11.1 `.env.test`

```env
# .env.test
DATABASE_URL="postgresql://postgres:postgres@localhost:5432/myapp_test"
```

Add `.env.test` to `.gitignore` if it contains credentials. In CI, inject `DATABASE_URL` as a secret pointing to a disposable Postgres instance (e.g. `myapp_test` on a GitHub Actions service container).

### 11.2 Apply Migrations

Before running integration tests locally:

```bash
dotenv -e .env.test -- npx prisma migrate deploy
```

In CI, `DATABASE_URL` is provided as an environment variable — run `npx prisma migrate deploy` directly.

This applies the same schema as production without running seed scripts that might pollute test data.

### 11.3 Truncate Between Tests

Create a helper that clears tables between tests:

```ts
// tests/helpers/db.ts
import { prisma } from "@/lib/prisma";

const TABLES = ["order_items", "orders", "products", "categories", "users"];

export async function truncateAll() {
	await prisma.$executeRawUnsafe(
		`TRUNCATE TABLE ${TABLES.join(", ")} RESTART IDENTITY CASCADE`,
	);
}
```

`TABLES` is a static, developer-controlled constant — that is why this specific use of `$executeRawUnsafe` is acceptable here. **`$executeRawUnsafe` is dangerous when SQL fragments contain user-controlled input.** Never concatenate user-controlled values into raw SQL. Do not treat `$executeRawUnsafe` as generally safe.

Use in integration test setup:

```ts
// tests/helpers/setup-integration.ts
import { beforeEach } from "vitest";
import { truncateAll } from "./db";

beforeEach(async () => {
	await truncateAll();
});
```

### 11.4 Transaction Rollback Limitations

Some teams wrap each test in a Prisma transaction and roll back after the test. This works for simple cases but has limitations:

- Code under test that calls `$transaction` internally may conflict with the outer rollback transaction
- Server Actions and Route Handlers that open their own connections may not share the test transaction
- `migrate deploy` and seed scripts run outside any test transaction

Use a dedicated test database and reset/truncate it between tests because the examples exercise multiple application entry points (Route Handlers, Server Actions, direct service calls). Transaction rollback can be faster but is not reliable across all Next.js entry points.

## 12. Mocking `next/navigation`, `next/headers`, and `next/cache`

Next.js server modules are not available in the Vitest/jsdom environment. Mock them when testing components or functions that import them.

### 12.1 `next/navigation`

```ts
// tests/mocks/next-navigation.ts
import { vi } from "vitest";

export const mockPush = vi.fn();
export const mockReplace = vi.fn();
export const mockRedirect = vi.fn();

vi.mock("next/navigation", () => ({
	useRouter: () => ({ push: mockPush, replace: mockReplace }),
	usePathname: () => "/products",
	useSearchParams: () => new URLSearchParams(),
	redirect: (...args: unknown[]) => mockRedirect(...args),
}));
```

Import this mock file at the top of tests that need it:

```ts
import "../mocks/next-navigation";
```

### 12.2 `next/headers`

```ts
vi.mock("next/headers", () => ({
	headers: vi.fn(() => new Headers()),
	cookies: vi.fn(() => ({
		get: vi.fn(),
		set: vi.fn(),
	})),
}));
```

### 12.3 `next/cache`

```ts
vi.mock("next/cache", () => ({
	revalidatePath: vi.fn(),
	revalidateTag: vi.fn(),
	unstable_cache: vi.fn((fn: () => unknown) => fn),
}));
```

Mocking cache functions prevents side effects during unit tests. Do not assert that `revalidatePath` was called unless cache invalidation **is** the behavior under test.

## 13. Mocking `auth()` from `@/auth`

The application uses Auth.js with `auth()` exported from `@/auth`. Mock the module so tests can run without a real login flow:

```ts
vi.mock("@/auth", () => ({
```

### 14.1 Validation — `validateProduct`

```ts
// features/products/product.validation.ts
export type ProductInput = {
	name: string;
	price: number;
	categoryId: number;
};

export type ValidationResult =
	| { success: true; data: ProductInput }
	| { success: false; errors: Record<string, string> };

export function validateProduct(input: ProductInput): ValidationResult {
	const errors: Record<string, string> = {};

	if (!input.name?.trim()) {
		errors.name = "Product name is required";
	} else if (input.name.trim().length > 255) {
		errors.name = "Product name must be 255 characters or fewer";
	}

	if (typeof input.price !== "number" || Number.isNaN(input.price)) {
		errors.price = "Price must be a number";
	} else if (input.price <= 0) {
		errors.price = "Price must be greater than zero";
	}

	if (!Number.isInteger(input.categoryId) || input.categoryId <= 0) {
		errors.categoryId = "Category is required";
	}

	if (Object.keys(errors).length > 0) {
		return { success: false, errors };
	}

	return {
		success: true,
		data: {
			name: input.name.trim(),
			price: input.price,
			categoryId: input.categoryId,
		},
	};
}
```

### 14.2 Service — `createProduct`

```ts
// features/products/product.service.ts
import { validateProduct, type ProductInput } from "./product.validation";
import { createProductRecord, findAllProducts } from "./product.repository";

function slugify(name: string): string {
	return name
		.toLowerCase()
		.replace(/[^a-z0-9]+/g, "-")
		.replace(/(^-|-$)/g, "");
}

export async function createProduct(input: ProductInput) {
	const result = validateProduct(input);
	if (!result.success) {
		throw new Error(JSON.stringify(result.errors));
	}

	return createProductRecord({
		name: result.data.name,
		slug: slugify(result.data.name),
		price: result.data.price,
		categoryId: result.data.categoryId,
	});
}

export async function getProducts() {
	return findAllProducts();
}
```

### 14.4 Server Action

```ts
// app/admin/products/actions.ts
"use server";

import { auth } from "@/auth";
import { createProduct } from "@/features/products/product.service";
import { validateProduct } from "@/features/products/product.validation";
import { revalidatePath } from "next/cache";

export type CreateProductState = {
	errors?: Record<string, string>;
	message?: string;
};

export async function createProductAction(
	_prevState: CreateProductState,
	formData: FormData,
): Promise<CreateProductState> {
	const session = await auth();
	if (!session?.user) {
		return { message: "You must be logged in" };
	}
	if (session.user.role !== "admin") {
		return { message: "You do not have permission to create products" };
	}

	const input = {
		name: String(formData.get("name") ?? ""),
		price: Number(formData.get("price")),
		categoryId: Number(formData.get("categoryId")),
	};

	const result = validateProduct(input);
	if (!result.success) {
		return { errors: result.errors };
	}

	try {
		await createProduct(result.data);
		revalidatePath("/admin/products");
		return { message: "Product created" };
	} catch {
		return { message: "Failed to create product" };
	}
}
```

### 14.5 Route Handler — `POST /api/admin/products`

```ts
// app/api/admin/products/route.ts
import { auth } from "@/auth";
import { createProduct } from "@/features/products/product.service";
import { validateProduct, type ProductInput } from "@/features/products/product.validation";

export async function POST(request: Request) {
	const session = await auth();
	if (!session?.user) {
		return Response.json({ error: "Unauthorized" }, { status: 401 });
	}
	if (session.user.role !== "admin") {
		return Response.json({ error: "Forbidden" }, { status: 403 });
	}

	let body: unknown;
	try {
		body = await request.json();
	} catch {
		return Response.json({ error: "Invalid JSON" }, { status: 400 });
	}

	const result = validateProduct(body as ProductInput);

	if (!result.success) {
		return Response.json({ errors: result.errors }, { status: 400 });
	}

	try {
		const product = await createProduct(result.data);
		return Response.json(product, { status: 201 });
	} catch {
		return Response.json({ error: "Internal server error" }, { status: 500 });
	}
}
```

```tsx
	if (!session?.user || session.user.role !== "admin") {
		redirect("/login");
	}

	const products = await getProducts();

	return (
		<div>
			<h1>Products</h1>
			<ProductTable products={products} />
		</div>
	);
}
```

Server Components call server-side application code **directly** — here `getProducts()` from the service layer. They do not need to HTTP-fetch their own API Route Handler.

```text
Server Component
    ↓
Service (getProducts)
    ↓
Repository (findAllProducts)
    ↓
Database
```

Per the [official Next.js Vitest guide](https://nextjs.org/docs/app/guides/testing/vitest):

> Vitest currently does **not** support `async` Server Components.

**Do not** try to `render(<AdminProductsPage />)` in Vitest — it will not work.

### 20.1 What to Test Instead

**Option A — test the service/data function in isolation (integration test with test DB):**

```ts
// features/products/product.service.integration.test.ts

import { prisma } from "@/lib/prisma";
import { getProducts } from "./product.service";

		});

		await prisma.product.create({
			data: {
				name: "Older Mouse",
				slug: "older-mouse",
				price: new Prisma.Decimal(19.99),
				categoryId: category.id,
				createdAt: new Date("2024-01-01"),
			},
		});

		await prisma.product.create({
			data: {
				name: "Newer Keyboard",
				slug: "newer-keyboard",
				price: new Prisma.Decimal(49.99),
				categoryId: category.id,
				createdAt: new Date("2024-06-01"),
			},
		});
	});

	it("returns products ordered by createdAt desc", async () => {
		const products = await getProducts();
		expect(products.map((p) => p.name)).toEqual(["Newer Keyboard", "Older Mouse"]);

});
```

Runs with the integration test setup (**Truncate Between Tests**) — `truncateAll()` runs first, then this `beforeEach` seeds fixtures.

**Option B — test the sync presentation component:**

```tsx
// app/admin/products/product-table.test.tsx
```

Use **Playwright** to verify the full async page loads correctly in a browser after login.

## 21. Auth Test Matrix for Create Product

Every entry point must enforce the same auth rules. Test each independently:

| Scenario | Session | Role | Expected |
| -------- | ------- | ---- | -------- |
| No session | `null` (mocked) | — | 401 / "You must be logged in" |
| Regular user | valid (mocked) | `user` | 403 / "You do not have permission" |
| Admin | valid (mocked) | `admin` | 201 / "Product created" |

Unit/API tests mock `auth()` returning `null` or a known session — they do **not** simulate real Auth.js cookie verification. Expired or tampered sessions should be tested in integration or E2E where the real auth flow runs (see **Auth Test Matrix (Reference)**).

Apply this matrix to:

```text
POST /api/admin/products     → Route Handler Tests
createProductAction          → Server Action Tests
AdminProductsPage (redirect) → Async Server Component (E2E)
Playwright login flow        → Full Playwright E2E Test
```

Authentication (is the user logged in?) and authorization (is this user allowed?) are different:

```text
401 → Not authenticated (Authentication: "Who are you?")
403 → Authenticated but not authorized (Authorization: "Are you allowed?")
```

### 22.1 Test Database Seed

E2E tests need known test data. Seed the test database before Playwright runs — these credentials exist **only** in the test database, never in production:

```ts
// prisma/seed-test.ts
import { prisma } from "@/lib/prisma";
import { hash } from "bcryptjs";
import { truncateAll } from "@/tests/helpers/db";

const TEST_ADMIN_EMAIL = "admin@example.com";
const TEST_ADMIN_PASSWORD = "test-admin-password-only"; // fake — test DB only

export async function seedTestData() {
	await truncateAll();

	await prisma.category.create({
		data: { name: "Furniture", slug: "furniture" },
	});

	const passwordHash = await hash(TEST_ADMIN_PASSWORD, 10);

	await prisma.user.create({
		data: {
			email: TEST_ADMIN_EMAIL,
			name: "Test Admin",
			role: "admin",
			passwordHash,
		},
	});
}
```

Run before E2E locally or in CI. These credentials exist **only** in the test database:

```bash
# Local (loads .env.test)
dotenv -e .env.test -- npx tsx prisma/seed-test.ts

# CI (DATABASE_URL already set)
npx tsx prisma/seed-test.ts
```

In `package.json`:

```json
{
	"scripts": {
		"db:seed:test": "tsx prisma/seed-test.ts",
		"db:seed:test:local": "dotenv -e .env.test -- npm run db:seed:test"
	}
}
```

`truncateAll()` at the start ensures each E2E run begins from a known clean state — preventing duplicate slug failures when re-running tests against the same database.

### 22.2 E2E Spec

```ts
// tests/admin-create-product.spec.ts

		await page.goto("/login");
```

Run locally:

```bash

npm run build

```

Or rely on `webServer` in `playwright.config.ts` (**Playwright** setup) in CI after seeding.

## 24. Transactions and Test Isolation

Database integration tests must not leak state between runs. Use a dedicated test database and reset/truncate it between tests because the examples exercise multiple application entry points (Route Handlers, Server Actions, direct service calls).

Alternative strategies — the appropriate choice depends on your architecture:

```text
Delete test rows after each test
Reset entire test database
Rollback transaction per test
Recreate test database from scratch
```

Transaction rollback is fast but limited (**Transaction Rollback Limitations**) — nested transactions and connection pooling can break isolation.

**Rule:** each test creates its own data or starts from a known clean state. Never depend on Test A's side effects in Test B.

---

## 25. Contract Testing

Contract testing is especially useful when your application **consumes an external API**. The expected response shape is a contract:

```json
{
	"id": "123",
	"name": "Laptop",
	"price": 999
}
```

If the provider renames fields, your app breaks. Validate the response at the boundary before your application logic uses it:

```text
External API
    ↓
response
    ↓
schema validation (e.g. Zod)
    ↓
application logic
```

Practical strategy — you do not need a separate contract-testing framework for most projects:

```text
Most tests → mock external provider
Small number → real sandbox / staging provider
```

Validate response shape with Zod at the service boundary and unit-test the parser against sample payloads.

---

## 26. Caching and Rendering

Next.js apps use static rendering, dynamic rendering, caching, and revalidation. Do not test internal framework implementation details.

Test **application behavior** at the appropriate level — often integration or E2E:

```text
Page returns expected content after mutation
API returns fresh data after create
Stale content is replaced after revalidation (E2E)
```

Do **not** write tests like `expect(revalidatePath).toHaveBeenCalled()` unless cache invalidation itself is explicitly the behavior under test. Prefer testing the user-visible outcome:

```text
mutation → revalidation → user sees fresh data
```

Mock `revalidatePath` in unit tests (**Mocking `next/cache`**) to prevent side effects, not to assert internal calls.

## 27. Regression Testing

A regression occurs when a previously working feature breaks after a change:

```text
Version 1 → Login works
Auth code changes
Version 2 → Login broken
```

Automated tests detect this:

```text
Code change → Test suite → Login test fails
```

This is one of the biggest benefits of testing. Run required unit, integration, and smoke tests on every PR — not necessarily the full E2E suite (**Practical CI Strategy**).

---

## 28. Flaky Tests

A flaky test sometimes passes and sometimes fails without code changes.

Common causes:

```text
Timing issues
Race conditions
Shared test data
External services
Random data
Network dependency
Hard-coded waits (page.waitForTimeout)
Unstable selectors
```

Do not simply add retries and ignore the problem. Find the root cause.

Prefer waiting for meaningful conditions:

```ts
await expect(page.getByText("Product created")).toBeVisible();
```

Instead of:

```ts
await page.waitForTimeout(5000);
```

## 29. Auth Test Matrix (Reference)

Use this table as a checklist for any protected feature:

| Scenario | Expected |
| -------- | -------- |
| Valid credentials | Login succeeds |
| Invalid password | Login rejected |
| No session | Redirect / 401 |
| Expired session | Redirect / 401 |
| Normal user accessing admin resource | 403 |
| Admin accessing admin resource | Allowed |
| Logout | Session invalidated |

Different layers can test different parts of this matrix. Unit/API tests mock `auth()` — they do **not** replace real login/session verification, which belongs in E2E:

```text
Unit / Integration  → auth helper behavior, session handling, protected service/action logic
API                 → 401 / 403 HTTP responses
E2E (Playwright)    → real login, expired session, protected page access, logout, full user journey
```

Endpoint-level matrix for create product and similar features:

| Endpoint / Action | No session | User | Admin |
| ----------------- | ---------- | ---- | ----- |
| `GET /api/profile` | 401 | 200 | 200 |
| `POST /api/admin/products` | 401 | 403 | 201 |
| `DELETE /api/users/:id` | 401 | 403 | 201/204 |
| Server Action (create) | error msg | error msg | success |
| Admin page | redirect login | redirect/forbidden | 200 |

Always test **object-level** authorization too: User A cannot access User B's private resource.

## 31. Test Environment and Determinism

Automated tests must be isolated from production:

```text
Development  → development resources
Test         → test database, test credentials
Production   → production resources (never used in tests)
```

A deterministic test produces the same result under the same conditions. Avoid uncontrolled current time, random values, real network, and production databases unless those are explicitly what you are testing.

Use fixed test data, a test database, and mocked external APIs when appropriate.

## 32. Independent Tests and Naming

Avoid test chains:

```text
Test A creates data → Test B depends on Test A → fragile
```

Prefer each test with its own setup and assertions.

Name tests by scenario + expected behavior:

```ts
// Bad
it("works", () => {});

// Good
it("rejects login when password is incorrect", () => {});
it("returns 403 when non-admin posts to /api/admin/products", () => {});
```

## 33. CI/CD — Vitest, Playwright, and Test Database

Use the **Node.js version standardized by your project** (the CI workflow examples use Node 20 for illustration only).

A typical GitHub Actions workflow runs three jobs:

```yaml

name: Test

on: [push, pull_request]

jobs:

    runs-on: ubuntu-latest
```

## 34. Practical CI Strategy

```text
Every PR (required checks):
  Vitest unit tests (seconds)
  Vitest integration tests (tens of seconds)
  Critical E2E smoke tests (login, create product — **Full Playwright E2E Test**)

Nightly or pre-release:
  Full Playwright E2E suite (all specs, optional cross-browser)

Before merge:
  Required PR checks must pass
```

Unit and integration tests are fast — run them on every commit. Critical E2E smoke tests protect the most important user journeys without making every PR wait for a full browser suite. Full E2E (including Firefox/WebKit if enabled) can run on a broader schedule because it is slower.

Keep unit tests under 30 seconds so developers actually run them locally. Fail fast: run Vitest before Playwright.

## 38. What Should I Test? — Decision Tree

```text
Pure business logic?
    ↓
Unit Test (Vitest)

Multiple application layers working together?
    ↓
Integration Test (Vitest + test DB)

HTTP endpoint (Route Handler / API Route)?
    ↓
API Test (status, body, auth — often integration-style)

Database persistence / constraints?
    ↓
Database Integration Test (Prisma + test DB)

Authentication / session behavior?
    ↓
Auth Test (mocked session + API/Action tests; E2E for real login)

Complete user workflow in a browser?
    ↓
Playwright E2E Test
```

Use the **lowest level** that gives you confidence for each behavior. These categories overlap — an API test can also be an integration test. Not every feature needs every level — but protected features (auth, payments, admin actions) usually need several.

## 39. Final Mental Model and Summary

Think of testing as multiple layers:

```text
                    User
                     │
                     ▼
                E2E Testing
                     │
                     ▼
                API Testing
                     │
                     ▼
             Integration Testing
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
       Service              Repository
          │                     │
          └──────────┬──────────┘
                     ▼
                Test Database
```

Unit tests sit underneath the architecture:

```text
Unit Tests
    ↓
Small isolated pieces of logic
```

The key question at each level:

```text
Unit           → Does this piece of logic work?
Integration    → Do these pieces work together?
API            → Does this HTTP endpoint behave correctly?
Database       → Does persistence work correctly?
Authentication → Who is the user? (401 if unknown)
Authorization  → Is this user allowed? (403 if not permitted)
E2E            → Can a real user successfully complete the workflow?
```

A strong Next.js testing strategy:

```text
Unit           → Fast verification of individual logic
Integration    → Verify internal components work together
API            → Verify HTTP contracts and server behavior
Database       → Verify real persistence behavior
Authentication → Verify login, sessions, cookies (E2E for real flows)
Authorization  → Verify role/permission checks on protected resources
E2E            → Verify complete user journeys
```

Key points:

> **Do not solve every testing problem with E2E tests.**

> **Do not solve every testing problem with unit tests.**

> **Use the lowest appropriate testing level for each behavior.**

> **Test behavior rather than implementation details.**

> **Authentication and authorization are security boundaries and deserve explicit tests. Authentication asks "Who are you?" (401). Authorization asks "Are you allowed?" (403).**

> **E2E tests should focus on important user journeys rather than every small UI detail.**

> **Async Server Components cannot be rendered in Vitest — test data functions and use E2E for the full page.**

> **A good test suite makes it safe to change the application without silently breaking important behavior.**
