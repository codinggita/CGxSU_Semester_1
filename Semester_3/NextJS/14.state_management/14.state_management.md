# 18. State Management

State management is about deciding where application data should live and how components access and update it.

In a Next.js App Router application, state commonly falls into three categories:

```text
State
├── Local state         → useState / useReducer
├── Server state        → Server Component fetch / TanStack Query
└── Global client state → Zustand / Redux Toolkit
```

Choose the simplest approach that fits the state. Not every value needs a global store or a state-management library.

---

## 1. Local State

Local state belongs to a component or a small part of the component tree.

Examples:

- Whether a modal is open
- The selected tab
- Input values
- A dropdown's visibility

```tsx
"use client";

import { useState } from "react";

export function Counter() {
	const [count, setCount] = useState(0);

	return <button onClick={() => setCount(count + 1)}>Count: {count}</button>;
}
```

Use `useState` when only the component, or a nearby group of components, needs the value. Avoid moving simple local state into a global store.

---

## 2. Server State

Server state is data owned by the backend or database and requested by the application.

Examples:

- Products
- Users
- Orders
- Product reviews

Server state is usually asynchronous and can become outdated when the backend data changes.

In Next.js, a Server Component can fetch data directly:

```tsx
// app/products/page.tsx
export default async function ProductsPage() {
	const response = await fetch("https://api.example.com/products");

	if (!response.ok) {
		throw new Error("Failed to fetch products");
	}

	const products = await response.json();

	return <ProductList products={products} />;
}
```

For pages that can render their data on the server, this is often enough. See the Data Fetching and Caching topics for details about server-side fetching and revalidation.

## 3. TanStack Query — Basic Introduction

TanStack Query is a library for managing server data in Client Components. It helps with fetching, caching, loading and error states, refetching, and mutations.

It is useful when the browser needs to interact with server data after the initial page render—for example, filtering a product list, refreshing order data, or updating data without manually managing every request state.

### 3.1 Basic Query

```tsx
"use client";

import { useQuery } from "@tanstack/react-query";

async function getProducts() {
	const response = await fetch("https://api.example.com/products");

	if (!response.ok) {
		throw new Error("Failed to fetch products");
	}

	return response.json();
}

export function Products() {
	const { data, isPending, isError } = useQuery({
		queryKey: ["products"],
		queryFn: getProducts,
	});

	if (isPending) return <p>Loading products...</p>;
	if (isError) return <p>Unable to load products.</p>;

	return <ProductList products={data} />;
}
```

- `queryKey` identifies the cached data.
- `queryFn` is the function that fetches the data.
- `isPending` and `isError` help display request states.
- Components using the same query key can share the cached result.

### 3.2 Basic Mutation

A mutation is used when the application creates, updates, or deletes server data.

```tsx
"use client";

import { useMutation, useQueryClient } from "@tanstack/react-query";

export function DeleteProduct({ id }: { id: string }) {
	const queryClient = useQueryClient();

	const mutation = useMutation({
		mutationFn: async () => {
			const response = await fetch(`/api/products/${id}`, {
				method: "DELETE",
			});

			if (!response.ok) {
				throw new Error("Failed to delete product");
			}
		},
		onSuccess: () => {
			queryClient.invalidateQueries({ queryKey: ["products"] });
		},
	});

	return (
		<button onClick={() => mutation.mutate()} disabled={mutation.isPending}>
			{mutation.isPending ? "Deleting..." : "Delete"}
		</button>
	);
}
```

Invalidating a query marks its cached data as stale so it can be refreshed. This is useful after a mutation changes data shown by a query.

### 3.3 When Is TanStack Query Needed?

Use it when Client Components need features such as:

- Client-side fetching and refetching
- Shared query caching
- Mutations and query invalidation
- Pagination or infinite scrolling

It is not required for every API request. A Server Component fetch may be simpler when data can be loaded on the server and passed to the UI.

**Remember:** TanStack Query manages server data in the client. It is not a replacement for local state or a global client-state store.

---

## 4. Global Client State

Global client state is UI or application state that needs to be shared by multiple Client Components.

Examples:

- Shopping cart contents
- Wishlist items
- Theme preference
- Sidebar state
- Multi-step form progress

A value does not become global just because it is client-side. Use a global store only when multiple parts of the application genuinely need to read or update it.

For this course, **Zustand** is the primary library for global client state.

---

## 5. Zustand

Zustand is a lightweight state-management library for React. It lets you create a store and access its state and actions from Client Components.

### 5.1 Creating a Store

Install Zustand:

```bash
npm install zustand
```

Create a cart store:

```ts
// lib/stores/cart.store.ts
import { create } from "zustand";

type CartStore = {
	count: number;
	addItem: () => void;
	removeItem: () => void;
};

export const useCartStore = create<CartStore>((set) => ({
	count: 0,

	addItem: () => set((state) => ({ count: state.count + 1 })),

	removeItem: () => set((state) => ({ count: Math.max(0, state.count - 1) })),
}));
```

- `create()` creates the store.
- `set()` updates the store.
- Store actions define how its state changes.

### 5.2 Using the Store in a Component

```tsx
"use client";

import { useCartStore } from "@/lib/stores/cart.store";

export function CartButton() {
	const count = useCartStore((state) => state.count);
	const addItem = useCartStore((state) => state.addItem);

	return <button onClick={addItem}>Add item — Cart ({count})</button>;
}
```

Another Client Component can read the same store:

```tsx
"use client";

import { useCartStore } from "@/lib/stores/cart.store";

export function CartCount() {
	const count = useCartStore((state) => state.count);

	return <span>Cart items: {count}</span>;
}
```

Both components stay in sync because they subscribe to the same store.

### 5.3 Does Zustand Need a Provider?

For the standard store created with Zustand's `create()` function, no Provider wrapper is required. Import the store hook into the Client Components that need it.

This keeps the setup simple in the App Router. Components that use the store must still be Client Components.

### 5.4 When to Use Zustand

Zustand is a good fit for shared client-side state such as:

- Shopping cart UI
- Wishlist
- Theme and UI preferences
- Multi-step client workflows

Do not use it as the main cache for backend data such as products, orders, or users. Keep server-owned data with Server Component fetching or a server-state library such as TanStack Query when client-side features are needed.

## 6. Zustand vs Redux Toolkit

Redux Toolkit is the recommended modern way to write Redux applications. Zustand and Redux Toolkit can both manage global client state, but they have different levels of structure and setup.

| Area           | Zustand                                        | Redux Toolkit                                                         |
| -------------- | ---------------------------------------------- | --------------------------------------------------------------------- |
| Setup          | Minimal                                        | More setup and defined structure                                      |
| Boilerplate    | Usually less                                   | Usually more                                                          |
| State updates  | Store actions using `set`                      | Slices and reducers                                                   |
| Provider       | Not required for the standard `create()` store | Uses a React-Redux Provider                                           |
| Learning curve | Generally simpler                              | More concepts to learn                                                |
| DevTools       | Supported                                      | Strong DevTools and ecosystem                                         |
| Best fit       | Small and medium shared client state           | Larger or more complex state workflows and established Redux projects |

### Why Are Many Developers Choosing Zustand?

Zustand has become a popular choice for many React projects because:

1. **Less boilerplate:** A store can be created with a small amount of code.
2. **Simple API:** Developers can define state and actions without first learning slices, reducers, and action conventions.
3. **No Provider for the standard store:** Components can import and use the store hook directly.
4. **Easy component usage:** Components subscribe to the specific state they need.
5. **Flexible structure:** It does not require an application to follow Redux's more prescriptive patterns.

This makes Zustand convenient when an application needs shared client state without the additional structure of Redux Toolkit.

### Is Redux Toolkit Outdated?

No. Redux Toolkit is still a capable and actively used choice. It can be a better fit when an application benefits from standardized state patterns, extensive middleware, strong debugging workflows, or an existing Redux codebase.

**Practical choice for this course:** Use Zustand for the E-commerce project's global client state. Understand Redux Toolkit as an alternative, but you do not need to implement both libraries.

---

## 7. Common Mistakes

- Putting every value into a global store instead of keeping simple state local.
- Copying all API responses into Zustand.
- Using TanStack Query for UI-only state such as opening a modal.
- Assuming Zustand automatically persists state after a page refresh.
- Choosing a library before understanding what kind of state needs to be managed.

**Key takeaway:** Use `useState` for local UI state, Server Components for server-rendered data, TanStack Query when the client needs server-data management, and Zustand for shared client state.
