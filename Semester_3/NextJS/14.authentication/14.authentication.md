# 14. Authentication

Authentication concepts apply to both the **App Router** and **Pages Router**; only some Next.js APIs differ between them.

---

## 1. Registration

Registration creates a new user account. The client sends `name`, `email`, and `password`; the server validates input, checks for an existing email, hashes the password, and stores a `passwordHash` — never the plain password.

Expected Prisma `User` model fields: `name`, `email`, `passwordHash`, and optionally `role`.

### 1.1 App Router

```text
app/api/auth/register/route.ts
```

```ts
import { prisma } from "@/lib/prisma";
import { hashPassword } from "@/lib/auth/password";

export async function POST(request: Request) {
	const body = await request.json();

	const { name, email, password } = body;

	if (!name || !email || !password) {
		return Response.json(
			{ error: "All fields are required" },
			{ status: 400 },
		);
	}

	const existingUser = await prisma.user.findUnique({
		where: { email },
	});

	if (existingUser) {
		return Response.json({ error: "User already exists" }, { status: 409 });
	}

	const passwordHash = await hashPassword(password);

	const user = await prisma.user.create({
		data: {
			name,
			email,
			passwordHash,
		},
	});

	return Response.json(
		{
			id: user.id,
			name: user.name,
			email: user.email,
		},
		{ status: 201 },
	);
}
```

### 1.2 Pages Router


## 2. Login

Login verifies an existing account, creates a server-side session, and sets a secure session cookie.

Request body:

```json
{
	"email": "alice@example.com",
	"password": "secret123"
}
```

### 2.1 App Router

```text
app/api/auth/login/route.ts
```

```ts
import { cookies } from "next/headers";

import { prisma } from "@/lib/prisma";
import { verifyPassword } from "@/lib/auth/password";
import { createSession } from "@/lib/auth/session";

export async function POST(request: Request) {
	const body = await request.json();
	const { email, password } = body;

	if (!email || !password) {
		return Response.json(
			{ error: "Email and password are required" },
			{ status: 400 },
		);
	}

	const user = await prisma.user.findUnique({
		where: { email },
	});

	if (!user) {
		return Response.json({ error: "Invalid credentials" }, { status: 401 });
	}

	const valid = await verifyPassword(password, user.passwordHash);

	if (!valid) {
		return Response.json({ error: "Invalid credentials" }, { status: 401 });
	}

	const session = await createSession(user.id);

	const cookieStore = await cookies();

	cookieStore.set("session", session.id, {
		httpOnly: true,
		secure: process.env.NODE_ENV === "production",
		sameSite: "lax",
		path: "/",
		maxAge: 60 * 60 * 24 * 7,
	});

	return Response.json({
		id: user.id,
		name: user.name,
		email: user.email,
	});
}
```

The Route Handler validates credentials, creates a session row, and sets the cookie in one response.

### 2.2 Pages Router

```text
pages/api/auth/login.ts
```

```ts
import type { NextApiRequest, NextApiResponse } from "next";

import { prisma } from "@/lib/prisma";
import { verifyPassword } from "@/lib/auth/password";
import { createSession } from "@/lib/auth/session";

export default async function handler(
	req: NextApiRequest,
	res: NextApiResponse,
) {
	if (req.method !== "POST") {
		return res.status(405).json({ error: "Method not allowed" });
	}

	const { email, password } = req.body;

	if (!email || !password) {
		return res.status(400).json({
			error: "Email and password are required",
		});
	}

	const user = await prisma.user.findUnique({
		where: { email },
	});

	if (!user) {
		return res.status(401).json({ error: "Invalid credentials" });
	}

	const valid = await verifyPassword(password, user.passwordHash);

	if (!valid) {
		return res.status(401).json({ error: "Invalid credentials" });
	}

	const session = await createSession(user.id);

	res.setHeader(
		"Set-Cookie",
		`session=${session.id}; HttpOnly; Path=/; SameSite=Lax; Max-Age=${60 * 60 * 24 * 7}${
			process.env.NODE_ENV === "production" ? "; Secure" : ""
		}`,
	);

	return res.status(200).json({
		id: user.id,
		name: user.name,
		email: user.email,
	});
}
```

Pages Router sets the cookie via `res.setHeader("Set-Cookie", ...)` instead of the `cookies()` helper. The authentication logic — lookup, verify, create session — is identical.

## 3. Sessions

A session represents an authenticated login. The browser keeps a session id in a cookie; the server resolves that id against a session store (PostgreSQL, Redis, etc.) to identify the user.

```text
Browser
   │  Cookie: session=abc123
   ▼
Next.js Server  →  Session Store  →  userId  →  User
```

Example session row:

```text
sessions
id       | userId | expiresAt
abc123   | 42     | 2026-08-20...
```

The cookie stores a **session identifier**, not the full user object.

## 4. JWT / Stateless Authentication

Another approach is token-based authentication:

```text
Login
  ↓
Create signed token
  ↓
Browser
  ↓
Send token
  ↓
Server verifies token
```

A common example is JWT:

```http
Authorization: Bearer <token>
```

JWT and server-side sessions are different approaches.

### 4.1 Avoid Storing JWTs in localStorage

A common but unsafe pattern in client-heavy applications is:

**Why storing a token in `localStorage` is a security risk:** Values in `localStorage` are readable by any JavaScript running on the page. If an attacker injects script through an XSS (cross-site scripting) vulnerability, that script can read the token and exfiltrate it — for example, by sending it to an external server. The browser provides no access restriction on `localStorage` comparable to the `HttpOnly` flag on cookies.

An **`HttpOnly` cookie cannot be read by client-side JavaScript** (`document.cookie` does not expose it). The browser attaches it automatically to HTTP requests, but page scripts cannot access the value. Session authentication with `HttpOnly`, `Secure`, and an appropriate `SameSite` setting is therefore the recommended default for a standard server-rendered or full-stack Next.js web application served to browsers.

By contrast, a JWT stored in `localStorage` and manually attached to requests is fully visible to any script on the page — including malicious script injected via XSS.

**When bearer tokens in headers are appropriate:** Non-browser clients that do not use cookies naturally — such as a native mobile app, a CLI tool, or a third-party API integration — commonly authenticate with `Authorization: Bearer <token>`. Those clients must store tokens in platform-secure storage (for example, a device keychain), not in web `localStorage`. The bearer-token pattern is a legitimate choice for those clients; it is a poor default for a browser-based Next.js app where HttpOnly session cookies are available.

For typical Next.js applications, prefer session cookies (custom or via Auth.js) over client-managed JWT storage.

## 5. Cookies

Cookies are browser-managed values associated with a website.

Server response:

```http
Set-Cookie: session=abc123
```

Later requests contain:

```http
Cookie: session=abc123
```

This makes cookies useful for session authentication.

---

## 6. Important Cookie Options

Authentication cookies should use the right attributes. In Next.js `cookies().set()`, option names are camelCase (`httpOnly`, `secure`, `sameSite`, `path`, `maxAge`, `expires`).

| Attribute | HTTP / Next.js option | Purpose | Why it matters for auth |
| --------- | --------------------- | ------- | ----------------------- |
| **HttpOnly** | `httpOnly: true` | Blocks client-side JavaScript from reading the cookie | Without it, any script on the page — including XSS-injected code — can read the session cookie via `document.cookie`. With `HttpOnly`, the browser sends the cookie on HTTP requests but page scripts cannot access it. This does not stop XSS itself, but prevents direct cookie theft by JavaScript. |
| **Secure** | `secure: true` | Cookie sent only over HTTPS | Prevents the session cookie from being transmitted on unencrypted HTTP connections. |
| **SameSite** | `sameSite: "lax"` \| `"strict"` \| `"none"` | Controls cross-site cookie sending | `Lax` — common default; sent on top-level navigations to your site. `Strict` — never sent cross-site; strongest isolation. `None` — sent cross-site; **requires** `Secure`. |
| **Path** | `path: "/"` | Limits which URL paths receive the cookie | Usually `/` so all routes on your domain receive the session cookie. |
| **Max-Age / Expires** | `maxAge: 3600` or `expires: Date` | Session lifetime | `maxAge` is in seconds. Controls how long the browser keeps the cookie before it expires. |

Example response header combining these attributes:

```http
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600
```

The correct values depend on your deployment (HTTPS, cross-site flows, session duration).

## 7. Cookies in Next.js

### 7.1 App Router

In the App Router, `cookies` from `next/headers` is an **async** function (Next.js 15+). Always `await` it before reading or writing.

Set (login):

```ts
import { cookies } from "next/headers";

const cookieStore = await cookies();

cookieStore.set("session", sessionId, {
	httpOnly: true,
	secure: process.env.NODE_ENV === "production",
	sameSite: "lax",
	path: "/",
	maxAge: 60 * 60 * 24 * 7,
});
```

Read (Server Component, Route Handler, or Server Action):

```ts
const cookieStore = await cookies();
const sessionId = cookieStore.get("session")?.value;
```

Delete (logout):

```ts
cookieStore.delete("session");
```

Constraints:

- **`.set()` and `.delete()`** only work in a **Route Handler** or **Server Action** — not during Server Component rendering.
- **Reading** works in Server Components (cookie data arrives in request headers).
- Never set auth cookies from a Client Component.

### 7.2 Pages Router

In the Pages Router, read cookies from `req.cookies` and write them with `res.setHeader("Set-Cookie", ...)`.

Read (API route or `getServerSideProps`):

```ts
import type { NextApiRequest, NextApiResponse } from "next";

export default function handler(req: NextApiRequest, res: NextApiResponse) {
	const sessionId = req.cookies.session;
	// ...
}
```

Set (login):

```ts
res.setHeader(
	"Set-Cookie",
	`session=${sessionId}; HttpOnly; Path=/; SameSite=Lax; Max-Age=${60 * 60 * 24 * 7}${
		process.env.NODE_ENV === "production" ? "; Secure" : ""
	}`,
);
```

Clear (logout):

```ts
res.setHeader(
	"Set-Cookie",
	"session=; HttpOnly; Path=/; Max-Age=0; SameSite=Lax",
);
```

The attribute names in the header string (`HttpOnly`, `Secure`, `SameSite`, `Path`, `Max-Age`) map to the options described in **Important Cookie Options**.

## 8. Logout

Logout must invalidate the server-side session **and** clear the browser cookie. Deleting only the cookie leaves a valid session id in the database.

### 8.1 App Router

```text
app/api/auth/logout/route.ts
```

```ts
import { cookies } from "next/headers";

import { deleteSession } from "@/lib/auth/session";

export async function POST() {
	const cookieStore = await cookies();

	const sessionId = cookieStore.get("session")?.value;

	if (sessionId) {
		await deleteSession(sessionId);
	}

	cookieStore.delete("session");

	return Response.json({ success: true });
}
```

### 8.2 Pages Router

```text
pages/api/auth/logout.ts
```

```ts
import type { NextApiRequest, NextApiResponse } from "next";

import { deleteSession } from "@/lib/auth/session";

export default async function handler(
	req: NextApiRequest,
	res: NextApiResponse,
) {
	if (req.method !== "POST") {
		return res.status(405).json({ error: "Method not allowed" });
	}

	const sessionId = req.cookies.session;

	if (sessionId) {
		await deleteSession(sessionId);
	}

	res.setHeader(
		"Set-Cookie",
		"session=; HttpOnly; Path=/; Max-Age=0; SameSite=Lax",
	);

	return res.status(200).json({ success: true });
}
```

## 9. Protected Pages

A protected page is accessible only to authenticated users — for example `/dashboard`. Unauthenticated users should be redirected to login.

### 9.1 App Router

```tsx
// app/dashboard/page.tsx

import { redirect } from "next/navigation";
import { getCurrentUser } from "@/lib/auth/session";

export default async function DashboardPage() {
	const user = await getCurrentUser();

	if (!user) {
		redirect("/login");
	}

	return (
		<div>
			<h1>Dashboard</h1>
			<p>Welcome, {user.name}</p>
		</div>
	);
}
```

Server Components check the session on the server, then redirect or render.

### 9.2 Pages Router

```ts
// pages/dashboard.tsx

export async function getServerSideProps(context) {
	const user = await getCurrentUser(context.req);

	if (!user) {
		return {
			redirect: {
				destination: "/login",
				permanent: false,
			},
		};
	}

	return {
		props: { user },
	};
}
```

```tsx
export default function DashboardPage({ user }) {
	return (
		<div>
			<h1>Dashboard</h1>
			<p>Welcome, {user.name}</p>
		</div>
	);
}
```

## 10. Protected APIs

Protecting a page does **not** automatically protect its API. `/dashboard` may require login while `/api/orders` remains open — an attacker can call the API directly. Every sensitive Route Handler or API route must enforce authentication itself.

### 10.1 App Router

```ts
// app/api/orders/route.ts

import { getCurrentUser } from "@/lib/auth/session";

export async function GET() {
	const user = await getCurrentUser();

	if (!user) {
		return Response.json({ error: "Unauthorized" }, { status: 401 });
	}

	const orders = await getOrdersForUser(user.id);

	return Response.json(orders);
}
```

### 10.2 Pages Router

```ts
// pages/api/orders.ts

import type { NextApiRequest, NextApiResponse } from "next";

import { getCurrentUser } from "@/lib/auth/session";

export default async function handler(
	req: NextApiRequest,
	res: NextApiResponse,
) {
	const user = await getCurrentUser(req);

	if (!user) {
		return res.status(401).json({ error: "Unauthorized" });
	}

	const orders = await getOrdersForUser(user.id);

	return res.status(200).json(orders);
}
```

## 11. Authentication Helper

Do not duplicate session lookup everywhere. Centralize it in `lib/auth/session.ts`:

```ts
export async function getCurrentUser() {
	const sessionId = await getSessionIdFromCookie();
	if (!sessionId) return null;

	const session = await findSession(sessionId);
	if (!session) return null;

	return session.user;
}
```

Reuse `getCurrentUser()` in Server Components, Route Handlers, and Server Actions.

## 12. Session Expiration

Sessions should expire. Store `expiresAt` on the session row and reject expired sessions as unauthenticated — same as having no session at all.

## 14. Auth.js

Manual authentication — registration, login, sessions, cookies, and route guards — covers the plumbing that **Auth.js** automates: session cookies, sign-in, sign-out, OAuth — so you focus on providers and authorization rules instead of cookie mechanics.

| Manual authentication | Auth.js |
| -------------- | ------- |
| Login Route Handler + `createSession` | `signIn("credentials", …)` |
| `getCurrentUser()` | `await auth()` |
| Logout Route Handler + `deleteSession` | `signOut()` |
| Manual `Set-Cookie` | Handled internally (HttpOnly cookie) |

Auth.js does **not** decide who may access what — your pages and APIs still enforce that.

---

## 15. Auth.js Configuration

Minimal `auth.ts` with Credentials + Google, JWT sessions, and a `role` claim:

```ts
// auth.ts
import NextAuth from "next-auth";
import Credentials from "next-auth/providers/credentials";
import Google from "next-auth/providers/google";
import { verifyCredentials } from "@/lib/auth/verify-credentials";

export const { handlers, auth, signIn, signOut } = NextAuth({
	providers: [
		Credentials({
			credentials: { email: {}, password: {} },
			authorize: async (c) => {
				const user = await verifyCredentials(c);
				return user
					? { id: String(user.id), email: user.email, name: user.name, role: user.role }
					: null;
			},
		}),
		Google({
			clientId: process.env.AUTH_GOOGLE_ID!,
			clientSecret: process.env.AUTH_GOOGLE_SECRET!,
		}),
	],
	session: { strategy: "jwt" },
	callbacks: {
		jwt({ token, user }) {
			if (user) token.role = user.role;
			return token;
		},
		session({ session, token }) {
			if (session.user) session.user.role = token.role as string;
			return session;
		},
	},
});
```

```ts
// app/api/auth/[...nextauth]/route.ts
import { handlers } from "@/auth";
export const { GET, POST } = handlers;
```

```env
AUTH_SECRET="..."
AUTH_GOOGLE_ID="..."
AUTH_GOOGLE_SECRET="..."
```

With `strategy: "jwt"`, Auth.js stores an encrypted token in an **HttpOnly** cookie (**Important Cookie Options**) — separate from the custom `sessions` table in **Sessions**. Use one approach per app.

Custom fields like `role` must flow through **`jwt`** (on sign-in) and **`session`** (on every read). Without both callbacks, `session.user.role` stays undefined.

## 16. Sign In and Sign Out

**Credentials login** — Server Action form:

```tsx
// app/login/page.tsx
import { signIn } from "@/auth";

export default function LoginPage() {
	return (
		<form
			action={async (formData) => {
				"use server";
				await signIn("credentials", formData);
			}}
		>
			<input name="email" type="email" required />
			<input name="password" type="password" required />
			<button type="submit">Sign in</button>
		</form>
	);
}
```

**Google OAuth** — same pattern, different provider id:

```tsx
<form action={async () => { "use server"; await signIn("google"); }}>
	<button type="submit">Continue with Google</button>
</form>
```

**Sign out:**

```tsx
import { signOut } from "@/auth";

<form action={async () => { "use server"; await signOut(); }}>
	<button type="submit">Sign out</button>
</form>
```

OAuth flow: user clicks button → redirect to Google → callback at `/api/auth/callback/google` → session cookie set → redirect back to your app.

The Credentials provider does not write to your database — `verifyCredentials` (same hash check as **Login**) remains your code.

## 17. Reading the Session

Replace `getCurrentUser()` with `auth()` on the server.

**Protected page** — same guard as **Protected Pages**, different API:

```tsx
// app/dashboard/page.tsx
import { auth } from "@/auth";
import { redirect } from "next/navigation";

export default async function DashboardPage() {
	const session = await auth();
	if (!session?.user) redirect("/login");

	return <h1>Welcome, {session.user.name}</h1>;
}
```

**Protected API** — same guard as **Protected APIs**:

```ts
// app/api/orders/route.ts
import { auth } from "@/auth";

export async function GET() {
	const session = await auth();
	if (!session?.user) {
		return Response.json({ error: "Unauthorized" }, { status: 401 });
	}

	return Response.json(await getOrdersForUser(session.user.id));
}
```

**Admin-only route** — uses `role` from **Auth.js Configuration** callbacks:

```ts
const session = await auth();
if (!session?.user) return Response.json({ error: "Unauthorized" }, { status: 401 });
if (session.user.role !== "admin") return Response.json({ error: "Forbidden" }, { status: 403 });
```

## 18. Middleware / Proxy and Authentication

Next.js request-level middleware/proxy mechanisms can be used for broad access checks.

Conceptually:

```text
Request
   ↓
Middleware / Proxy
   ↓
Authentication check
   ↓
Allow / redirect
   ↓
Page or API
```

This can be useful for protecting groups of routes.

However, do not treat it as the only authorization layer.

Sensitive server-side operations should still verify authentication and authorization at the point where the operation happens.

---

## 19. Client-Side Authentication State

A Client Component may display different UI:

```text
Logged in:
[Dashboard] [Logout]

Logged out:
[Login] [Register]
```

But client state is not a security boundary.

Never rely on:

```ts
if (isAdmin) {
	// perform sensitive operation
}
```

for security.

A malicious user can modify client-side code.

Instead:

```text
Client
  ↓
Server request
  ↓
Authenticate
  ↓
Authorize
  ↓
Perform operation
```

The server is the security boundary.

## 20. Password Change

A secure password-change flow:

```text
Authenticated user
       ↓
Verify current password
       ↓
Validate new password
       ↓
Hash new password
       ↓
Update passwordHash
       ↓
Optionally revoke old sessions
```

Never store the new password directly.

---

## 21. Forgot Password

A password reset should not send the existing password.

Typical flow:

```text
Forgot password
      ↓
Enter email
      ↓
Generate random short-lived token
      ↓
Send reset link
      ↓
Open link
      ↓
Validate token
      ↓
Set new password
      ↓
Hash password
      ↓
Invalidate reset token
```

Reset tokens should be:

- Random
- Short-lived
- Single-use
- Stored securely

## 22. Authentication Error Handling

Common responses:

```text
400
→ Invalid input

401
→ Not authenticated

403
→ Authenticated but not allowed

409
→ Account already exists

429
→ Too many requests

500
→ Unexpected server error
```

Do not expose internal details such as:

```text
PostgreSQL connection failed at ...
```

Return a safe message and log details server-side.

## 23. Brute-Force Protection

Authentication endpoints are sensitive.

An attacker could repeatedly try:

```text
password1
password2
password3
...
```

Consider:

- Rate limiting
- Strong passwords
- MFA where appropriate
- Monitoring
- Temporary controls for suspicious activity
- CAPTCHA/challenges when appropriate

Example:

```text
Many login attempts
       ↓
Rate limiter
       ↓
429 Too Many Requests
```

```text
Current User
   ↓

   ↓
```

## 25. Common Authentication Mistakes

- Store **`passwordHash`**, never plain `password`
- Do not trust client-side checks like `if (isAdmin)` — enforce authorization on the server
- Protect APIs as well as pages — `/dashboard` locked down but `/api/orders` open is a common hole
- Never trust client-supplied user ids (`/api/orders?userId=42`) — derive identity from the session
- Never return `passwordHash` (or any secret) in JSON responses
- Use proper cookie attributes: `HttpOnly`, `Secure`, `SameSite`, `path`, and expiration
- Rate-limit login and password-reset endpoints against brute-force attempts
- Use established libraries for hashing and tokens — do not roll your own crypto
