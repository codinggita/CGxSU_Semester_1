# 22. Proxy / Request Interception

Next.js can inspect and control incoming requests before they reach the requested page or route — including redirects, rewrites, authentication checks, and request-based logic. Request-level logic in Next.js serves a role similar to middleware in an Express application (`app.use`). Modern Next.js uses `proxy.ts`; older projects and tutorials often use `middleware.ts` for the same concept — use the file convention that matches your Next.js version.

---

## 1. Proxy

A proxy runs between the incoming request and the final application destination.

```text
Browser
   ↓
HTTP Request
   ↓
Proxy
   ↓
Next.js Page / Route Handler
```

A proxy can inspect the request and decide whether to:

- Continue
- Redirect
- Rewrite
- Apply request-level logic

Example:

```text
Request
   ↓
Authentication check
   ↓
Authenticated?
   ├── Yes → Continue
   └── No  → Redirect /login
```

---

## 2. Why Use a Proxy?

Request-level rules are often common across multiple routes.

For example:

```text
/dashboard
    ↓
Authentication required

/admin
    ↓
Authentication + admin access

/old-products
    ↓
Redirect to /products

/api/*
    ↓
Request-based routing
```

A proxy allows this logic to be handled at a common request boundary instead of duplicating it in every page.

---

## 3. Express Middleware Comparison

If you have used Express middleware, `proxy.ts` does the same conceptual job — code that runs before the route handler and can inspect, redirect, or pass the request through — with a Next.js-specific API and file convention instead of `app.use()`.

```text
Express middleware                      Next.js proxy.ts
──────────────────────────────────────  ──────────────────────────────────────
app.use((req, res, next) => {...})       export function proxy(request) {...}
next()                                   return NextResponse.next()
res.redirect(url)                        return NextResponse.redirect(url)
res.status(401).json({...})              return NextResponse.json({...}, { status: 401 })
Registered per-route or globally         Runs at the project root, scoped via matcher
```

Express middleware can be composed and ordered explicitly — multiple `app.use()` calls run in sequence. Next.js has a **single** `proxy.ts` file per project; use `matcher` to scope where it applies rather than composing multiple middleware functions.

`NextResponse.rewrite()` has no direct Express middleware equivalent — it internally serves a different path while keeping the browser URL unchanged.

---

## 4. Proxy vs Route Handler

Do not confuse a proxy with a Route Handler.

### 4.1 Proxy

Runs before the request reaches its destination.

```text
Request
   ↓
Proxy
   ↓
Page / Route Handler
```

### 4.2 Route Handler

Actually handles the HTTP request and produces the API response.

```text
Request
   ↓
Route Handler
   ↓
Response
```

Example:

```text
GET /api/products
       ↓
     Proxy
       ↓
Route Handler
       ↓
JSON Response
```

A proxy is therefore **not a replacement for a Route Handler**.

## 5. Request Interception

Request interception means inspecting an incoming request before it reaches its final destination.

A request can contain:

```text
URL
Path
Query parameters
HTTP method
Headers
Cookies
```

Conceptually:

```text
Incoming Request
       ↓
   Inspect Request
       ↓
┌──────┴─────────┐
│                │
Continue       Change
│                │
↓                ├── Redirect
Page/API         └── Rewrite
```

---

## 6. Creating `proxy.ts`

For modern Next.js, create:

```text
proxy.ts
```

at the project root.

Example:

```text
my-next-app/
├── app/
│   ├── page.tsx
│   └── dashboard/
│       └── page.tsx
├── public/
├── proxy.ts
├── next.config.ts
└── package.json
```

If the project uses a `src` directory, the proxy can be placed according to the project's Next.js structure.

## 7. Basic Proxy

Example:

```ts
import { NextResponse } from "next/server";

export function proxy() {
  return NextResponse.next();
}
```

`NextResponse.next()` means:

```text
Continue processing the request normally.
```

Flow:

```text
Request
   ↓
proxy()
   ↓
NextResponse.next()
   ↓
Page / Route Handler
```

## 8. Simple Authentication Example

Suppose login creates:

```text
session=abc123
```

Proxy:

```ts
import {
  NextRequest,
  NextResponse,
} from "next/server";

export function proxy(request: NextRequest) {
  const session =
    request.cookies.get("session");

  if (!session) {
    return NextResponse.redirect(
      new URL("/login", request.url)
    );
  }

  return NextResponse.next();
}
```

This middleware example only checks whether a session cookie exists — it does not validate the session. In production, verify sessions through your auth provider.

---

## 9. Keep Proxy Lightweight

The proxy runs at the request boundary.

Avoid putting large business workflows inside it.

Bad:

```text
Proxy
 ↓
Multiple database queries
 ↓
Complex calculations
 ↓
Payment logic
 ↓
Page
```

Prefer:

```text
Proxy
 ↓
Light request-level decision
 ↓
Page / API
 ↓
Service
 ↓
Repository
 ↓
Database
```

```text

 ↓

 ↓
```

### 10.1 Proxy


## 11. Full Example — Shop Admin App

The Shop Admin project combines request-interception patterns — middleware, route matchers, and auth checks — into one App Router app. Comments in each file explain what each block does and whether it belongs in the proxy.

### 11.1 Scenario

A small e-commerce admin app needs:

- Public product catalog at `/products`
- Login at `/login` (redirect authenticated users away)
- Protected dashboard at `/dashboard`
- Admin-only area at `/admin`
- Legacy URL `/old-products` redirected permanently (static rule in config)
- Internal rewrite so `/catalog` serves `/products` content without changing the URL
- `/api/*` proxied to a separate Node.js backend on another host
- Locale prefix routing (`/` → `/en` or `/fr` based on cookie)
- Role-based gate for `/admin` (admin role required)

```text
Browser
   ↓
proxy.ts          ← request-level routing, auth gates, rewrites
   ↓
app/ pages        ← Server Components, Server Actions
   ↓
Route Handlers    ← API responses with their own auth
   ↓
Service / Repository / Database
```

Works the same with the Pages Router — the proxy sits before `pages/` instead of `app/`.

### 11.3 Static Redirect — `next.config.ts`

Static mappings that never depend on cookies, headers, or method belong in config — not the proxy.

```ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  async redirects() {
    return [
      {
        // Static rule: /old-products → /products (301 permanent)
        // No request inspection needed — handled at build/deploy time.
        source: "/old-products",
        destination: "/products",
        permanent: true, // HTTP 308 in production
      },
    ];
  },
};

export default nextConfig;
```

### 11.4 Complete `proxy.ts`

```ts
import {
  NextRequest,
  NextResponse,
} from "next/server";

// ─── Helpers ───────────────────────────────────────────────────────────────

/** Decode a demo session cookie. In production, verify a signed JWT or call your auth provider. */
function parseSession(request: NextRequest) {
  const raw = request.cookies.get("session")?.value;
  if (!raw) return null;
  try {
    return JSON.parse(raw) as { userId: string; role: "USER" | "ADMIN" };
  } catch {
    return null;
  }
}

// ─── Main proxy function ─────────────────────────────────────────────────────

export function proxy(request: NextRequest) {
  // ── NextRequest: access method, full URL, pathname, searchParams ──────────
  const { method } = request; // GET | POST | PUT | PATCH | DELETE
  const { pathname, searchParams } = request.nextUrl;

  // Query param example: /products?page=2
  const page = searchParams.get("page");

  // ── Headers ───────────────────────────────────────────────────────────────
  const userAgent = request.headers.get("user-agent") ?? "";
  // User-Agent can inform routing decisions but is NOT a security mechanism.
  const isMobile = /mobile/i.test(userAgent);

  // ── Cookies ───────────────────────────────────────────────────────────────
  const session = parseSession(request);
  const localeCookie = request.cookies.get("locale")?.value ?? "en";

  // ── 1. Static-style redirect handled in proxy (request-dependent variant) ─
  // /legacy-admin always redirects — could also live in next.config.ts if static.
  if (pathname === "/legacy-admin") {
    return NextResponse.redirect(new URL("/admin", request.url), 307);
  }

  // ── 2. Rewrite: browser shows /catalog, server serves /products ──────────
  // Redirect = browser navigates, URL changes.
  // Rewrite  = internal mapping, URL stays the same.
  if (pathname === "/catalog") {
    const url = request.nextUrl.clone();
    url.pathname = "/products";
    if (page) url.searchParams.set("page", page); // preserve query params
    return NextResponse.rewrite(url);
  }

  // ── 3. Locale routing: / → /en or /fr based on cookie ────────────────────
  if (pathname === "/") {
    return NextResponse.redirect(
      new URL(`/${localeCookie}`, request.url)
    );
  }

  // ── 4. API rewrite: proxy /api/* to external Node.js backend ───────────────
  // Browser calls same origin (/api/products) — no CORS issues for the client.
  // The backend must still configure CORS if called directly from other origins.
  if (pathname.startsWith("/api/")) {
    const backendUrl = new URL(pathname, "https://api.example.com");
    backendUrl.search = request.nextUrl.search; // forward ?page=2 etc.
    return NextResponse.rewrite(backendUrl);
  }

  // ── 5. Redirect logged-in users away from /login ───────────────────────────
  if (pathname === "/login" && session) {
    return NextResponse.redirect(new URL("/dashboard", request.url));
  }

  // ── 6. Authentication gate: /dashboard requires a session ──────────────────
  // Authentication = "Who are you?" (valid session exists)
  if (pathname.startsWith("/dashboard") && !session) {
    const loginUrl = new URL("/login", request.url);
    loginUrl.searchParams.set("from", pathname); // return URL after login
    return NextResponse.redirect(loginUrl);
  }

  // ── 7. Authorization gate: /admin requires ADMIN role ─────────────────────
  // Authorization = "What are you allowed to do?" (role / permission check)
  // Never trust the cookie alone — this demo parses it; production must verify server-side.
  if (pathname.startsWith("/admin")) {
    if (!session) {
      return NextResponse.redirect(new URL("/login", request.url));
    }
    if (session.role !== "ADMIN") {
      // 403 — user is authenticated but not authorized
      return NextResponse.json({ error: "Forbidden" }, { status: 403 });
    }
  }

  // ── 8. Request-based logic: block DELETE on /api/admin from proxy layer ──
  // (Real DELETE auth still belongs in the Route Handler / service layer.)
  if (pathname.startsWith("/api/admin") && method === "DELETE" && !session) {
    return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
  }

  // ── 9. Forward request with modified headers ───────────────────────────────
  const requestHeaders = new Headers(request.headers);
  requestHeaders.set("x-locale", localeCookie);
  requestHeaders.set("x-device", isMobile ? "mobile" : "desktop");

  const response = NextResponse.next({
    request: { headers: requestHeaders },
  });

  // ── 10. Attach response headers ────────────────────────────────────────────
  response.headers.set("x-request-id", crypto.randomUUID());

  return response;
}

// ─── Matcher: limit which paths run the proxy ────────────────────────────────
// Without a matcher, proxy runs on EVERY request including _next/static assets.
// Exclude static files; only run on routes that need request-level logic.
//
// ⚠ Server Functions (Server Actions) are POST requests to the PAGE route —
//   NOT separate URLs. If /products is excluded here, Server Actions on that
//   page are also excluded from proxy coverage. Always verify auth INSIDE
//   each Server Action (see app/products/actions.ts).
export const config = {
  matcher: [
    /*
     * Match all paths except Next.js internals and static files:
     * - _next/static, _next/image, favicon.ico
     */
    "/((?!_next/static|_next/image|favicon.ico).*)",
  ],
};
```

### 11.5 Shared Auth Helper — `lib/auth.ts`

Proxy checks are a **navigation filter**, not the real security layer. Reuse validation in Server Actions and Route Handlers.

```ts
import { cookies } from "next/headers";

export type Session = { userId: string; role: "USER" | "ADMIN" };

/** Validate session server-side. Call this inside every protected Server Action / Route Handler. */
export async function getSession(): Promise<Session | null> {
  const raw = (await cookies()).get("session")?.value;
  if (!raw) return null;
  try {
    const session = JSON.parse(raw) as Session;
    // Production: verify JWT signature, check expiry, call auth provider, etc.
    return session;
  } catch {
    return null;
  }
}

export async function requireAdmin(): Promise<Session> {
  const session = await getSession();
  if (!session) throw new Error("Unauthorized");
  if (session.role !== "ADMIN") throw new Error("Forbidden");
  return session;
}
```

### 11.6 Server Action with Internal Auth — `app/products/actions.ts`

`/products` is a **public page** — it may be excluded from strict proxy auth. Any mutation on that page must still enforce auth **inside the action**.

```ts
"use server";

import { getSession } from "@/lib/auth";
import { revalidatePath } from "next/cache";

// Server Actions are invoked as POST /products — same route as the page.
// If proxy matcher excludes /products, this action bypasses proxy entirely.
// Hard rule: never rely on proxy alone for mutations.
export async function addToWishlist(productId: string) {
  const session = await getSession();
  if (!session) {
    throw new Error("You must be logged in to save products.");
  }

  // Service layer would handle the actual DB write:
  // await wishlistService.add(session.userId, productId);

  revalidatePath("/products");
}
```

### 11.7 Route Handler with Authorization — `app/api/admin/users/[id]/route.ts`

Route Handlers produce API responses. Proxy can gate navigation; the handler must enforce permissions for the operation.

```ts
import { requireAdmin } from "@/lib/auth";
import { NextResponse } from "next/server";

// DELETE /api/admin/users — proxy may block unauthenticated DELETE,
// but this handler still verifies ADMIN role before any DB operation.
export async function DELETE(
  request: Request,
  { params }: { params: Promise<{ id: string }> }
) {
  try {
    await requireAdmin(); // Authentication + authorization
  } catch {
    return NextResponse.json({ error: "Forbidden" }, { status: 403 });
  }

  const { id } = await params;
  // await userService.delete(id);  ← service layer, not proxy

  return NextResponse.json({ deleted: id });
}
```

### 11.8 Request Flow Diagrams

**Redirect (URL changes in browser):**

```text
Browser ──GET /legacy-admin──▶ Proxy ──307──▶ Browser ──GET /admin──▶ Page
```

**Rewrite (URL stays the same):**

```text
Browser ──GET /catalog──▶ Proxy ──internal rewrite──▶ /products page
         (browser still shows /catalog)
```

**Protected dashboard:**

```text
GET /dashboard
      ↓
    Proxy
      ↓
  session cookie?
   ┌──┴──┐
  No    Yes
   │      │
   ↓      ↓
/login  Dashboard page
```

**Full stack (proxy is not the business-logic layer):**

```text
Browser
   ↓
Proxy          ← redirect / rewrite / session gate / header injection
   ↓
Page / Route Handler
   ↓
Service        ← business rules
   ↓
Repository     ← database access
   ↓
Database
```

## 12. Common Mistakes

### 12.1 Treating Proxy as a Backend

Do not put all backend functionality into the proxy.

Avoid:

```text
Database workflows
Payment processing
Complex business rules
Large data transformations
```

---

### 12.2 Using Proxy as the Only Authorization Layer

Bad:

```text
Proxy
 ↓
User appears authenticated
 ↓
Sensitive API trusts request
```

Better:

```text
Proxy
 ↓
Navigation/request filtering

API / Server Action
 ↓
Authentication
 ↓
Authorization
 ↓
Business operation
```

Per the [official Next.js proxy docs](https://nextjs.org/docs/app/api-reference/file-conventions/proxy#matcher): Server Functions are POST requests to the page route — a matcher that excludes a path also skips Server Actions on that path. Always verify auth inside each Server Function.

---

### 12.3 Running Expensive Logic for Every Request

Use `matcher` to limit where the proxy applies.

```ts
export const config = {
  matcher: [
    "/dashboard/:path*",
    "/admin/:path*",
  ],
};
```

---

### 12.4 Confusing Redirect and Rewrite

Redirect and rewrite behave differently:

```text
Redirect
 ↓
Browser navigates
 ↓
URL changes
```

```text
Rewrite
 ↓
Server internally maps request
 ↓
URL can remain unchanged
```

### 12.5 Assuming a Cookie Means the User Is Authorized

A cookie existing does not automatically prove:

```text
Valid session
Correct user
Correct role
Correct permission
```

The authentication system must validate the session.

---

## 13. When Should You Use Proxy?

Use proxy for request-level concerns such as:

```text
✓ Request-dependent redirects
✓ Request-dependent rewrites
✓ Authentication-related routing
✓ Cookie inspection
✓ Header inspection
✓ Locale/request routing
✓ Request filtering
```

Do not use it for:

```text
✗ Complex business logic
✗ Database architecture
✗ Payment workflows
✗ General API implementation
✗ Replacing authorization in sensitive operations
```
