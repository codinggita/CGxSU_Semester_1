# 25. Logging & Monitoring

Logging and monitoring help identify errors, performance problems, and unexpected behavior in Next.js applications — during development and in production.

---

# 1. Structured Logging

Logging means recording useful information about what an application is doing.

Examples:

```text
User logged in
Product created
Database query failed
Payment request failed
```

Production logs should help answer:

```text
What happened?
When did it happen?
Which request caused it?
Where did it fail?
What was the error?
```

A structured log can look like:

```json
{
  "level": "info",
  "event": "product.created",
  "requestId": "req_123",
  "userId": "user_456",
  "productId": "product_789",
  "timestamp": "2026-08-18T12:00:00.000Z"
}
```

---

# 2. Why `console.log()` Is Not Enough

During development:

```ts
console.log("User created");
```

is perfectly useful.

In production, however, applications need:

- Consistent log structure
- Log levels
- Request correlation
- Search and filtering
- Centralized storage
- Error context

Instead of:

```text
User created product 123
```

prefer structured information:

```json
{
  "event": "product.created",
  "productId": "123",
  "userId": "456"
}
```

---

# 3. Setting Up Structured Logging with Pino

Every server-side example in this document uses a shared `logger` object. Configure it once, then import it wherever Node.js runtime code runs.

## Install Pino

```bash
npm install pino
npm install -D pino-pretty
```

Pino is the most widely used structured-logging library for Node.js and Next.js — it is extremely fast and outputs JSON by default, which is what centralized log platforms (Datadog, Logtail, etc.) expect.

`pino-pretty` is a **dev-only** dependency. It formats JSON logs into human-readable output during local development. Do not rely on it in production.

## Create the Logger — `lib/logger.ts`

```ts
// lib/logger.ts
import pino from "pino";

const isDevelopment = process.env.NODE_ENV === "development";

export const logger = pino({
  level: process.env.LOG_LEVEL ?? "info",
  ...(isDevelopment && {
    transport: {
      target: "pino-pretty",
      options: {
        colorize: true,
      },
    },
  }),
});
```

- **`level`** — minimum severity logged. `DEBUG` in development and `INFO` in production is a common convention. Use the `LOG_LEVEL` environment variable so operators can change verbosity without redeploying code.
- **`pino-pretty` transport** — enabled only in development. In production, Pino writes raw JSON that log platforms parse and index automatically.
- **Named export** — other files import with `import { logger } from "@/lib/logger"`.

## Edge Runtime Limitation

> **Warning:** Pino imports Node.js-specific modules and does **not** work in the **Edge Runtime** (Proxy, Edge Route Handlers). For those files only, use `console.log()` or an Edge-compatible logger. Structured logging with Pino is for **Node.js runtime** code: Server Components, standard Route Handlers, Server Actions, and the service layer.

## Coming from MERN

| Express / MERN | Next.js |
| --- | --- |
| Morgan (HTTP request logging) | Proxy + `logger` (see **Proxy / Request Interception**) |
| Winston (structured logging) | Pino (same concept, leaner, faster) |
| `console.log()` in routes | `logger.info()` in Route Handlers / service layer |
| `express-async-errors` | `onRequestError` hook in `instrumentation.ts` |

# 4. Log Levels

Common log levels include:

```text
TRACE
DEBUG
INFO
WARN
ERROR
FATAL
```

A practical application commonly uses:

```text
DEBUG
INFO
WARN
ERROR
```

## 4.1 DEBUG

Detailed information useful during development.

```ts
import { logger } from "@/lib/logger";
logger.debug({
  productId,
}, "Fetching product");
```

## 4.2 INFO

Normal important application events.

```ts
import { logger } from "@/lib/logger";
logger.info({
  userId,
  productId,
}, "Product created");
```

## 4.3 WARN

Unexpected situations that do not necessarily mean failure.

```ts
import { logger } from "@/lib/logger";
logger.warn({
  durationMs: 3200,
}, "Slow database query");
```

## 4.4 ERROR

Failures requiring investigation.

```ts
import { logger } from "@/lib/logger";
logger.error({
  err,
  requestId,
}, "Failed to create order");
```

# 6. What Should NOT Be Logged?

Never casually log:

```text
Passwords
Authentication tokens
Session secrets
API keys
Private keys
Credit card information
Sensitive personal information
```

Bad:

```ts
import { logger } from "@/lib/logger";
logger.info({
  email,
  password,
}, "Login attempt");
```

Better:

```ts
import { logger } from "@/lib/logger";
logger.info({
  userId,
}, "Login successful");
```

Be especially careful with request bodies, cookies, and authorization headers.


Prefer meaningful events:

```ts
import { logger } from "@/lib/logger";

  event: "product.created",
  userId,
  productId,
});
```

Examples:

```text

order.created
payment.completed
payment.failed

```

A consistent naming convention makes logs easier to search.

A request ID is a unique identifier assigned to a request.

Example:

```text

```

The same ID should be included in logs generated while processing that request.

```text
Request received

Validation completed
requestId = req_123

Database operation
requestId = req_123

Product created
requestId = req_123
```

# 10. Why Request IDs Matter

Suppose production receives:

```text
500 requests per second
```

One request fails.

Without a request ID:

```text
Which database error belongs to this request?
```

With a request ID:

```text
req_123
   ↓
HTTP request
   ↓
Service log
   ↓
Database error
   ↓
500 response
```

You can search all logs using:

```text
requestId = req_123
```

# 12. Generating a Request ID

A simple implementation:

```ts
const requestId =
  crypto.randomUUID();
```

Then:

```ts
import { logger } from "@/lib/logger";
logger.info({
  requestId,
}, "Request started");
```

In larger deployments, infrastructure may already provide a correlation identifier.

> In a real application, the request ID is often generated centrally in `proxy.ts` and injected as an `x-request-id` header, so every Route Handler and Server Action automatically receives it from the header without generating its own. **Existing Request IDs** shows how to read an existing header value — combine both patterns for a clean implementation.

---

# 13. Existing Request IDs

You may receive a request ID through a header:

```ts
const requestId =
  request.headers.get("x-request-id")
  ?? crypto.randomUUID();
```

Do not use an arbitrary client-provided ID for security decisions. It is a correlation value, not an authentication mechanism.

---

# 14. Returning the Request ID

It can be useful to return the request ID in an API response:

```ts
return Response.json(
  {
    message: "Internal server error",
    requestId,
  },
  {
    status: 500,
  }
);
```

The response can also include:

```http
x-request-id: req_123
```

Then support teams can ask users for the request ID when investigating a problem.

# 16. Server Errors

Server-side errors can happen in:

```text
Server Components
Route Handlers
Server Actions
Database operations
External APIs
Background jobs
```

Example:

```ts
import { logger } from "@/lib/logger";
try {
  const product =
    await productService.create(data);

  return Response.json(
    product,
    { status: 201 }
  );

  logger.error({
    err: error,
    requestId,
  }, "Failed to create product");

  return Response.json(
    {
      message: "Internal server error",
      requestId,
    },
    { status: 500 }
  );

```

Bad:

```ts
return Response.json({
  error: error.message,
});
```

The error may reveal:

```text

Internal paths
SQL information
Service names
Implementation details
```

Better:

```ts
return Response.json(
  {
    message: "Internal server error",
    requestId,
  },
  { status: 500 }

```

# 23. Connecting Observability Tools — `instrumentation.ts`

Error monitoring platforms (Sentry, Datadog, New Relic) must hook into Next.js at server startup and at the moment an unhandled server error occurs. Next.js provides official file conventions for both.

Place `instrumentation.ts` in the **project root** or **`src/`** — not inside `app/` or `pages/`.

## The `register()` Function

Called **once** when a new Next.js server instance starts. It must complete before the server handles requests.

```ts
// instrumentation.ts

export async function register() {
  if (process.env.NEXT_RUNTIME === "nodejs") {
    // Server-side monitoring SDK initialization goes here
    // Example: await import("./sentry.server.config")
    // Example: initialize OpenTelemetry
  }
}
```

- **`register()`** runs at server startup — the documented place to initialize Sentry, Datadog, OpenTelemetry, or other Node.js-only SDKs.
- **`process.env.NEXT_RUNTIME === "nodejs"`** — required guard because some SDKs import Node.js-only modules that fail in Edge or client environments. The same file can target Edge separately when needed.
- Do **not** initialize monitoring SDKs inside a page, layout, or Route Handler — those run per request and would re-initialize constantly.

## The `onRequestError()` Hook

Export this optional hook to capture **server** errors automatically — no try/catch at every entry point.

```ts
// instrumentation.ts
import type { Instrumentation } from "next";

export const onRequestError: Instrumentation.onRequestError = async (
  err,
  request,
  context
) => {
  const message = err instanceof Error ? err.message : String(err);
  const digest =
    typeof err === "object" && err !== null && "digest" in err
      ? String(err.digest)
      : undefined;

  // Send to your error monitoring service here
  // Example: Sentry.captureRequestError(err, request, context)

  console.error({
    message,
    digest,
    path: request.path,
    method: request.method,
    routePath: context.routePath,
    routeType: context.routeType,
  });
};
```

- **`onRequestError`** fires for unhandled errors in Server Components, Route Handlers, Server Actions, and Proxy — `context.routeType` indicates which (`'render'`, `'route'`, `'action'`, or `'proxy'`).
- The **`error`** argument may not be the original thrown value if React processed it during Server Component rendering. Use the **`digest`** property on the error object to identify the underlying failure type.
- **Await** async work inside this hook — Next.js waits for `onRequestError` to finish before completing error handling.
- Sentry's Next.js integration exports `onRequestError = Sentry.captureRequestError` — this is the same pattern.

## Client-Side Instrumentation — `instrumentation-client.ts`

Place `instrumentation-client.ts` in the **project root** or **`src/`**. It runs **after** the HTML document loads and **before** React hydration begins — the correct place for browser-side Sentry, analytics, or client error tracking.

```ts
// instrumentation-client.ts

try {
  // Initialize client-side error monitoring here
  // Example: Sentry browser SDK init (synchronous setup)
} catch (error) {
  console.error("Client instrumentation failed:", error);
}

window.addEventListener("unhandledrejection", (event) => {
  // Send to client-side error monitoring service
  console.error("Unhandled promise rejection:", event.reason);
});
```

- Only **synchronous, top-level** code is guaranteed to finish before hydration. Async work started here (`Promise`, dynamic `import()`, top-level `await`) is fire-and-forget and may complete after hydration has begun.
- Wrap initialization in **try/catch** so a monitoring failure does not break the app.
- For client-side errors in interactive components, combine this with route-level **`error.tsx`** boundaries (see earlier sections).

# 30. Measuring Request Duration

A basic pattern:

```ts
import { logger } from "@/lib/logger";
const start = performance.now();

try {
  // request processing
} finally {
  const durationMs =
    performance.now() - start;

  logger.info({
    requestId,
    durationMs,
  }, "Request completed");
}
```

# 39. Logs, Metrics, Traces, and Observability

Observability commonly combines logs, metrics, traces, and errors.

```text
             Observability
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
     Logs       Metrics    Traces
       │          │          │
       ▼          ▼          ▼
   What?       How much?   Where?
```

### Logs

Detailed events:

```text
Order created
Database error
User logged in
```

### Metrics

Numerical measurements:

```text
500 requests/sec
2% error rate
180ms latency
```

### Traces

Follow a request through multiple components:

```text
Request
  ↓
API
  ↓
Service
  ↓
Database
  ↓
External API
```

Together they provide a much stronger understanding of production behavior.

Three complementary questions frame the relationship:

- **Logging** — What happened?
- **Monitoring** — Is the system healthy?
- **Observability** — Why is the system behaving this way?

Monitoring tracks known health and performance signals (error rate, latency, throughput). Observability provides enough correlated information to investigate unexpected behavior — often by combining logs, metrics, traces, and errors.

# 43. Server vs Client Logging

Next.js has both server and client execution environments.

| Location | Typical logging destination |
|---|---|
| Server Component | Server logs |
| Route Handler | Server logs |
| Server Action | Server logs |
| Client Component | Browser console |
| Browser exception | Client error monitoring |
| Database | Database/system logs |

This is important because:

```text
console.log()
```

inside a Server Component does not appear in the browser console.

# 44. Logging in Server Components

Example:

```tsx
import { logger } from "@/lib/logger";
export default async function ProductsPage() {
  logger.info(
    "Loading products"
  );

  const products =
    await getProducts();

  return (
    <ProductList
      products={products}
    />
  );
}
```

This executes on the server.

Therefore the log belongs to the server environment.

---

# 45. Logging in Client Components

Example:

```tsx
"use client";

export function Button() {
  function handleClick() {
    console.log("Clicked");
  }

  return (
    <button onClick={handleClick}>
      Click
    </button>
  );
}
```

This runs in the browser.

`console.log()` in Client Components is useful during development but does not reach centralized server logs. For production client-side errors and unhandled promise rejections, initialize browser error monitoring in **`instrumentation-client.ts`** (see **Connecting Observability Tools — `instrumentation.ts`**) and combine it with route-level **`error.tsx`** boundaries for component crashes.

# 46. Logging in Route Handlers

Example:

```ts
import { logger } from "@/lib/logger";
export async function GET(
  request: Request
) {
  const requestId =
    request.headers.get("x-request-id")
    ?? crypto.randomUUID();

  const start = performance.now();

  try {
    const products =
      await productService.getAll();

    return Response.json(
      products,
      {
        headers: {
          "x-request-id": requestId,
        },
      }
    );
  } catch (error) {
    logger.error({
      err: error,
      requestId,
    }, "Failed to fetch products");

    return Response.json(
      {
        message: "Internal server error",
        requestId,
      },
      { status: 500 }
    );
  } finally {
    logger.info({
      requestId,
      durationMs:
        performance.now() - start,
    }, "Request completed");
  }
}
```

This demonstrates:

```text
Request ID
+
Error logging
+
Performance measurement
```

# 47. Logging in the Service Layer

Avoid logging every line:

```ts
import { logger } from "@/lib/logger";
logger.info("Entering function");
logger.info("Validation completed");
logger.info("Calling repository");
logger.info("Returning result");
```

This creates noise.

Prefer meaningful business events:

```ts
import { logger } from "@/lib/logger";
logger.info({
  userId,
  productId,
}, "product.created");
```

and meaningful failures:

```ts
import { logger } from "@/lib/logger";
logger.error({
  err: error,
  productId,
}, "product.creation_failed");
```

A clean architecture makes observability easier:

```text

      ↓

      ↓

      ↓
```

Possible responsibilities:

### Route Handler

# 49. Correlating Errors With Logs

Suppose error monitoring reports:

```text
Order creation failed
```

with:

```text
requestId = req_123
```

Search centralized logs:

```text
requestId:req_123
```

You may find:

```text
POST /api/orders
   ↓
Validation passed
   ↓
Payment request started
   ↓
Payment request failed
   ↓
Order creation failed
```

This is one of the most useful production debugging workflows.

# 50. Release and Version Monitoring

Production deployments should ideally have a release/version identifier.

Example:

```text
release = 2.5.1
```

Then monitoring can show:

```text
2.5.0 → 0.4% error rate
2.5.1 → 4.8% error rate
```

This immediately suggests that the new release may have introduced a regression.

# 51. Production Alerts

Useful alerts can include:

```text
Error rate > threshold
API latency > threshold
Database unavailable
Memory usage > threshold
Health check failing
External provider failure rate increasing
```

Do not alert on every warning.

Too many alerts cause:

```text
Alert fatigue
```

---

# 52. Good vs Bad Alerts

Good:

```text
Checkout API 5xx rate exceeded 5%
```

Someone can investigate it.

Bad:

```text
One request took 2 seconds
```

This may not require immediate action.

A good alert should mean:

```text
Something is wrong
+
Someone needs to take action
```

# 54. Percentile Latency

Average latency can hide slow requests.

Example:

```text
99 requests → 100ms
1 request   → 10 seconds
```

Useful percentiles include:

```text
P50 → median
P95 → 95% of requests are faster
P99 → 99% of requests are faster
```

For production APIs, P95 and P99 can be more useful than average latency alone.

# 56. Core Web Vitals

### LCP — Largest Contentful Paint

Measures loading performance of the main content.

### INP — Interaction to Next Paint

Measures responsiveness to user interactions.

### CLS — Cumulative Layout Shift

Measures unexpected layout movement.

These are user-experience metrics rather than server metrics.

# 63. Final Summary

Production observability should answer four questions:

```text
1. What happened?
   → Logs

2. What failed?
   → Error monitoring

3. Which request caused it?
   → Request ID / Trace ID

4. How well is the system performing?
   → Metrics and performance monitoring
```

The overall model:

```text
                 Next.js
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
      Logs        Errors      Metrics
        │           │           │
        └───────────┼───────────┘
                    ▼
              Observability
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
      Dashboard             Alerts
```

Key principles:

> **Log useful events, not everything.**

> **Use structured logs so machines can search and filter them.**

> **Use request IDs to connect logs belonging to the same request.**

> **Never expose sensitive information through logs or error responses.**

> **Monitor both errors and performance.**

> **Use error boundaries to protect the user experience and error monitoring to investigate failures.**

> **For distributed systems, combine request correlation with tracing when necessary.**

> **Good observability should answer not only "what failed?" but also "why did it fail?"**
