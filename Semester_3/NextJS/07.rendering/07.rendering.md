# 07. Rendering in Next.js

Rendering is the process of generating the UI that the browser displays.

In a web application, rendering can happen:

- In the **browser**
- On the **server**
- Ahead of time during the **build**
- Through a combination of these approaches

Next.js supports different rendering approaches so that each route can use the approach that best matches its data and user experience.

---

# 1. Rendering in Next.js

The main rendering concepts are:

```text
Rendering
│
├── Static Rendering
│   ├── SSG — Static Site Generation
│   └── ISR — Incremental Static Regeneration
│
├── Dynamic Rendering
│   └── Request-time rendering (SSR)
│
└── CSR — Client-Side Rendering
```

The important approaches are:

1. **CSR — Client-Side Rendering**
2. **SSR — Server-Side Rendering**
3. **SSG — Static Site Generation**
4. **ISR — Incremental Static Regeneration**

Next.js also uses the terms **Static Rendering** and **Dynamic Rendering**.

> **Important:** CSR, SSR, SSG, and ISR describe rendering approaches, while Static Rendering and Dynamic Rendering describe how Next.js generates a route. ISR is a **form of static rendering** with revalidation — not a separate top-level category.

In the App Router, the term **Dynamic Rendering** is commonly used for request-time server rendering.

---

# 2. Static Rendering

**Static Rendering** means that a route is rendered ahead of the user's request and the generated result can be reused for multiple users.

The content does not need to be generated from scratch for every request.

Conceptually:

```text
Build / Static Generation
        ↓
Generate HTML
        ↓
Store / Cache Result
        ↓
User Request
        ↓
Serve Existing Result
```

Static rendering is useful when the content does not depend on request-specific information.

Examples:

```text
/about
/pricing
/docs
/blog/my-first-post
```

Static rendering usually provides:

- Fast responses
- Good scalability
- Good SEO for public content
- Reduced request-time server work

---

# 3. Dynamic Rendering

**Dynamic Rendering** means that a route is rendered using request-specific information or data that must be determined at request time.

Conceptually:

```text
User Request
      ↓
Next.js Server
      ↓
Fetch / calculate request-specific data
      ↓
Generate response
      ↓
Browser
```

Dynamic rendering is useful when the output depends on information such as:

- Cookies
- Authentication
- Request-specific data
- User-specific information
- Frequently changing data that must be requested at runtime

Examples:

```text
/account
/orders
/profile
/personalized-dashboard
```

Dynamic rendering is closely related to SSR because both involve generating the response at request time.

---

# What Can Make a Route Dynamic?

Next.js can treat a route as dynamic when it uses request-specific APIs or explicitly opts into request-time rendering.

Common examples include:

```text
cookies()
headers()
searchParams
cache: "no-store"
connection()
```

You can also explicitly force dynamic rendering:

```tsx
export const dynamic = "force-dynamic";
```

For example:

```tsx
import { cookies } from "next/headers";

export default async function ProfilePage() {
	const cookieStore = await cookies();
	const session = cookieStore.get("session");

	return <h1>Welcome, {session?.value}</h1>;
}
```

Because the page reads request-specific cookie data, the output cannot be generated once and shared identically with every user.

> Detailed cache behavior and revalidation options are covered later in **Caching & Revalidation**.

---

# 4. CSR — Client-Side Rendering

**Client-Side Rendering (CSR)** means that important data fetching and UI work happens in the browser after JavaScript has loaded.

```text
Browser
   ↓
Load JavaScript
   ↓
React runs
   ↓
Fetch API
   ↓
Update UI
```

A simple React example:

```tsx
"use client";

import { useEffect, useState } from "react";

export default function Products() {
	const [products, setProducts] = useState([]);

	useEffect(() => {
		fetch("https://fakestoreapi.com/products")
			.then((res) => res.json())
			.then(setProducts);
	}, []);

	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

Here, the browser fetches the products after the JavaScript code runs.

---

# CSR in the App Router

In the App Router, components are Server Components by default.

Therefore, a component using browser-side React features such as:

```tsx
useState();
useEffect();
```

needs to be a Client Component:

```tsx
"use client";
```

However:

> **A Client Component is not automatically the same thing as a completely client-rendered page.**

Next.js can still pre-render Client Components and then hydrate them in the browser.

So:

```text
"use client"
      ≠
Entire page uses CSR
```

CSR usually refers to important rendering or data-fetching work happening in the browser after JavaScript loads.

---

# When to Use CSR

Reach for CSR when the primary value of the page or section lives in the browser after load.

Good fits include:

| Situation                        | Why CSR can work                                         |
| -------------------------------- | -------------------------------------------------------- |
| Highly interactive UI            | State updates and browser interactions happen frequently |
| Data depends on browser context  | Filters, sorting, selections, or client-side preferences |
| Real-time or user-driven updates | Chat, live dashboards, notifications                     |
| Complex browser interactions     | Drag-and-drop, interactive analytics                     |
| Content loaded after user action | Search-as-you-type, infinite scroll, tabbed panels       |

Typical examples:

```text
Chat application
Admin dashboard
Interactive analytics
Complex multi-step form
Client-side filtering / search
```

In the App Router, CSR often involves Client Components using `useEffect`, `fetch`, or a client-side data library.

Do not make an entire route client-rendered when only a small interactive section requires browser-side behavior.

---

# 5. SSR and Dynamic Rendering

**Server-Side Rendering (SSR)** is the general idea of generating HTML on the server for a request.

Conceptually:

```text
User Request
      ↓
Next.js Server
      ↓
Fetch request-specific data
      ↓
Generate HTML
      ↓
Browser
      ↓
Hydration for interactivity
```

SSR is useful when the content needs to be generated using information available at request time.

Examples:

```text
User profile
Personalized page
Authenticated dashboard
Order details
```

## SSR in the App Router

In the App Router, request-time server rendering is generally described as **Dynamic Rendering**.

For example:

```tsx
async function getProfile() {
	const response = await fetch("https://api.example.com/profile", {
		cache: "no-store",
	});

	return response.json();
}

export default async function ProfilePage() {
	const profile = await getProfile();

	return <h1>{profile.name}</h1>;
}
```

Here, `cache: "no-store"` requests fresh data at request time, resulting in dynamic rendering.

> For this course, focus on **Dynamic Rendering** in the App Router rather than Pages Router APIs such as `getServerSideProps`.

---

# When to Use Dynamic Rendering

Use Dynamic Rendering when the response must reflect the specific request.

Good fits:

| Situation                  | Why dynamic rendering fits                    |
| -------------------------- | --------------------------------------------- |
| Authentication-gated pages | Content depends on the user's session         |
| User-specific data         | Profile, orders, dashboard                    |
| Request-time decisions     | Redirects or role-based decisions             |
| Fresh data every visit     | Data must be requested at runtime             |
| Personalized public pages  | Different users may receive different content |

Typical examples:

```text
/account
/orders
/profile
/personalized-feed
/dashboard
```

---

# 6. SSG — Static Site Generation

**Static Site Generation (SSG)** means generating pages ahead of time so that the result can be served without generating the page for every request.

Conceptually:

```text
Build
  ↓
Fetch data
  ↓
Generate page
  ↓
Store / cache result
  ↓
Users receive the result
```

SSG is ideal when content can be generated ahead of time and does not need to change for every request.

Examples:

```text
/about
/pricing
/docs
/blog
```

In the App Router, this behavior is generally discussed as **Static Rendering**.

The important idea is:

```text
Generate once
     ↓
Reuse the result
```

---

# 7. Static Rendering for Dynamic Routes

A route can be dynamic in its URL structure while still being statically rendered.

For example:

```text
/products/[id]
```

can have many product pages:

```text
/products/1
/products/2
/products/3
```

If you know which product IDs should be generated ahead of time, use:

```tsx
generateStaticParams();
```

Example:

```tsx
export async function generateStaticParams() {
	const response = await fetch("https://fakestoreapi.com/products");

	const products = await response.json();

	return products.map((product: { id: number }) => ({
		id: product.id.toString(),
	}));
}
```

At build time, Next.js can generate pages for the returned parameters.

Conceptually:

```text
/products/[id]
       ↓
generateStaticParams()
       ↓
Known IDs
       ↓
Pre-render pages
```

For example:

```text
/products/1
/products/2
/products/3
```

> `generateStaticParams()` is used for dynamic routes that should have known paths generated ahead of time.

For your ecommerce application, remember that a large product dataset does not automatically mean every product must be pre-rendered. The rendering strategy should match the application's requirements.

---

# 8. ISR — Incremental Static Regeneration

**Incremental Static Regeneration (ISR)** extends static rendering by allowing generated content to be updated after a period of time without rebuilding the entire application.

Conceptually:

```text
Generate Static Page
        ↓
Serve Cached Page
        ↓
Revalidation Time Reached
        ↓
Regenerate Page
        ↓
Serve Updated Version
```

For example:

```text
revalidate = 60 seconds
```

The important idea is:

```text
Static Rendering
      +
Periodic Revalidation
      ↓
ISR
```

> ISR is a **form of static rendering** with controlled revalidation — not a separate rendering category from SSG.

---

# ISR in the App Router

In the App Router, a fetch request can specify a revalidation period:

```tsx
async function getProducts() {
	const response = await fetch("https://fakestoreapi.com/products", {
		next: {
			revalidate: 60,
		},
	});

	return response.json();
}

export default async function StorePage() {
	const products = await getProducts();

	return (
		<div>
			{products.map((product: { id: number; title: string }) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

The exact caching and revalidation behavior will be covered in detail in **Caching & Revalidation**.

For this topic, focus on the rendering idea:

```text
Static result
      ↓
Serve result
      ↓
Revalidate periodically
      ↓
Updated result
```

---

# When to Use ISR

Use ISR when content can be static most of the time but should refresh periodically without rebuilding the entire application.

Good fits:

| Situation                                    | Why ISR fits                                              |
| -------------------------------------------- | --------------------------------------------------------- |
| Periodically updated catalogs                | Small delays in freshness are acceptable                  |
| Content that changes occasionally            | Blog indexes, job boards, listings                        |
| Static performance with occasional freshness | Cached content can be reused between updates              |
| Many pages with infrequent changes           | Individual routes can be regenerated without a full build |
| Dynamic routes with known IDs                | Can combine static generation with revalidation           |

Typical examples:

```text
Product catalog
News website
Blog listing
Real-estate listings
Travel listings
```

---

# Time-Based vs On-Demand Revalidation

ISR can be refreshed in different ways.

### Time-Based Revalidation

Content is revalidated after a configured period.

```text
revalidate: 60
```

means the route can be revalidated based on that interval.

### On-Demand Revalidation

An application can also request revalidation when content changes.

For example:

```text
revalidatePath()
revalidateTag()
```

These APIs are part of the broader caching and revalidation system.

> Detailed implementation of on-demand revalidation belongs to **Caching & Revalidation**, not this topic.

# 9. Static Rendering vs Dynamic Rendering

| Static Rendering                   | Dynamic Rendering                    |
| ---------------------------------- | ------------------------------------ |
| Generated ahead of request         | Generated at request time            |
| Result can be reused               | Result depends on request            |
| Good for shared public content     | Good for request-specific content    |
| Usually fast for repeated requests | Server performs work for the request |
| Example: `/about`                  | Example: `/account`                  |
| Includes SSG and ISR               | Closely related to SSR               |

The key difference is:

```text
Static
→ Generate ahead of request

Dynamic
→ Generate for the request
```

---

# 10. CSR vs SSR vs SSG vs ISR

| Strategy      | Where main rendering/data work happens | When                   | Best for                          |
| ------------- | -------------------------------------- | ---------------------- | --------------------------------- |
| CSR           | Browser                                | After JavaScript loads | Highly interactive UI             |
| SSR / Dynamic | Server                                 | Every request          | Request-specific content          |
| SSG / Static  | Build/static generation                | Ahead of requests      | Mostly static content             |
| ISR           | Static generation + revalidation       | Periodically           | Content that changes occasionally |

A simple way to remember:

```text
CSR  → Browser renders / fetches
SSR  → Server renders for request
SSG  → Generate ahead of time
ISR  → Generate ahead of time + update periodically
```

For the App Router:

```text
SSR concept
    ↓
Dynamic Rendering

SSG concept
    ↓
Static Rendering

ISR
    ↓
Static Rendering + Revalidation
```

# 11. Choosing the Rendering Strategy

Ask these questions when deciding how a page should render.

## Question 1: Can the content be generated ahead of time?

```text
YES
 ↓
Static Rendering / SSG
```

Examples:

```text
/about
/pricing
/docs
```

---

## Question 2: Can it be generated ahead of time but needs periodic updates?

```text
YES
 ↓
ISR
```

Examples:

```text
/products
/news
/blog
```

---

## Question 3: Does it depend on request-specific information?

```text
YES
 ↓
Dynamic Rendering / SSR
```

Examples:

```text
/account
/orders
/profile
```

---

## Question 4: Is the page or section mainly a highly interactive browser application?

```text
YES
 ↓
CSR / client-side data fetching
```

Examples:

```text
/chat
/interactive-dashboard
/analytics
```

> These are decision guidelines, not strict rules. A single route can also combine Server Components, Client Components, static content, dynamic data, and interactive sections.

# 12. Real-World E-commerce Example

An e-commerce application can use multiple rendering approaches.

```text
/about
    ↓
Static Rendering

/products
    ↓
ISR

/products/123
    ↓
Static Rendering / ISR
(with generateStaticParams when appropriate)

 /account
    ↓
Dynamic Rendering

/cart
    ↓
Client-side interactivity
```

The important point is:

> **A Next.js application does not need to use one rendering strategy for the entire application.**

Different routes and sections can use different approaches based on their requirements.

For example, a product page could combine:

```text
Product Page
│
├── Product Information
│      ↓
│   Server-rendered
│
├── Product Images
│      ↓
│   Server-rendered
│
├── Variant Selector
│      ↓
│   Client interaction
│
└── Quantity Selector
       ↓
    Client interaction
```

Rendering strategy and Server/Client Components are related concepts, but they are **not the same thing**.

# 13. Rendering and SEO

Rendering strategy can affect how quickly important page content becomes available in the initial response.

Static and server-rendered pages can provide HTML content before client-side JavaScript finishes loading, which is useful for public, SEO-focused pages.

However:

> **Rendering strategy alone does not guarantee good SEO.**

Good SEO also depends on:

- Metadata
- Page content
- Semantic HTML
- Internal links
- Structured data when appropriate
- Site performance
- Accessibility

For public content-heavy pages, static rendering, ISR, or dynamic rendering can all be suitable depending on how frequently the content changes.

---

# 14. Rendering and Performance

Different strategies have different performance characteristics.

## CSR

```text
JavaScript
    ↓
Fetch data
    ↓
Render UI
```

The initial experience can depend heavily on JavaScript and client-side data fetching.

## SSR / Dynamic Rendering

```text
Request
    ↓
Server generates response
    ↓
Browser receives HTML
```

The server performs work for the request, but the browser can receive meaningful HTML in the response.

## SSG / Static Rendering

```text
Generate ahead of time
    ↓
Serve existing result
```

The generated result can be reused across requests.

## ISR

```text
Static result
    +
Periodic revalidation
```

ISR provides static delivery while allowing content to become updated over time.

# 15. Common Mistakes

## Mistake 1: Thinking Client Component = CSR

This is not always true.

```tsx
"use client";
```

means the component is a **Client Component**.

It does not automatically mean the entire page is rendered only in the browser.

Next.js can pre-render Client Components and then hydrate them.

```text
"use client"
      ≠
Entire page = CSR
```

---

## Mistake 2: Using CSR for Everything

Not every page needs:

```tsx
"use client";
useEffect();
fetch();
```

For data that can be fetched on the server, a Server Component can often be simpler:

```tsx
export default async function ProductsPage() {
	const response = await fetch("https://api.example.com/products");

	const products = await response.json();

	return <div>...</div>;
}
```

Use Client Components when browser-side interactivity or client-only APIs are actually required.

---

## Mistake 3: Using Dynamic Rendering for Everything

Dynamic Rendering is useful for request-specific content, but not every page needs request-time rendering.

If content can be generated and reused, Static Rendering may be a better choice.

---

## Mistake 4: Using Static Rendering for Frequently Changing Data

If data changes constantly, generating a static result may not provide the required freshness.

Consider ISR or Dynamic Rendering depending on the freshness requirements.

---

## Mistake 5: Thinking ISR Means Real-Time Data

ISR does not mean every request receives the newest data immediately.

It uses static/cached results and revalidation.

If data must always be generated from the current request, Dynamic Rendering may be more appropriate.

---

## Mistake 6: Not Knowing Why a Page Became Dynamic

If a page unexpectedly renders at request time, check whether it uses request-specific APIs such as:

```text
cookies()
headers()
searchParams
```

or explicitly requests request-time behavior.

Detailed caching behavior will be covered in **Caching & Revalidation**.

---

# Summary

- **Rendering** determines when and where page content is generated.
- **Static Rendering** includes **SSG** and **ISR**.
- **Dynamic Rendering** generates content at request time and is closely related to SSR.
- **CSR** performs important rendering/data-fetching work in the browser.
- A **Client Component is not automatically the same thing as CSR**.
- Request-specific APIs such as `cookies()` and `headers()` can make a route dynamic.
- Use **`generateStaticParams`** to pre-render known dynamic routes such as `/products/[id]`.
- **ISR** combines static rendering with revalidation.
- A single Next.js application can use multiple rendering approaches.
- Rendering strategy and Server/Client Components are related but different concepts.
- Rendering strategy can affect initial content delivery and SEO, but it does not guarantee good SEO.
- Detailed caching and revalidation behavior belongs to the **Caching & Revalidation** topic.

---

# Quick Decision Guide

```text
Can generate ahead of time?
        │
        ├── Yes → Does it need periodic updates?
        │             │
        │             ├── No → Static Rendering / SSG
        │             │
        │             └── Yes → ISR
        │
        └── No → Does it depend on request/user data?
                      │
                      ├── Yes → Dynamic Rendering / SSR
                      │
                      └── No → Is the main work browser-driven?
                                   │
                                   ├── Yes → CSR / Client-side data fetching
                                   │
                                   └── No → Re-evaluate the route requirements
```

> **Simple rule:** Prefer Static Rendering when content can be reused, ISR when it needs periodic updates, Dynamic Rendering when it depends on the request, and client-side rendering/data fetching when the browser needs to control the interaction or data flow.
