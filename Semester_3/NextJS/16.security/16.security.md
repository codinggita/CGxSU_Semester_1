# 16. Security

Production security practices in Next.js — env secrets, validation, injection, XSS/CSRF, cookies, CORS, rate limiting, headers, and file uploads. Express security concepts apply, but **where code runs in Next.js** (Server Components, Client Components, Route Handlers, Server Actions) determines what changes.

---

## 1. Security in Next.js

Next.js combines frontend, backend, Server Components, Route Handlers, and Server Actions in one codebase. Security depends on knowing **which layer executes your code**:

```text
Browser (untrusted)
      ↓
Route Handler / Server Action / Server Component (trusted boundary)
      ↓
Validation → Authorization → Business logic → Database
```

Never trust client-side validation, role checks, hidden buttons, or state. The server must enforce security for every entry point — including Server Actions, which clients can invoke directly.

```tsx
// UX only — not security
{
	user.role === "ADMIN" && <DeleteButton />;
}
```

```ts
// Required on the server
await requireApiAdmin();
await deleteUser(userId);
```

## 2. Environment Variables and Secrets

Store secrets in environment variables, never in source code:

```env
DATABASE_URL="postgresql://..."
AUTH_SECRET="..."
STRIPE_SECRET_KEY="..."
```

```ts
const secret = process.env.AUTH_SECRET;
```

**Local dev:** use `.env.local` and gitignore `.env*`.

**Next.js-specific rule:** only variables prefixed with `NEXT_PUBLIC_` are exposed to browser code.

```env
# Safe — public config
NEXT_PUBLIC_API_URL="https://api.example.com"

# Never do this — secrets become client-accessible
NEXT_PUBLIC_AUTH_SECRET="..."
NEXT_PUBLIC_STRIPE_SECRET_KEY="..."
```

Keep `DATABASE_URL`, `AUTH_SECRET`, and payment keys server-only. Env vars are not encryption — protect them via deployment access control and secret managers.

**Never log secrets** — avoid logging `process.env.AUTH_SECRET`, raw `Authorization` headers, or cookies.

**Never pass secrets to Client Components:**

```tsx
// Bad — props reach browser-side code
<PaymentForm secretKey={process.env.STRIPE_SECRET_KEY} />
```

Call third-party APIs from a Server Action or Route Handler instead.

## 3. Input Validation

All request input is untrusted — forms, bodies, query params, route params, headers, cookies, and Server Action arguments. Clients can bypass your UI entirely.

Validate on the server with a schema library (e.g. Zod):

```ts
import { z } from "zod";

const userSchema = z.object({
	name: z.string().min(2),
	email: z.email(),
	age: z.number().int().min(18),
});

export async function POST(request: Request) {
	const body = await request.json();
	const result = userSchema.safeParse(body);

	if (!result.success) {
		return Response.json({ error: "Invalid input" }, { status: 400 });
	}

	// use result.data — not raw body
}
```

Validate route and query parameters too — **route params first, then query params** (page, limit):

### 3.1 Route parameter — App Router

```text
GET /api/orders/123
app/api/orders/[id]/route.ts
```

```ts
export async function GET(
	request: Request,
	context: { params: Promise<{ id: string }> },
) {
	const { id } = await context.params;
	const orderId = Number(id);

	if (!Number.isInteger(orderId) || orderId <= 0) {
		return Response.json({ error: "Invalid order ID" }, { status: 400 });
	}

	const order = await orderService.getById(orderId);
	return Response.json(order);
}
```

### 3.2 Route parameter — Pages Router

```text
GET /api/orders/123
pages/api/orders/[id].ts
```

```ts
import type { NextApiRequest, NextApiResponse } from "next";

export default async function handler(
	req: NextApiRequest,
	res: NextApiResponse,
) {
	const orderId = Number(req.query.id);

	if (!Number.isInteger(orderId) || orderId <= 0) {
		return res.status(400).json({ error: "Invalid order ID" });
	}

	const order = await orderService.getById(orderId);
	return res.status(200).json(order);
}
```

### 3.3 Page and limit — App Router

Validate pagination on **Route Handlers** and **pages** that read `searchParams`.

**Route Handler** — `app/api/orders/route.ts`:

```text
GET /api/orders?page=1&limit=20
```

```ts
export async function GET(request: Request) {
	const { searchParams } = new URL(request.url);
	const page = Number(searchParams.get("page") ?? "1");
	const limit = Number(searchParams.get("limit") ?? "20");

	if (!Number.isInteger(page) || page < 1) {
		return Response.json({ error: "Invalid page" }, { status: 400 });
	}

	if (!Number.isInteger(limit) || limit < 1 || limit > 100) {
		return Response.json({ error: "Invalid limit" }, { status: 400 });
	}

	const orders = await orderService.list({ page, limit });
	return Response.json(orders);
}
```

**Page** — `app/orders/page.tsx`:

```tsx
export default async function OrdersPage({
  searchParams,
}: {
  searchParams: Promise<{ page?: string; limit?: string }>;
}) {
  const params = await searchParams;
  const page = Number(params.page ?? "1");
  const limit = Number(params.limit ?? "20");

  if (!Number.isInteger(page) || page < 1) {
    throw new Error("Invalid page");
  }

  if (!Number.isInteger(limit) || limit < 1 || limit > 100) {
    throw new Error("Invalid limit");
  }

  const orders = await orderService.list({ page, limit });
  return (/* render orders */);
}
```

### 3.4 Page and limit — Pages Router

**API route** — `pages/api/orders.ts`:

```ts

	req: NextApiRequest,
	res: NextApiResponse,

	const page = Number(req.query.page ?? "1");
	const limit = Number(req.query.limit ?? "20");

		return res.status(400).json({ error: "Invalid page" });
	}

	if (!Number.isInteger(limit) || limit < 1 || limit > 100) {
		return res.status(400).json({ error: "Invalid limit" });
	}

	const orders = await orderService.list({ page, limit });
	return res.status(200).json(orders);
}
```

**Page** — `pages/orders.tsx`:

```tsx
export async function getServerSideProps(context) {
	const page = Number(context.query.page ?? "1");
	const limit = Number(context.query.limit ?? "20");

	if (!Number.isInteger(page) || page < 1) {
		return { notFound: true };
	}

	if (!Number.isInteger(limit) || limit < 1 || limit > 100) {
		return { notFound: true };
	}

	const orders = await orderService.list({ page, limit });
	return { props: { orders, page, limit } };
}
```

Preferred order: authenticate → authorize → validate route params → validate query params → business logic → database.

## 4. SQL Injection

Use parameterized queries or ORM APIs — never concatenate user input into SQL strings.

**Prisma (safe by default):**

```ts
const user = await prisma.user.findUnique({ where: { email } });
```

**Raw SQL — use parameterized form:**

```ts
// Bad
await prisma.$queryRawUnsafe(`SELECT * FROM users WHERE email = '${email}'`);

// Good
await prisma.$queryRaw`SELECT * FROM users WHERE email = ${email}`;
```

Same principle as MongoDB: do not pass arbitrary request objects into queries.

```ts
// Bad
User.find(req.body);

// Good
User.find({ email: validatedEmail });
```

## 5. XSS

React escapes text in `{comment}` by default. XSS risk increases when rendering untrusted HTML:

```tsx
// Dangerous with user-generated content
<div dangerouslySetInnerHTML={{ __html: content }} />
```

If HTML is required, sanitize with a maintained library — do not roll your own regex sanitizer.

Watch for untrusted content in: user profiles, markdown rendered as HTML, CMS content, third-party embeds, and dynamic URLs.

Server Components do not automatically make HTML safe — the same rules apply.

## 6. CSRF

CSRF tricks a logged-in browser into sending authenticated requests. Relevant when auth uses cookies and requests change server state (`POST`, `PUT`, `PATCH`, `DELETE`).

Defenses:

- **`SameSite` cookies** — common setting for session cookies:

```ts
cookieStore.set("session", sessionId, {
	httpOnly: true,
	secure: process.env.NODE_ENV === "production",
	sameSite: "lax",
	path: "/",
	maxAge: 60 * 60,
});
```

- **CSRF tokens** for state-changing cookie-authenticated endpoints when your architecture requires it.

`GET` requests should not mutate data. `SameSite` alone is not a universal fix — choose cookie policy based on your auth flow.

---

## 7. Secure Cookies

| Option               | Purpose                                                      |
| -------------------- | ------------------------------------------------------------ |
| `httpOnly`           | JS cannot read the cookie (helps limit XSS cookie theft)     |
| `secure`             | Sent only over HTTPS — use in production                     |
| `sameSite`           | Controls cross-site cookie sending (`strict`, `lax`, `none`) |
| `maxAge` / `expires` | Session lifetime                                             |

`sameSite: "none"` requires `secure: true` — only when cross-site cookies are genuinely needed.

## 8. CORS

CORS is a **browser** mechanism — it does not stop `curl`, Postman, or server-to-server calls. CORS ≠ authentication ≠ authorization.

**Next.js monolith (same origin):** frontend and `/api/*` on the same domain — CORS usually not needed.

**Separate frontend + API:**

```text
https://app.example.com  →  https://api.example.com
```

Configure explicit allowed origins. Avoid `Access-Control-Allow-Origin: *` on private or credentialed APIs. With cookies across origins, you need `Access-Control-Allow-Credentials: true` and a specific origin — not a wildcard.

### 8.1 App Router

Global headers in `next.config.ts` (applies to Route Handlers and pages):

```ts
const nextConfig = {
	async headers() {
		return [
			{
				source: "/api/:path*",
				headers: [
					{
						key: "Access-Control-Allow-Origin",
						value: "https://app.example.com",
					},
					{
						key: "Access-Control-Allow-Credentials",
						value: "true",
					},
					{
						key: "Access-Control-Allow-Methods",
						value: "GET, POST, PUT, PATCH, DELETE, OPTIONS",
					},
				],
			},
		];
	},
};

export default nextConfig;
```

Per-route in a Route Handler — `app/api/products/route.ts`:

```ts
const corsHeaders = {
	"Access-Control-Allow-Origin": "https://app.example.com",
	"Access-Control-Allow-Credentials": "true",
};

export async function OPTIONS() {
	return new Response(null, { status: 204, headers: corsHeaders });
}

export async function GET() {
	const products = await productService.list();
	return Response.json(products, { headers: corsHeaders });
}
```

### 8.2 Pages Router

Global headers use the same `next.config.ts` pattern as the **App Router** CORS example.

Per-route in an API file — `pages/api/products.ts`:

```ts
import type { NextApiRequest, NextApiResponse } from "next";

const ALLOWED_ORIGIN = "https://app.example.com";

export default async function handler(
	req: NextApiRequest,
	res: NextApiResponse,
) {
	res.setHeader("Access-Control-Allow-Origin", ALLOWED_ORIGIN);
	res.setHeader("Access-Control-Allow-Credentials", "true");

	if (req.method === "OPTIONS") {
		res.setHeader(
			"Access-Control-Allow-Methods",
			"GET, POST, PUT, PATCH, DELETE, OPTIONS",
		);
		return res.status(204).end();
	}

	if (req.method !== "GET") {
		return res.status(405).json({ error: "Method not allowed" });
	}

	const products = await productService.list();
	return res.status(200).json(products);
}
```

## 9. Rate Limiting

Protect authentication and abuse-prone endpoints: login, registration, password reset, OTP, search, uploads.

```text
10 login attempts / minute → 429 Too Many Requests
```

In-memory counters work for single-server dev. Production with multiple instances needs a shared store (e.g. Redis). Combine signals (IP + account identifier) rather than relying on IP alone.

Shared helper — `lib/rate-limit.ts`:

```ts
type RateLimitEntry = {
	count: number;
	resetAt: number;
};

const store = new Map<string, RateLimitEntry>();

export function rateLimit(options: {
	key: string;
	limit: number;
	windowMs: number;
}) {
	const now = Date.now();
	const entry = store.get(options.key);

	if (!entry || now > entry.resetAt) {
		const resetAt = now + options.windowMs;
		store.set(options.key, { count: 1, resetAt });
		return { success: true, remaining: options.limit - 1, resetAt };
	}

	if (entry.count >= options.limit) {
		return { success: false, remaining: 0, resetAt: entry.resetAt };
	}

	entry.count += 1;
	return {
		success: true,
		remaining: options.limit - entry.count,
		resetAt: entry.resetAt,
	};
}

export function getClientKeyFromRequest(request: Request) {
	const forwarded = request.headers.get("x-forwarded-for");
	return forwarded?.split(",")[0]?.trim() ?? "unknown";
}

export function getClientKeyFromApiRequest(req: {
	headers: Record<string, string | string[] | undefined>;
	socket: { remoteAddress?: string | null };
}) {
	const forwarded = req.headers["x-forwarded-for"];
	const ip = Array.isArray(forwarded) ? forwarded[0] : forwarded;
	return ip?.split(",")[0]?.trim() ?? req.socket.remoteAddress ?? "unknown";
}
```

### 9.1 App Router

`app/api/auth/login/route.ts`:

```text
POST /api/auth/login
```

```ts
import { rateLimit, getClientKeyFromRequest } from "@/lib/rate-limit";

export async function POST(request: Request) {
	const clientKey = getClientKeyFromRequest(request);
	const result = rateLimit({
		key: `login:${clientKey}`,
		limit: 10,
		windowMs: 60_000,
	});

	if (!result.success) {
		const retryAfter = Math.ceil((result.resetAt - Date.now()) / 1000);

		return Response.json(
			{ error: "Too many login attempts. Try again later." },
			{
				status: 429,
				headers: {
					"Retry-After": String(retryAfter),
					"X-RateLimit-Remaining": "0",
				},
			},
		);
	}

	const body = await request.json();
	// validate input, verify credentials, create session...
	return Response.json({ success: true });
}
```

For production across multiple server instances, replace the in-memory `Map` with a Redis-backed limiter (e.g. Upstash) using the same `429` response pattern.

### 9.2 Pages Router

`pages/api/auth/login.ts`:

```ts
import type { NextApiRequest, NextApiResponse } from "next";

import { rateLimit, getClientKeyFromApiRequest } from "@/lib/rate-limit";

export default async function handler(
	req: NextApiRequest,
	res: NextApiResponse,
) {
	if (req.method !== "POST") {
		return res.status(405).json({ error: "Method not allowed" });
	}

	const clientKey = getClientKeyFromApiRequest(req);
	const result = rateLimit({
		key: `login:${clientKey}`,
		limit: 10,
		windowMs: 60_000,
	});

	if (!result.success) {
		const retryAfter = Math.ceil((result.resetAt - Date.now()) / 1000);

		res.setHeader("Retry-After", String(retryAfter));
		res.setHeader("X-RateLimit-Remaining", "0");
		return res.status(429).json({
			error: "Too many login attempts. Try again later.",
		});
	}

	const { email, password } = req.body;
	// validate input, verify credentials, create session...
	return res.status(200).json({ success: true });
}
```

Apply the same pattern to registration, password reset, and OTP endpoints. Tighten limits on auth routes; use looser limits on read-heavy public APIs.

## 10. HTTP Security Headers

Set response headers in `next.config.ts`:

```ts
const nextConfig = {
	async headers() {
		return [
			{
				source: "/(.*)",
				headers: [
					{ key: "X-Content-Type-Options", value: "nosniff" },
					{
						key: "Referrer-Policy",
						value: "strict-origin-when-cross-origin",
					},
					{
						key: "Strict-Transport-Security",
						value: "max-age=31536000; includeSubDomains",
					},
				],
			},
		];
	},
};

export default nextConfig;
```

Useful headers:

- **Content-Security-Policy** — restricts script/style/load sources; test thoroughly with your app's scripts and third parties.
- **Strict-Transport-Security** — force HTTPS (only when HTTPS is correctly configured).
- **X-Content-Type-Options: nosniff**
- **Referrer-Policy**
- **Permissions-Policy** — disable unused browser features (camera, microphone, geolocation).

Do not copy a random CSP without testing — Next.js apps often need specific script allowances.

## 11. File Upload Security

Treat uploads as hostile input. A `.jpg` filename does not guarantee a safe image.

Checklist:

- Authenticate and authorize the uploader
- Enforce max file size
- Validate MIME type **and** file content/signature (magic bytes)
- Generate server-side filenames (`crypto.randomUUID()`) — never use untrusted names in paths
- Prevent path traversal — no `../../` via filename
- Store in object storage (S3, R2, etc.) or an isolated directory — never where the web server executes files
- Rate limit and apply per-user quotas
- Scan for malware where appropriate

```ts
const filename = crypto.randomUUID();
// store metadata: fileId, userId, storageKey, mimeType, size
```


### 12.3 Server Components

Server Components can access server-only resources, but:

- Do not pass secrets or sensitive data to Client Components unnecessarily
- Do not construct unsafe database queries from URL/search params without validation

## 13. Secure API Example

```ts
export async function GET(
	request: Request,
	context: { params: Promise<{ id: string }> },
) {
	const user = await requireApiUser();

	const { id } = await context.params;
	const orderId = Number(id);

	if (!Number.isInteger(orderId)) {
		return Response.json({ error: "Invalid order ID" }, { status: 400 });
	}

	const order = await orderService.getById(orderId);

	if (!order) {
		return Response.json({ error: "Order not found" }, { status: 404 });
	}

	if (order.userId !== user.id && user.role !== "ADMIN") {
		return Response.json({ error: "Forbidden" }, { status: 403 });
	}

	return Response.json(order);
}
```

## 14. Security Checklists

**API / Route Handler / Server Action:**

- Authentication and authorization
- Input validation (body, params, query)
- Resource ownership where applicable
- Parameterized queries / safe ORM usage
- Rate limiting on sensitive endpoints
- Safe error responses (no stack traces or secrets in production)
- No sensitive logging

**Authentication endpoints (`/api/auth/login`):**

- Validate input, hash passwords securely
- Generic error messages (do not reveal whether email exists)
- Rate limiting
- Secure session generation, `httpOnly` + `secure` cookies, appropriate `SameSite`
- Session expiration and logout/invalidation

**File upload endpoints:**

- Auth, size/type/content validation, safe filenames, isolated storage, rate limits

## 15. Common Mistakes (MERN → Next.js)

- **Assuming server code is automatically secure** — Server Components and `"use server"` still need validation and authorization.
- **Treating Server Actions as trusted** — clients can call them directly.
- **Exposing secrets via `NEXT_PUBLIC_`** or Client Component props.
- **Trusting frontend validation only** — always validate on the server.
- **SQL string concatenation** — use Prisma or parameterized queries.
- **`dangerouslySetInnerHTML` without sanitization.**
- **`Access-Control-Allow-Origin: *`** on private or credentialed APIs.
- **No rate limiting on login/OTP/password reset.**
- **Trusting uploaded filenames** — validate content, generate safe names.
- **Middleware as the only security gate** — enforce checks where operations run.

## 16. Recommended Architecture

```text
                         Browser (untrusted)
                                │
                                ▼
                    Middleware (optional early checks)
                                │
                                ▼
              Route Handler / Server Action / Server Component
                                │
                    ┌───────────┼───────────┐
                    ▼           ▼           ▼
            Authentication  Validation  Authorization
                    └───────────┼───────────┘
                                ▼
                         Business Logic
                                ▼
                          Repository
                                ▼
                           Database
```

Security is layered — no single mechanism is enough. HTTPS, secure cookies, auth, authorization, validation, parameterized queries, XSS/CSRF defenses, rate limiting, headers, and safe file handling each address different attack classes.

> **Never trust browser-supplied data.**
>
> **Client validation is UX; server validation is security.**
>
> **Treat Server Actions and Route Handlers as public server entry points.**
>
> **Keep server-only secrets out of Client Components and `NEXT_PUBLIC_` variables.**
