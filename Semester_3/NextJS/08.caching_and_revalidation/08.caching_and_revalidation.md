# 08. Caching & Revalidation

Caching is an important concept in Next.js because it allows applications to reuse previously fetched data or rendered results instead of doing the same work repeatedly.

Caching can improve:

- Performance
- Response time
- API efficiency
- Server efficiency
- Database efficiency

Caching and revalidation are closely related:

```text
Caching
   ↓
Reuse existing result
   ↓
Faster response

Revalidation
   ↓
Determine when cached data should be considered stale
   ↓
Allow fresh data to be generated or fetched
```

> Caching behavior can depend on the Next.js version, APIs being used, and the application's caching configuration. Do not assume that every `fetch()` is automatically cached.

---

# 1. What Is Caching?

Caching means storing a result so that it can be reused later.

Suppose an application requests:

```text
/products
```

Without caching:

```text
Request 1 → API
Request 2 → API
Request 3 → API
Request 4 → API
```

With caching:

```text
Request 1 → API → Cache

Request 2 → Cache
Request 3 → Cache
Request 4 → Cache
```

This can reduce:

- API requests
- Database queries
- Server work
- Response time

However, cached data can become outdated.

That is why caching is often combined with **revalidation**.

---

# 2. Caching Layers in Next.js

For the App Router, it is useful to understand four different concepts:

```text
Next.js Application
│
├── Data Cache
├── Full Route Cache
├── Client Router Cache
└── Request Memoization
```

They solve different problems.

| Concept             | What it stores / does                        | Where   |
| ------------------- | -------------------------------------------- | ------- |
| Data Cache          | Stores fetched data                          | Server  |
| Full Route Cache    | Stores rendered route output                 | Server  |
| Client Router Cache | Stores route segments used during navigation | Browser |
| Request Memoization | Avoids duplicate requests during a render    | Server  |

The first three are caching layers. Request Memoization is a request-level optimization that avoids duplicate work during a render.

---

# 3. Data Cache

The **Data Cache** stores the result of data fetching so that the same data does not always have to be fetched again.

Conceptually:

```text
Server
   ↓
Fetch API / Data
   ↓
Data Cache
   ↓
Reuse cached result
```

For example:

```tsx
async function getProducts() {
	const response = await fetch("https://example.com/api/products");

	return response.json();
}
```

Depending on the caching configuration, the fetched result can be reused.

The important idea is:

```text
Data Cache
    ↓
Cached fetched data
```

It is about the **data**, not the complete rendered page.

---

# 4. Full Route Cache

The **Full Route Cache** stores the rendered result of a route on the server.

It is different from the Data Cache.

### Data Cache

Stores:

```text
Fetched data
```

### Full Route Cache

Stores:

```text
Rendered route output
```

Conceptually:

```text
Data
 ↓
Server Component rendering
 ↓
Rendered route
 ↓
Full Route Cache
```

For statically rendered routes, Next.js can reuse the rendered result instead of rendering the complete route again for every request.

---

# 5. Data Cache vs Full Route Cache

On one route, **both** caches can be involved. They store different things.

```text
Request for /products
        ↓
getProducts()  ──►  Data Cache  (cached JSON from fetch)
        ↓
Server Component renders JSX
        ↓
Full Route Cache  (cached HTML/RSC payload for /products)
        ↓
Response to the browser
```

| Layer                | What is stored                          | Question it answers              |
| -------------------- | --------------------------------------- | -------------------------------- |
| **Data Cache**       | Result of a cached `fetch` (or similar) | What data did we fetch?          |
| **Full Route Cache** | Rendered output for a route             | What did we render for this URL? |

Invalidating or updating one layer does **not** always update the other in the same way. That is why the distinction matters when debugging stale pages.

### Example — Data Cache (`fetch` result)

The **Data Cache** applies to the **data** returned from `fetch`, not the whole page.

```tsx
async function getProducts() {
	const response = await fetch(
		"https://jsonplaceholder.typicode.com/posts?_limit=3",
		{
			next: {
				revalidate: 60,
			},
		},
	);

	return response.json();
}
```

Conceptually:

```text
First call to getProducts()
        ↓
Network request
        ↓
JSON stored in Data Cache

Later call (within revalidate window)
        ↓
Reuse cached JSON
        ↓
No new network request for the same fetch
```

If two Server Components in the **same render** call `getProducts()` with the same URL and options, **Request Memoization** can also dedupe the call during that render. The **Data Cache** still refers to persisted fetch results across requests and renders.

### Example — Full Route Cache (rendered `/products` page)

The **Full Route Cache** applies when Next.js can **reuse the rendered route** (common for static routes and ISR).

```tsx
async function getProducts() {
	const response = await fetch(
		"https://jsonplaceholder.typicode.com/posts?_limit=3",
		{
			next: {
				revalidate: 60,
			},
		},
	);

	return response.json();
}

export default async function ProductsPage() {
	const products = await getProducts();
	const renderedAt = Date.now();

	return (
		<div>
			<h1>Products</h1>
			<p>Rendered at: {new Date(renderedAt).toLocaleString()}</p>
			<ul>
				{products.map((post: { id: number; title: string }) => (
					<li key={post.id}>{post.title}</li>
				))}
			</ul>
		</div>
	);
}
```

For a **statically rendered** or **ISR** route, Next.js can store the **output of this page** in the Full Route Cache:

```text
Build or first request
        ↓
getProducts()  →  Data Cache gets JSON
        ↓
ProductsPage renders list + "Rendered at"
        ↓
Full Route Cache stores rendered /products output

Later request (cache still valid)
        ↓
Can serve cached route output without rendering the page again
```

### Same page, two layers

Walk through one `/products` visit:

```text
1. Data Cache
   "Do we already have this fetch result?"

2. Render (if needed)
   Server Component turns data into JSX/HTML

3. Full Route Cache
   "Do we already have this route's rendered output?"
```

Simple mental model:

```text
Data Cache
→ Cached API / fetch data

Full Route Cache
→ Cached rendered page for a route
```

Example of why both matter:

```text
revalidateTag("products")
        ↓
Can invalidate cached fetch data in the Data Cache

revalidatePath("/products")
        ↓
Can invalidate the cached rendered output for that route
```

You will use those APIs in later sections. For now, remember: **data** and **rendered route** are separate cache targets.

---

# 6. Client Router Cache

The **Client Router Cache** is a client-side cache used by the Next.js App Router.

It stores previously received or prefetched route segments in the browser during navigation.

Conceptually:

```text
Browser
   ↓
Next.js Router Cache
   ↓
Previously received route segments
```

This helps make client-side navigation faster.

For example:

```text
/home
   ↓
/products
   ↓
/profile
   ↓
/products
```

When navigating back to `/products`, Next.js can reuse cached route information when appropriate.

The important distinction is:

```text
Router Cache
   ↓
Client-side route segments

Data Cache
   ↓
Server-side fetched data
```

They are different caches and should not be confused.

---

# 7. Request Memoization

Request Memoization prevents duplicate requests during the same server render when identical requests can be memoized.

Suppose two components request the same product:

```tsx
async function getProduct(id: string) {
	const response = await fetch(`https://example.com/api/products/${id}`);

	return response.json();
}
```

Component A:

```tsx
const product = await getProduct("10");
```

Component B:

```tsx
const product = await getProduct("10");
```

Conceptually:

```text
Component A
     ↓
Same request
     ↓
Request Memoization
     ↓
Reuse result
     ↑
Same request
     ↑
Component B
```

The important point:

> Request Memoization is about avoiding duplicate work during a render. It is not the same as persistent data caching.

### Request Memoization vs Data Cache

| Request Memoization                   | Data Cache                                    |
| ------------------------------------- | --------------------------------------------- |
| Avoids duplicate work during a render | Stores reusable fetched data                  |
| Request/render-level optimization     | Caching layer                                 |
| Short-lived                           | Can be reused across requests when configured |
| Prevents duplicate requests           | Can prevent fetching data again               |

---

# 8. Cache Behavior

Caching behavior depends on:

- What is being cached
- Cache configuration
- Whether the route is static or dynamic
- Revalidation settings
- Next.js version
- APIs used by the route

Therefore, avoid these oversimplified assumptions:

```text
fetch() = always cached
```

Do not assume the opposite either:

```text
fetch() = never cached
```

Instead, ask:

```text
What is being cached?
        ↓
How long should it stay fresh?
        ↓
What should make it stale?
```

---

# 9. Fetch Cache Options

The `cache` and `next` options on `fetch()` can control how fetched data is handled.

### `force-cache`

```tsx
fetch("https://example.com/api/products", {
	cache: "force-cache",
});
```

This requests that the fetched result be cached and reused when the cache is applicable.

---

### `next.revalidate`

```tsx
fetch("https://example.com/api/products", {
	next: {
		revalidate: 60,
	},
});
```

This expresses that the cached data should be revalidated periodically.

Here:

```text
60 = 60 seconds
```

---

### `no-store`

```tsx
fetch("https://example.com/api/products", {
	cache: "no-store",
});
```

This requests that the fetch result not be stored in the Data Cache and that fresh data be fetched for the request.

---

### Basic comparison

| Option                    | Purpose                                         |
| ------------------------- | ----------------------------------------------- |
| `force-cache`             | Reuse cached data when applicable               |
| `next: { revalidate: N }` | Cache data with periodic revalidation           |
| `no-store`                | Do not store the fetch result in the Data Cache |

> Exact rendering and caching behavior can also depend on the surrounding route and other APIs used by that route.

---

# 10. Caching and Rendering

Caching and rendering are closely connected.

From the previous topic:

```text
Static Rendering
Dynamic Rendering
ISR
CSR
```

Caching decisions can influence whether data can be reused and whether a route can be statically rendered.

Conceptually:

```text
Cached / revalidated data
        ↓
Can support static rendering / ISR

Fresh data on every request
        ↓
Can require dynamic rendering
```

For example, this fetch can support periodically refreshed product data:

```tsx
fetch("https://example.com/api/products", {
	next: {
		revalidate: 60,
	},
});
```

Whereas this pattern is appropriate when fresh request-specific data is required:

```tsx
fetch("https://example.com/api/account", {
	cache: "no-store",
});
```

# 11. Revalidation

Cached data should not necessarily remain unchanged forever.

Suppose a product catalog changes periodically.

```text
Product catalog
      ↓
Cached
      ↓
Data changes
      ↓
Cached result becomes stale
      ↓
Fresh data is generated/fetched
```

**Revalidation** is the process of allowing cached content or data to become stale and be refreshed according to a defined strategy.

There are two important approaches:

```text
Time-Based Revalidation
        +
On-Demand Revalidation
```

---

# 12. Time-Based Revalidation

Time-based revalidation means configuring a period after which cached data becomes eligible for revalidation.

For example:

```text
Cache lifetime = 60 seconds
```

Conceptually:

```text
0 sec
 ↓
Cached data is reused

60 sec
 ↓
Data becomes eligible for revalidation
```

This is useful when data changes periodically but does not need to be refreshed for every request.

Examples:

- Product catalog
- Blog posts
- News
- Public statistics
- Categories

---

# 13. `revalidate`

A fetch can specify a revalidation period:

```tsx
const response = await fetch("https://example.com/api/products", {
	next: {
		revalidate: 60,
	},
});

const products = await response.json();
```

Conceptually:

```text
Fetch data
    ↓
Cache data
    ↓
Revalidate according to configured interval
```

The value `60` in `revalidate: 60` represents **60 seconds**.

Choose the interval based on how frequently the data changes and how fresh the application needs the data to be.

---

# 14. Route-Level `revalidate`

A route can also define a revalidation interval:

```tsx
export const revalidate = 60;
```

This expresses a freshness requirement for the route.

For example:

```text
Blog page
   ↓
Revalidate periodically
```

Route-level and fetch-level revalidation should be chosen based on the application's data requirements.

---

# 15. Choosing a Revalidation Time

Do not choose a revalidation value randomly.

Think about:

```text
How frequently does the data change?
        ↓
How fresh must the data be?
        ↓
How much repeated work is acceptable?
```

For example:

| Data                     | Possible Strategy                     |
| ------------------------ | ------------------------------------- |
| Company information      | Long revalidation                     |
| Blog posts               | Periodic revalidation                 |
| Product catalog          | Periodic revalidation                 |
| News                     | Shorter revalidation                  |
| Frequently changing data | Short revalidation                    |
| Real-time data           | Usually requires a different approach |

The general trade-off is:

```text
Longer cache
    ↓
Better reuse / less work
    ↓
Potentially older data
```

Compare with:

```text
Shorter cache
    ↓
Fresher data
    ↓
More frequent work
```

---

# 16. On-Demand Revalidation

Sometimes waiting for a timer is not ideal.

Consider an ecommerce application:

```text
Admin changes product price
₹999 → ₹799
```

If the product uses time-based revalidation:

```text
Wait for configured interval
        ↓
Fresh data
```

Instead, the application can invalidate the relevant cached content when the product changes.

This is called **on-demand revalidation**.

Conceptually:

```text
Update data
    ↓
Invalidate affected cache
    ↓
Cached result becomes stale
    ↓
Fresh data becomes available on subsequent use
```

Two important APIs for this topic are:

```text
revalidatePath()
revalidateTag()
```

---

# 17. `revalidatePath()`

`revalidatePath()` is used when you know which route is affected by a data change.

Import:

```tsx
import { revalidatePath } from "next/cache";
```

Example:

```tsx
revalidatePath("/products");
```

Conceptually:

```text
Update product
      ↓
revalidatePath("/products")
      ↓
Affected route marked stale
      ↓
Next visit can use fresh data
```

For a specific product:

```tsx
revalidatePath("/products/123");
```

This is useful when a particular route is directly affected.

---

# 18. `revalidateTag()`

Sometimes the same data is used by many routes.

For example, these routes may all use product data:

```text
/products
/products/123
/search
/home
```

Instead of thinking only about individual routes, related cached data can be associated with a tag.

Example:

```tsx
const response = await fetch("https://example.com/api/products", {
	next: {
		tags: ["products"],
	},
});
```

The cached data is associated with:

```text
products
```

After the product data changes:

```tsx
revalidateTag("products", "max");
```

This allows the application to invalidate related tagged data.

The important mental model is:

```text
Tag related data
      ↓
Product data changes
      ↓
Invalidate the tag
      ↓
Fresh data becomes available on subsequent use
```

---

# 19. `revalidatePath()` vs `revalidateTag()`

These APIs solve different problems.

### `revalidatePath()`

Think:

```text
Which route is affected?
```

Example:

```tsx
revalidatePath("/products");
```

### `revalidateTag()`

Think:

```text
Which group of cached data is affected?
```

Example:

```tsx
revalidateTag("products", "max");
```

Comparison:

|             | `revalidatePath()`      | `revalidateTag()`                |
| ----------- | ----------------------- | -------------------------------- |
| Focus       | Route                   | Data                             |
| Targets     | Specific path           | Tagged cached data               |
| Useful when | Known route is affected | Same data is used by many routes |
| Example     | `/products`             | `"products"`                     |

A simple mental model:

```text
Known affected route
       ↓
revalidatePath()

Shared affected data
       ↓
revalidateTag()
```

---

# 20. Time-Based vs On-Demand Revalidation

### Time-Based

```text
Cache
  ↓
Configured time passes
  ↓
Revalidation
  ↓
Fresh data
```

Example:

```tsx
next: {
  revalidate: 60,
}
```

Use this when data changes periodically.

### On-Demand

```text
Data changes
   ↓
Invalidate affected cache
   ↓
Fresh data on subsequent use
```

Use this when the application knows when data has changed.

# 21. Common Caching Mistakes

## Assuming Everything Is Cached

Do not assume:

```text
fetch()
   ↓
Always cached
```

Caching depends on configuration and the surrounding application.

---

## Caching Data That Requires Freshness

Some data may require very fresh information.

Examples:

```text
Live trading information
Real-time chat
Frequently changing account information
```

A long cache duration may not be appropriate for such data.

---

## Choosing a Very Long Revalidation Time

For example, `revalidate: 86400` means the cache can remain valid for **24 hours**:

```tsx
revalidate: 86400;
```

If the data changes every few minutes, this can result in outdated information.

Choose the revalidation period according to the data's freshness requirements.

---

## Confusing Router Cache with Data Cache

Remember:

```text
Router Cache
    ↓
Client-side route segments

Data Cache
    ↓
Server-side fetched data
```

They solve different problems.

---

## Revalidating the Wrong Path

Suppose product data is displayed on `/products`, `/search`, and `/home`, but the application only invalidates:

```tsx
revalidatePath("/products");
```

Other routes may still have cached results.

When the same data is shared across multiple routes, consider using a cache tag.

---

# 22. Best Practices

### Cache reusable data

Good candidates can include:

```text
Product catalog
Categories
Blog posts
Documentation
Public configuration
```

### Choose revalidation based on freshness

Ask:

```text
How often does the data change?
        ↓
How fresh must it be?
        ↓
Choose an appropriate strategy
```

### Use paths when a specific route is affected

```tsx
revalidatePath("/products");
```

### Use tags when data is shared

```tsx
next: {
  tags: ["products"],
}
```

Then invalidate the related tag when the data changes.

### Keep caching strategy simple

Start with:

```text
What data?
    ↓
How often does it change?
    ↓
Who needs fresh data?
    ↓
Choose caching strategy
```

Do not introduce complicated caching rules without a clear requirement.

# Summary

- Caching allows Next.js to reuse previously fetched or generated results.
- Caching can reduce unnecessary API, database, and server work.
- **Data Cache** stores fetched data.
- **Full Route Cache** stores rendered route output.
- **Client Router Cache** stores route segments on the client for faster navigation.
- **Request Memoization** avoids duplicate requests during a server render.
- These concepts solve different problems and should not be treated as the same cache.
- Cache behavior depends on the Next.js version, configuration, and APIs used.
- `cache: "force-cache"` requests reuse of cached fetch data.
- `cache: "no-store"` avoids storing the fetch result in the Data Cache.
- `next: { revalidate: N }` configures periodic revalidation.
- Time-based revalidation is useful when data changes periodically.
- On-demand revalidation is useful when the application knows that data has changed.
- `revalidatePath()` focuses on an affected route.
- `revalidateTag()` focuses on related cached data.
- Use paths when the affected route is known.
- Use tags when the same data is shared across multiple routes.
- Choose caching and revalidation based on the application's freshness requirements.

> **Simple rule:** Cache data when it can be reused, choose a freshness strategy based on how often it changes, and invalidate the affected path or shared data when the underlying data changes.
