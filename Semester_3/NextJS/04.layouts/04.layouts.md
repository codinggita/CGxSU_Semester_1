# 04. Layouts

A **layout** is a special Next.js file used to create UI that is shared between multiple pages.

Common examples:

- Navbar
- Footer
- Sidebar
- Dashboard menu
- Global providers

Instead of repeating shared UI in every page, place it inside a `layout.tsx`.

---

# 1. What is a Layout?

A layout is a special file named:

```text
layout.tsx
```

It wraps the pages inside its route segment.

```text
app/
├── layout.tsx
├── page.tsx
└── about/
    └── page.tsx
```

The root layout can provide:

```text
Navbar
   ↓
Page Content
   ↓
Footer
```

### `page.tsx` vs `layout.tsx`

```text
page.tsx   → UI for a specific route
layout.tsx → Shared UI for multiple routes
```

---

# 2. Root Layout

The **root layout** is the top-level layout of an App Router application.

```text
app/layout.tsx
```

It must contain:

```html
<html>
	<body></body>
</html>
```

### Example

```tsx
import "./globals.css";

export default function RootLayout({
	children,
}: {
	children: React.ReactNode;
}) {
	return (
		<html lang='en'>
			<body>{children}</body>
		</html>
	);
}
```

`children` represents the page or nested layout rendered inside the current layout.

```text
Root Layout
    ↓
{children}
    ↓
Current Page
```

The root layout is commonly used for:

- Global CSS
- Global providers
- Navbar / Footer
- Application-wide UI

Metadata can also be defined at the root layout level, but detailed metadata and SEO will be covered later.

---

# 3. Shared UI with a Layout

Example structure:

```text
app/
├── layout.tsx
├── page.tsx
├── products/
│   └── page.tsx
└── about/
    └── page.tsx
```

`layout.tsx`:

```tsx
import Navbar from "@/components/Navbar";
import Footer from "@/components/Footer";

export default function RootLayout({
	children,
}: {
	children: React.ReactNode;
}) {
	return (
		<html lang='en'>
			<body>
				<Navbar />

				<main>{children}</main>

				<Footer />
			</body>
		</html>
	);
}
```

Now:

```text
/           → Home
/products   → Products
/about      → About
```

all use the same `Navbar` and `Footer`.

Reusable components such as `Navbar` and `Footer` can be kept inside:

```text
components/
```

---

# 4. Nested Layouts

Layouts can also exist inside route segments.

Example:

```text
app/
├── layout.tsx
└── dashboard/
    ├── layout.tsx
    ├── page.tsx
    └── settings/
        └── page.tsx
```

The structure becomes:

```text
Root Layout
    ↓
Dashboard Layout
    ↓
Dashboard Page
```

### Dashboard Layout

```tsx
export default function DashboardLayout({
	children,
}: {
	children: React.ReactNode;
}) {
	return (
		<section>
			<aside>Dashboard Menu</aside>

			<main>{children}</main>
		</section>
	);
}
```

The dashboard layout can contain UI shared by:

```text
/dashboard
/dashboard/settings
/dashboard/profile
```

For example:

```text
Root Layout
├── Navbar
│
└── Dashboard Layout
    ├── Sidebar
    └── Page Content
```

---

# 5. Layout Persistence

One of the main benefits of layouts is that they **remain mounted while navigating between routes that share the same layout segment**.

For example:

```text
/dashboard
      ↓
/dashboard/settings
      ↓
/dashboard/profile
```

The dashboard layout remains while the page content changes.

This is useful for:

- Sidebars
- Dashboard menus
- Persistent headers
- Navigation
- Dashboard shells

Conceptually:

```text
Dashboard Layout
┌─────────────────────────┐
│ Sidebar                 │
│                         │
│   Page Content          │
│                         │
└─────────────────────────┘
```

When navigating:

```text
/dashboard
      ↓
/dashboard/settings
```

the layout remains and only the page content changes.

---

# 6. Layout Hierarchy

Layouts can be nested multiple levels deep.

Consider:

```text
app/
├── layout.tsx
└── dashboard/
    ├── layout.tsx
    └── settings/
        ├── layout.tsx
        └── page.tsx
```

The page is rendered through the layout hierarchy:

```text
Root Layout
    ↓
Dashboard Layout
    ↓
Settings Layout
    ↓
Settings Page
```

Each layout can add UI shared by the routes inside its segment.

For example:

```text
Root Layout
├── Website Header
│
└── Dashboard Layout
    ├── Dashboard Sidebar
    │
    └── Settings Layout
        └── Settings Page
```

# 7. Different Layouts for Different Sections

Large applications may have different layouts for different sections.

For example:

```text
Marketing → Marketing Layout
Dashboard → Dashboard Layout
Admin     → Admin Layout
```

Route groups can help organize these sections.

```text
app/
├── layout.tsx
│
├── (marketing)/
│   ├── layout.tsx
│   ├── page.tsx
│   └── pricing/
│       └── page.tsx
│
└── (dashboard)/
    ├── layout.tsx
    └── dashboard/
        ├── page.tsx
        └── settings/
            └── page.tsx
```

The folder names inside parentheses are **route groups**:

```text
(marketing)
(dashboard)
```

They **do not appear in the URL**.

For example:

```text
(marketing)/pricing
```

produces:

```text
/pricing
```

Route groups allow different sections of an application to have different layouts without changing the URL structure.

# 8. Recommended Organization

A practical structure:

```text
src/
├── app/
│   ├── layout.tsx
│   ├── page.tsx
│   │
│   ├── products/
│   │   └── page.tsx
│   │
│   └── dashboard/
│       ├── layout.tsx
│       ├── page.tsx
│       └── settings/
│           └── page.tsx
│
└── components/
    ├── Navbar.tsx
    └── Footer.tsx
```

### Simple Rule

```text
Application-wide UI
        ↓
Root Layout

Section-specific UI
        ↓
Nested Layout

Page-specific UI
        ↓
page.tsx

Reusable UI
        ↓
components/
```

# 9. Best Practices

### 1. Keep global UI in the root layout

Examples:

- Navbar
- Footer
- Global providers
- Global CSS

### 2. Keep section-specific UI in nested layouts

For example, a dashboard sidebar belongs in:

```text
dashboard/layout.tsx
```

instead of being repeated in every dashboard page.

### 3. Don't put page-specific UI in a layout

If UI is needed only for:

```text
/products
```

keep it in the products page or its own component.

### 4. Avoid unnecessary layouts

Create a nested layout when multiple routes actually need the same shared UI.

### 5. Keep interactive UI in Client Components

Layouts are Server Components by default.

If shared UI needs client-side features, extract that interactive part into a Client Component.

For example:

```text
Root Layout
└── Navbar
    ├── Logo
    ├── Navigation
    └── Search / Cart
        ↓
    Client Component when interaction is required
```

The entire layout does not need to become a Client Component just because one part of the UI is interactive.

---

# Summary

- `layout.tsx` provides shared UI for a route segment.
- `app/layout.tsx` is the root layout.
- Root layout must contain `<html>` and `<body>`.
- `children` represents the page or nested layout inside the current layout.
- Layouts can be nested.
- Layouts persist across navigation within their route segment.
- Route groups `(group)` organize routes without affecting URLs.
- Use the root layout for global UI.
- Use nested layouts for section-specific UI.
- Use `page.tsx` for page-specific UI.
- Use `components/` for reusable UI.
- Layouts are Server Components by default; interactive parts can be extracted into Client Components.
