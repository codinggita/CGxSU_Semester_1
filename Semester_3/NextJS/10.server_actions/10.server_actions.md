# 10. Server Actions

Server Actions handle what happens when a form's `action` fires.

Server Actions are functions that run on the server and can be called from Client Components, Server Components, or forms depending on how they are defined and used.

They are commonly used for mutations such as creating, updating, and deleting records.

```text
User submits a form or triggers an action
                  ↓
             Server Action
                  ↓
     Authenticate and authorize the user
                  ↓
          Validate submitted data
                  ↓
           Perform the mutation
                  ↓
      Revalidate cached data if needed
                  ↓
          Return a result or redirect
```

---

## 1. What Are Server Actions?

A **Server Action** is an asynchronous server-side function that can be invoked by the application. It is useful when a Next.js UI needs to perform an operation on the server, such as saving a product or updating user settings.

```tsx
"use server";

export async function createUser(formData: FormData) {
	const email = formData.get("email");

	// Validate input and perform server-side work.
}
```

Server Actions can perform database operations and other server-side work. They do not make those operations automatically safe: the action must still validate input and check permissions.

A common API-based flow is:

```text
Client Component → fetch() → Route Handler/API → Database
```

A form can instead invoke a Server Action:

```text
Form → Server Action → Database
```

This can reduce API boilerplate when a mutation is only needed by the Next.js application. Server Actions do not replace Route Handlers or public APIs in every situation.

---

## 2. The `"use server"` Directive

The `"use server"` directive marks server-side action code.

### At the top of a file

```tsx
"use server";

export async function createProduct(formData: FormData) {
	// Server-side logic
}

export async function deleteProduct(id: string) {
	// Server-side logic
}
```

When the directive is at the top of a module, its exported functions must be async Server Actions.

### Inside a function

You can also place the directive **inside a single function** instead of at the top of the file:

```tsx
export async function createProduct(formData: FormData) {
	"use server";

	const name = formData.get("name");
	// Server-side code
}
```

An inline directive marks that function as a Server Action. This can be useful when defining an action within a Server Component. Reusable actions can also be kept in a separate module for easier organization.

---

## 3. Using a Server Action with a Form

A form can use a Server Action through its `action` prop:

```tsx
import { createUser } from "./actions";

export default function SignupForm() {
	return (
		<form action={createUser}>
			<label htmlFor='email'>Email</label>
			<input id='email' name='email' type='email' required />
			<button type='submit'>Create Account</button>
		</form>
	);
}
```

The form submits to the server-side function. The field's `name` identifies its value in the submitted `FormData`.

### Reading `FormData`

```tsx
"use server";

export async function login(formData: FormData) {
	const email = formData.get("email");
	const password = formData.get("password");

	// Validate and process the submitted values.
}
```

`formData.get()` returns a `FormDataEntryValue` or `null`. A text field usually provides a string, but the server should not assume that the submitted value is valid merely because the UI uses a particular input type.

## 4. Server-Side Mutations

A **mutation** changes data:

- Create --- add a record.
- Update --- change an existing record.
- Delete --- remove a record.

A Server Action can perform a database mutation:

```tsx
"use server";

export async function updateProduct(id: string, price: number) {
	// Authenticate, authorize, and validate before this operation.
	await db.product.update({
		where: { id },
		data: { price },
	});
}
```

Here, `db` represents the application's configured database client.

---

## 5. Validate Data Inside Server Actions

Never rely only on client-side validation. A user can bypass the UI and submit unexpected values directly to the server.

Use a schema to validate data before performing the mutation:

```tsx
"use server";

import { z } from "zod";

const signupSchema = z.object({
	email: z.email(),
	password: z.string().min(8),
});

export async function createUser(formData: FormData) {
	const result = signupSchema.safeParse({
		email: formData.get("email"),
		password: formData.get("password"),
	});

	if (!result.success) {
		return { error: "Please check your submitted information." };
	}

	// Use result.data for validated values and perform the mutation.
	return { success: true };
}
```

This uses **Zod v4** syntax (`z.email()`). In Zod v3, the email rule is commonly written as `z.string().email()`.

`safeParse()` returns either validated data or validation details. Do not perform a mutation when validation fails.

### Converting form values

`FormData` values are not automatically converted to numbers. A price from an HTML input generally arrives as text. Convert it deliberately and validate the result.

```tsx
const productSchema = z.object({
	name: z.string().trim().min(1, "Name is required"),
	price: z.coerce.number().positive("Price must be greater than zero"),
});
```

`.positive()` rejects zero. If zero is valid for your use case, use a suitable rule such as `.min(0)` and an accurate error message.

## 6. Authentication and Authorization

A Server Action must not assume that a user is permitted to perform an operation just because a button is hidden or a page is protected.

- **Authentication:** Who is the user?
- **Authorization:** Is this user allowed to perform this operation on this resource?

Before deleting a product, for example, the server should check that the user is authenticated and has permission to delete that product.

```text
Server Action
      ↓
Authenticate user
      ↓
Authorize operation
      ↓
Validate submitted data
      ↓
Perform mutation
```

Perform these checks inside the server-side operation, before changing data. Server Actions can be invoked through requests even when the UI does not expose a button for them.

## 7. Returning Errors and Success Results

A Server Action can return a serializable result describing an expected outcome.

```tsx
"use server";

export async function createUser(formData: FormData) {
	const email = formData.get("email");

	if (typeof email !== "string" || !email.trim()) {
		return {
			errors: {
				email: "Email is required",
			},
		};
	}

	// Validate, authorize, and create the user.
	return { success: true };
}
```

A structured result makes it possible for the UI to show a message beside the field that needs correction:

```tsx
return {
	errors: {
		email: "Please enter a valid email address.",
		password: "Password must be at least 8 characters.",
	},
};
```

Return only information the UI needs. Do not expose credentials, tokens, database details, or sensitive internal errors.

## 8. `useActionState`

React's `useActionState` connects an action's returned result to component state. It is useful when a form needs to display server-side validation errors or a success message.

When used with `useActionState`, the action receives the previous state and the submitted form data.

```tsx
"use server";

type FormState = {
	error?: string;
	success?: boolean;
};

export async function createUser(
	prevState: FormState,
	formData: FormData,
): Promise<FormState> {
	const email = formData.get("email");

	if (typeof email !== "string" || !email.trim()) {
		return { error: "Email is required" };
	}

	// Validate, authorize, and perform the mutation.
	return { success: true };
}
```

In the Client Component, pass the action to `useActionState` and use the returned `formAction` as the form's action:

```tsx
"use client";

import { useActionState } from "react";
import { createUser } from "./actions";

const initialState = {};

export default function SignupForm() {
	const [state, formAction, pending] = useActionState(
		createUser,
		initialState,
	);

	return (
		<form action={formAction}>
			<label htmlFor='email'>Email</label>
			<input id='email' name='email' type='email' required />

			{state.error && <p role='alert'>{state.error}</p>}
			{state.success && <p>Account created!</p>}

			<button type='submit' disabled={pending}>
				{pending ? "Creating..." : "Sign up"}
			</button>
		</form>
	);
}
```

Key points:

- `state` contains the most recent value returned by the action.
- `formAction` is the function passed to the form's `action` prop.
- `pending` indicates that the action is being processed.
- The action's return type and initial state should be compatible.

For field-level errors, define an `errors` object in the state and render each message beside its input.

## 9. React Hook Form with a Server Action

React Hook Form can provide immediate client-side validation, while a Server Action performs trusted server-side validation and the mutation.

When React Hook Form's `handleSubmit` handles submission, build a `FormData` object and dispatch the `useActionState` action within `startTransition`.

```tsx
"use client";

import { startTransition, useActionState } from "react";
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import { z } from "zod";
import { createProduct } from "./actions";

const schema = z.object({
	name: z.string().trim().min(1, "Name is required"),
	price: z.coerce.number().positive("Price must be greater than zero"),
});

type FormValues = z.infer<typeof schema>;

type ProductFormState = {
	errors?: {
		name?: string;
		price?: string;
	};
	success?: boolean;
};

export default function ProductForm() {
	const [state, formAction, pending] = useActionState<
		ProductFormState,
		FormData
	>(createProduct, {});

	const {
		register,
		handleSubmit,
		formState: { errors },
	} = useForm<FormValues>({
		resolver: zodResolver(schema),
	});

	function onValid(data: FormValues) {
		const formData = new FormData();
		formData.set("name", data.name);
		formData.set("price", String(data.price));

		startTransition(() => {
			formAction(formData);
		});
	}

	return (
		<form onSubmit={handleSubmit(onValid)} noValidate>
			<label htmlFor='name'>Name</label>
			<input id='name' {...register("name")} />
			{errors.name && <p role='alert'>{errors.name.message}</p>}
			{state.errors?.name && <p role='alert'>{state.errors.name}</p>}

			<label htmlFor='price'>Price</label>
			<input id='price' type='number' {...register("price")} />
			{errors.price && <p role='alert'>{errors.price.message}</p>}
			{state.errors?.price && <p role='alert'>{state.errors.price}</p>}

			{state.success && <p>Product created!</p>}

			<button type='submit' disabled={pending}>
				{pending ? "Saving..." : "Save"}
			</button>
		</form>
	);
}
```

The Server Action must return a state compatible with `ProductFormState` and independently validate the received `FormData`.

- React Hook Form's `errors` are client-side validation errors.
- `state.errors` are returned by the server, including errors that only the server can detect.
- `pending` can disable the submit button while the action is processing.

For simpler forms, a native `<form action={...}>` with `useActionState` may be enough. React Hook Form is optional.

## 10. Calling a Server Action Outside a Form

Server Actions can also be called from a button or another client interaction, such as a Like button.

```tsx
"use client";

import { startTransition } from "react";
import { likePost } from "./actions";

export function LikeButton({ postId }: { postId: string }) {
	return (
		<button
			type='button'
			onClick={() => {
				startTransition(() => {
					likePost(postId);
				});
			}}
		>
			Like
		</button>
	);
}
```

```tsx
"use server";

export async function likePost(postId: string) {
	// Authenticate, authorize, validate postId, and perform the mutation.
	return { success: true };
}
```

Use `startTransition` when calling an action directly from an event handler. If the UI needs to display the result or pending state, store and render that state explicitly. The same server-side security checks apply.

## 11. Expected Errors vs Unexpected Errors

### Expected errors

These are outcomes the application can reasonably anticipate, such as:

- Required information is missing.
- An email address is already registered.
- A product does not exist.
- A user is not allowed to edit a particular record.

Return a useful, safe result so the UI can explain the problem.

### Unexpected errors

These include unanticipated programming errors or infrastructure failures. Handle and log them using the application's error-handling approach, without exposing sensitive internal details to users.

Avoid catching every exception and silently returning a generic result if doing so hides failures that should be investigated. Also note that `redirect()` throws internally, so it should not be accidentally swallowed by a broad `try/catch`.

## 12. Revalidating Data After Mutations

After a mutation, cached content may need to be refreshed. The correct method depends on how the data is cached and which pages use it.

### `revalidatePath()`

Use `revalidatePath()` when a specific route needs revalidation after a mutation.

```tsx
"use server";

import { revalidatePath } from "next/cache";

export async function updateProduct(id: string, price: number) {
	await db.product.update({
		where: { id },
		data: { price },
	});

	revalidatePath("/products");
	revalidatePath(`/products/${id}`);
}
```

This example assumes the relevant product pages use data affected by path revalidation.

### `revalidateTag()`

Tags are useful when cached data is shared across multiple routes. A fetch can be tagged:

```tsx
const response = await fetch("https://api.example.com/products", {
	next: {
		tags: ["products"],
	},
});
```

After a mutation:

```tsx
import { revalidateTag } from "next/cache";

revalidateTag("products", "max");
```

With the `"max"` profile, tagged data is marked stale and can be refreshed in the background when next requested. This is a stale-while-revalidate strategy, not an immediate cache purge.

---

## 13. Redirecting After a Mutation

After a successful operation, the user may need to navigate to another route.

```tsx
"use server";

import { revalidatePath } from "next/cache";
import { redirect } from "next/navigation";

export async function createProduct(formData: FormData) {
	// Validate, authorize, and create the product.

	revalidatePath("/products");
	redirect("/products");
}
```

## 14. Server Actions vs Route Handlers

Server Actions and Route Handlers both allow server-side operations, but they serve different needs.

### Server Action

Server Actions are convenient for mutations that belong to the Next.js application, especially form submissions.

### Route Handler / API endpoint

```text
Web app ───┐
Mobile app ├──→ API endpoint → Server logic
Other app ─┘
```

Route Handlers are often a better fit when multiple clients need a documented HTTP API or an endpoint must be consumed independently by a mobile app, another frontend, or an external service.

A Server Action is not a replacement for every API endpoint. Choose based on who needs to call the operation and how the application is structured.

## 15. Common Mistakes and Best Practices

### Common mistakes

1. **Trusting client validation:** Always validate submitted data on the server.
2. **Skipping authorization:** Check permissions inside the action before changing data.
3. **Assuming `FormData` is already typed:** Values can be missing or have unexpected types; validate and convert them.
4. **Returning sensitive details:** Return only safe information needed by the UI.
5. **Forgetting cache revalidation:** If a mutation changes cached content, revalidate the affected path or tag as appropriate.
6. **Using Server Actions for every API requirement:** Use a Route Handler when multiple clients need an explicit endpoint.
7. **Catching unexpected failures indiscriminately:** Handle expected outcomes as results, but let unexpected failures reach appropriate logging and error handling.
8. **Mismatching action state types:** Keep the `useActionState` initial state, action return type, and UI expectations consistent.

### Best practices

- Authenticate and authorize every sensitive mutation on the server.
- Validate all untrusted input before performing a mutation.
- Use structured, user-safe results for expected validation errors.
- Keep database operations, secrets, and sensitive business logic on the server.
- Use `useActionState` when the UI needs to display action results.
- Use `useFormStatus` for pending UI when it fits the form structure.
- Revalidate affected cached data after mutations when needed.
- Redirect after success when it matches the intended user flow.
- Prefer the simplest approach that meets the form's needs.

---

## Summary

- Server Actions run server-side logic and are commonly used for mutations and form processing.
- `"use server"` can mark a module's exported actions or an individual function.
- Forms can invoke an action through `<form action={...}>`.
- `FormData` contains submitted values, which must be validated and converted as needed.
- Validate and authorize every sensitive operation on the server.
- Use structured action results and `useActionState()` to show expected errors and success messages.
- React Hook Form can provide client-side validation; server-side validation is still required.
- Use `startTransition()` when calling an action directly from a client event handler.
- Use `revalidatePath()` or `revalidateTag()` according to the cache behavior required.
- `redirect()` can send the user to another route after successful processing.
- Use Route Handlers when an explicit HTTP API is needed by multiple clients.
- Keep sensitive details out of action results and handle unexpected failures appropriately.

> **Simple rule:** Server Actions make application mutations convenient, but they do not remove the need for server-side validation, authentication, authorization, safe error handling, or deliberate cache revalidation.
