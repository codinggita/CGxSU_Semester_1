# 23. File Uploads & External Services

Uploading files from a Next.js app to Cloudinary. The **primary pattern** is a direct browser-to-Cloudinary upload authenticated with a short-lived server-generated signature — file bytes never pass through your Next.js server. A secondary server-proxy pattern (Server Action + `upload_stream`) is included for cases that need server-side file inspection before Cloudinary sees the file.

The database stores file **metadata** (`secure_url`, `public_id`). Cloudinary stores the **actual file**.

---

## File Upload Flow (Direct Signed Upload)

This is the default architecture for product images, avatars, and galleries:

```text
Browser                    Route Handler (signature)           Cloudinary
   │                                  │                            │
   │── POST /api/cloudinary/sign ────▶│                            │
   │                                  │── verify session           │
   │                                  │── build paramsToSign       │
   │                                  │── api_sign_request()       │
   │◀── { signature, timestamp,       │   (API secret stays        │
   │      apiKey, cloudName, ... } ───│    server-side only)       │
   │                                                                  │
   │── POST file + signature ────────────────────────────────────────▶│
   │◀── { secure_url, public_id, bytes, ... } ────────────────────────│
   │                                                                  │
   │── saveProductImage({ url, publicId }) ──▶ Server Action ──▶ DB  │
```

**Why this is the primary pattern:**

- The file travels **browser → Cloudinary in one hop**, not browser → Next.js → Cloudinary
- Your server only issues a short-lived signature — it never buffers the file
- The Server Action **1 MB body size limit does not apply** — the file never hits a Server Action
- Serverless execution time is not spent proxying file bytes

Common use cases:

```text
Profile picture       → single image
Product gallery       → multiple images
```

## Validation

With direct signed uploads, validation happens in **two places** — not inside a file-handling Server Action.

### Client-side (UX only)

The file input `accept` attribute filters the picker UI. It is **not** a security mechanism.

```tsx
<input type="file" accept="image/jpeg,image/png,image/webp" />
```

### Server-side via signed upload parameters

Restrictions are defined in the parameters your signature endpoint signs. Cloudinary **enforces them at upload time** — your server never sees the file.

Per the [Cloudinary Upload API reference](https://cloudinary.com/documentation/image_upload_api_reference#upload_optional_parameters), common signed parameters include:

| Parameter | Purpose |
| --------- | ------- |
| `allowed_formats` | Comma-separated extensions Cloudinary accepts (e.g. `"jpg,png,webp"`) — other formats are rejected |
| `max_file_size` | Maximum file size in **bytes** (e.g. `5242880` for 5 MB) |
| `folder` | Target folder in your Cloudinary account (e.g. `"shop/products"`) |

These parameters must appear in **both** the signed payload (`paramsToSign` passed to `api_sign_request`) **and** the upload `FormData` sent to Cloudinary. If they differ, the upload fails.

If you need **custom validation** Cloudinary cannot express through upload parameters — inspecting raw bytes, virus scanning, generating a custom thumbnail before upload — use the [server-proxy pattern](#when-to-use-the-server-proxy-pattern-instead) instead.

## Why Cloudinary?

Cloudinary is a hosted media platform — upload, store, transform, and deliver images and videos via URL.

```text
Browser ──direct upload (signed)──▶ Cloudinary CDN
                                           ↓
                          https://res.cloudinary.com/.../image.jpg
```

Benefits over storing files on the app server:

```text
✓ Works in serverless / multi-instance deployments
✓ Built-in transforms (resize, crop, format) via URL
✓ CDN delivery
✓ No local /uploads folder to manage
```

### Signature Route Handler — `app/api/cloudinary/sign/route.ts`

**This endpoint is the security boundary.** Without an auth check here, anyone can request a valid signature and upload directly to your Cloudinary account.

Per [Cloudinary authentication signatures](https://cloudinary.com/documentation/authentication_signatures):

- Sign every parameter sent in the upload POST **except** `file`, `api_key`, `cloud_name`, and `resource_type`
- Include `timestamp` (Unix seconds) in `paramsToSign`
- Signatures are valid for **one hour** from that timestamp

```ts
import { NextResponse } from "next/server";
import cloudinary from "@/lib/cloudinary";
import { getSession } from "@/lib/auth";
import {
  PRODUCT_IMAGE_UPLOAD,
  GALLERY_IMAGE_UPLOAD,
} from "@/lib/cloudinary-upload-params";

const PRESETS = {
  product: PRODUCT_IMAGE_UPLOAD,
  gallery: GALLERY_IMAGE_UPLOAD,
} as const;

export async function POST(request: Request) {
  const session = await getSession();
  if (!session) {
    return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
  }

  const { preset = "product" } = await request.json();
  const uploadParams = PRESETS[preset as keyof typeof PRESETS] ?? PRESETS.product;

  const timestamp = Math.round(Date.now() / 1000);

  // Parameters included here MUST also be sent in the Cloudinary upload FormData
  const paramsToSign = {
    timestamp,
    folder: uploadParams.folder,
    allowed_formats: uploadParams.allowed_formats,
    max_file_size: uploadParams.max_file_size,
  };

  const signature = cloudinary.utils.api_sign_request(
    paramsToSign,
    process.env.CLOUDINARY_API_SECRET!
  );

  return NextResponse.json({
    signature,
    timestamp,
    apiKey: process.env.CLOUDINARY_API_KEY,
    cloudName: process.env.CLOUDINARY_CLOUD_NAME,
    ...uploadParams,
  });
}
```

### Auth Helper — `lib/auth.ts`

```ts
import { cookies } from "next/headers";

export async function getSession() {
  const raw = (await cookies()).get("session")?.value;
  if (!raw) return null;
  try {
    return JSON.parse(raw) as { userId: string };
  } catch {
    return null;
  }
}
```

### Client Upload Helper — `lib/cloudinary-direct-upload.ts`

Runs in the browser. Posts directly to Cloudinary's REST API:

`https://api.cloudinary.com/v1_1/{cloud_name}/{resource_type}/upload`

Per the [upload documentation](https://cloudinary.com/documentation/upload_images#using_signature_based_authentication), a signed upload requires `file`, `api_key`, `timestamp`, and `signature` in the POST body, plus any optional signed parameters.

```ts
type SignResponse = {
  signature: string;
  timestamp: number;
  apiKey: string;
  cloudName: string;
  folder: string;
  allowed_formats: string;
  max_file_size: number;
};

type CloudinaryUploadResult = {
  secure_url: string;
  public_id: string;
  bytes: number;
  width: number;
  height: number;
};

export async function uploadToCloudinaryDirect(
  file: File,
  preset: "product" | "gallery" = "product"
): Promise<CloudinaryUploadResult> {
  // 1. Request a signed upload permission from your server
  const signRes = await fetch("/api/cloudinary/sign", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ preset }),
  });

  if (signRes.status === 401) {
    throw new Error("You must be logged in to upload");
  }
  if (!signRes.ok) {
    throw new Error("Failed to get upload signature");
  }

  const sign: SignResponse = await signRes.json();

  // 2. Upload directly to Cloudinary — file bytes never touch Next.js
  const formData = new FormData();
  formData.append("file", file);
  formData.append("api_key", sign.apiKey);
  formData.append("timestamp", String(sign.timestamp));
  formData.append("signature", sign.signature);
  formData.append("folder", sign.folder);
  formData.append("allowed_formats", sign.allowed_formats);
  formData.append("max_file_size", String(sign.max_file_size));

  const uploadRes = await fetch(
    `https://api.cloudinary.com/v1_1/${sign.cloudName}/image/upload`,
    { method: "POST", body: formData }
  );

  if (!uploadRes.ok) {
    const err = await uploadRes.json().catch(() => ({}));
    throw new Error(err.error?.message ?? "Cloudinary upload failed");
  }

  return uploadRes.json();
}
```

### Client Component — `SingleImageUpload.tsx`

```tsx
"use client";

import { useState } from "react";
import { uploadToCloudinaryDirect } from "@/lib/cloudinary-direct-upload";
import { saveProductImage } from "../actions";

export function SingleImageUpload() {
  const [preview, setPreview] = useState<string | null>(null);
  const [error, setError] = useState<string | null>(null);
  const [isUploading, setIsUploading] = useState(false);

  async function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
    const file = e.target.files?.[0];
    if (!file) return;

    setError(null);
    setIsUploading(true);

    try {
      // Direct upload to Cloudinary (browser → Cloudinary)
      const result = await uploadToCloudinaryDirect(file, "product");

      // Save metadata via Server Action (no file bytes)
      await saveProductImage({
        url: result.secure_url,
        publicId: result.public_id,
        bytes: result.bytes,
        width: result.width,
        height: result.height,
      });

      setPreview(result.secure_url);
    } catch (err) {
      setError(err instanceof Error ? err.message : "Upload failed");
    } finally {
      setIsUploading(false);
    }
  }

  return (
    <div>
      <input
        type="file"
        accept="image/jpeg,image/png,image/webp"
        onChange={handleChange}
        disabled={isUploading}
      />
      {isUploading && <p>Uploading…</p>}
      {error && <p>{error}</p>}
      {preview && (
        // eslint-disable-next-line @next/next/no-img-element
        <img src={preview} alt="Uploaded product" width={200} />
      )}
    </div>
  );
}
```

```text
User selects file

        ↓
POST https://api.cloudinary.com/.../upload  (file goes direct)
        ↓

        ↓
```


### Client Component — `MultiImageUpload.tsx`

When signed parameters (`folder`, `allowed_formats`, `max_file_size`, `timestamp`) are **identical for every file**, one signature can be reused for the whole batch — per [Cloudinary's signature rules](https://cloudinary.com/documentation/authentication_signatures), the upload POST must send the **same** signed fields that were hashed.

```tsx
"use client";

import { useState } from "react";
import { uploadToCloudinaryDirect } from "@/lib/cloudinary-direct-upload";
import { saveProductImages } from "../actions";

const MAX_FILES = 5;

export function MultiImageUpload() {
  const [urls, setUrls] = useState<string[]>([]);
  const [error, setError] = useState<string | null>(null);
  const [isUploading, setIsUploading] = useState(false);

  async function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
    const files = Array.from(e.target.files ?? []);
    if (files.length === 0) return;

    if (files.length > MAX_FILES) {
      setError(`Maximum ${MAX_FILES} images`);
      return;
    }

    setError(null);
    setIsUploading(true);

    try {
      const uploaded = [];

      // Same signed params for each file → one signature request, reused uploads
      for (const file of files) {
        const result = await uploadToCloudinaryDirect(file, "gallery");
        uploaded.push({
          url: result.secure_url,
          publicId: result.public_id,
          bytes: result.bytes,
          width: result.width,
          height: result.height,
        });
      }

      await saveProductImages(uploaded);
      setUrls(uploaded.map((r) => r.url));
    } catch (err) {
      setError(err instanceof Error ? err.message : "Upload failed");
    } finally {
      setIsUploading(false);
    }
  }

  return (
    <div>
      <input
        type="file"
        accept="image/jpeg,image/png,image/webp"
        multiple
        onChange={handleChange}
        disabled={isUploading}
      />
      {isUploading && <p>Uploading…</p>}
      {error && <p>{error}</p>}
      <div style={{ display: "flex", gap: 8, flexWrap: "wrap" }}>
        {urls.map((url) => (
          // eslint-disable-next-line @next/next/no-img-element
          <img key={url} src={url} alt="Uploaded" width={120} height={120} />
        ))}
      </div>
    </div>
  );
}
```

> **Optimization:** Request the signature once, then pass the signed fields into a lower-level upload helper for each file instead of calling `/api/cloudinary/sign` per file. The multi-file upload example calls the helper per file for clarity; the signed `timestamp` remains valid for one hour.

## When to Use the Server-Proxy Pattern Instead

Direct signed upload is the **default** for straightforward image uploads. Route the file through your Next.js server **only** when you need to inspect or modify bytes before Cloudinary receives them:

```text
Custom content validation beyond MIME type (magic-byte inspection)
Server-generated derivatives before upload (custom thumbnail pipeline)
Virus / malware scanning
Any workflow where Cloudinary signed parameters are not enough
```

Most product image uploads do **not** need this.

### Server-Proxy Flow

```text
Browser → FormData → Server Action → validate → Buffer → upload_stream → Cloudinary
```

This pattern inherits the Server Action **~1 MB default body limit**. Raise it in `next.config.ts` if you use this path:

```ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  experimental: {
    serverActions: {
      bodySizeLimit: "10mb",
    },
  },
};

export default nextConfig;
```

### Upload Helper — `lib/upload-to-cloudinary-proxy.ts`

```ts
import type { UploadApiResponse } from "cloudinary";
import cloudinary from "@/lib/cloudinary";

/** Secondary pattern: buffer file on server, then stream to Cloudinary. */
export async function uploadToCloudinaryProxy(
  file: File,
  folder: string
): Promise<UploadApiResponse> {
  const arrayBuffer = await file.arrayBuffer();
  const buffer = Buffer.from(arrayBuffer);

  return new Promise((resolve, reject) => {
    cloudinary.uploader
      .upload_stream({ folder, resource_type: "auto" }, (error, result) => {
        if (error || !result) {
          reject(error ?? new Error("Upload failed"));
          return;
        }
        resolve(result);
      })
      .end(buffer);
  });
}
```

### Server Action — proxy upload + save

```ts
"use server";

import { revalidatePath } from "next/cache";
import { getSession } from "@/lib/auth";
import { uploadToCloudinaryProxy } from "@/lib/upload-to-cloudinary-proxy";

const MAX_SIZE = 5 * 1024 * 1024;
const ALLOWED_TYPES = ["image/jpeg", "image/png", "image/webp"];

export async function uploadImageViaServer(formData: FormData) {
  const session = await getSession();
  if (!session) throw new Error("Unauthorized");

  const file = formData.get("image");
  if (!(file instanceof File)) throw new Error("Image is required");

  // Server-side validation — required in this pattern because Cloudinary
  // signed params are not in the upload path
  if (file.size > MAX_SIZE) throw new Error("Image must be 5 MB or smaller");
  if (!ALLOWED_TYPES.includes(file.type)) {
    throw new Error("Only JPEG, PNG, and WebP are allowed");
  }

  const result = await uploadToCloudinaryProxy(file, "shop/products");

  // await db.productImage.create({ url: result.secure_url, publicId: result.public_id, ... });

  revalidatePath("/products");
  return { url: result.secure_url, publicId: result.public_id };
}
```

```ts
import cloudinary from "@/lib/cloudinary";
```

## Security Checklist

```text
□ Signature endpoint (/api/cloudinary/sign) verifies auth before signing
□ Signed params include allowed_formats, max_file_size, folder — Cloudinary enforces them
□ Signature timestamp is fresh (valid for 1 hour per Cloudinary docs)
□ CLOUDINARY_API_SECRET is server-only (never NEXT_PUBLIC_)
□ Metadata-save Server Actions also verify auth (defense in depth)
□ Store public_id in DB so files can be deleted when records are removed
□ For server-proxy pattern only: set bodySizeLimit in next.config.ts
```

## Common Mistakes

### Trusting Client Validation

`accept="image/png"` only filters the file picker. With direct uploads, enforce restrictions via signed `allowed_formats` and `max_file_size` — not client-side checks alone.

### Exposing Cloudinary Secrets

```env
# Wrong — visible in the browser bundle
NEXT_PUBLIC_CLOUDINARY_API_SECRET=...

# Correct — server-only
CLOUDINARY_API_SECRET=...
```

The `api_key` is intentionally sent to the browser for uploads. The secret is not.

### Skipping Auth on the Signature Endpoint

In the direct-upload architecture, **`/api/cloudinary/sign` is the security boundary** — not the metadata Server Action. Without an auth check there, anyone can request a valid signature and upload to your Cloudinary account, bypassing your application entirely.

### Treating the Signature Endpoint as Low-Risk

Returning "just a signature" does not make this endpoint harmless. It controls who can write to your Cloudinary storage. Apply the same rigor as any authenticated, mutating-adjacent Route Handler.

### Using the Server-Proxy Pattern by Default

Buffering every file through Next.js doubles transfer time, consumes serverless execution budget, and hits the Server Action body limit. Use direct signed upload unless you genuinely need server-side byte inspection.

---

## Route Handler vs Server Action

| Role | Pattern | Handles file bytes? |
| ---- | ------- | ------------------- |
| **Signature Route Handler** | `POST /api/cloudinary/sign` | No — generates signature only |
| **Direct upload (browser)** | `fetch` to `api.cloudinary.com` | Yes — but bypasses Next.js |
| **Metadata Server Action** | `saveProductImage()` | No — saves URL/public_id to DB |
| **Server-proxy Server Action** | `uploadImageViaServer(formData)` | Yes — secondary pattern only |

Keep Cloudinary signing logic in `lib/` and Route Handlers. Keep database writes in Server Actions. Do not mix file buffering into metadata-only actions.
