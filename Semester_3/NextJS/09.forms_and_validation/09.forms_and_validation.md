# 09. Forms & Validation

Forms are an important part of most web applications.

Forms collect user input such as login details, profile information, product data, feedback, and search queries.

A typical flow is:

```text
User enters data
       ↓
Validation
       ↓
Valid?
  ┌────┴────┐
  No        Yes
  ↓          ↓
Show errors  Submit data
                 ↓
          Server processing
```

Next.js App Router forms use standard HTML elements. Client Components can handle interactive state and client-side validation, while server-side logic processes submitted data.

---

## 1. HTML Forms and Form Handling

Common form elements include `<form>`, `<input>`, `<select>`, `<textarea>`, `<label>`, and `<button>`.

```tsx
export default function LoginForm() {
	return (
		<form>
			<label htmlFor='email'>Email</label>
			<input id='email' name='email' type='email' />

			<label htmlFor='password'>Password</label>
			<input id='password' name='password' type='password' />

			<button type='submit'>Login</button>
		</form>
	);
}
```

### The `name` attribute

Every field whose value should be included in normal form submission needs a `name` attribute. The `name` identifies the field in submitted form data. An `id` identifies the element in the document and can connect it to a label.

```tsx
<input type='email' name='email' />
```

### Connecting a form to a Server Action

In the App Router, a form can use a Server Action through its `action` prop:

```tsx
import { createUser } from "./actions";

export default function SignupForm() {
	return (
		<form action={createUser}>
			<input type='email' name='email' required />
			<input type='password' name='password' required />
			<button type='submit'>Create Account</button>
		</form>
	);
}
```

When the user submits, Next.js sends the form data to `createUser` on the server.

The Server Action itself — the `"use server"` directive, reading `FormData`, validation, mutations, revalidation, and returning errors — is covered in **Server Actions**.

## 2. Client-Side and Server-Side Validation

**Validation** checks whether submitted data follows the application's rules. For example, an email may be required, a password may need at least 8 characters, and a name may not be empty.

### Client-side validation

Client-side validation runs in the browser before data is submitted.

It provides quick feedback and can prevent unnecessary submissions.

```tsx
"use client";

import { useState } from "react";

export default function EmailForm() {
	const [email, setEmail] = useState("");
	const [error, setError] = useState("");

	function handleSubmit(event: React.FormEvent<HTMLFormElement>) {
		event.preventDefault();

		if (!email.trim()) {
			setError("Email is required");
			return;
		}

		setError("");
	}

	return (
		<form onSubmit={handleSubmit}>
			<label htmlFor='email'>Email</label>
			<input
				id='email'
				name='email'
				type='email'
				value={email}
				onChange={(event) => setEmail(event.target.value)}
			/>

			{error && <p role='alert'>{error}</p>}
			<button type='submit'>Submit</button>
		</form>
	);
}
```

Client-side validation can be bypassed. A user can send a request without using the application's UI.

### Server-side validation

Server-side validation checks submitted data on the server. The server must validate data before using it in authentication, business logic, database operations, or external API requests.

**Client-side validation improves user experience; server-side validation is required for correctness and security.**

| | Client-side validation | Server-side validation |
| --- | --- | --- |
| Where it runs | In the browser | On the server |
| Feedback | Provides immediate feedback | Checks submitted data at the trusted boundary |
| Submissions | Can prevent unnecessary submissions | Must not trust client-provided data |
| Security | Can be bypassed | Must be performed regardless of client checks |

Use both when appropriate. Never rely only on client-side validation.

## 3. HTML Validation Attributes

HTML provides built-in validation features for common requirements.

```tsx
<label htmlFor="email">Email</label>
<input
  id="email"
  name="email"
  type="email"
  required
/>

<label htmlFor="password">Password</label>
<input
  id="password"
  name="password"
  type="password"
  required
  minLength={8}
/>
```

Common attributes:

| Attribute | Purpose |
| --- | --- |
| `required` | Requires a value |
| `minLength` | Sets a minimum text length |
| `maxLength` | Sets a maximum text length |
| `min` / `max` | Sets a numeric or date range, where supported |
| `pattern` | Requires a value to match a pattern |
| `type="email"` | Enables browser email-format validation |
| `type="url"` | Enables browser URL-format validation |

Browser validation is not a replacement for server-side validation. The server must independently check submitted data.

## 4. Form Errors and Submission States

A form should explain what went wrong and how the user can fix it.

A generic message such as `Something went wrong` may be appropriate for an unexpected failure, but it does not explain how to correct an invalid field.

A field-level message is more actionable:

```text
Email
[invalid-email]

Please enter a valid email address.
```

Show validation errors near the relevant fields when possible.
Unexpected failures may need a general form-level message.

### Submission states

A form should communicate when it is being processed:

```text
Before submission:  [Create Account]
During submission:  [Creating...]
After completion:   Show the result
```

Without feedback, users may think nothing happened and submit repeatedly. A pending state communicates progress and can prevent accidental repeated clicks.

### `useFormStatus()`

React provides `useFormStatus()` from `react-dom` to read the submission status of a parent form. It is useful for displaying pending feedback in a submit button.

```tsx
"use client";

import { useFormStatus } from "react-dom";

export function SubmitButton() {
	const { pending } = useFormStatus();

	return (
		<button type='submit' disabled={pending}>
			{pending ? "Creating..." : "Create Account"}
		</button>
	);
}
```

Place the component inside the form whose status it should read:

```tsx
import { createUser } from "./actions";
import { SubmitButton } from "./submit-button";

export default function SignupForm() {
	return (
		<form action={createUser}>
			<input type='email' name='email' required />
			<SubmitButton />
		</form>
	);
}
```

`useFormStatus()` reads the status of a parent form. The Server Action implementation is covered separately.

## 5. Zod and Schema Validation

**Zod** is a TypeScript-first schema validation library. A schema defines the shape of data and the rules the data must satisfy.

```tsx
import { z } from "zod";

const signupSchema = z.object({
	email: z.email(),
	password: z.string().min(8),
});
```

This example uses **Zod v4** syntax. In Zod v3, the email rule is commonly written as `z.string().email()`.

### Validating with `safeParse()`

```tsx
const result = signupSchema.safeParse({
	email: "user@example.com",
	password: "password123",
});

if (result.success) {
	console.log(result.data);
} else {
	console.log(result.error);
}
```

`safeParse()` returns a result indicating whether the data is valid; it does not throw simply because validation failed.

- If `result.success` is `true`, validated data is available in `result.data`.
- If `result.success` is `false`, validation details are available in `result.error`.

### Why use a schema?

A schema keeps related rules together rather than scattering manual checks throughout an application. Benefits include centralized rules, reuse, TypeScript integration, structured errors, and less repetitive code.

Client-side validation can use Zod for immediate feedback. The server must also validate submitted data; client-side checks alone are insufficient.

## 6. React Hook Form

**React Hook Form** is a library for managing forms in React. It provides utilities for registering fields, handling submission, tracking errors, and managing form state.

It is useful for forms with many fields, dynamic inputs, or more involved client-side validation. Standard HTML forms may be enough for simple cases.

```tsx
"use client";

import { useForm } from "react-hook-form";

type LoginFormValues = {
	email: string;
	password: string;
};

export default function LoginForm() {
	const {
		register,
		handleSubmit,
		formState: { errors },
	} = useForm<LoginFormValues>();

	function onSubmit(data: LoginFormValues) {
		console.log(data);
	}

	return (
		<form onSubmit={handleSubmit(onSubmit)}>
			<label htmlFor='email'>Email</label>
			<input
				id='email'
				type='email'
				{...register("email", { required: "Email is required" })}
			/>
			{errors.email && <p role='alert'>{errors.email.message}</p>}

			<label htmlFor='password'>Password</label>
			<input
				id='password'
				type='password'
				{...register("password", { required: "Password is required" })}
			/>
			{errors.password && <p role='alert'>{errors.password.message}</p>}

			<button type='submit'>Login</button>
		</form>
	);
}
```

In this example:

- `register()` connects an input to React Hook Form.
- `handleSubmit()` runs the submission handler after client-side validation succeeds.
- `errors` contains field validation errors.
- `onSubmit()` receives the form values.

This example demonstrates client-side form handling. It does not replace server-side validation or implement a Server Action.

## 7. React Hook Form with Zod

React Hook Form and Zod have different responsibilities:

```text
React Hook Form
    ↓
Manages fields, form state, and submission

Zod
    ↓
Defines and validates data rules
```

They can be integrated using `zodResolver` from `@hookform/resolvers/zod`.

```tsx
"use client";

import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import { z } from "zod";

const loginSchema = z.object({
	email: z.email(),
	password: z.string().min(8, "Password must be at least 8 characters"),
});

type LoginFormValues = z.infer<typeof loginSchema>;

export default function LoginForm() {
	const {
		register,
		handleSubmit,
		formState: { errors },
	} = useForm<LoginFormValues>({
		resolver: zodResolver(loginSchema),
	});

	function onSubmit(data: LoginFormValues) {
		console.log(data);
	}

	return (
		<form onSubmit={handleSubmit(onSubmit)} noValidate>
			<label htmlFor='email'>Email</label>
			<input id='email' type='email' {...register("email")} />
			{errors.email && <p role='alert'>{errors.email.message}</p>}

			<label htmlFor='password'>Password</label>
			<input id='password' type='password' {...register("password")} />
			{errors.password && <p role='alert'>{errors.password.message}</p>}

			<button type='submit'>Login</button>
		</form>
	);
}
```

- `z.object()` defines validation rules.
- `z.infer<typeof loginSchema>` derives a TypeScript type from the schema.
- `zodResolver(loginSchema)` connects Zod validation to React Hook Form.
- `errors` provides messages that can be shown beside fields.

This example handles client-side validation. Submitted data must also be validated on the server. Connecting a form to server-side processing is covered in the Server Actions topic.

## 8. Form Accessibility

Forms should be usable by people who use keyboards and assistive technologies.

### Associate labels with inputs

```tsx
<label htmlFor="email">Email</label>
<input id="email" name="email" type="email" />
```

The label's `htmlFor` value should match the input's `id`. This association helps users identify each field and allows the label to activate the input when clicked.

### Connect error messages to fields

```tsx
<label htmlFor="email">Email</label>
<input
  id="email"
  name="email"
  type="email"
  aria-invalid="true"
  aria-describedby="email-error"
/>
<p id="email-error">
  Please enter a valid email address.
</p>
```

- `aria-invalid` communicates that a field's current value is invalid.
- `aria-describedby` connects the input to descriptive text, such as an error message.

### Accessibility checklist

- Use a visible, meaningful label for each field.
- Give submitted fields appropriate `name` attributes.
- Use suitable input types, such as `email`, `password`, and `date`.
- Show clear error messages near relevant fields.
- Connect field errors with `aria-describedby` where appropriate.
- Use `aria-invalid` when a field is invalid.
- Do not rely only on color to communicate errors.
- Keep keyboard navigation usable.
- Use meaningful button text.

## 9. Best Practices and Common Mistakes

### Best practices

1. **Validate on the server.** Client-provided data must not be trusted.
2. **Use client validation for feedback.** Let users correct mistakes before submission.
3. **Keep validation rules organized.** A schema can help keep rules consistent.
4. **Choose tools based on complexity.** HTML may be enough for simple forms; React Hook Form can help with complex ones.
5. **Show clear errors.** Explain what is wrong and how the user can fix it.
6. **Show submission progress.** Provide a pending state while processing.
7. **Keep forms accessible.** Use labels, meaningful controls, keyboard support, and clear error relationships.

### Common mistakes

**1. Trusting only client-side validation**

Client-side checks can be bypassed. Validate submitted data on the server as well.

**2. Forgetting `name` attributes**

```tsx
<input type='email' />
```

This input has no field name for normal `FormData` submission. Prefer:

```tsx
<input type='email' name='email' />
```

**3. Showing only a generic error**

A message such as `Something went wrong` does not explain how to fix an invalid email. Use a field-level message for validation errors when possible.

**4. Providing no submission feedback**

Show a pending state so users know the form is being processed.

**5. Ignoring accessibility**

Inputs without labels and errors that rely only on color make forms harder to use. Use semantic HTML and accessible error relationships.

**6. Using complex libraries for every form**

A small form may not need React Hook Form. Choose libraries when their features provide value.

## Quick Comparison

| Concept | Purpose |
| --- | --- |
| HTML form | Collects user input |
| `name` attribute | Identifies a field in submitted form data |
| Client-side validation | Provides immediate feedback |
| Server-side validation | Checks submitted data on the server |
| HTML validation attributes | Provide browser-level checks |
| Field-level errors | Explain which field needs correction |
| `useFormStatus()` | Reads the pending status of a parent form |
| Zod | Defines and validates data schemas |
| React Hook Form | Manages form fields, state, errors, and submission |
| React Hook Form + Zod | Combines form management with schema validation |
| Accessibility | Makes forms easier to use with different input methods and assistive technologies |

## Summary

- Forms use standard HTML elements such as `form`, `input`, `label`, and `button`.
- Fields need a `name` attribute to be included under a name in normal form submission.
- The App Router supports connecting forms to Server Actions through the `action` prop; action implementation is covered separately.
- Client-side validation improves user experience, but submitted data must also be validated on the server.
- HTML validation attributes provide useful browser-level checks.
- Clear field-level errors help users correct invalid values.
- `useFormStatus()` can display pending feedback for a parent form's submission.
- Zod defines reusable validation schemas and provides structured validation results.
- React Hook Form manages form state, fields, errors, and submission.
- React Hook Form and Zod can be combined using `zodResolver`.
- Accessible forms use labels, suitable input types, clear error messages, and appropriate ARIA attributes.

### Quick Decision Guide

```text
Need a simple form?
    → Start with standard HTML form elements.

Need basic browser-level checks?
    → Use HTML validation attributes.

Need reusable schema rules?
    → Use Zod.

Need more involved client-side form state?
    → Consider React Hook Form.

Need both form management and schema validation?
    → Combine React Hook Form and Zod.

Need to process submitted data safely?
    → Validate on the server. Server Action implementation is covered in the Server Actions topic.
```

> **Remember:** Client-side validation helps users; server-side validation protects correctness and security. Choose the simplest form approach that meets the application's needs.
