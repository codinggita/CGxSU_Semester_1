# 12. Database, Prisma & PostgreSQL

Examples use a typical e-commerce schema: **categories**, **products**, **orders**, and **order items** linking products to orders.

Models, schemas, and CRUD from Mongoose map directly to **relational databases** (PostgreSQL) and **Prisma** — the ORM Next.js teams use most often.

---

# 1. Database Integration

The application needs persistent storage: product catalog, category hierarchy, customer orders. Route Handlers and Server Actions can start with in-memory arrays; the same entry points connect to a real database once persistence is added.

## Where the database lives in Next.js

```text
Browser (Client Component)
        │
        │  fetch("/api/products")  ← HTTP only, never Prisma
        ▼
Server Action / Route Handler / Server Component
        │
        │  import { prisma } from "@/lib/prisma"
        ▼
Prisma Client  (query builder + type-safe API)
        │
        │  SQL over TCP
        ▼
PostgreSQL  (application data on disk)
```

**Server Components** can call Prisma directly — no Route Handler needed for read-only pages:

```text
app/products/page.tsx  (Server Component)
        │
        │  await prisma.product.findMany()
        ▼
PostgreSQL
```

## Why not browser → database?

- **Credentials**: `DATABASE_URL` contains username and password. Exposing it in the browser would let anyone read, modify, or delete your entire store.
- **Security rules**: PostgreSQL has no concept of "this user can only see their own orders." Your Next.js server enforces auth, validation, and business logic before touching the DB.
- **Connection limits**: PostgreSQL handles a finite number of connections. Thousands of browsers opening direct connections would crash the database.

Every database call runs on the **server** — inside Server Components, Server Actions, Route Handlers, or `lib/services/`.

# 2. PostgreSQL & Schema Fundamentals

## PostgreSQL

MongoDB stores documents in collections. PostgreSQL stores **rows** in **tables**, grouped inside a **database**.

A typical e-commerce PostgreSQL database might contain:

| Table         | What it stores                                     |
| ------------- | -------------------------------------------------- |
| `categories`  | Product groupings (e.g. electronics, accessories)  |
| `products`    | Items for sale — each linked to a category         |
| `orders`      | Customer purchase records with status and total    |
| `order_items` | Line items: which product, how many, at what price |

Example rows in `products`:

| id  | name     | price | stock | category_id |
| --- | -------- | ----- | ----- | ----------- |
| 1   | Laptop   | 49999 | 120   | 1           |
| 2   | Keyboard | 899   | 45    | 2           |
| 3   | Mouse    | 149   | 500   | 3           |

Example rows in `categories`:

| id  | name        | slug        |
| --- | ----------- | ----------- |
| 1   | Electronics | electronics |
| 2   | Accessories | accessories |
| 3   | Peripherals | peripherals |

PostgreSQL is **ACID-compliant**, supports **transactions** (critical for orders), and enforces **relationships** between tables — something you previously handled manually with embedded documents or `ref` fields in Mongoose.

---

## Database Connection

PostgreSQL runs as a server process. Your Next.js app connects via a connection string stored in an environment variable.

```env
# .env  (never commit this file)
DATABASE_URL="postgresql://app_user:secret@localhost:5432/myapp?schema=public"
```

| Part             | Meaning                                    |
| ---------------- | ------------------------------------------ |
| `app_user`       | Database username                          |
| `secret`         | Password                                   |
| `localhost:5432` | Host and port (5432 is PostgreSQL default) |
| `myapp`          | Database name                              |
| `schema=public`  | Default schema (namespace for tables)      |

**Local development** options:

Prisma reads `DATABASE_URL` automatically from `.env` when you run migrations or use Prisma Client.

---

## Database Schema

A **schema** defines the structure of your tables — column names, types, and rules. In MongoDB/Mongoose you define this in a schema file. In PostgreSQL you define it with **SQL DDL** (Data Definition Language).

`products` table:

```sql
CREATE TABLE products (
	id          SERIAL PRIMARY KEY,
	name        VARCHAR(255) NOT NULL,
	slug        VARCHAR(255) NOT NULL,
	description TEXT,
	price       DECIMAL(10, 2) NOT NULL,
	stock       INTEGER NOT NULL DEFAULT 0,
	category_id INTEGER NOT NULL,
	created_at  TIMESTAMP NOT NULL DEFAULT NOW(),
	updated_at  TIMESTAMP NOT NULL DEFAULT NOW()
);
```

`categories` table:

```sql
CREATE TABLE categories (
	id         SERIAL PRIMARY KEY,
	name       VARCHAR(100) NOT NULL,
	slug       VARCHAR(100) NOT NULL UNIQUE,
	created_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```

You won't hand-write all of this SQL day-to-day — Prisma generates it from `schema.prisma`. But understanding the SQL helps when you read migrations, debug queries, or discuss design with a DBA.

---

## Tables, Rows, and Columns

| Relational term | Mongoose equivalent | Example                        |
| --------------- | ------------------- | ------------------------------ |
| Table           | Collection          | `products`                     |
| Row             | Document            | One product record             |
| Column          | Field               | `name`, `price`, `category_id` |

```text
products (TABLE)
├── id          (COLUMN)  →  1, 2, 3 …
├── name        (COLUMN)  →  "Laptop", "Keyboard" …
├── price       (COLUMN)  →  499.00, 899.00 …
└── category_id (COLUMN)  →  1, 2, 3 …

Each horizontal line is one ROW (one product).
```

A row is atomic — you cannot store two product names in the same row. If the app needs multiple prices per product (wholesale vs retail), that becomes a separate table, not an extra column crammed into one cell.

---

## Primary Keys

Every table needs a way to uniquely identify each row. That column (or set of columns) is the **primary key**.

```sql
id SERIAL PRIMARY KEY
```

- `SERIAL` auto-increments: 1, 2, 3 … (like MongoDB's auto-generated `_id`, but numeric and sequential).
- `PRIMARY KEY` enforces uniqueness and creates an index for fast lookups.

```text
products
┌────┬─────────────┬────────┐
│ id │ name        │ price  │  ← id is the primary key
├────┼─────────────┼────────┤
│ 1  │ Laptop      │ 49999  │
│ 2  │ Keyboard    │ 899    │
└────┴─────────────┴────────┘

You cannot insert two rows with id = 1.
```

In Route Handlers, `GET /api/products/5` uses `5` as the primary key to fetch exactly one product.

---

## CRUD Operations

CRUD operations map from Mongoose-style patterns to SQL and the API routes from Backend & API Route Handlers:

| Operation | HTTP / Action            | SQL (simplified)                               | Mongoose equivalent         |
| --------- | ------------------------ | ---------------------------------------------- | --------------------------- |
| Create    | `POST /api/products`     | `INSERT INTO products (…) VALUES (…)`          | `Product.create({…})`       |
| Read all  | `GET /api/products`      | `SELECT * FROM products`                       | `Product.find()`            |
| Read one  | `GET /api/products/5`    | `SELECT * FROM products WHERE id = 5`          | `Product.findById("5")`     |
| Update    | `PUT /api/products/5`    | `UPDATE products SET price = 549 WHERE id = 5` | `Product.findByIdAndUpdate` |
| Delete    | `DELETE /api/products/5` | `DELETE FROM products WHERE id = 5`            | `Product.findByIdAndDelete` |

```sql
-- Create
INSERT INTO products (name, slug, price, stock, category_id)
VALUES ('Laptop', 'laptop', 49999, 120, 1);

-- Read
SELECT id, name, price FROM products WHERE category_id = 1;

-- Update
UPDATE products SET price = 549.00, updated_at = NOW() WHERE id = 1;

-- Delete
DELETE FROM products WHERE id = 1;
```

Prisma translates its API into these SQL statements under the hood.

# 3. Constraints & Relationships

## Constraints

Constraints are rules the database enforces so bad data never enters the database — even if application code has a bug.

### NOT NULL

A column marked `NOT NULL` must have a value on every insert.

```sql
name VARCHAR(255) NOT NULL
```

The database cannot store a product with no name. The database rejects the insert before it reaches your UI.

### UNIQUE

No two rows may share the same value in that column.

```sql
slug VARCHAR(255) NOT NULL UNIQUE
```

Two products cannot both have slug `laptop`. URLs like `/products/laptop` would break otherwise.

### CHECK

Custom validation at the database level.

```sql
price DECIMAL(10, 2) NOT NULL CHECK (price > 0)
stock INTEGER NOT NULL CHECK (stock >= 0)
```

The database rejects a product priced at `-100` or with `-5` stock, even if server validation is bypassed.

### DEFAULT

Used when the caller omits a column.

```sql
stock INTEGER NOT NULL DEFAULT 0
created_at TIMESTAMP NOT NULL DEFAULT NOW()
```

New products start with zero stock unless the admin specifies otherwise.

PRIMARY KEY

Combines `UNIQUE` + `NOT NULL`. One primary key per table. Use a single-column key (`id`) on every table.

### Foreign Key

A **foreign key** links a column in one table to the primary key of another — enforcing that referenced rows actually exist.

Products belong to categories:

```sql
-- categories must exist first
CREATE TABLE categories (
	id   SERIAL PRIMARY KEY,
	name VARCHAR(100) NOT NULL,
	slug VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE products (
	id          SERIAL PRIMARY KEY,
	name        VARCHAR(255) NOT NULL,
	slug        VARCHAR(255) NOT NULL UNIQUE,
	price       DECIMAL(10, 2) NOT NULL,
	stock       INTEGER NOT NULL DEFAULT 0,
	category_id INTEGER NOT NULL,
	CONSTRAINT fk_products_category
		FOREIGN KEY (category_id) REFERENCES categories(id)
		ON DELETE RESTRICT
);
```

```text
categories                    products
┌────┬──────────┐             ┌────┬─────────┬─────────────┐
│ id │ name     │◄────────────│ id │ name    │ category_id │
├────┼──────────┤   FK        ├────┼─────────┼─────────────┤
│ 1  │ Electronics │        │ 1  │ Laptop  │ 1           │  ✓ valid
│ 2  │ Accessories │        │ 2  │ Keyboard│ 2           │  ✓ valid
└────┴──────────┘             │ 3  │ Unknown │ 99          │  ✗ rejected
                              └────┴─────────┴─────────────┘
```

What foreign keys prevent:

- Inserting a product with `category_id = 99` when category 99 does not exist
- Orphan rows that reference deleted parents (depending on `ON DELETE` behavior)

**ON DELETE options:**

| Option     | Behavior when parent row is deleted                         |
| ---------- | ----------------------------------------------------------- |
| `RESTRICT` | Reject the delete if children exist (safest for categories) |
| `CASCADE`  | Delete all child rows automatically                         |
| `SET NULL` | Set foreign key column to NULL (column must allow NULL)     |

Use `RESTRICT` on `products.category_id → categories.id` so you cannot delete a category while products still reference it.

Order items reference both orders and products:

```sql
CREATE TABLE order_items (
	id         SERIAL PRIMARY KEY,
	order_id   INTEGER NOT NULL,
	product_id INTEGER NOT NULL,
	quantity   INTEGER NOT NULL CHECK (quantity > 0),
	price      DECIMAL(10, 2) NOT NULL,
	CONSTRAINT fk_order_items_order
		FOREIGN KEY (order_id) REFERENCES orders(id) ON DELETE CASCADE,
	CONSTRAINT fk_order_items_product
		FOREIGN KEY (product_id) REFERENCES products(id) ON DELETE RESTRICT
);
```

In Mongoose you'd use `ref: 'Category'` and `.populate()`. In PostgreSQL the database itself guarantees the link — not just your application code.

---

## Relationships

Relational databases express entity relationships through foreign keys and junction tables.

### One-to-One

One row in table A relates to exactly one row in table B.

Example: a `Product` and an optional `ProductInventory` detail record (warehouse aisle, reorder threshold). Uncommon; often merged into the product row unless the detail is large or sensitive.

```text
products (1) ────── (1) product_inventory
```

### One-to-Many

One category has many products. Each product belongs to **one** category.

```text
categories (1) ──────< (many) products

categories.id  ←──  products.category_id
```

Mongoose equivalent: either embed an array of product IDs on the category document, or store `categoryId` on each product with `.populate('category')`.

SQL query — all products in a category:

```sql
SELECT p.*
FROM products p
JOIN categories c ON p.category_id = c.id
WHERE c.slug = 'electronics';
```

### Many-to-Many

Orders contain multiple products. A product appears in many orders. You cannot put an array of product IDs on the order row (PostgreSQL doesn't work that way) — you use a **junction table**.

```text
orders (many) ───< order_items >─── (many) products
```

```text
orders                order_items              products
┌────┬────────┐      ┌────┬─────────┬────────────┐     ┌────┬────────┐
│ id │ total  │      │ id │ order_id│ product_id │     │ id │ name   │
├────┼────────┤      ├────┼─────────┼────────────┤     ├────┼────────┤
│ 1  │ 1398   │      │ 1  │ 1       │ 1          │────►│ 1  │ Laptop │
│ 2  │ 149    │      │ 2  │ 1       │ 2          │────►│ 2  │ Keyboard │
└────┴────────┘      │ 3  │ 2       │ 3          │────►│ 3  │ Mouse  │
                     └────┴─────────┴────────────┘     └────┴────────┘
```

Each `order_items` row stores `quantity` and the **price at time of purchase** — so a future price change on the product doesn't rewrite order history.

# 4. Indexes, Transactions & ACID

## Indexes

An **index** is a lookup structure — like a book's index — that speeds up queries on specific columns.

```sql
CREATE INDEX idx_products_category_id ON products(category_id);
```

Without an index, `SELECT * FROM products WHERE category_id = 2` scans every row. With 100,000 products, that is slow. With an index, PostgreSQL jumps directly to matching rows.

Common indexes worth having:

| Index                   | Speeds up                              |
| ----------------------- | -------------------------------------- |
| `products(category_id)` | Filter products by category            |
| `products(slug)`        | Lookup `/products/laptop` by slug      |
| `order_items(order_id)` | Load all items for an order            |
| `orders(created_at)`    | Sort orders by date on admin dashboard |

Trade-off: indexes speed reads but slightly slow writes (each insert/update must update the index too). Index columns you filter or sort on frequently — not every column.

---

## Unique Indexes

A **unique index** enforces uniqueness and accelerates lookups simultaneously.

```sql
CREATE UNIQUE INDEX idx_products_slug ON products(slug);
CREATE UNIQUE INDEX idx_categories_slug ON categories(slug);
```

Equivalent to `UNIQUE` on the column definition. Use unique slugs for SEO-friendly URLs: `/categories/electronics`, `/products/laptop`.

Attempting to insert a second product with slug `laptop`:

```text
ERROR: duplicate key value violates unique constraint "idx_products_slug"
```

Prisma surfaces this as a `PrismaClientKnownRequestError` with code `P2002`.

---

## Transactions

A **transaction** groups multiple SQL statements into one atomic unit: **all succeed, or all fail**.

When a customer checks out, three things must happen together:

1. Create an `orders` row
2. Create one or more `order_items` rows
3. Decrement `stock` on each purchased product

If step 3 fails halfway, you must not leave an order with wrong stock counts.

```sql
BEGIN;

INSERT INTO orders (status, total) VALUES ('PENDING', 1398.00);
-- assume returned id = 10

INSERT INTO order_items (order_id, product_id, quantity, price)
VALUES (10, 1, 2, 499.00);

INSERT INTO order_items (order_id, product_id, quantity, price)
VALUES (10, 2, 1, 400.00);

UPDATE products SET stock = stock - 2 WHERE id = 1;
UPDATE products SET stock = stock - 1 WHERE id = 2;

COMMIT;
```

If any statement fails:

```sql
ROLLBACK;  -- undo everything since BEGIN
```

Without transactions, the app could charge a customer, create the order, but fail to reduce stock — leading to overselling.

---

## ACID Properties

Transactions guarantee **ACID**:

| Property    | Meaning                                  | Example scenario                              |
| ----------- | ---------------------------------------- | --------------------------------------------- |
| Atomicity   | All or nothing                           | Order + items + stock update succeed together |
| Consistency | DB moves from valid state to valid state | Foreign keys still valid after checkout       |
| Isolation   | Concurrent transactions don't interfere  | Two customers buying the last unit in stock   |
| Durability  | Committed data survives crashes          | Order survives server restart                 |

MongoDB added multi-document transactions in v4.0, but in PostgreSQL they are foundational — not an afterthought. Checkout logic in e-commerce apps relies on them.

# 5. Prisma Setup & Schema

## Prisma

**Prisma** is a TypeScript-first ORM for Node.js. It replaces hand-written SQL and raw drivers with a type-safe API generated from your schema.

### Mongoose ↔ Prisma comparison

| Concept              | Mongoose                          | Prisma                                         |
| -------------------- | --------------------------------- | ---------------------------------------------- |
| Schema + Model       | `productSchema` + `Product` model | `model Product { … }` in `schema.prisma`       |
| Create               | `Product.create({ name, price })` | `prisma.product.create({ data: { … } })`       |
| Read many            | `Product.find({ category: id })`  | `prisma.product.findMany({ where: { … } })`    |
| Read one             | `Product.findById(id)`            | `prisma.product.findUnique({ where: { id } })` |
| Update               | `Product.findByIdAndUpdate(…)`    | `prisma.product.update({ where, data })`       |
| Delete               | `Product.findByIdAndDelete(id)`   | `prisma.product.delete({ where: { id } })`     |
| Relations / populate | `.populate('category')`           | `include: { category: true }`                  |
| Validation           | Schema validators in Mongoose     | DB constraints + Zod in your app layer         |
| Migrations           | No built-in (schemaless)          | `prisma migrate dev` generates SQL files       |
| GUI                  | MongoDB Compass                   | `npx prisma studio`                            |

Prisma does **not** store nested documents. Related data lives in separate tables and you join via `include` or separate queries.

## Prisma Schema

A full e-commerce schema with all models, relations, and indexes:

```prisma
// prisma/schema.prisma

generator client {
	provider = "prisma-client-js"
}

datasource db {
	provider = "postgresql"
	url      = env("DATABASE_URL")
}

model Category {
	id        Int       @id @default(autoincrement())
	name      String    @db.VarChar(100)
	slug      String    @unique @db.VarChar(100)
	createdAt DateTime  @default(now()) @map("created_at")
	products  Product[]

	@@map("categories")
}

model Product {
	id          Int         @id @default(autoincrement())
	name        String      @db.VarChar(255)
	slug        String      @unique @db.VarChar(255)
	description String?     @db.Text
	price       Decimal     @db.Decimal(10, 2)
	stock       Int         @default(0)
	categoryId  Int         @map("category_id")
	createdAt   DateTime    @default(now()) @map("created_at")
	updatedAt   DateTime    @updatedAt @map("updated_at")
	category    Category    @relation(fields: [categoryId], references: [id], onDelete: Restrict)
	orderItems  OrderItem[]

	@@index([categoryId])
	@@map("products")
}

model Order {
	id        Int         @id @default(autoincrement())
	status    OrderStatus @default(PENDING)
	total     Decimal     @db.Decimal(10, 2)
	createdAt DateTime    @default(now()) @map("created_at")
	items     OrderItem[]

	@@index([createdAt])
	@@map("orders")
}

model OrderItem {
	id        Int     @id @default(autoincrement())
	orderId   Int     @map("order_id")
	productId Int     @map("product_id")
	quantity  Int
	price     Decimal @db.Decimal(10, 2)
	order     Order   @relation(fields: [orderId], references: [id], onDelete: Cascade)
	product   Product @relation(fields: [productId], references: [id], onDelete: Restrict)

	@@index([orderId])
	@@index([productId])
	@@map("order_items")
}

enum OrderStatus {
	PENDING
	CONFIRMED
	SHIPPED
	DELIVERED
	CANCELLED
}
```

Key mapping notes:

- `@@map("products")` — Prisma model `Product`, SQL table `products`
- `@map("category_id")` — Prisma field `categoryId`, SQL column `category_id`
- `@relation` — defines the foreign key Prisma generates in migrations
- `onDelete: Restrict` / `Cascade` — matches the SQL foreign key behavior from **Constraints → Foreign Key**

---

## Model Fields

Using the `Product` model to explain field types:

```prisma
model Product {
	id          Int         @id @default(autoincrement())
	name        String      @db.VarChar(255)
	slug        String      @unique @db.VarChar(255)
	description String?     @db.Text
	price       Decimal     @db.Decimal(10, 2)
	stock       Int         @default(0)
	categoryId  Int         @map("category_id")
	createdAt   DateTime    @default(now()) @map("created_at")
	updatedAt   DateTime    @updatedAt @map("updated_at")
	category    Category    @relation(fields: [categoryId], references: [id])
	orderItems  OrderItem[]
}
```

| Prisma type / attribute         | SQL equivalent           | Typical usage                       |
| ------------------------------- | ------------------------ | ----------------------------------- |
| `Int`                           | `INTEGER`                | ids, stock counts                   |
| `String`                        | `VARCHAR` / `TEXT`       | name, slug, description             |
| `String?`                       | nullable `TEXT`          | optional description                |
| `Decimal`                       | `DECIMAL(10,2)`          | price — never use `Float` for money |
| `DateTime`                      | `TIMESTAMP`              | createdAt, updatedAt                |
| `@id @default(autoincrement())` | `SERIAL PRIMARY KEY`     | product id                          |
| `@unique`                       | `UNIQUE` constraint      | slug                                |
| `@default(0)`                   | `DEFAULT 0`              | initial stock                       |
| `@updatedAt`                    | auto-set on update       | tracks last modification            |
| `@relation(…)`                  | `FOREIGN KEY`            | links to Category                   |
| `Category` (type)               | join to categories table | nested reads via `include`          |
| `OrderItem[]`                   | reverse relation         | all order lines for this product    |

**Money rule:** always `Decimal` for `price` and `total`. Floating-point rounding errors would corrupt checkout totals.

## Migrations

Migrations are version-controlled SQL files that evolve your schema over time.

```bash
npx prisma migrate dev --name init_ecommerce
```

Prisma compares `schema.prisma` to the database, generates SQL, applies it, and saves a migration folder:

```text
prisma/
├── schema.prisma
└── migrations/
```

## Why Migrations Matter

In MongoDB, schema changes are often informal — add a field, backfill with a script, hope old documents cope. In PostgreSQL + Prisma, schema changes are **explicit, ordered, and replayable**.

| Without migrations           | With migrations                           |
| ---------------------------- | ----------------------------------------- |
| "Works on my machine" schema | Same SQL applied on every environment     |
| Manual ALTER on production   | Reviewed migration files in git           |
| Team members out of sync     | `prisma migrate dev` pulls latest         |
| No rollback story            | Migration history + down scripts (manual) |

Typical workflow when adding a `sku` column to products:

1. Add `sku String? @unique` to `Product` in `schema.prisma`
2. Run `npx prisma migrate dev --name add_product_sku`
3. Commit the migration folder alongside your code
4. CI/production runs `npx prisma migrate deploy`

Never use `prisma db push` in production — it skips migration history. Use it only for quick local prototyping.

## Prisma Client

Prisma Client is the generated, type-safe query API. Create a **singleton** so Next.js hot reload doesn't spawn hundreds of connections.

```ts
// lib/prisma.ts

import { PrismaClient } from "@prisma/client";

const globalForPrisma = globalThis as unknown as {
	prisma: PrismaClient | undefined;
};

export const prisma =
	globalForPrisma.prisma ??
	new PrismaClient({
		log:
			process.env.NODE_ENV === "development"
				? ["query", "error", "warn"]
				: ["error"],
	});

if (process.env.NODE_ENV !== "production") {
	globalForPrisma.prisma = prisma;
}
```

Import this everywhere — never `new PrismaClient()` in Route Handlers or components:

```ts
import { prisma } from "@/lib/prisma";
```

After schema changes, always run `npx prisma generate` so TypeScript types match your models.

## Update

`update` throws if the row doesn't exist (`P2025`). Use `updateMany` when you don't care about the returned row:

## Delete

```ts

	where: { id: 1 },

	where: { categoryId: 99 },
```

- Deleting a category with products → `RESTRICT` error
- Deleting an order → `CASCADE` removes its order items

Handle Prisma errors in Route Handlers:

```ts
import { Prisma } from "@prisma/client";

try {
	await prisma.product.delete({ where: { id: Number(id) } });
	return new Response(null, { status: 204 });
} catch (error) {
	if (
		error instanceof Prisma.PrismaClientKnownRequestError &&
		error.code === "P2003"
	) {
		return Response.json(
			{ error: "Cannot delete — product is referenced by orders" },
			{ status: 409 },
		);
	}
	throw error;
}
```

Common filter operators:

| Operator             | Meaning             | Example                             |
| -------------------- | ------------------- | ----------------------------------- |
| `equals`             | exact match         | `{ status: { equals: "PENDING" } }` |

| `AND` / `OR` / `NOT` | logical combos      | nested `OR` example                 |

```ts
const complex = await prisma.product.findMany({

		OR: [
			{ category: { slug: "electronics" } },
			{ category: { slug: "accessories" } },
		],
		AND: [{ stock: { gt: 0 } }, { price: { lt: 1000 } }],
	},
});
```

Filter on related models with nested `where` — no manual join syntax.

# 7. Prisma Relations & Advanced

## Relations

Relations in `schema.prisma` mirror the **Relationships** model:

```text
Category (1) ───< Product (many)     via Product.categoryId
Order (1) ───< OrderItem (many)      via OrderItem.orderId
Product (1) ───< OrderItem (many)    via OrderItem.productId
Order >───< Product                  many-to-many through OrderItem
```

Prisma relation fields:

| Field on model | Type          | Role                            |
| -------------- | ------------- | ------------------------------- |
| `categoryId`   | `Int`         | Foreign key column (scalar)     |
| `category`     | `Category`    | Relation field for nested reads |
| `products`     | `Product[]`   | Reverse relation from Category  |
| `orderItems`   | `OrderItem[]` | Reverse relation from Product   |

You write to scalar FK fields (`categoryId`). You read related data through relation fields (`category`, `items`).

## Querying Relations

Mongoose `.populate('category')` → Prisma `include`:

```ts

		category: true,

// Result shape:
// {
//   id: 1,
//   name: "Laptop",
//   price: 499,
//   categoryId: 1,
//   category: { id: 1, name: "Electronics", slug: "electronics" }
// }
```

Select specific fields to reduce payload:

```ts

	include: {
		category: {
			select: { name: true, slug: true },
		},
	},
});
```

Categories with all their products:

```ts
const categories = await prisma.category.findMany({
	include: {
		products: {
			where: { stock: { gt: 0 } },
			orderBy: { price: "asc" },
		},
	},
});
```

> **⚠️ N+1 Query Problem**
>
> Loading 100 products and then calling `prisma.category.findUnique()` inside a loop for each one = **101 queries**. Always use `include` or a single `findMany` with nested relations.
>
> ```ts
> // ❌ N+1 — one query per product
> const products = await prisma.product.findMany();
> for (const p of products) {
> 	p.category = await prisma.category.findUnique({
> 		where: { id: p.categoryId },
> 	});
> }
>
> // ✅ One query with JOIN
> const products = await prisma.product.findMany({
> 	include: { category: true },
> });
> ```

Prisma logs in development (`log: ["query"]`) help you spot N+1 issues — watch for repeated identical queries in the console.

## Transactions

Nested creates work for simple checkout. When you also need to **decrement stock** atomically, use `$transaction`:

```ts
// lib/services/order.service.ts

import { prisma } from "@/lib/prisma";

type CartItem = { productId: number; quantity: number };

export async function placeOrder(items: CartItem[]) {
	return prisma.$transaction(async (tx) => {
		// 1. Validate stock and calculate total
		let total = 0;
		const lineItems: {
			productId: number;
			quantity: number;
			price: number;
		}[] = [];

		for (const item of items) {
			const product = await tx.product.findUniqueOrThrow({
				where: { id: item.productId },
			});

			if (product.stock < item.quantity) {
				throw new Error(`Insufficient stock for ${product.name}`);
			}

			const price = Number(product.price);
			total += price * item.quantity;
			lineItems.push({
				productId: item.productId,
				quantity: item.quantity,
				price: price,
			});
		}

		// 2. Create order with items
		const order = await tx.order.create({
			data: {
				status: "CONFIRMED",
				total,
				items: {
					create: lineItems,
				},
			},
			include: { items: true },
		});

		// 3. Decrement stock for each product
		for (const item of lineItems) {
			await tx.product.update({
				where: { id: item.productId },
				data: { stock: { decrement: item.quantity } },
			});
		}

		return order;
	});
}
```

If any step throws, Prisma rolls back the entire transaction — no partial orders, no incorrect stock.

Batch independent writes with array form:

```ts
await prisma.$transaction([
	prisma.product.update({
		where: { id: 1 },
		data: { stock: { decrement: 2 } },
	}),
	prisma.product.update({
		where: { id: 2 },
		data: { stock: { decrement: 1 } },
	}),
]);
```

Use interactive transactions (callback form) when later steps depend on earlier results — like e-commerce checkout.

## Indexes in Schema

Define indexes in `schema.prisma` — Prisma generates them in migrations:

```prisma
model Product {
	// …
	categoryId Int @map("category_id")

	@@index([categoryId])
	@@index([price])
	@@map("products")
}

model Order {
	// …
	createdAt DateTime @default(now()) @map("created_at")

	@@index([createdAt])
	@@map("orders")
}
```

`@unique` on `slug` creates a unique index automatically.

Add an index when:

- You filter (`WHERE category_id = ?`) or sort (`ORDER BY created_at`) on a column frequently
- A query is slow in production logs

Don't index every column — writes get slower and disk usage grows.

---

## Constraints in Schema

Prisma enforces constraints through schema attributes — migrated to PostgreSQL:

```prisma
model Product {
	id     Int     @id @default(autoincrement())
	name   String  @db.VarChar(255)       // NOT NULL (no ?)
	slug   String  @unique                // UNIQUE
	price  Decimal @db.Decimal(10, 2)     // NOT NULL
	stock  Int     @default(0)            // NOT NULL + DEFAULT

	categoryId Int @map("category_id")
	category   Category @relation(fields: [categoryId], references: [id], onDelete: Restrict)
}

model OrderItem {
	quantity Int @db.SmallInt   // use appropriate integer size

	order   Order   @relation(fields: [orderId], references: [id], onDelete: Cascade)
	product Product @relation(fields: [productId], references: [id], onDelete: Restrict)
}
```

Prisma error codes to handle:

| Code    | Meaning                          | Example                              |
| ------- | -------------------------------- | ------------------------------------ |
| `P2002` | Unique constraint failed         | Duplicate product slug               |
| `P2003` | Foreign key constraint failed    | Invalid categoryId on product create |
| `P2025` | Record not found (update/delete) | Deleting non-existent product        |

App-layer validation (Zod) catches user mistakes early. DB constraints catch bugs, race conditions, and bypassed validation — **use both**.

# 10. Database Design Rules

Inline Route Handler examples keep Prisma calls in the handler for clarity. Once the application grows, move queries into `lib/services/` — same separation you already use with Express controllers/services; only the folder names change.

Single checklist for any Next.js + Prisma project.

## Schema constraints

- Enforce `NOT NULL`, `UNIQUE`, and foreign keys in the schema — not only in application code
- Use `Decimal` for money (`price`, `total`) — never `Float`
- Store snapshot prices on `OrderItem` — never rely on live `Product.price` for historical orders
- Use `onDelete: Restrict` for references you must not orphan; `Cascade` only when children have no meaning without the parent

## Transaction rules

- Wrap multi-step writes (order + items + stock) in `prisma.$transaction`
- Validate stock inside the transaction — not before it — to prevent race conditions

## Credentials and security

- Keep `DATABASE_URL` in `.env` — add `.env` to `.gitignore`
- Never import `prisma` in Client Components or expose connection strings in API responses
- Use connection pooling in production (Neon/Supabase pooler URL, or PgBouncer)

## Migration workflow

- Commit migration folders to git
- Run `prisma migrate deploy` in CI/production — not `db push`
- Run `prisma generate` after every schema change

## Project structure

```text
lib/
├── prisma.ts              ← singleton client
└── services/
    ├── product.service.ts
    ├── category.service.ts
    └── order.service.ts

prisma/
├── schema.prisma
├── seed.ts
└── migrations/

app/
├── products/page.tsx      ← Server Component → service
├── api/products/route.ts  ← Route Handler → service
└── actions/order.actions.ts ← Server Action → service
```

Route Handlers, Server Actions, and Server Components stay thin. All Prisma queries live in `lib/services/`.

# Summary

## Final Mental Model

You came from Mongoose documents and collections. A typical Next.js app on PostgreSQL + Prisma looks like this:

```text
┌─────────────────────────────────────────────────────────────────┐
│                        NEXT.JS APPLICATION                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   Client Component ──fetch──► Route Handler                     │
│                                    │                            │
│   Server Component ────────────────┤                            │
│                                    │                            │
│   Server Action ───────────────────┤                            │
│                                    ▼                            │
│                          lib/services/*.ts                      │
│                          (business logic)                       │
│                                    │                            │
│                                    ▼                            │
│                          lib/prisma.ts                          │
│                          (singleton client)                     │
│                                    │                            │
│                                    ▼                            │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │                     PostgreSQL                          │   │
│   │  categories ◄── products ◄── order_items ──► orders    │   │
│   │       │              │              │                   │   │
│   │    slug, name    price, stock   qty, price@purchase     │   │
│   └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│   prisma/schema.prisma  ──migrate──►  SQL tables + constraints  │
│   prisma db seed        ──seed───►    starter categories/products│
│   prisma studio         ──GUI────►    inspect & edit data       │
└─────────────────────────────────────────────────────────────────┘
```

**Mongoose mental model → Prisma mental model:**

| You used to think…              | Now think…                                  |
| ------------------------------- | ------------------------------------------- |
| Collection of documents         | Table of rows with fixed columns            |
| Embedded array of refs          | Junction table (`order_items`) or FK column |
| `.populate('category')`         | `include: { category: true }`               |
| Flexible schema, migrate ad hoc | `schema.prisma` + versioned migrations      |
| `Product.create()`              | `prisma.product.create({ data: { … } })`    |
| MongoDB Compass                 | `npx prisma studio`                         |

The data layer is relational, typed, and migrated. Your Next.js server owns every database call. Prisma translates TypeScript into SQL. PostgreSQL guarantees integrity at checkout time.

With Prisma and PostgreSQL, your in-memory arrays from Route Handlers can now persist in a production-grade database.
