# 06. Data Fetching & UI States

Modern Next.js applications often need to:

- Fetch data from APIs
- Fetch data from databases
- Show loading states
- Handle errors
- Show a not-found page
- Stream UI as data becomes available

The App Router provides several built-in patterns for handling these situations.

A typical request can look like:

```text
User visits page
      ↓
Fetch data
      ↓
┌───────────────┐
│ Loading state │
└───────────────┘
      ↓
Data received
      ↓
Render UI
```

If something goes wrong:

```text
Fetch data
    ↓
Error
    ↓
Error UI
```

If the requested resource does not exist:

```text
Request resource
      ↓
Not found
      ↓
404 UI
```

---

# Data Fetching

## Overview

**Data fetching** means retrieving data required by a page or component.

Data can come from:

```text
External API
Database
Internal service
File / CMS
```

For example:

```text
Next.js Application
        ↓
Products API
        ↓
Product Data
        ↓
UI
```

In the App Router, Server Components are the preferred place for many initial data-fetching operations.

The page:

1. Runs on the server.
2. Fetches the products.
3. Receives the data.
4. Renders the UI.

When a page needs data from **multiple independent sources**, you can fetch them in two ways — on both the server and the client:

**Sequential fetch** — run one request, wait for it to finish, then run the next. Total wait time is the **sum** of all requests. Use this when one fetch depends on the result of another (e.g. fetch a user ID first, then fetch that user's orders).

**Parallel fetch** — start all independent requests at the same time and wait for all to complete. Use `Promise.all([...])` or a data-fetching library. Total wait time is roughly the **slowest** single request — not the sum of all.

```text
Sequential:  API 1 ──► wait ──► API 2 ──► wait ──► done
Parallel:     API 1 ──┐
              API 2 ──┼──► wait ──► done
              API 3 ──┘
```

Use parallel fetching when the data sources do **not** depend on each other. Code examples appear under **Server Side** and **Client Side**.

---

## Server-Side vs Client-Side Data Fetching

| Server-Side Fetching             | Client-Side Fetching                 |
| -------------------------------- | ------------------------------------ |
| Runs on the server               | Runs in the browser                  |
| Good for initial page data       | Good for interactive data            |
| Can access server-only resources | Can use browser APIs                 |
| Can keep secrets on the server   | Cannot safely contain server secrets |
| Often uses Server Components     | Usually uses Client Components       |
| Useful for database access       | Useful for browser-driven updates    |

Simple rule:

```text
Initial page data
       ↓
Prefer Server-side fetching

Interactive / browser-driven data
       ↓
Consider Client-side fetching
```

---

### Server Side

#### Data Fetching with Route Parameters (`params`)

Dynamic routes pass **route parameters** from the URL path — for example `/products/25` maps to `app/products/[id]/page.tsx` with `id

Route parameters come from the **path**, not the query string.

A Server Component page receives `params` as a prop:

```tsx
// app/products/[id]/page.tsx

export default async function ProductPage({
	params,
}: {
	params: { id: string };
}) {
	const { id } = await params;

	const response = await fetch(`https://fakestoreapi.com/products/${id}`);
	const product = await response.json();

	return (
		<div>
			<h1>{product.title}</h1>
			<p>{product.price}</p>
		</div>
	);
}
```

---

#### Data Fetching with Query Parameters

Data can depend on search parameters.

For example:

```text
/products?category=electronics
```

A Server Component page receives `searchParams` as a prop and can fetch using that value on the server:

```tsx
type Props = {
	searchParams: Promise<{
		category?: string;
	}>;
};

export default async function ProductsPage({ searchParams }: Props) {
	const { category } = await searchParams;

	const response = await fetch(
		category
			? `https://fakestoreapi.com/products/category/${category}`
			: "https://fakestoreapi.com/products",
	);

	const products = await response.json();

	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

> Using `searchParams` in a page triggers **dynamic rendering**.

---

### Client Side

#### Data Fetching with Route Parameters (`params`)

On the client, read route parameters with `useParams` and fetch when the segment changes:

```tsx
"use client";

import { useParams } from "next/navigation";
import { useEffect, useState } from "react";

export default function ProductPage() {
	const params = useParams();
	const id = params.id as string;
	const [product, setProduct] = useState<{
		title: string;
		price: number;
	} | null>(null);

	useEffect(() => {
		fetch(`https://fakestoreapi.com/products/${id}`)
			.then((res) => res.json())
			.then(setProduct);
	}, [id]);

	if (!product) return <p>Loading...</p>;

	return (
		<div>
			<h1>{product.title}</h1>
			<p>{product.price}</p>
		</div>
	);
}
```

When the user navigates from `/products/25` to `/products/30`, `id` updates and `useEffect` refetches.

#### Data Fetching with Query Parameters

On the client, read query parameters with `useSearchParams` and fetch when they change:

```tsx
"use client";

import { useSearchParams } from "next/navigation";
import { useEffect, useState } from "react";

export default function ProductsPage() {
	const searchParams = useSearchParams();
	const category = searchParams.get("category");
	const [products, setProducts] = useState([]);

	useEffect(() => {
		const url = category
			? `https://fakestoreapi.com/products/category/${category}`
			: "https://fakestoreapi.com/products";

		fetch(url)
			.then((res) => res.json())
			.then(setProducts);
	}, [category]);

	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

When the user changes the category in the URL, `category` updates and `useEffect` refetches the data.

> `useSearchParams()` is a Client Component hook. Wrap the component in `<Suspense>` if the route is statically rendered — see Routing and Navigation (Routing and Navigation).

# UI States

# 1. Loading State

Data fetching can take time.

Instead of showing a blank page, provide feedback to the user:

```text
Loading...
```

A good loading UI tells users that the application is working.

Loading states are especially important for:

- Slow APIs
- Database queries
- Large pages
- Navigation between routes
- Streaming content

---

## `loading.tsx`

The App Router provides a special file:

```text
loading.tsx
```

It is used to create a loading UI for a route segment.

Example file structure:

```text
app/
└── products/
    ├── page.tsx
    └── loading.tsx
```

`loading.tsx`:

```tsx
export default function Loading() {
	return <p>Loading products...</p>;
}
```

When the products route is loading, Next.js can display this UI while the page content is being prepared.

### Full Example

Project:

```text
app/
├── page.tsx
└── products/
    ├── page.tsx
    └── loading.tsx
```

`page.tsx`:

```tsx
export default async function ProductsPage() {
	const response = await fetch("https://fakestoreapi.com/products");

	const products = await response.json();

	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

`loading.tsx`:

```tsx
export default function Loading() {
	return <p>Loading products...</p>;
}
```

Conceptually:

```text
/products → loading.tsx → Data fetching → page.tsx
```

---

## Route-Level Loading UI

A `loading.tsx` file applies to **its route segment and all child segments** — unless a child segment defines its own `loading.tsx`.

For example:

```text
app/
├── loading.tsx          ← applies to / and all children without their own loading.tsx
├── page.tsx
│
└── dashboard/
    ├── loading.tsx      ← overrides parent for /dashboard and its children
    └── page.tsx
```

There can be:

```text
Global loading UI     → app/loading.tsx
Dashboard loading UI  → app/dashboard/loading.tsx
```

This allows different sections to have different loading experiences.

---

## Suspense

React's `<Suspense>` displays fallback UI when a component inside its boundary **suspends while rendering**. In Next.js, it is useful for loading a slow, independent section without making the whole page wait.

Example with an async Server Component:

```tsx
import { Suspense } from "react";

async function Reviews() {
	const response = await fetch("https://example.com/api/reviews");
	const reviews = await response.json();

	return <div>{/* render reviews */}</div>;
}

export default function ProductPage() {
	return (
		<div>
			<h1>Product Details</h1>

			<Suspense fallback={<p>Loading reviews...</p>}>
				<Reviews />
			</Suspense>
		</div>
	);
}
```

While `Reviews` is waiting for its data, the fallback can appear. When the data is ready, React renders the reviews in its place. The product details can render independently because they are outside the boundary.

### Suspense with Client Components

`<Suspense>` also works with Client Components, but the component must use a Suspense-compatible feature, such as React's `use()` reading a pending Promise or a Suspense-enabled data-fetching library.

A normal fetch inside `useEffect()` does **not** trigger the Suspense fallback automatically. For that pattern, manage loading with state, such as `useState`.

| Pattern                                                  | Does Suspense show its fallback automatically? |
| -------------------------------------------------------- | ---------------------------------------------- |
| Async Server Component awaiting data inside the boundary | Yes, while it suspends                         |
| Client Component using `use()` with a pending Promise    | Yes                                            |
| Client Component fetching inside `useEffect()`           | No                                             |
| Client Component using `useState` for loading            | No; render its loading UI from state           |

### `loading.tsx` vs Suspense

- **`loading.tsx`**: Next.js route-segment loading UI, useful while a route segment is being prepared.
- **`<Suspense>`**: React loading boundary for a specific part of a page; useful for independently loading sections.

```text
Loading UI
├── Route-level      → loading.tsx
└── Section-level    → Suspense
```

Do not think of it as “`loading.tsx` is for the server and Suspense is for the client.” Both server and client rendering can use Suspense; what matters is whether the component suspends.

# 2. Error Handling

Data fetching can fail.

Examples:

```text
API unavailable
Database error
Network failure
Invalid response
Unexpected server error
```

Applications should provide useful error UI instead of showing a broken page.

Next.js provides:

```text
error.tsx
```

for route-level error handling.

---

# 3. `error.tsx`

An `error.tsx` file creates an error UI for a route segment.

Example file structure:

```text
app/
└── products/
    ├── page.tsx
    └── error.tsx
```

`error.tsx`:

```tsx
"use client";

export default function ErrorPage({
	error,
	reset,
}: {
	error: Error & { digest?: string };
	reset: () => void;
}) {
	return (
		<div>
			<h2>Something went wrong!</h2>

			<button onClick={() => reset()}>Try again</button>
		</div>
	);
}
```

> **Gotcha:** `error.tsx` does **not** catch errors thrown in the **root layout** (`app/layout.tsx`). For errors in the root layout, use `global-error.tsx` at `app/global-error.tsx` — it must include its own `<html>` and `<body>` tags.

---

# 4. Why `error.tsx` Is a Client Component

An error boundary needs client-side behavior such as:

```tsx
reset();
```

and often an interactive button.

Therefore, `error.tsx` must be a Client Component:

```tsx
"use client";
```

This allows the error UI to respond to user actions.

---

# 5. Error Boundaries

An **Error Boundary** catches errors that happen while rendering a part of the application and displays fallback UI instead.

Conceptually:

```text
Route
  │
  ├── Page
  │
  └── Error Boundary
          ↓
       Error?
        /   \
      No     Yes
      ↓       ↓
    Page    error.tsx
```

In Next.js, the special `error.tsx` file is used to create a route-level error boundary.

## Error Flow Example

Suppose:

```tsx
export default async function ProductsPage() {
	const response = await fetch("https://fakestoreapi.com/products");

	if (!response.ok) {
		throw new Error("Failed to fetch products");
	}

	const products = await response.json();

	return <div>Products...</div>;
}
```

If the request fails:

```text
fetch() → Error thrown → Error Boundary → error.tsx → Error UI
```

The user can see:

```text
Something went wrong!

[Try again]
```

instead of an unhandled error page.

---

# 6. `reset()` in `error.tsx`

The `reset()` function can be used to retry rendering the affected route segment.

Example:

```tsx
"use client";

export default function Error({ reset }: { reset: () => void }) {
	return (
		<div>
			<h2>Something went wrong.</h2>

			<button onClick={() => reset()}>Try again</button>
		</div>
	);
}
```

When the user clicks **Try again**, Next.js attempts to re-render the affected route segment.

# 7. `not-found.tsx`

Sometimes there is no error, but the requested resource simply does not exist.

For example:

```text
/products/123
```

If product `123` does not exist, the application should show a 404-style page.

Next.js provides:

```text
not-found.tsx
```

for this purpose.

Example file structure:

```text
app/
└── products/
    └── [id]/
        ├── page.tsx
        └── not-found.tsx
```

`not-found.tsx`:

```tsx
export default function NotFound() {
	return (
		<div>
			<h1>Product Not Found</h1>
			<p>The product you requested does not exist.</p>
		</div>
	);
}
```

---

# 8. `notFound()`

The `notFound()` function is used to trigger the nearest `not-found.tsx` UI.

Import it from:

```tsx
import { notFound } from "next/navigation";
```

Example:

```tsx
import { notFound } from "next/navigation";

export default async function ProductPage({
	params,
}: {
	params: Promise<{ id: string }>;
}) {
	const { id } = await params;

	const response = await fetch(`https://fakestoreapi.com/products/${id}`);

	if (!response.ok) {
		notFound();
	}

	const product = await response.json();

	if (!product) {
		notFound();
	}

	return (
		<div>
			<h1>{product.title}</h1>
		</div>
	);
}
```

The flow is:

```text
Request /products/123 → Find product → Product exists?
     /       \
   Yes        No
    ↓          ↓
 Render      notFound() → not-found.tsx
```

---

# 9. `not-found.tsx` vs `error.tsx`

These two files solve different problems.

## `error.tsx`

Used when something goes wrong.

```text
API failure
Database failure
Unexpected error
```

Flow: `Error → error.tsx`

## `not-found.tsx`

Used when the requested resource does not exist.

```text
Product does not exist
User does not exist
Post does not exist
```

Flow: `notFound() → not-found.tsx`

Simple rule:

```text
Something went wrong?      → error.tsx
Resource does not exist? → not-found.tsx
```

# 10. Complete Data Fetching Flow

A typical Next.js page may use several of these features together.

Example:

```text
Request
   ↓
Server Component
   ↓
Fetch data
   │
   ├── Loading → loading.tsx
   │
   ├── Error → error.tsx
   │
   ├── Resource missing → notFound() → not-found.tsx
   │
   └── Success → Render UI
```

If the page contains slow independent sections:

```text
Page
├── Fast Content  → renders immediately
└── Slow Content  → Suspense → streams in when ready
```

For independent fetches at the top of the page, use `Promise.all` so they run in parallel.

# 11. Best Practices

## Prefer Server-Side Fetching for Initial Data

If data is required to render the initial page and can be fetched on the server, prefer a Server Component.

## Fetch Independent Data in Parallel

Use `Promise.all` when multiple fetches do not depend on each other.

## Keep Secrets on the Server

Never expose database passwords, private API keys, or secret tokens to Client Components.

## Handle API Errors

Do not blindly assume `fetch(...)` always succeeds. Check `response.ok` and throw so `error.tsx` can handle it.

## Provide Loading UI

Use `loading.tsx` for route-level loading, or `<Suspense>` for granular control inside a page.

## Use Suspense for Independent Slow Sections

If one part of the page is slow, do not make the entire page wait for it. Wrap the slow section in `<Suspense>`.

## Use `notFound()` for Missing Resources

Do not treat a missing product as a generic application error. Use `notFound()` when the resource does not exist.

---

# Summary

- Data fetching means retrieving data required by the application.
- Server Components are a preferred place for many initial data-fetching operations.
- Fetch **independent data in parallel** with `Promise.all` — avoid slow sequential fetches.
- The `cache` option on `fetch` controls static vs dynamic behavior (Caching & Revalidation).
- Client-side fetching is useful for browser-driven and highly interactive data.
- Use `useState<Product[]>([])` (or similar) — not bare `useState([])` — to avoid TypeScript `never[]` errors.
- Databases should normally be accessed from server-side code.
- `loading.tsx` applies to its route segment **and child segments** unless a child defines its own.
- `<Suspense>` defines streaming boundaries — the page shell renders first; slow sections stream in as they complete.
- `error.tsx` provides route-level error UI but does **not** catch root layout errors — use `global-error.tsx` for that.
- `notFound()` triggers the nearest not-found UI;
- Use Server Components for server-side data and Client Components when browser-side behavior is required.

## Quick Decision Guide

```text
Need initial page data?
        ↓
Server-side fetching

Multiple independent fetches?
        ↓
Promise.all

Need browser-driven / interactive data?
        ↓
Client-side fetching

Route is loading?
        ↓
loading.tsx

Only part of page is slow?
        ↓
Suspense + Streaming

Unexpected error?
        ↓
error.tsx (use global-error.tsx for root layout)

Resource does not exist?
        ↓
notFound() → not-found.tsx
```
