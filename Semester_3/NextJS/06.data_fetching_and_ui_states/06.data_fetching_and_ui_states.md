# 06. Data Fetching & UI States

Modern Next.js applications often need to:

- Fetch data from APIs
- Fetch data from databases
- Show loading states
- Handle errors
- Show a not-found page
- Redirect users
- Stream parts of the UI as data becomes available

The App Router provides built-in patterns for handling these situations.

A typical request can look like:

```text
User visits page
      ↓
Fetch data
      ↓
Loading state
      ↓
Data received
      ↓
Render UI
```

If something goes wrong:

```text
Fetch data
    ↓
  Error
    ↓
 Error UI
```

If the requested resource does not exist:

```text
Request resource
      ↓
  Not found
      ↓
  404 UI
```

---

# Data Fetching

## Overview

**Data fetching** means retrieving data required by a page or component.

Data can come from:

```text
External API
Database
Internal service
File / CMS
```

For example:

```text
Next.js Application
        ↓
Products API
        ↓
Product Data
        ↓
UI
```

In the App Router, Server Components are the preferred place for many initial data-fetching operations.

A Server Component can:

1. Run on the server.
2. Fetch the required data.
3. Receive the result.
4. Render the UI.

---

# Server-Side vs Client-Side Data Fetching

| Server-Side Fetching                 | Client-Side Fetching                                      |
| ------------------------------------ | --------------------------------------------------------- |
| Runs on the server                   | Runs in the browser                                       |
| Useful for initial page data         | Useful for browser-driven or interactive data             |
| Can access server-only resources     | Can use browser APIs                                      |
| Can keep secrets on the server       | Cannot safely contain server secrets                      |
| Commonly used with Server Components | Commonly used with Client Components                      |
| Useful for database access           | Useful for data that changes based on browser interaction |

A simple rule:

```text
Initial page data
       ↓
Prefer Server-side fetching
```

```text
Interactive / browser-driven data
       ↓
Consider Client-side fetching
```

Server-side fetching is not a rule for every situation. The choice depends on where the data is needed and how the UI behaves.

---

# Fetching Data with Route Parameters

Dynamic routes can provide values from the URL path.

For example:

```text
/products/25
```

can map to:

```text
app/
└── products/
    └── [id]/
        └── page.tsx
```

The `id` value comes from the route parameters.

```tsx
export default async function ProductPage({
	params,
}: {
	params: Promise<{ id: string }>;
}) {
	const { id } = await params;

	const response = await fetch(`https://fakestoreapi.com/products/${id}`);

	const product = await response.json();

	return (
		<div>
			<h1>{product.title}</h1>
			<p>{product.price}</p>
		</div>
	);
}
```

The important idea is:

```text
/products/25
      ↓
params.id
      ↓
Fetch product 25
      ↓
Render product
```

Route parameters come from the **path**, not the query string.

---

# Fetching Data with Query Parameters

Data can also depend on search parameters.

For example:

```text
/products?category=electronics
```

A Server Component page can read the search parameters and use them when fetching data.

```tsx
type Props = {
	searchParams: Promise<{
		category?: string;
	}>;
};

export default async function ProductsPage({ searchParams }: Props) {
	const { category } = await searchParams;

	const response = await fetch(
		category
			? `https://fakestoreapi.com/products/category/${category}`
			: "https://fakestoreapi.com/products",
	);

	const products = await response.json();

	return (
		<div>
			{products.map((product: any) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

# Client-Side Data Fetching

Client-side fetching can be useful when data depends on browser interaction or needs to update after the page has loaded.

Common examples include:

- Interactive search
- Client-side filters
- Polling
- Browser-specific data
- Frequently changing dashboard information

A Client Component can use browser-side React logic to fetch data.

For example:

```tsx
"use client";

import { useParams } from "next/navigation";
import { useEffect, useState } from "react";

type Product = {
	title: string;
	price: number;
};

export default function ProductDetails() {
	const params = useParams();
	const id = params.id as string;

	const [product, setProduct] = useState<Product | null>(null);

	useEffect(() => {
		fetch(`https://fakestoreapi.com/products/${id}`)
			.then((response) => response.json())
			.then(setProduct);
	}, [id]);

	if (!product) {
		return <p>Loading...</p>;
	}

	return (
		<div>
			<h1>{product.title}</h1>
			<p>{product.price}</p>
		</div>
	);
}
```

Client-side fetching should not be used simply because it is possible. For initial page data, server-side fetching is often the simpler approach.

---

# Sequential vs Parallel Data Fetching

A page may need data from multiple sources.

There are two common approaches.

## Sequential Fetching

Requests run one after another.

```text
API 1 → wait → API 2 → wait → API 3 → done
```

Use sequential fetching when one request depends on the result of another.

For example:

```text
Fetch user → Get user ID → Fetch user's orders
```

The second request cannot start until the required information from the first request is available.

---

## Parallel Fetching

Independent requests can start at the same time.

```text
API 1 ──┐
API 2 ──┼──→ wait → done
API 3 ──┘
```

Use `Promise.all()` when multiple requests are independent.

```tsx
const [products, categories] = await Promise.all([
	fetchProducts(),
	fetchCategories(),
]);
```

Conceptually:

```text
Independent requests → Start together → Promise.all() → Continue when all are ready
```

### Simple Rule

```text
Dependent data → Sequential fetching

Independent data → Parallel fetching
```

# UI States

A data-driven application should handle more than just the successful state.

A typical page can have:

```text
Loading → Success → Error → Not Found
```

These states provide feedback to users and make the application more reliable.

---

# 1. Loading State

Data fetching can take time.

Instead of showing a blank page, provide feedback:

```text
Loading products...
```

Loading states are especially useful for:

- Slow APIs
- Database queries
- Large pages
- Route navigation
- Slow UI sections

Next.js provides `loading.tsx` for route-level loading UI.

---

# `loading.tsx`

A `loading.tsx` file creates a loading UI for a route segment.

Example:

```text
app/
├── page.tsx
└── products/
    ├── page.tsx
    └── loading.tsx
```

`loading.tsx`:

```tsx
export default function Loading() {
	return <p>Loading products...</p>;
}
```

Conceptually:

```text
/products
    ↓
loading.tsx
    ↓
page.tsx
```

While the route's content is being prepared, Next.js can display the loading UI.

---

# Route-Level Loading UI

A `loading.tsx` file applies to its route segment and child segments unless a child segment defines its own `loading.tsx`.

For example:

```text
app/
├── loading.tsx         ← applies to / and all children without their own loading.tsx
├── page.tsx
│
└── dashboard/
    ├── loading.tsx     ← overrides parent for /dashboard and its children
    └── page.tsx
```

Here:

```text
app/loading.tsx
      ↓
Global route-level loading

app/dashboard/loading.tsx
      ↓
Dashboard-specific loading
```

This allows different sections of an application to have different loading experiences.

---

# 2. Suspense

React provides `<Suspense>` for showing fallback UI while a part of the UI is waiting.

Example:

```tsx
import { Suspense } from "react";

function LoadingReviews() {
	return <p>Loading reviews...</p>;
}

export default function ProductPage() {
	return (
		<div>
			<ProductDetails />

			<Suspense fallback={<LoadingReviews />}>
				<Reviews />
			</Suspense>
		</div>
	);
}
```

The important part is:

```tsx
<Suspense fallback={<LoadingReviews />}>
	<Reviews />
</Suspense>
```

While `Reviews` is waiting, the fallback UI is displayed.

---

# `loading.tsx` vs Suspense

Both provide loading UI, but they operate at different levels.

## `loading.tsx`

Use it for route-level loading UI.

```text
Route → loading.tsx → page.tsx
```

Example:

```text
/products → Entire products route is loading → loading.tsx
```

## Suspense

Use it for more granular loading behavior inside a page.

```text
Product Page
├── Product Details → ready
├── Images          → ready
└── Reviews         → still loading
                         ↓
                     Suspense
                         ↓
                  Reviews Loading
```

This allows fast parts of the page to appear while slower sections continue loading.

---

# Streaming with Suspense

Suspense can create boundaries where parts of the UI become available independently.

For example:

```text
Product Page
      ↓
┌───────────────────────┐
│ Product Information   │
└───────────────────────┘
      ↓
available immediately

┌───────────────────────┐
│ Reviews               │
│ Loading...            │
└───────────────────────┘
      ↓
Reviews become available
      ↓
Reviews UI appears
```

The user does not necessarily have to wait for every section before seeing the page.

### Simple Rule

```text
Entire route is loading
        ↓
loading.tsx

Only one section is slow
        ↓
Suspense
```

# 3. Error Handling

Data fetching can fail.

Common causes include:

```text
API unavailable
Database error
Network failure
Invalid response
Unexpected server error
```

An application should provide useful error UI instead of leaving the user with a broken page.

Next.js provides:

```text
error.tsx
```

for route-level error handling.

---

# `error.tsx`

An `error.tsx` file creates an error UI for a route segment.

Example:

```text
app/
└── products/
    ├── page.tsx
    └── error.tsx
```

Example:

```tsx
"use client";

export default function Error({
	error,
	reset,
}: {
	error: Error & { digest?: string };
	reset: () => void;
}) {
	return (
		<div>
			<h2>Something went wrong!</h2>

			<button onClick={() => reset()}>Try again</button>
		</div>
	);
}
```

`error.tsx` is a Client Component because the error UI can contain interactive behavior such as `reset()`.

---

# Error Boundary

An **Error Boundary** catches errors that occur while rendering a part of the application and displays fallback UI.

Conceptually:

```text
Route
  │
  ├── Page
  │
  └── Error Boundary
          ↓
       Error?
        /   \
      No     Yes
      ↓       ↓
    Page    error.tsx
```

For example:

```tsx
export default async function ProductsPage() {
	const response = await fetch("https://fakestoreapi.com/products");

	if (!response.ok) {
		throw new Error("Failed to fetch products");
	}

	const products = await response.json();

	return <div>Products...</div>;
}
```

If an error is thrown:

```text
fetch() → Error thrown → Error Boundary → error.tsx → Error UI
```

---

# `reset()` in `error.tsx`

The `reset()` function allows the user to retry rendering the affected route segment.

Example:

```tsx
<button onClick={() => reset()}>Try again</button>
```

When the user clicks **Try again**, Next.js attempts to re-render the affected route segment.

---

# Root Layout Errors

`error.tsx` handles errors that occur within a route segment, but it does not catch errors thrown by the root layout itself.

```text
app/
├── layout.tsx
├── page.tsx
└── error.tsx

```

If an error occurs in: `app/page.tsx`
it can be handled by: `app/error.tsx`

However, if an error occurs in: `app/layout.tsx`

the error.tsx boundary cannot catch it because the root layout is outside that error boundary.

For errors in the root layout, Next.js provides: `app/global-error.tsx`

So the basic distinction is:

```text
Error in a route segment
        ↓
    error.tsx

Error in the root layout
        ↓
global-error.tsx

```

Easy way to remember:

- `error.tsx` → handles errors in a route segment and its children.
- `global-error.tsx` → handles critical errors at the root level, including errors in app/layout.tsx.

`global-error.tsx` replaces the root layout when it is rendered, so it must define its own <html> and <body> tags.

# 4. Not Found Handling

Sometimes there is no application error.

The requested resource simply does not exist.

For example:

```text
/products/12345
```

The application may successfully communicate with the server, but product `12345` may not exist.

In this situation, the correct UI is a **not-found** state.

Next.js provides:

```text
not-found.tsx
```

---

# `not-found.tsx`

Example structure:

```text
app/
└── products/
    └── [id]/
        ├── page.tsx
        └── not-found.tsx
```

Example:

```tsx
export default function NotFound() {
	return (
		<div>
			<h1>Product Not Found</h1>
			<p>The product you requested does not exist.</p>
		</div>
	);
}
```

---

# `notFound()`

The `notFound()` function triggers the nearest `not-found.tsx` UI.

Import it from:

```tsx
import { notFound } from "next/navigation";
```

Example:

```tsx
import { notFound } from "next/navigation";

export default async function ProductPage({
	params,
}: {
	params: Promise<{ id: string }>;
}) {
	const { id } = await params;

	const response = await fetch(`https://fakestoreapi.com/products/${id}`);

	if (!response.ok) {
		notFound();
	}

	const product = await response.json();

	if (!product) {
		notFound();
	}

	return (
		<div>
			<h1>{product.title}</h1>
		</div>
	);
}
```

The flow is:

```text
Request /products/123 → Find product → Product exists?
     /       \
   Yes        No
    ↓          ↓
 Render      notFound() → not-found.tsx
```

---

# `error.tsx` vs `not-found.tsx`

These solve different problems.

## `error.tsx`

Use when something unexpected goes wrong.

```text
API failure
Database failure
Unexpected error
```

## `not-found.tsx`

Use when the requested resource does not exist.

```text
Product does not exist
User does not exist
Post does not exist
```

# Best Practices

## 1. Prefer Server-Side Fetching for Initial Data

If data is required to render the initial page and can be fetched on the server, prefer a Server Component.

## 2. Use Client-Side Fetching When Browser Interaction Requires It

Use client-side fetching when data depends on browser interaction or needs to update dynamically after the page has loaded.

## 3. Fetch Independent Data in Parallel

Use `Promise.all()` when multiple requests do not depend on each other.

## 4. Keep Secrets on the Server

Never expose:

- Database passwords
- Private API keys
- Secret tokens

to Client Components.

## 5. Handle API Errors

Do not blindly assume a request succeeds.

Check the response and throw an error when the request should be treated as an application failure.

```tsx
if (!response.ok) {
	throw new Error("Failed to fetch products");
}
```

## 6. Provide Loading UI

Use `loading.tsx` for route-level loading and `<Suspense>` for granular loading inside a page.

## 7. Use Suspense for Independent Slow Sections

If one section is slow, do not necessarily make the entire page wait for it.

Use a Suspense boundary around the slower section.

## 8. Use `notFound()` for Missing Resources

A missing product is not necessarily an application error.

Use `notFound()` when the requested resource does not exist.

---

# Summary

- Data fetching means retrieving data required by the application.
- Server Components are a preferred place for many initial data-fetching operations.
- Client-side fetching is useful for browser-driven and interactive data.
- Use `params` for values from dynamic route segments.
- Use `searchParams` for values from the URL query string.
- Use sequential fetching when requests depend on each other.
- Use `Promise.all()` for independent requests.
- Use `loading.tsx` for route-level loading UI.
- Use `<Suspense>` for granular loading behavior.
- Suspense can allow slower sections to appear independently.
- Use `error.tsx` for route-level error UI.
- `error.tsx` is a Client Component because it can contain interactive error handling such as `reset()`.
- Use `notFound()` when the requested resource does not exist.
- `not-found.tsx` displays the not-found UI.
- Keep server-only secrets and resources on the server.
