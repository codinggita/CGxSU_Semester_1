# 13. Backend Architecture

Layer backend code with services and repositories, and connect them to Route Handlers, Server Actions, and Server Components. Compared to Express routes/controllers/services with Mongoose, the main addition is an explicit **Repository** layer separate from the ORM, plus Next.js calling the service layer directly without an HTTP hop. Use this pattern when complexity grows — not every route needs the full stack.

---

## 1. Why Layer Backend Code Now?

By now your `app/api/products/route.ts` is handling validation, database queries, and response formatting all in one function. That is the moment to introduce a service layer — not before.

A small app can start simple:

```text
Route Handler
     ↓
Database
```

As the application grows, a clearer structure helps:

```text
Route Handler / Server Action / Server Component
      ↓
Service
      ↓
Repository
      ↓
Database
```

Each layer has one job:

```text
Route Handler  →  HTTP concerns
Service        →  Business logic
Repository     →  Data access
Database       →  Persistent storage
```

You already do this in Express — **routes/controllers/services** or **routes/controllers/models**. Same idea here, translated to Next.js:

- **Route Handler / Server Action** takes the place of your Express route + controller
- **Service** is your business logic layer (same role as in Express)
- **Repository** is **new** — **Repository Layer** explains why it exists on top of Prisma

The goal is not the most layers possible. The goal is clear responsibilities and code that is easier to change.

```text
API / Route  →  Service  →  Repository  →  Database
```

## 3. Route Handler Layer

The Route Handler handles HTTP. Example path:

```text
app/api/products/route.ts
```

Example:

```ts
import { createProduct } from "@/features/products/product.service";

export async function POST(request: Request) {
	const body = await request.json();

	const product = await createProduct(body);

	return Response.json(product, {
		status: 201,
	});
}
```

Route Handler responsibilities:

- Read the request (body, params, headers)
- Authentication/authorization entry point
- Call the appropriate service
- Return the HTTP response
- Map errors to HTTP status codes

It should not contain complex business logic or raw database queries.

## 5. Service Layer

The Service Layer contains application/business logic. It does not know about HTTP.

Example — what a service function looks like in isolation:

```ts
// features/products/product.service.ts

import { createProductRecord } from "@/features/products/product.repository";

type CreateProductInput = {
	name: string;
	slug: string;
	price: number;
	stock: number;
	categoryId: number;
};

export async function createProduct(data: CreateProductInput) {
	if (!data.name?.trim()) {
		throw new Error("Product name is required");
	}

	if (data.price <= 0) {
		throw new Error("Product price must be positive");
	}

	return createProductRecord(data);
}
```

The service decides **what should happen**. It is reusable from multiple entry points:

```text
Route Handler ───────┐
                     │
Server Action ───────┼──→ Product Service
                     │
Server Component ────┘
```

---

## 6. What Belongs in the Service Layer?

Typical service responsibilities:

- Business rules and validation
- Calculations and workflow coordination
- Calling multiple repositories
- Calling external services
- Coordinating transactions

The service coordinates the operation — it does not parse HTTP or write SQL.

---

## 7. Repository Layer

The Repository Layer is responsible for **data access only**.

```text
features/products/product.repository.ts
```

```ts
import { prisma } from "@/lib/prisma";

export async function getProductById(id: number) {
	return prisma.product.findUnique({
		where: { id },
		include: { category: true },
	});
}

export async function createProductRecord(data: {
	name: string;
	slug: string;
	price: number;
	stock: number;
	categoryId: number;
}) {
	return prisma.product.create({ data });
}
```

The repository answers: **"How do we read/write the data?"**

It knows about Prisma, SQL, and database-specific operations. The service does not need to know the exact Prisma query.

### Why is the Repository layer separate from the service?

In Mongoose, the **Model** is both your schema and your data-access API — `Product.findById()`, `Product.create()`, and so on. **Prisma Client already plays that role** — it is a query builder and data-access layer, closer to Mongoose itself.

A Repository wrapping Prisma is an **additional abstraction on top** of what Mongoose gave you for free. You add it when repeated queries, multiple data sources, or test isolation justify the extra files — not because Prisma failed to do its job.

---

## 8. Database Layer

The database layer is persistent storage — **PostgreSQL** via Prisma:

```text
Route Handler
      ↓
Service
      ↓
Repository
      ↓
Prisma
      ↓
PostgreSQL
```

| Layer         | Responsibility     |
| ------------- | ------------------ |
| Route Handler | HTTP               |
| Service       | Business logic     |
| Repository    | Data access        |
| Prisma        | Database client    |
| PostgreSQL    | Persistent storage |

## 10. Complete Example

Product creation — Route Handler → Service → Repository → Prisma.

### 10.1 Route Handler

```ts
// app/api/products/route.ts

import { createProduct } from "@/features/products/product.service";

export async function POST(request: Request) {
	try {
		const body = await request.json();

		const product = await createProduct(body);

		return Response.json(product, {
			status: 201,
		});
	} catch (error) {
		console.error(error);

		return Response.json(
			{ error: "Failed to create product" },
			{ status: 500 },
		);
	}
}
```

The route handles HTTP concerns only.

### 10.2 Service

```ts
// features/products/product.service.ts

import { createProductRecord } from "@/features/products/product.repository";

type CreateProductInput = {
	name: string;
	slug: string;
	price: number;
	stock: number;
	categoryId: number;
};

export async function createProduct(data: CreateProductInput) {
	if (!data.name?.trim()) {
		throw new Error("Product name is required");
	}

	if (!data.slug?.trim()) {
		throw new Error("Product slug is required");
	}

	if (data.price <= 0) {
		throw new Error("Product price must be positive");
	}

	if (data.stock < 0) {
		throw new Error("Stock cannot be negative");
	}

	return createProductRecord(data);
}
```

The service handles business rules.

### 10.3 Repository

```ts
// features/products/product.repository.ts

import { prisma } from "@/lib/prisma";

export async function createProductRecord(data: {
	name: string;
	slug: string;
	price: number;
	stock: number;
	categoryId: number;
}) {
	return prisma.product.create({
		data,
		include: { category: true },
	});
}
```

The repository handles database access.

### 10.4 Prisma and PostgreSQL

Prisma generates the SQL; PostgreSQL persists the row in `products` with a foreign key to `categories`.

## 11. Error Flow

Errors travel up through the layers:

```text
PostgreSQL  →  Database error  →  Repository  →  Service  →  Route Handler  →  HTTP Response
```

The route handler converts application errors into HTTP responses:

```ts
try {
	const product = await createProduct(body);
	return Response.json(product, { status: 201 });
} catch (error) {
	return Response.json(
		{ error: "Failed to create product" },
		{ status: 500 },
	);
}
```

Production apps should use structured/custom errors:

```ts
class ProductNotFoundError extends Error {}
```

Then the HTTP layer maps them:

```text
ProductNotFoundError  →  HTTP 404
Unexpected DB failure →  HTTP 500
```

---

## 12. Keep HTTP Logic Out of Services

Avoid:

```ts
// Bad — service tied to HTTP

export async function createProduct(req: Request, res: Response) {
	// business logic + database + response
}
```

Prefer:

```ts
// Service — framework-agnostic
export async function createProduct(data: CreateProductInput) {
	// business logic only
}

// Route Handler — HTTP only
const product = await createProduct(body);
return Response.json(product);
```

This makes the service reusable from Route Handlers, Server Actions, and Server Components.

---

## 13. Keep Database Queries Out of Route Handlers

For a tiny route, direct Prisma access is fine:

```ts
export async function GET() {
	const products = await prisma.product.findMany();
	return Response.json(products);
}
```

Once the application has a deliberate service/repository architecture, keep routes thin:

```ts
export async function GET() {
	const products = await getProducts();
	return Response.json(products);
}
```

The point is **consistency** once the app has grown enough to benefit from layers — not that direct Prisma is always wrong.

## 14. Service Layer Calling Multiple Repositories

A checkout flow often needs one service coordinating User, Product, and Order repositories.

```ts
// features/orders/order.service.ts

import { getUserById } from "@/features/auth/user.repository";
import { getProductById } from "@/features/products/product.repository";
import { createOrderRecord } from "@/features/orders/order.repository";

export async function createOrder(userId: number, productId: number) {
	const user = await getUserById(userId);
	if (!user) throw new Error("User not found");

	const product = await getProductById(productId);
	if (!product) throw new Error("Product not found");
	if (product.stock <= 0) throw new Error("Product is out of stock");

	return createOrderRecord({ userId, productId, price: product.price });
}
```

```text
                 Product Repository
                       ↑
                       │
Route → Service ───────┼──→ Order Repository
                       │
                       ↓
                  User Repository
```

The service coordinates the business workflow; repositories handle individual data-access calls.

## 15. Transactions and Architecture

Transactions are often coordinated at the service level because the service understands the complete business operation.

Example — placing an order:

```text
Create Order
    │
    ├── Create order record
    ├── Reduce product stock
    └── Create payment record
```

These operations must succeed or fail together:

```text
Service
   ↓
Transaction
   ├── Order Repository
   ├── Product Repository
   └── Payment Repository
```

With Prisma:

```ts
await prisma.$transaction(async (tx) => {
	// operations using tx
});
```

The key architectural idea:

> The service coordinates the business operation; repositories perform the individual data-access operations.

## 16. When to Add Each Layer

A repository layer is **optional**. Do not add layers preemptively — introduce each one when it solves a real problem.

### 16.1 Stage 1 — Small application

```text
Route  →  Prisma  →  Database
```

Fine when the route is a simple CRUD read with no business rules.

### 16.2 Stage 2 — Business logic grows

```text
Route  →  Service  →  Prisma  →  Database
```

Add a service when validation, calculations, or multi-step workflows appear — or when the same logic is needed from a Route Handler **and** a Server Action.

### 16.3 Stage 3 — Data access becomes complex or repeated

```text
Route  →  Service  →  Repository  →  Prisma  →  Database
```

Add a repository when:

- The same Prisma query appears in multiple services
- You need to hide multiple data sources (PostgreSQL + Redis + external API)
- Unit tests need to swap real DB access for fakes
- Business logic is reused across Route Handler, Server Action, and background jobs

### 16.4 When not to add layers

For a one-line `GET` that lists users, adding Route → Service → Repository → Prisma buys nothing and makes navigation harder.

**Bad reason:**

> "Every backend must have Controller → Service → Repository."

**Better principle:**

> Introduce a layer when it solves a real complexity, reuse, testing, or maintainability problem.

Start simple. Extract when the pain is real — not when a diagram says you should.

## 17. Feature-Based Organization

As the application grows, organizing by technical layer alone gets hard:

```text
services/
├── user.service.ts
├── product.service.ts
└── order.service.ts

repositories/
├── user.repository.ts
├── product.repository.ts
└── order.repository.ts
```

Feature-based organization keeps related code together:

```text
features/
├── auth/
│   ├── user.service.ts
│   ├── user.repository.ts
│   └── user.schema.ts
│
├── products/
│   ├── product.service.ts
│   ├── product.repository.ts
│   └── product.schema.ts
│
└── orders/
    ├── order.service.ts
    ├── order.repository.ts
    └── order.schema.ts
```

Both approaches are valid. Choose the organization that makes the codebase easier to navigate.

## 19. Separation of Concerns

For product creation, each layer has one responsibility. **Complete Example** has full code — the following table summarizes responsibilities:

| Layer         | Responsibility     | Does not handle          |
| ------------- | ------------------ | ------------------------ |
| Route Handler | HTTP               | Business rules, SQL      |
| Service       | Business logic     | Request parsing, Prisma  |
| Repository    | Data access        | HTTP, business decisions |
| Database      | Persistent storage | Application logic        |

## 20. Dependency Direction

Higher-level logic should not be tightly coupled to low-level details:

```text
Route  →  Service  →  Repository  →  Database
```

The service calls `productRepository.findById(id)` — it cares about **find product**, not `SELECT * FROM products WHERE id = …`.

This separation makes swapping ORMs or data sources easier when the need arises.

## 21. Common Architectural Mistakes

### 21.1 Mistake 1 — Fat Route Handlers

```text
route.ts
├── validation
├── business logic
├── database queries
├── email
└── response
```

**Better:** Route → Service → Repository when complexity justifies it.

### 21.2 Mistake 2 — Business Logic in Repository

Bad:

```ts
async function createOrder(data) {
	if (data.total > 100000) {
		// business rule — belongs in service
	}
	return prisma.order.create({ data });
}
```

The repository should primarily handle data access.

### 21.3 Mistake 3 — HTTP Logic in Repository

The repository should not know about `Request`, `Response`, or HTTP status codes.

### 21.4 Mistake 4 — Service Directly Returning HTTP Responses

Bad:

```ts
return Response.json(product); // inside service
```

Prefer:

```ts
return product; // service returns data; route returns HTTP
```

### 21.5 Mistake 5 — Over-Abstraction

Avoid creating Controller, Service, Repository, Factory, Adapter, Mapper, Provider, and Interface for every tiny feature without a reason.

More layers do not automatically mean better architecture. **Advanced (Optional) — Interface-Based Repositories** covers interface-based repositories — useful in larger codebases, but premature here.

### 21.6 Mistake 6 — One Giant Service

Avoid `app.service.ts` containing every operation. Prefer feature-focused services:

```text
product.service.ts
order.service.ts
user.service.ts
```

Pages Router →  API Route      (pages/api/products.ts)

## 23. Server Components and This Architecture

A Server Component can call the service layer **directly** — no API round-trip. There is no Express equivalent for this pattern.

```tsx
// app/products/page.tsx

import { getProducts } from "@/features/products/product.service";

export default async function ProductsPage() {
	const products = await getProducts();

	return (
		<div>
			{products.map((product) => (
				<div key={product.id}>
					{product.name} — ₹{Number(product.price)}
				</div>
			))}
		</div>
	);
}
```

Flow:

```text
Server Component
      ↓
Service
      ↓
Repository
      ↓
Prisma
      ↓
PostgreSQL
```

This is a key Next.js distinction:

```text
Server Component  →  Server-side service     (no HTTP hop)

Client Component  →  HTTP API or Server Action
```

---

## 24. Client Components and This Architecture

A Client Component cannot access the database or import Prisma. It reaches the service layer through:

```text
Client Component
      ↓
Route Handler / API Route
      ↓
Service
      ↓
Repository
      ↓
Database
```

or:

```text
Client Component
      ↓
Server Action
      ↓
Service
      ↓
Repository
      ↓
Database
```

Both paths converge on the same service:

```text
                    Server
                      │
             ┌────────┴────────┐
             │                 │
       Route Handler      Server Action
             │                 │
             └────────┬────────┘
                      ↓
                   Service
                      ↓
                 Repository
                      ↓
                   Prisma
                      ↓
                PostgreSQL
```

## Advanced (Optional) — Interface-Based Repositories

**Not needed for most applications at this stage.** Interface-based repositories are useful in larger codebases with multiple data sources or heavy unit testing, but introducing them prematurely is itself an example of **Over-Abstraction**.

For applications that genuinely benefit from stronger abstraction, a repository contract can be defined:

```ts
export interface ProductRepository {
	findById(id: number): Promise<Product | null>;
	create(data: CreateProductInput): Promise<Product>;
}
```

A Prisma implementation:

```ts
export class PrismaProductRepository implements ProductRepository {
	async findById(id: number) {
		return prisma.product.findUnique({ where: { id } });
	}

	async create(data: CreateProductInput) {
		return prisma.product.create({ data });
	}
}
```

The service depends on the contract rather than Prisma directly:

```ts
export class ProductService {
	constructor(private repository: ProductRepository) {}

	async getProduct(id: number) {
		return this.repository.findById(id);
	}
}
```

This helps when you need interchangeable implementations or isolated testing. For most applications at this stage, plain functions in `product.repository.ts` are enough.
