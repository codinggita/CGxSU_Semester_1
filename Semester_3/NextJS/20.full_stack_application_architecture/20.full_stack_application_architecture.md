# 26. Full-Stack Application Architecture in Next.js

This is the final architecture topic for the Next.js App Router course. It combines frontend architecture and backend architecture into one practical guide for building a complete, maintainable application.

The examples use Next.js App Router and TypeScript. The architecture is intentionally **database- and ORM/ODM-agnostic**. The same principles apply whether an application uses MongoDB with Mongoose, PostgreSQL or MySQL with Prisma or Drizzle, another SQL database, a document database, or an external data service.

The goal is not to create the maximum number of folders or layers. The goal is to give each part of the application a clear responsibility, keep dependencies understandable, and introduce abstractions when they solve a real problem.

---

## 1. What Is Application Architecture?

Application architecture describes how an application is divided into parts, what each part is responsible for, and how those parts communicate.

A full-stack Next.js application contains several responsibilities:

- **Routing:** URLs, pages, layouts, loading states, error boundaries, and HTTP endpoints.
- **Presentation:** components, forms, tables, navigation, and page composition.
- **Client interaction:** event handlers, browser APIs, and interactive state.
- **Application logic:** business rules, calculations, and workflows.
- **Data access:** reading and writing data through a database client, ORM, ODM, or external service.
- **Infrastructure:** database connections, authentication utilities, integrations, and shared configuration.

A useful high-level model is:

```text
                         Next.js Application
                                  |
             +--------------------+--------------------+
             |                    |                    |
          Frontend             Application          Infrastructure
             |                   logic                    |
       Routes and UI           Services             Database client
       Components              Workflows            Authentication
       Client state            Business rules       External services
             |                    |                    |
             +--------------------+--------------------+
                                  |
                            Data access
                                  |
                         Database / APIs
```

The frontend and backend live in one project, but they should not become one undifferentiated block of code.

### Why architecture matters

Without clear boundaries, a page or API endpoint can gradually become responsible for everything: reading input, validating it, checking permissions, applying business rules, querying a database, sending emails, and formatting the response.

That makes code harder to understand, test, reuse, debug, and change. Separation of concerns keeps each part focused and makes the overall system easier to maintain.

## 2. Recommended Project Structure

A practical feature-based structure for a growing e-commerce application can look like this:

```text
src/
├── app/
│   ├── (store)/
│   │   ├── layout.tsx
│   │   ├── page.tsx
│   │   ├── products/
│   │   │   ├── page.tsx
│   │   │   └── [id]/
│   │   │       └── page.tsx
│   │   ├── cart/
│   │   │   └── page.tsx
│   │   └── checkout/
│   │       └── page.tsx
│   ├── (account)/
│   │   ├── layout.tsx
│   │   ├── profile/page.tsx
│   │   └── orders/page.tsx
│   ├── api/

│   │   └── orders/route.ts

│
├── features/

│       ├── services/

```

This is an example, not a mandatory template. A small feature does not need every folder. For a small project, database-specific code may live in `lib/db/` or inside a feature's data-access module. The important part is keeping the responsibilities clear and avoiding accidental exposure of server-only code to the browser.

### Responsibility of each directory

| Directory | Responsibility |
|---|---|
| `app/` | URL routing, layouts, pages, loading/error UI, Route Handlers |
| `components/ui/` | Generic reusable UI components |
| `components/layout/` | Shared application layout components |
| `features/` | Feature-specific UI, business-facing operations, schemas, and types |
| `server/` | Server-only infrastructure and persistence implementation, if the project needs a dedicated boundary |
| `lib/` | Shared utilities and infrastructure helpers |
| `types/` | Types genuinely shared by multiple unrelated features |

### Keep `app/` focused on routing

The `app/` directory should define routes and compose the components or server-side operations required by those routes. Avoid placing every product component, business rule, and data query inside `app/products/`.

```tsx
// app/products/page.tsx

import { ProductList } from "@/features/products/components/product-list";
import { getProducts } from "@/features/products/services/product.service";

export default async function ProductsPage() {
  const products = await getProducts();

  return <ProductList products={products} />;
}
```

The page is responsible for route-level composition. The products feature owns product-specific UI and application operations.

## 3. Route Structure and Feature Structure

These structures solve different problems.

### Route structure

The App Router determines which URL renders which page:

```text
app/
└── products/
    ├── page.tsx
    └── [id]/
        └── page.tsx
```

This defines `/products` and `/products/[id]`.

### Feature structure

The `features/` directory groups code by business domain:

```text
features/
└── products/
    ├── components/
    ├── services/
    ├── schemas/
    └── types/
```

The route structure answers, “Which UI should render for this URL?” The feature structure answers, “Where does product-related code belong?”

### Route groups

Route groups use parentheses and do not add a URL segment:

```text
app/
├── (store)/
│   ├── products/
│   └── cart/
└── (account)/
    ├── profile/
    └── orders/
```

The group names organize routes and can be used to define different layouts. They do not appear in the URL.

## 4. Where Should Components Live?

Choose a component's location based on its responsibility and actual reuse.

### Generic UI components

Location: `components/ui/`

Examples include Button, Input, Card, Modal, Badge, and Table. These components should not contain product, order, or checkout business rules.

```tsx
// components/ui/button.tsx

import type { ButtonHTMLAttributes } from "react";

type ButtonProps = ButtonHTMLAttributes<HTMLButtonElement> & {
  variant?: "primary" | "secondary";
};

export function Button({
  variant = "primary",
  className,
  ...props
}: ButtonProps) {
  return (
    <button
      className={`button button-${variant} ${className ?? ""}`}
      {...props}
    />
  );
}
```

The Button is generic because it does not know what a product or order is.

### Layout components

Location: `components/layout/`

Examples include Navbar, Footer, Header, and Sidebar. These are shared parts of the application layout.

### Feature components

Location: `features/<feature>/components/`

Examples include ProductCard, ProductGallery, AddToCartButton, CheckoutForm, and OrderSummary. These components understand a particular business domain.

### Route-only components

A component used by only one route and closely related to that route can be colocated with it:

```text
app/products/[id]/
├── page.tsx
├── product-gallery.tsx
└── product-description.tsx
```

Move it into `features/products/components/` when it becomes useful across multiple routes. Do not extract every component into a shared folder before reuse exists.

## 5. Naming Conventions

Consistent naming makes a codebase easier to navigate. A practical TypeScript convention is:

| Item | Convention | Example |
|---|---|---|
| Folders | lowercase, often kebab-case | `product-details/` |
| Component files | kebab-case | `product-card.tsx` |
| Component names | PascalCase | `ProductCard` |
| Functions | camelCase | `getProductById` |
| Variables | camelCase | `activeProducts` |
| Constants | camelCase by default | `pageSize` |
| Environment variables | UPPER_SNAKE_CASE | `DATABASE_URL` |
| Types and interfaces | PascalCase | `Product`, `CreateProductInput` |
| Boolean variables | descriptive prefix | `isActive`, `hasStock`, `canEdit` |

Use names that explain purpose:

```ts
const activeProducts = products.filter((product) => product.isActive);
```

Avoid unclear names such as `x`, `arr`, or `data1` for important business values. Short callback names can be acceptable in very small expressions, but use descriptive names when the callback becomes more involved.

## 6. Variable Declaration: `const`, `let`, and `var`

Choose a declaration based on whether the variable binding needs to be reassigned.

### `const` — the default choice

Use `const` when the variable will not be reassigned:

```ts
const productName = "Laptop";
const productPrice = 50000;
const products = await getProducts();
```

Most variables in application code should use `const`.

`const` prevents reassignment of the variable binding. It does not make an object or array immutable:

```ts
const product = {
  name: "Laptop",
  price: 50000,
};

product.price = 45000; // Allowed
// product = {};       // Not allowed
```

### `let` — when reassignment is required

Use `let` when the same variable must hold a different value later:

```ts
let total = 0;

for (const item of cartItems) {
  total += item.price * item.quantity;
}
```

Another example:

```ts
let selectedCategory = "electronics";

if (searchParams.category) {
  selectedCategory = searchParams.category;
}
```

If the code can be written with `const`, prefer `const`.

### `var` — avoid in modern TypeScript

`var` is function-scoped and has older hoisting behavior, which can create confusing bugs:

```ts
if (true) {
  var message = "Hello";
}

console.log(message); // Accessible outside the block
```

`let` and `const` are block-scoped:

```ts
if (true) {
  const message = "Hello";
}

// message is not accessible here
```

Use `const` or `let` in modern Next.js applications.

### Should every `const` be uppercase?

No. Uppercase names are commonly used for fixed configuration values when that convention improves clarity:

```ts
const DEFAULT_PAGE_SIZE = 20;
const MAX_CART_ITEMS = 50;
```

Do not uppercase every `const` variable. Use normal camelCase for ordinary local values.

## 7. Functions and Function Organization

Functions should have one clear responsibility and descriptive names.

### Function declarations

Use named function declarations for reusable operations, especially exported functions:

```ts
export function calculateDiscount(
  price: number,
  discountPercentage: number
): number {
  return price * (discountPercentage / 100);
}
```

### Arrow functions

Arrow functions are commonly used for callbacks, short expressions, and component-local handlers:

```ts
const activeProducts = products.filter(
  (product) => product.isActive
);
```

```tsx
"use client";

export function SearchButton() {
  const handleSearch = () => {
    console.info("Search submitted");
  };

  return <button onClick={handleSearch}>Search</button>;
}
```

### Which should be used?

- Use named function declarations for reusable exported operations when they make the API easier to read.
- Use arrow functions for callbacks and short local handlers.
- Avoid deeply nested callbacks and functions that perform unrelated work.
- Give exported functions descriptive names.
- TypeScript can infer simple local return types. Add explicit return types when they improve clarity, particularly for shared service functions and public module boundaries.

Do not combine request parsing, validation, business rules, database access, and response formatting into one large function. Split responsibilities where it improves clarity.

## 8. Types, Interfaces, and Type Organization

TypeScript types describe data shapes and help prevent invalid operations.

### `type`

Use `type` for object shapes, unions, intersections, and aliases:

```ts
export type ProductStatus = "draft" | "active" | "archived";

export type ProductSummary = {
  id: string;
  name: string;
  price: number;
  status: ProductStatus;
};
```

### `interface`

Use `interface` for object contracts, particularly when extension or implementation is useful:

```ts
export interface PaginationOptions {
  page: number;
  limit: number;
}

export interface ProductReader {
  findById(id: string): Promise<ProductSummary | null>;
}
```

Both `type` and `interface` can describe object shapes. Choose a consistent convention for similar declarations. Do not create an interface automatically for every object.

### Input types and output types

Separate data accepted from a caller from data returned by the application:

```ts
export type CreateProductInput = {
  name: string;
  price: number;
  stock: number;
};

export type ProductDTO = {
  id: string;
  name: string;
  price: number;
  stock: number;
  createdAt: string;
};
```

An input type should contain only fields the caller is allowed to provide. Do not accept database-managed fields such as IDs, timestamps, ownership fields, or internal flags from an untrusted client.

### Avoid `any`

`any` disables important TypeScript checks:

```ts
// Avoid
function createProduct(data: any) {
  // Type checking is disabled for data.
}
```

Prefer a known type:

```ts
type CreateProductInput = {
  name: string;
  price: number;
};

function createProduct(data: CreateProductInput) {
  // TypeScript checks the input shape.
}
```

Use `unknown` when a value is genuinely unknown, then validate or narrow it before use. For example, parsed JSON should not automatically be trusted just because a TypeScript type is assigned to it.

### Where types belong

- Feature-specific types: `features/products/types/`.
- Types shared by multiple unrelated features: `types/`.
- Component-only props: keep close to the component unless reused.
- Service input and output types: keep with the feature or its type definitions.

Do not place every type in one large global file.

## 9. Server and Client Components

In the App Router, components are Server Components by default. A Server Component executes on the server. A Client Component is needed when browser-side interactivity is required.

| Capability | Server Component | Client Component |
|---|---|---|
| Default in App Router | Yes | Requires `"use client"` boundary |
| Access server-only data sources | Yes | No |
| Use `useState` / `useEffect` | No | Yes |
| Handle browser events | No | Yes |
| Use browser APIs | No | Yes |
| Keep secrets on server | Yes | No |

Server/Client Components describe execution boundaries. SSR, SSG, ISR, and CSR describe rendering strategies. They are related but not interchangeable concepts.

### Decision rule

```text
Start with a Server Component
             |
             v
Does it need state, effects, event handlers,
or browser APIs?
             |
       +-----+-----+
       |           |
      No          Yes
       |           |
   Server       Client
  Component    Component
```

Do not add `"use client"` just because a component renders UI.

### Keep client boundaries small

For a product page:

```text
ProductPage              Server
├── ProductGallery       Server-compatible
├── ProductInformation   Server
├── QuantitySelector     Client
├── AddToCartButton      Client
└── ProductReviews       Server
```

Only the interactive parts need to be Client Components. Avoid converting an entire page to a Client Component because one button needs an event handler.

### Server-to-client data flow

Pass serializable data to Client Components:

```tsx
// app/products/[id]/page.tsx

import { AddToCartButton } from "@/features/cart/components/add-to-cart-button";
import { getProductById } from "@/features/products/services/product.service";

type ProductPageProps = {
  params: Promise<{ id: string }>;
};

export default async function ProductPage({
  params,
}: ProductPageProps) {
  const { id } = await params;
  const product = await getProductById(id);

  if (!product) {
    return <p>Product not found.</p>;
  }

  return (
    <main>
      <h1>{product.name}</h1>
      <p>₹{product.price}</p>
      <AddToCartButton productId={product.id} />
    </main>
  );
}
```

```tsx
// features/cart/components/add-to-cart-button.tsx

"use client";

type AddToCartButtonProps = {
  productId: string;
};

export function AddToCartButton({
  productId,
}: AddToCartButtonProps) {
  function handleAddToCart() {
    // Update client cart state or invoke a server operation.
    console.info("Add product:", productId);
  }

  return <button onClick={handleAddToCart}>Add to Cart</button>;
}
```

Do not pass database connections, secrets, or server-only objects to Client Components. Return only the fields the UI needs.

### Shared components

A shared Button, Card, or Badge does not automatically need to be a Client Component. Keep it server-compatible unless it needs client-side capabilities.

### State ownership

- **Server data:** products, orders, and user records. Fetch on the server when appropriate.
- **Local client state:** open modal, selected tab, form input, and dropdown state.
- **Shared client state:** cart or wishlist state when multiple client components need the same state.

Do not copy all server-fetched data into a global client store without a clear reason.

## 10. Frontend Data Flow and Server Entry Points

A Server Component can call server-side application code directly. It does not need to make an HTTP request to its own Route Handler just to fetch data.

```text
Server Component
       |
       v
Application Service
       |
       v
Data-access module
       |
       v
Database / external service
```

For client interactions, use a Server Action or Route Handler:

```text
Client Component
       |
       +-------------------+
       |                   |
       v                   v
  Server Action       Route Handler
       |                   |
       +---------+---------+
                 |
                 v
          Application Service
                 |
                 v
             Data access
```

Choose an entry point based on the use case:

- **Server Component:** read data needed to render a server page.
- **Server Action:** perform a server-side mutation initiated by the application's UI.
- **Route Handler:** expose an HTTP endpoint for browser requests, external clients, webhooks, or integrations.

A Server Action is still a server entry point. Validate its arguments and authenticate and authorize the caller. Do not treat it as a private function that is automatically safe just because it is called by your own UI.

Do not call your own Route Handler from a Server Component when the server-side service can be called directly.

## 11. Backend Architecture: Separate Responsibilities

The backend should separate HTTP handling, business rules, and data access.

A common layered flow is:

```text
Route Handler / Server Action
             |
             v
          Service
             |
             v
       Data-access layer
             |
             v
       ORM / ODM / SDK
             |
             v
       Database / API
```

| Part | Responsibility |
|---|---|
| Route Handler | HTTP request and response concerns |
| Server Action | UI-triggered server operation and result for the UI |
| Service | Business rules and workflow coordination |
| Repository / data-access module | Queries and persistence operations |
| ORM / ODM / database client | Technology-specific data operations |
| Database or external API | Persistent storage or remote capability |

The repository is optional. A small application may call a database client from a focused service. Add a repository or data-access module when it gives useful separation, reuse, or testability.

### Route Handler responsibilities

A Route Handler should:

- Read request data such as body, query parameters, and headers.
- Validate untrusted input.
- Authenticate the caller and authorize the requested operation.
- Call the appropriate service.
- Return an appropriate HTTP response and status code.
- Map known application errors to HTTP responses.

It should not contain large business workflows or many unrelated database queries.

```ts
// app/api/products/route.ts

import { createProduct } from "@/features/products/services/product.service";
import { createProductSchema } from "@/features/products/schemas/product.schema";

export async function POST(request: Request) {
  const body: unknown = await request.json();
  const parsed = createProductSchema.safeParse(body);

  if (!parsed.success) {
    return Response.json(
      { error: "Invalid product data" },
      { status: 400 }
    );
  }

  const product = await createProduct(parsed.data);

  return Response.json(product, { status: 201 });
}
```

This example focuses on responsibility boundaries. A production endpoint should also handle malformed JSON and map known service errors to the correct status codes through the application's error-handling convention.

## 12. Service Layer: Business Logic

A service contains application and business logic. It should not depend on Next.js request or response objects.

Typical service responsibilities include:

- Applying business rules.
- Coordinating a multi-step operation.
- Checking domain conditions.
- Calling one or more data-access modules.
- Calling external services when required.
- Coordinating a transaction when an operation must be atomic.

A service should accept ordinary typed arguments and return application data or throw a meaningful application error. It should not return `Response.json()` or read directly from `Request`.

```ts
// features/products/services/product.service.ts

import { productRepository } from "@/features/products/repositories/product.repository";
import type { CreateProductInput } from "@/features/products/types/product.types";

export async function createProduct(input: CreateProductInput) {
  if (!input.name.trim()) {
    throw new Error("Product name is required");
  }

  if (input.price <= 0) {
    throw new Error("Product price must be positive");
  }

  if (input.stock < 0) {
    throw new Error("Stock cannot be negative");
  }

  return productRepository.create(input);
}
```

This is an illustrative service. In a production codebase, use the application's established domain-error types rather than relying on generic `Error` messages for every expected failure.

### One service can be reused by multiple entry points

```text
Route Handler ---------+
                       |
Server Action ----------+----> Product Service
                       |
Server Component -------+
```

A Server Component may call a read service directly. A Route Handler or Server Action may call the same business operation where appropriate.

## 13. Data-Access Layer and Repository Pattern

The data-access layer is responsible for communicating with a database or another data source.

Depending on the chosen technology, this layer may use:

- Mongoose models and queries.
- Prisma Client operations.
- Drizzle queries.
- A SQL driver or query builder.
- A document database SDK.
- An external service SDK.

The service should focus on what the application needs to do. The data-access implementation focuses on how the data is retrieved or stored.

Example using a technology-neutral module boundary:

```ts
// features/products/repositories/product.repository.ts

import { database } from "@/server/database/client";
import type { CreateProductInput } from "@/features/products/types/product.types";

export const productRepository = {
  async findById(id: string) {
    // Implement using the selected ORM, ODM, or database client.
  },

  async create(input: CreateProductInput) {
    // Implement using the selected ORM, ODM, or database client.
  },
};
```

The example intentionally does not assume a specific query API. Prisma, Drizzle, Mongoose, and other tools have different query syntax, schema definitions, return types, and transaction APIs. Keep those differences inside the technology-specific data-access implementation.

### Is a repository always required?

No. An ORM or ODM already provides data-access functionality. A repository adds another layer around it; it is not automatically required just because the project uses an ORM.

Add a repository or dedicated data-access module when:

- Multiple services need the same query or persistence operation.
- Queries are complex and should be kept out of business logic.
- The application needs to isolate persistence details from services.
- Tests benefit from replacing the persistence implementation.
- Data is combined from more than one source.

For a simple feature, a service can call a focused database module directly. Avoid creating a repository class and interface for every model without a practical reason.

## 14. ORM, ODM, Database, and Application Boundaries

These terms describe different parts of the persistence system:

- **Database:** stores and retrieves persistent data, such as PostgreSQL, MySQL, SQLite, or MongoDB.
- **ORM (Object-Relational Mapper):** maps application objects and operations to relational database structures. Prisma is commonly described as an ORM; Drizzle is a TypeScript ORM.
- **ODM (Object-Document Mapper):** maps application objects to document database structures. Mongoose is a common MongoDB ODM.
- **Database driver/client:** provides lower-level communication with the database.
- **Query builder:** helps construct database queries, often with more direct control over SQL.

The architecture should not depend on a specific vendor's query syntax outside the persistence boundary.

### Technology-specific code belongs behind the boundary

Keep connection setup, generated clients, model definitions, schema definitions, and query syntax in server-only persistence modules.

```text
features/products/
├── services/
│   └── product.service.ts          # application rules
├── repositories/
│   └── product.repository.ts       # persistence operations
└── types/
    └── product.types.ts            # application-facing types

server/database/
├── client.ts                       # connection/client setup
└── schema-or-models/               # ORM/ODM-specific definitions
```

The exact folder names can vary. A project using Prisma may organize its generated client and schema differently from a project using Drizzle or Mongoose. Preserve the boundary, not a rigid directory name.

### Do not leak persistence-specific types everywhere

Avoid making every component depend directly on ORM-generated or ODM document types. Database results may include internal fields, methods, relations, special date/decimal types, or fields the UI should never receive.

Map persistence results to application-facing types or DTOs where that improves safety and clarity:

```ts
export type ProductDTO = {
  id: string;
  name: string;
  price: number;
  stock: number;
};
```

A mapper can convert the database representation into the shape required by the application:

```ts
export function toProductDTO(record: ProductRecord): ProductDTO {
  return {
    id: String(record.id),
    name: record.name,
    price: Number(record.price),
    stock: record.stock,
  };
}
```

`ProductRecord` represents the type returned by the selected persistence implementation. Its exact definition depends on the ORM or ODM. Do not copy this illustrative type name into a project without defining it.

Use DTOs when they establish a useful boundary—for example, when hiding internal fields, normalizing values, or ensuring the client receives serializable data. Do not create mapping layers for every trivial object if they add no value.

## 15. Validation: Types Are Not Runtime Validation

TypeScript types are removed at runtime. They do not validate JSON received from a browser, a webhook, an external client, or an untrusted source.

This annotation does not validate the request body:

```ts
const body = (await request.json()) as CreateProductInput;
```

It only tells TypeScript to treat the value as that type. The actual input may still contain missing, invalid, or unexpected values.

Use runtime validation at system boundaries. A schema library such as Zod can validate and transform untrusted input:

```ts
// features/products/schemas/product.schema.ts

import { z } from "zod";

export const createProductSchema = z.object({
  name: z.string().trim().min(1).max(120),
  price: z.number().positive(),
  stock: z.number().int().min(0),
});

export type CreateProductInput = z.infer<typeof createProductSchema>;
```

Validate at entry points such as Route Handlers, Server Actions, and external integrations. Services should still enforce important business invariants because they may be called from more than one entry point.

Avoid duplicating every validation rule in multiple places. Separate:

- **Input validation:** Is the submitted value well-formed and of the expected shape?
- **Business validation:** Is this operation allowed under the application's rules?
- **Persistence constraints:** Does the database enforce required uniqueness, relations, and integrity constraints?

These layers complement one another; one does not replace the others.

---

## 16. Authentication and Authorization Boundaries

Authentication determines who the caller is. Authorization determines what that caller is allowed to do.

Authentication and authorization must be enforced on the server for protected data and mutations. Hiding a button or protecting a page visually is not sufficient.

A practical flow is:

```text
Request / Server Action
          |
          v
  Identify authenticated user
          |
          v
   Check permission / ownership
          |
          v
     Execute service
          |
          v
      Data access
```

Use shared server-side helpers for retrieving the current user and checking permissions. Keep those helpers server-only. Apply authorization close to the protected operation, not only in navigation or a layout.

For example, a user who can view their own orders should not be able to change an order ID in a request and read another user's order. The service or its trusted calling boundary must verify ownership or permission before returning the record.

Do not trust user IDs, roles, prices, ownership fields, or admin flags supplied by the browser. Derive trusted identity from the authenticated session and verify sensitive values on the server.

---

## 17. Error Handling Across Layers

Errors can originate from input validation, business rules, persistence, external services, or unexpected programming failures.

A clear error flow is:

```text
Data source / external service
              |
              v
       Data-access layer
              |
              v
           Service
              |
              v
   Route Handler / Server Action
              |
              v
      Safe result for caller
```

Each layer should add context only when it can do so meaningfully. Avoid catching an error only to throw the same error again without adding useful information or performing recovery.

### Use meaningful application errors

Expected failures should be distinguishable from unexpected failures. For example:

```ts
export class ProductNotFoundError extends Error {
  constructor() {
    super("Product not found");
    this.name = "ProductNotFoundError";
  }
}

export class InsufficientStockError extends Error {
  constructor() {
    super("Insufficient stock");
    this.name = "InsufficientStockError";
  }
}
```

A service can throw a domain-specific error:

```ts
const product = await productRepository.findById(productId);

if (!product) {
  throw new ProductNotFoundError();
}
```

The HTTP entry point maps known errors to appropriate HTTP status codes. Unexpected errors should be logged and return a generic safe message rather than exposing stack traces, SQL queries, database details, or secrets.

```ts
try {
  const product = await getProductById(id);
  return Response.json(product);
} catch (error) {
  if (error instanceof ProductNotFoundError) {
    return Response.json({ error: "Product not found" }, { status: 404 });
  }

  console.error("Failed to retrieve product", error);

  return Response.json(
    { error: "Something went wrong" },
    { status: 500 }
  );
}
```

This is a simplified example. A larger application can centralize error-to-response mapping so each Route Handler does not repeat the same logic.

### Keep HTTP details out of services and repositories

Avoid:

```ts
// Bad: service tied to HTTP
export async function createProduct(request: Request) {
  // Parse request, apply business rules, query database,
  // and return Response.json(...).
}
```

Prefer:

```ts
// Service: application operation
export async function createProduct(input: CreateProductInput) {
  return productRepository.create(input);
}

// Route Handler: HTTP response
const product = await createProduct(input);
return Response.json(product, { status: 201 });
```

A service returns application data or raises an application error. The Route Handler decides how that becomes an HTTP response.

---

## 18. Server Actions and Route Handlers: Choosing the Right Entry Point

Both can initiate server-side work, but they serve different purposes.

### Use a Server Action when

- A mutation is initiated by the application's own UI.
- The operation is closely tied to a form or interactive workflow.
- You want to use the Server Action model for submission and UI updates.

### Use a Route Handler when

- You need a conventional HTTP endpoint.
- An external client or service must call the application.
- You are implementing a webhook or integration endpoint.
- The endpoint needs explicit HTTP methods, headers, or response behavior.

Both should validate input, authenticate and authorize the caller, and reuse the same application service where appropriate.

Do not implement the same business rules separately in a Server Action and a Route Handler. Keep the shared operation in a service and let each entry point handle its own protocol concerns.

## 19. Data Flow: Read and Write Operations

### Read from a server-rendered page

```text
Browser requests page
        |
        v
Server Component
        |
        v
Read service
        |
        v
Data-access module
        |
        v
Database
        |
        v
DTO / serializable data
        |
        v
Rendered page
```

A Server Component should call the server-side service directly rather than making an unnecessary HTTP request to the same application.

### Write from a form or interactive component

```text
User submits form
        |
        v
Client Component
        |
        v
Server Action or Route Handler
        |
        v
Validate + authenticate + authorize
        |
        v
Application service
        |
        v
Data-access module
        |
        v
Database
        |
        v
Return safe result / update UI
```

The browser should never connect directly to a private database or receive server credentials.

## 20. Transactions and Multi-Step Workflows

A transaction ensures that a group of database operations is committed together or rolled back together, according to the database's transaction guarantees.

An e-commerce order might involve:

```text
Place Order
    |
    +--> Create order record
    +--> Reserve or reduce product stock
    +--> Create payment record
```

If these operations must succeed or fail as one unit, use a database transaction when supported and appropriate.

The service usually coordinates the workflow because it understands the complete business operation. The persistence layer executes the transaction using the selected database technology.

Different databases and ORMs expose different transaction APIs. For example, Prisma, Drizzle, Mongoose, and native database drivers do not share one universal transaction syntax. Keep that implementation detail inside the persistence boundary and follow the selected database's transaction semantics.

Important considerations:

- A transaction does not automatically include external services such as an email provider or payment gateway.
- Do not keep a database transaction open while waiting unnecessarily for a slow external API.
- For workflows involving external systems, use an appropriate sequence such as creating a pending record, calling the provider, and updating the final status, with retry and failure handling.
- Use database constraints and atomic update operations to protect critical invariants such as unique values and stock limits.

Do not add transaction complexity to operations that do not require it.

## 21. Dependency Direction

A maintainable architecture has understandable dependency direction.

A typical direction is:

```text
app/ route composition
       |
       v
feature components / entry points
       |
       v
application services
       |
       v
data-access implementation
       |
       v
ORM / ODM / database client
       |
       v
database
```

Shared generic UI should not import from a specific business feature. For example, `components/ui/button.tsx` should not import product services or order models.

A product feature may use shared UI components. The shared UI should not depend on the product feature. This keeps generic components reusable and prevents circular dependencies.

Keep database clients, secrets, and server-only modules out of Client Component import graphs. Use server-only boundaries where appropriate so accidental client imports are caught early.

## 22. Feature-Based Organization

As an application grows, organizing every file only by technical category can make related code difficult to find:

```text
services/
├── user.service.ts
├── product.service.ts
└── order.service.ts

repositories/
├── user.repository.ts
├── product.repository.ts
└── order.repository.ts
```

Feature-based organization keeps related code together:

```text
features/
├── auth/
│   ├── services/
│   ├── schemas/
│   └── types/
├── products/
│   ├── components/
│   ├── services/
│   ├── repositories/
│   ├── schemas/
│   └── types/
└── orders/
    ├── components/
    ├── services/
    ├── repositories/
    ├── schemas/
    └── types/
```

Both feature-based and layer-based organization can work. For a growing product application, grouping by feature often makes ownership and navigation easier. Choose the structure that helps the team find and change related code.

## 23. Shared Code: What Should Be Shared?

Share code when it represents a genuinely common responsibility.

Good candidates include:

- Generic UI components.
- Formatting helpers such as currency or date formatting.
- Authentication utilities used by multiple server entry points.
- Common validation primitives.
- Shared application types used by multiple features.

Do not create a shared abstraction just because two pieces of code look similar. They may represent different business rules that will evolve independently.

Avoid a huge `utils.ts`, `helpers.ts`, or `common.ts` file containing unrelated functions. Group utilities by purpose, such as `currency.ts`, `date.ts`, or `permissions.ts`.

---

## 24. Environment Variables and Server-Only Configuration

Configuration and secrets belong on the server.

Examples of server environment variables:

```env
DATABASE_URL=...
AUTH_SECRET=...
PAYMENT_PROVIDER_SECRET=...
```

Only values intentionally exposed to browser code should use the framework's public environment-variable convention, such as `NEXT_PUBLIC_` in Next.js. Never put database credentials, private API keys, signing secrets, or payment secrets in public variables.

Read and validate required environment variables in a central server-only configuration module where practical. Fail clearly during startup or initialization if required configuration is missing rather than allowing obscure runtime failures later.

Do not commit real `.env` files to source control. Provide a safe `.env.example` containing variable names and placeholder values, not real credentials.

## 25. Performance and Maintainability Considerations

Architecture should support performance without introducing unnecessary complexity.

### Frontend

- Keep Client Component boundaries as small as practical.
- Fetch server data in Server Components when appropriate.
- Avoid sending unused fields to Client Components.
- Avoid putting every value into global state.
- Reuse components when there is a real shared responsibility.
- Use appropriate image, font, and code-splitting techniques covered in the performance topic.

### Backend

- Keep database queries focused and request only required fields when supported.
- Avoid repeated queries when one appropriate query can provide the needed data.
- Add indexes based on actual query patterns and database capabilities.
- Paginate large collections instead of loading unbounded data.
- Measure slow operations before optimizing them.
- Use caching only when its invalidation and freshness behavior are understood.

### Code organization

- Keep functions focused.
- Prefer explicit names over clever abstractions.
- Avoid giant files and giant services.
- Avoid unnecessary layers and pass-through functions.
- Keep server-only and client-side code separated.
- Use consistent formatting, linting, and TypeScript checks.

Production-level code is not code with the most abstractions. It is code that is readable, predictable, secure, observable, testable, and appropriate for the application's complexity.

## 26. Common Architectural Mistakes

### 26.1 One giant page or component

**Problem:** One component fetches data, handles authentication, manages every interaction, and renders the entire page.

**Better:** Keep the route focused on composition. Extract feature components and server operations according to responsibility.

### 26.2 Adding `"use client"` everywhere

**Problem:** More code is sent to the browser and server-only capabilities become harder to use safely.

**Better:** Start with Server Components and add narrow Client Component boundaries only where interactivity is required.

### 26.3 Putting business logic in Route Handlers

**Problem:** Business rules become tied to HTTP and are duplicated when another entry point needs the same operation.

**Better:** Put reusable business operations in services. Keep HTTP parsing and response formatting in Route Handlers.

### 26.4 Putting business rules in repositories

**Problem:** Data access becomes mixed with decisions about how the application should behave.

**Better:** Keep repositories focused on persistence. Let services coordinate business rules and workflows.

### 26.5 Forcing a repository layer into every operation

**Problem:** Simple code becomes a chain of files that only forward arguments.

**Better:** Add a repository when query reuse, persistence isolation, or testing justifies it. It is optional.

### 26.6 Using ORM/ODM types throughout the UI

**Problem:** UI code becomes coupled to database-specific fields and special data types. Internal fields may accidentally be exposed.

**Better:** Return application-facing types or DTOs when a clear boundary is useful.

### 26.7 Trusting TypeScript types as runtime validation

**Problem:** External JSON can still contain invalid data even if it has been cast to a TypeScript type.

**Better:** Validate untrusted input at runtime.

### 26.8 Relying only on frontend authorization

**Problem:** Users can bypass UI restrictions by calling server endpoints directly.

**Better:** Authenticate and authorize every protected server operation.

### 26.9 Putting secrets in client code

**Problem:** Client-side values can be inspected by users.

**Better:** Keep secrets and private integrations in server-only modules.

### 26.10 Over-abstraction

**Problem:** Every feature has controllers, interfaces, factories, adapters, mappers, repositories, and multiple service layers without a real need.

**Better:** Introduce a layer only when it solves a concrete problem.

## 27. When Should Each Layer Be Added?

Start with the simplest structure that keeps the code understandable.

### Stage 1 — Simple operation

```text
Route Handler / Server Component
              |
              v
       Database client
              |
              v
           Database
```

A direct data call can be acceptable for a simple read or small operation.

### Stage 2 — Business logic grows

```text
Route Handler / Server Action / Server Component
                         |
                         v
                      Service
                         |
                         v
                  Database client
                         |
                         v
                      Database
```

Add a service when business rules, calculations, workflows, or reuse become meaningful.

### Stage 3 — Data access becomes complex or repeated

```text
Route Handler / Server Action / Server Component
                         |
                         v
                      Service
                         |
                         v
                   Repository
                         |
                         v
                  ORM / ODM / driver
                         |
                         v
                      Database
```

Add a repository when repeated queries, complex persistence logic, multiple data sources, or test isolation justify the extra boundary.

Do not add layers because a diagram says every application must have them. Add them when they make the code easier to change and understand.

## 29. Final Architecture Principles

1. Keep route files focused on routing and page composition.
2. Organize business code by feature as the application grows.
3. Start with Server Components and keep Client Component boundaries narrow.
4. Keep local UI state local; use shared state only when multiple components need it.
5. Use `const` by default and `let` only when reassignment is required. Avoid `var`.
6. Use descriptive names and focused functions.
7. Separate caller input types from application output types where their responsibilities differ.
8. Validate untrusted input at runtime; TypeScript alone is not runtime validation.
9. Keep HTTP concerns in Route Handlers and UI invocation concerns in Server Actions.
10. Put reusable business rules and workflows in services.
11. Keep database-specific queries and technology-specific types behind a data-access boundary.
12. Use a repository when it provides real value; it is not mandatory.
13. Do not expose secrets, database clients, or private server modules to the browser.
14. Enforce authentication and authorization on the server.
15. Use transactions for operations that require atomic database changes, respecting the chosen database's capabilities.
16. Return safe, application-facing data to the client.
17. Prefer readable, consistent code over clever abstractions.
18. Introduce architecture layers when they solve real complexity, reuse, testing, or maintainability problems.

> **Separate responsibilities, not simply files.**
>
> **Keep technology-specific persistence details behind a clear boundary.**
>
> **Good architecture is the simplest structure that keeps the application understandable as it grows.**
