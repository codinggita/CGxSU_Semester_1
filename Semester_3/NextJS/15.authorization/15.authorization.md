# 15. Authorization

Authorization in Next.js — protect pages, Server Actions, APIs, admin routes, and user-owned resources. RBAC and role-based access concepts from Express applications apply; the difference is **where and how** authorization is enforced in Next.js (App Router and Pages Router).

---

## 1. Authorization in Next.js

After authentication resolves the current user, authorization decides whether that user may perform an operation.

```text
getCurrentUser()  →  role / ownership check  →  allow or deny
```

Keep authentication and authorization separate:

```ts
const user = await getCurrentUser();
if (!user) return unauthorized(); // 401 — not logged in
if (user.role !== "ADMIN") return forbidden(); // 403 — logged in, not allowed
```

**Roles in Prisma:**

```prisma
enum Role {
  USER
  ADMIN
}

model User {
  id           Int      @id @default(autoincrement())
  name         String
  email        String   @unique
  passwordHash String
  role         Role     @default(USER)
  createdAt    DateTime @default(now())
}
```

For small apps, `user.role === "ADMIN"` is enough. For larger apps, map roles to permissions (`users:delete`, `orders:refund`) and check with a `hasPermission(user, permission)` helper. Start with roles; introduce permissions when role combinations become hard to manage.

## 2. Authorization Helpers — Page vs API

Pages and APIs need **different failure behavior**:

- **Page helpers** call `redirect()` — send the browser to `/login` or `/forbidden`.
- **API helpers** **throw** — Route Handlers and Server Actions return `401` / `403` JSON. You cannot redirect from an API response.

Define both in `lib/auth/authorization.ts`:

```ts
import { redirect } from "next/navigation";
import { getCurrentUser } from "@/lib/auth/session";

// Pages — redirect on failure
export async function requirePageUser() {
	const user = await getCurrentUser();
	if (!user) redirect("/login");
	return user;
}

export async function requirePageAdmin() {
	const user = await requirePageUser();
	if (user.role !== "ADMIN") redirect("/forbidden");
	return user;
}

// Route Handlers / Server Actions — throw on failure
export async function requireApiUser() {
	const user = await getCurrentUser();
	if (!user) throw new Error("Unauthorized");
	return user;
}

export async function requireApiAdmin() {
	const user = await requireApiUser();
	if (user.role !== "ADMIN") throw new Error("Forbidden");
	return user;
}
```

Optional role helper for custom checks:

```ts
export function requireRole(user: { role: string }, role: string) {
	if (user.role !== role) throw new Error("Forbidden");
}
```

## 3. Protected Pages

### 3.1 App Router

```tsx
import { requirePageAdmin } from "@/lib/auth/authorization";

export default async function AdminPage() {
	await requirePageAdmin();

	return (
		<div>
			<h1>Admin Dashboard</h1>
		</div>
	);
}
```

Authenticated user route (no admin required):

```tsx
import { requirePageUser } from "@/lib/auth/authorization";

export default async function DashboardPage() {
	const user = await requirePageUser();

	return (
		<div>
			<h1>Dashboard</h1>
			<p>{user.name}</p>
		</div>
	);
}
```

### 3.2 Pages Router

```tsx
export async function getServerSideProps(context) {
	const user = await getCurrentUser(context.req);

	if (!user) {
		return { redirect: { destination: "/login", permanent: false } };
	}

	if (user.role !== "ADMIN") {
		return { redirect: { destination: "/forbidden", permanent: false } };
	}

	return { props: {} };
}
```

Folder structure (`app/admin/...`) does **not** enforce access — you must check authorization in every page, action, and API.

## 4. Protected Server Actions

`"use server"` means the function runs on the server. It does **not** mean only authorized users can call it. A client can invoke any exposed Server Action directly — always authorize inside the action.

```ts
"use server";

import { requireApiAdmin } from "@/lib/auth/authorization";
import { prisma } from "@/lib/prisma";

export async function deleteUser(userId: number) {
	await requireApiAdmin();

	await prisma.user.delete({ where: { id: userId } });
}
```

---

## 5. Protected APIs

APIs must enforce authorization independently of pages. An attacker can call `/api/admin/users` without visiting `/admin`.

### 5.1 App Router

```ts
import { getCurrentUser } from "@/lib/auth/session";

export async function GET() {
	const user = await getCurrentUser();

	if (!user) {
		return Response.json({ error: "Unauthorized" }, { status: 401 });
	}

	if (user.role !== "ADMIN") {
		return Response.json({ error: "Forbidden" }, { status: 403 });
	}

	const users = await getAllUsers();
	return Response.json(users);
}
```

With helpers, map thrown errors to status codes:

```ts
export async function DELETE(
	request: Request,
	context: { params: Promise<{ id: string }> },
) {
	try {
		await requireApiAdmin();
	} catch (e) {
		const message = e instanceof Error ? e.message : "Unauthorized";
		const status = message === "Forbidden" ? 403 : 401;
		return Response.json({ error: message }, { status });
	}

	const { id } = await context.params;
	await userService.deleteUser(Number(id));
	return new Response(null, { status: 204 });
}
```

### 5.2 Pages Router

```ts
import type { NextApiRequest, NextApiResponse } from "next";

export default async function handler(
	req: NextApiRequest,
	res: NextApiResponse,
) {
	const user = await getCurrentUser(req);

	if (!user) return res.status(401).json({ error: "Unauthorized" });
	if (user.role !== "ADMIN")
		return res.status(403).json({ error: "Forbidden" });

	const users = await getAllUsers();
	return res.status(200).json(users);
}
```

## 6. Resource Ownership

Role checks alone are not enough when users share the same role but must only access their own data.

```ts
const user = await requireApiUser();

const order = await prisma.order.findUnique({ where: { id: orderId } });

if (!order) return notFound();
if (order.userId !== user.id) return forbidden();
```

Combine role and ownership when admins need broader access:

```ts
if (user.role === "ADMIN") {
	// allowed
} else if (user.id === targetUserId) {
	// owner allowed
} else {
	return forbidden();
}
```

Scope queries to the current user — never trust a client-supplied `userId`:

```ts
const user = await requirePageUser();

const orders = await prisma.order.findMany({
	where: { userId: user.id },
});
```

## 7. Authorization and the Service Layer

Authorize at the route/action boundary, then delegate to a service:

```text
Route Handler / Server Action / API
      ↓
requireApiUser() / requireApiAdmin()
      ↓
Service → Repository → Database
```

```ts
"use server";

export async function updateProduct(
	productId: number,
	data: UpdateProductInput,
) {
	await requireApiAdmin();
	return productService.update(productId, data);
}
```

Suggested folder layout:

```text
lib/
├── auth/
│   ├── session.ts
│   ├── authentication.ts
│   └── authorization.ts
├── services/
│   └── user.service.ts
└── repositories/
    └── user.repository.ts
```

## 8. Route Groups and Middleware

**Route groups** organize routes without changing URLs. They do **not** enforce authorization:

```text
app/
├── (public)/login/
├── (user)/dashboard/
└── (admin)/admin/
```

You still call `requirePageUser()` or `requirePageAdmin()` in each page.

**Middleware** can provide an early check on paths like `/admin/*`, but do not rely on it as the only boundary — Server Actions, Route Handlers, and APIs must still authorize at the operation level.

---

## 9. App Router vs Pages Router

| Concern         | App Router                               | Pages Router                    |
| --------------- | ---------------------------------------- | ------------------------------- |
| Page protection | `requirePageAdmin()` in Server Component | `getServerSideProps` + redirect |
| API protection  | `app/api/.../route.ts`                   | `pages/api/...`                 |
| Server Actions  | `"use server"` + `requireApiAdmin()`     | N/A (use API routes)            |

The security model is identical: authenticate → authorize → perform operation.

## 10. End-to-End Example: Admin User Management

```text
/admin/users          → requirePageAdmin() on page
Delete button (UI)    → hide for non-admins (UX only)
deleteUser action     → requireApiAdmin()
userService.delete()  → business logic
```

```tsx
// Page
export default async function AdminUsersPage() {
  await requirePageAdmin();
  const users = await userService.getAll();
  return (/* render users */);
}
```

```ts
// Server Action
"use server";

export async function deleteUser(userId: number) {
	await requireApiAdmin();
	await userService.deleteUser(userId);
}
```

UI checks improve UX; server checks provide security.

---

## 11. Common Authorization Mistakes

- **Only hiding buttons** — `{isAdmin && <DeleteButton />}` is not security; the Server Action/API must also check.
- **Trusting role from the client** — never accept `{ "role": "ADMIN" }` from the browser; read role from session/server state.
- **Trusting user IDs from the client** — use `user.id` from `requireApiUser()`, not `?userId=10` from the query string.
- **Protecting the page but not the API** — `/admin` can be gated while `/api/admin/users` stays open.
- **Protecting the API but not the Server Action** — both mutate data; both need checks.
- **Middleware as the only gate** — enforce authorization where the operation runs.
- **Default role `ADMIN`** — use `@default(USER)` in Prisma.
- **One giant auth function** — separate `getCurrentUser()`, page helpers, and API helpers.

## 12. Recommended Architecture

```text
                    Request
                       │
                       ▼
                Authentication
                       │
                       ▼
                 Current User
                       │
                       ▼
                Authorization
                ┌──────┴──────┐
                │             │
              Role       Ownership
                │             │
                └──────┬──────┘
                       ▼
                 Service Layer
                       │
                       ▼
               Repository Layer
                       │
                       ▼
                    Database
```

For every sensitive operation: authenticate → authorize (role and/or ownership) → execute via service layer.

> **Client-side checks improve UX. Server-side checks provide security.**
>
> **Protect pages, Server Actions, APIs, and individual resources independently.**
>
> **Role and permissions must come from trusted server-side state, not client-supplied data.**
