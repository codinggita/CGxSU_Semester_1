# 21. Images, Fonts & Performance

Next.js handles images, fonts, JavaScript bundles, code splitting, lazy loading, dynamic imports, and overall application performance through built-in APIs and conventions. `next/image`, `next/font`, and dynamic imports work with both the App Router and Pages Router. Server/Client Component optimization is primarily an App Router concept.

---

## 1. Why Performance Matters

A web application can be functionally correct but still provide a poor user experience if it loads slowly.

Common performance costs include:

- Large images
- Large JavaScript bundles
- Too many network requests
- Slow fonts
- Unnecessary client-side JavaScript
- Request waterfalls
- Slow backend/database operations

A useful mental model is:

```text
Performance
│
├── Images
├── Fonts
├── JavaScript
├── Network
├── Rendering
└── Server / Database
```

Performance optimization is therefore not only a frontend problem.

## 2. Next.js Performance Features

Next.js provides several features that help optimize applications:

- `next/image`
- `next/font`
- Automatic route-level code splitting
- Dynamic imports
- Lazy loading
- Server Components
- Client Components
- Streaming and loading UI
- Caching mechanisms

The goal is not to use every feature everywhere.

The goal is:

```text
Send less unnecessary work
        ↓
Load important content earlier
        ↓
Improve user experience
```

## 3. `next/image`

Use `next/image` instead of `<img>` for automatic optimization, responsive sizing, lazy loading, and layout stability.

```tsx
import Image from "next/image";

<Image src='/product.jpg' alt='Product' width={800} height={600} />;
```

### Local & Static Imports

**Public folder** — reference by path:

```tsx
<Image src='/images/product.jpg' alt='Product' width={800} height={600} />
```

**Static import** — Next.js reads dimensions automatically:

```tsx
import heroImage from "./assets/hero.png";

<Image src={heroImage} alt='Hero' />;
```

### Responsive Images & `sizes`

Use `fill` when the image should fill a container; the parent must have `position: relative` and defined dimensions:

```tsx
<div className='relative h-96 w-full'>
	<Image src='/images/hero.jpg' alt='Hero' fill className='object-cover' />
</div>
```

With `fill`, add `sizes` so the browser downloads an appropriately sized file:

```tsx
<Image
	src='/images/hero.jpg'
	alt='Hero'
	fill
	sizes='(max-width: 768px) 100vw, 50vw'
/>
```

### `quality`, `priority`, and Lazy Loading

```tsx
<Image src='/product.jpg' alt='Product' width={800} height={600} quality={75} />
```

Use `priority` for above-the-fold images (hero, main product image). In Next.js 16+, `preload` replaces deprecated `priority`. Do not mark every image as priority.

Images below the viewport lazy-load by default — no extra configuration needed.

### Remote Images

External images require `remotePatterns` in `next.config.ts`:

```ts
const nextConfig: NextConfig = {
	images: {
		remotePatterns: [{ protocol: "https", hostname: "cdn.example.com" }],
	},
};
```

```tsx
<Image
	src='https://cdn.example.com/products/macbook.jpg'
	alt='MacBook Pro'
	width={800}
	height={600}
/>
```

With a separate Node.js API returning image URLs (`product.image` from S3/Cloudinary/CDN), pass the URL to `Image` — the hostname must be in `remotePatterns`.

## 4. `next/font`

Next.js provides:

```tsx
next / font;
```

for optimized font loading.

Example:

```tsx
import { Inter } from "next/font/google";

const inter = Inter({
	subsets: ["latin"],
});
```

Then:

```tsx
<body className={inter.className}>{children}</body>
```

---

### Why Use `next/font`?

Poor font loading can cause:

- Flash of invisible text
- Flash of unstyled text
- Layout shifts
- Additional network work

`next/font` integrates fonts into the Next.js application so they can be optimized as part of the application build/runtime behavior.

---

### Google Fonts

Example:

```tsx
import { Inter } from "next/font/google";

const inter = Inter({
	subsets: ["latin"],
	display: "swap",
});
```

Then:

```tsx
export default function RootLayout({
	children,
}: {
	children: React.ReactNode;
}) {
	return (
		<html lang='en'>
			<body className={inter.className}>{children}</body>
		</html>
	);
}
```

Only load the font configuration your application actually needs.

---

### Font Weights

Example:

```tsx
const inter = Inter({
	subsets: ["latin"],
	weight: ["400", "600", "700"],
});
```

If the application only uses:

```text
400
600
700
```

there is little reason to load many additional weights.

Avoid unnecessarily loading:

```text
100
200
300
500
800
900
```

---

### Local Fonts

For local font files:

```tsx
import localFont from "next/font/local";

const myFont = localFont({
	src: "./fonts/MyFont.woff2",
});
```

Then:

```tsx
<body className={myFont.className}>{children}</body>
```

---

### Multiple Local Font Weights

Example:

```tsx
const myFont = localFont({
	src: [
		{
			path: "./fonts/MyFont-Regular.woff2",
			weight: "400",
			style: "normal",
		},
		{
			path: "./fonts/MyFont-Bold.woff2",
			weight: "700",
			style: "normal",
		},
	],
});
```

This lets the browser use the appropriate font file for the requested weight.

---

### Font Optimization Principles

Fonts are assets too.

A useful rule is:

```text
Load only what you need.
```

Avoid:

```text
5 font families
×
10 weights
×
multiple styles
```

when the design only needs:

```text
1 font family
×
3 weights
```

## 5. Code Splitting & Bundle Size

Code splitting divides JavaScript into smaller chunks. Lazy loading defers fetching a chunk until it is needed. Dynamic imports achieve both.

```text
One huge bundle
       ↓
┌────────────┬────────────┬────────────┐
│ Home       │ Dashboard  │ Admin      │
│ chunk      │ chunk      │ chunk      │
└────────────┴────────────┴────────────┘
```

```text
Code splitting:  Large bundle  →  Multiple chunks
Lazy loading:   Chunk exists  →  Load when needed (not immediately)
```

Goal: send only the JavaScript the user needs for the current route — not one monolithic bundle on every page load.

## 6. Next.js Code Splitting

**Automatic (route-level):** Each `page.tsx` gets its own JavaScript chunk — no configuration needed.

```text
app/
├── page.tsx           → home chunk
├── products/page.tsx  → products chunk
└── dashboard/page.tsx → dashboard chunk
```

**Manual (component-level):** Use `next/dynamic` when one route contains heavy components that should load in a separate chunk — or only when needed.

```tsx
import dynamic from "next/dynamic";

const HeavyChart = dynamic(() => import("@/components/HeavyChart"));

export default function DashboardPage() {
  return (
    <main>
      <h1>Dashboard</h1>
      <HeavyChart />
    </main>
  );
}
```

Load on condition (e.g. admin-only panel):

```tsx
"use client";

import { useState } from "react";
import dynamic from "next/dynamic";

const AdminPanel = dynamic(() => import("@/components/AdminPanel"));

export default function DashboardPage() {
  const [showAdmin, setShowAdmin] = useState(false);

  return (
    <main>
      <h1>Dashboard</h1>
      <button onClick={() => setShowAdmin(true)}>Admin</button>
      {showAdmin && <AdminPanel />}
    </main>
  );
}
```

Route splitting handles pages. `next/dynamic` handles heavy components **inside** a page.

## 7. Dynamic Imports

`next/dynamic` is the Next.js API for manual code splitting. If you have used `React.lazy()` in CRA/Vite, the difference is SSR support:

| | `React.lazy()` | `next/dynamic()` |
| --- | --- | --- |
| SSR | No | Yes, by default |
| Suspense | Required | Optional via `loading` |
| Client-only | N/A | `{ ssr: false }` in a Client Component |

```tsx
// React.lazy — client-only, Suspense required
"use client";
import { lazy, Suspense } from "react";
const Chart = lazy(() => import("./Chart"));
// <Suspense fallback={...}><Chart /></Suspense>

// next/dynamic — SSR by default
import dynamic from "next/dynamic";
const Chart = dynamic(() => import("./Chart"), {
  loading: () => <p>Loading...</p>,
});
```

### `ssr: false` for browser-only components

`ssr: false` **must** be in a Client Component — using it in a Server Component causes a build error:

```text
`ssr: false` is not allowed with `next/dynamic` in Server Components.
```

Use it only when a component depends on `window`, `document`, WebGL, or similar browser APIs — not as a generic optimization.

```tsx
"use client";

import dynamic from "next/dynamic";

const Map = dynamic(() => import("./Map"), { ssr: false });

export default function MapSection() {
  return <Map />;
}
```

Import `MapSection` from a Server Component page. The map chunk loads client-side only; the rest of the page still server-renders.

## 8. Common Causes of Large Bundles

Common causes include:

- Large dependencies
- Unused dependencies
- Large chart libraries
- Rich text editors
- Large UI libraries
- Duplicate packages
- Excessive Client Components
- Importing unnecessary functionality

---

## 9. Avoid Unnecessary Client Components

Bad:

```tsx
"use client";

export default function ProductPage() {
	return (
		<main>
			<h1>Product</h1>
			<p>Description...</p>
		</main>
	);
}
```

If the component does not require:

```text
useState
useEffect
Event handlers
Browser APIs
Client-only libraries
```

it may not need to be a Client Component.

Prefer:

```tsx
export default function ProductPage() {
	return (
		<main>
			<h1>Product</h1>
			<p>Description...</p>
		</main>
	);
}
```

## 10. Performance Checklist

### Images

```text
□ Use next/image where appropriate
□ Provide meaningful alt text
□ Provide correct dimensions
□ Use sizes for responsive images
□ Optimize important above-the-fold images
□ Lazy-load non-critical images
□ Configure trusted remote image sources
□ Avoid unnecessarily large source files
```

### Fonts

```text
□ Use next/font where appropriate
□ Load only required font families
□ Load only required weights
□ Avoid unnecessary font styles
□ Use local fonts when appropriate
```

### JavaScript

```text
□ Keep Server Components as Server Components
□ Keep Client Component boundaries small
□ Avoid unnecessary dependencies
□ Use dynamic imports for genuinely heavy/optional code
□ Lazy-load non-critical interactive components
□ Inspect bundle size
```

### Network

```text
□ Avoid request waterfalls
□ Parallelize independent requests
□ Cache appropriate data
□ Avoid duplicate requests
□ Optimize backend/database operations
```
