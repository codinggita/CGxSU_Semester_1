# 14. Authentication & Authorization

Authentication and authorization work together to protect a Next.js application. Authentication identifies the user; authorization determines what that user is allowed to access or do.

This topic uses the **App Router** and **Auth.js (NextAuth)** as the primary authentication approach. Custom sessions and JWTs are also introduced to explain the alternatives.

---

## 1. Authentication Approaches

There are different ways to implement authentication in a web application.

### 1.1 Session-Based Authentication

In session-based authentication, the server creates a session after successful login.

- The server stores the session, usually in a database or session store.
- The browser receives a session identifier in a cookie.
- The browser automatically sends the cookie with subsequent requests.
- The server uses the session identifier to find the authenticated user.

```text
Login
  |
  v
Server creates session
  |
  v
Browser receives session cookie
  |
  v
Browser sends cookie with later requests
  |
  v
Server looks up session and identifies user
```

```tsx
// app/api/auth/login/route.ts

import { cookies } from "next/headers";

import { connectToDatabase } from "@/lib/db";
import User from "@/models/user";
import { verifyPassword } from "@/lib/auth/password";
import { createSession } from "@/lib/auth/session";

export async function POST(request: Request) {
	try {
		const body = await request.json();
		const { email, password } = body;

		if (!email || !password) {
			return Response.json(
				{ error: "Email and password are required" },
				{ status: 400 },
			);
		}

		await connectToDatabase();

		const user = await User.findOne({ email }).select("+passwordHash");

		if (!user) {
			return Response.json(
				{ error: "Invalid credentials" },
				{ status: 401 },
			);
		}

		const valid = await verifyPassword(password, user.passwordHash);

		if (!valid) {
			return Response.json(
				{ error: "Invalid credentials" },
				{ status: 401 },
			);
		}

		const session = await createSession(user._id.toString());

		const cookieStore = await cookies();

		cookieStore.set("session", session.id, {
			httpOnly: true,
			secure: process.env.NODE_ENV === "production",
			sameSite: "lax",
			path: "/",
			maxAge: 60 * 60 * 24 * 7,
		});

		return Response.json({
			id: user._id.toString(),
			name: user.name,
			email: user.email,
		});
	} catch {
		return Response.json(
			{ error: "Something went wrong" },
			{ status: 500 },
		);
	}
}
```

```ts
// lib/auth/password.ts
import bcrypt from "bcryptjs";

export async function verifyPassword(password: string, passwordHash: string) {
	return bcrypt.compare(password, passwordHash);
}
```

```ts
// lib/auth/session.ts

import { randomBytes, createHash } from "crypto";
import { connectToDatabase } from "@/lib/db";
import Session from "@/models/session";

export async function createSession(userId: string) {
	await connectToDatabase();

	const sessionToken = randomBytes(32).toString("hex");

	const tokenHash = createHash("sha256").update(sessionToken).digest("hex");

	const expiresAt = new Date(Date.now() + 7 * 24 * 60 * 60 * 1000);

	await Session.create({
		userId,
		tokenHash,
		expiresAt,
	});

	return {
		id: sessionToken,
		expiresAt,
	};
}
```

```ts
// lib/auth/get-user.ts

import { cookies } from "next/headers";
import { connectToDatabase } from "@/lib/db";
import Session from "@/models/session";

export async function getAuthenticatedUserId() {
	const cookieStore = await cookies();
	const sessionId = cookieStore.get("session")?.value;

	if (!sessionId) return null;

	try {
		await connectToDatabase();

		const session = await Session.findOne({
			sessionId,
			expiresAt: { $gt: new Date() },
		}).select("userId");

		return session?.userId?.toString() ?? null;
	} catch {
		return null;
	}
}
```

Implement this code snippet in every route handler where you want to authenticate the user.

```ts
const userId = await getAuthenticatedUserId();

if (!userId) {
	return Response.json({ error: "Unauthorized" }, { status: 401 });
}
```

```ts
// app/api/auth/logout/route.ts

import { cookies } from "next/headers";

import { deleteSession } from "@/lib/auth/session";

export async function POST() {
	try {
		const cookieStore = await cookies();

		const sessionId = cookieStore.get("session")?.value;

		if (sessionId) {
			await deleteSession(sessionId);
		}

		cookieStore.delete("session");

		return Response.json({ success: true });
	} catch {
		return Response.json(
			{ error: "Something went wrong" },
			{ status: 500 },
		);
	}
}
```

```tsx
// app/(auth)/login/page.tsx

import { redirect } from "next/navigation";
import { getAuthenticatedUserId } from "@/lib/auth/session";
import LoginForm from "@/components/auth/login-form";

export default async function LoginPage() {
	const userId = await getAuthenticatedUserId();

	if (userId) {
		redirect("/dashboard");
	}

	return <LoginForm />;
}
```

The cookie stores a session identifier, not the user's password or complete user record.

### 1.2 JWT-Based Authentication

JWT (JSON Web Token) is a token-based approach. After successful login, the server creates a signed token. The client sends that token with later requests, and the server verifies it.

A common request format is:

```http
Authorization: Bearer <token>
```

JWTs can be useful for APIs and clients such as mobile applications. A JWT-based system does not necessarily require a server-side session record, although applications may maintain additional server-side state for revocation or other requirements.

### Implementing JWT Authentication with Cookies

For browser-based Next.js applications, a JWT can be stored in an `HttpOnly` cookie. The browser automatically sends this cookie with requests to the same site. The server can verify the JWT signature and expiry without querying the database for a session record on every request.

This implementation uses `jose` to sign and verify JWTs.

Install the package:

```bash
npm install jose
```

Create a secret for signing tokens and keep it in the server environment. Generate a strong secret (for example, using `openssl rand -base64 32`).

```env
JWT_SECRET="your-long-random-secret"
```

Do not commit the real secret to source control or expose it using a `NEXT_PUBLIC_` variable.

#### 1. Create JWT Utilities

Create functions for signing and verifying JWTs. These functions are shared by the login route, Proxy, and server-side authentication helper.

```ts
// lib/auth/jwt.ts
import { SignJWT, jwtVerify } from "jose";

const secret = process.env.JWT_SECRET;

if (!secret) {
	throw new Error("JWT_SECRET is not configured");
}

const secretKey = new TextEncoder().encode(secret);

export async function signToken(userId: string) {
	return new SignJWT({ userId })
		.setProtectedHeader({ alg: "HS256" })
		.setIssuedAt()
		.setExpirationTime("7d")
		.sign(secretKey);
}

export async function verifyToken(token: string) {
	try {
		const { payload } = await jwtVerify(token, secretKey, {
			algorithms: ["HS256"],
		});

		if (typeof payload.userId !== "string") return null;

		return { userId: payload.userId };
	} catch {
		return null;
	}
}
```

- `signToken()` creates a signed JWT containing the user ID and an expiration time.
- `verifyToken()` verifies the signature and expiration, returning the user ID only when the token is valid.
- The signing secret stays on the server and is never sent to the browser.

#### 2. Login Route — Create JWT and Set Cookie

After validating the email and password against the database, create a JWT and store it in an `HttpOnly` cookie. The credential-checking portion remains the same as the session-based login; only the session creation and cookie value change.

```ts
// app/api/auth/login/route.ts
import { cookies } from "next/headers";

import { connectToDatabase } from "@/lib/db";
import User from "@/models/user";
import { verifyPassword } from "@/lib/auth/password";
import { signToken } from "@/lib/auth/jwt";

export async function POST(request: Request) {
	try {
		const body = await request.json();
		const { email, password } = body;

		if (!email || !password) {
			return Response.json(
				{ error: "Email and password are required" },
				{ status: 400 },
			);
		}

		await connectToDatabase();

		const user = await User.findOne({ email }).select("+passwordHash");

		if (!user) {
			return Response.json(
				{ error: "Invalid credentials" },
				{ status: 401 },
			);
		}

		const valid = await verifyPassword(password, user.passwordHash);

		if (!valid) {
			return Response.json(
				{ error: "Invalid credentials" },
				{ status: 401 },
			);
		}

		const token = await signToken(user._id.toString());
		const cookieStore = await cookies();

		cookieStore.set("auth-token", token, {
			httpOnly: true,
			secure: process.env.NODE_ENV === "production",
			sameSite: "lax",
			path: "/",
			maxAge: 60 * 60 * 24 * 7,
		});

		return Response.json({
			id: user._id.toString(),
			name: user.name,
			email: user.email,
		});
	} catch {
		return Response.json(
			{ error: "Something went wrong" },
			{ status: 500 },
		);
	}
}
```

The cookie contains the signed JWT, rather than a session ID. Because the cookie is `HttpOnly`, client-side JavaScript cannot read it. The browser sends it automatically with requests to the site.

#### 3. Authentication Helper — Read and Verify JWT

Create a reusable server-side function that reads the cookie and verifies the token. Unlike the session-based helper, this function does not query the sessions collection.

```ts
// lib/auth/get-user.ts
import { cookies } from "next/headers";
import { verifyToken } from "@/lib/auth/jwt";

export async function getAuthenticatedUserId() {
	const cookieStore = await cookies();
	const token = cookieStore.get("auth-token")?.value;

	if (!token) return null;

	const payload = await verifyToken(token);
	return payload?.userId ?? null;
}
```

Use this helper in protected server-side operations:

```ts
const userId = await getAuthenticatedUserId();

if (!userId) {
	return Response.json({ error: "Unauthorized" }, { status: 401 });
}
```

#### 4. Protect Routes Using Proxy

Proxy can perform an early authentication check and redirect unauthenticated visitors away from protected route groups. Since JWT verification is local, this check does not require a database lookup.

```ts
// proxy.ts
import { NextRequest, NextResponse } from "next/server";
import { verifyToken } from "@/lib/auth/jwt";

export async function proxy(request: NextRequest) {
	const token = request.cookies.get("auth-token")?.value;
	const payload = token ? await verifyToken(token) : null;

	if (!payload) {
		return NextResponse.redirect(new URL("/login", request.url));
	}

	return NextResponse.next();
}

export const config = {
	matcher: ["/dashboard/:path*", "/admin/:path*"],
};
```

The matcher limits Proxy checks to the specified route patterns. A valid JWT allows the request to continue; a missing, expired, or invalid token redirects the user to the login page.

Proxy is an early navigation guard, not the only security boundary. Route Handlers and Server Actions must still authenticate the user before performing sensitive operations and enforce permissions or resource ownership where required.

#### 5. Protect a Page on the Server

Proxy handles early redirects, but a protected Server Component can also use the authentication helper before rendering private content.

```tsx
// app/dashboard/page.tsx
import { redirect } from "next/navigation";
import { getAuthenticatedUserId } from "@/lib/auth/get-user";

export default async function DashboardPage() {
	const userId = await getAuthenticatedUserId();

	if (!userId) {
		redirect("/login");
	}

	return <h1>Dashboard</h1>;
}
```

#### 6. Logout Route — Remove Cookie

With this stateless JWT implementation, logout removes the authentication cookie from the browser. There is no database session to delete. The JWT remains cryptographically valid until it expires, but the browser no longer sends it after the cookie is cleared.

```ts
// app/api/auth/logout/route.ts
import { cookies } from "next/headers";

export async function POST() {
	const cookieStore = await cookies();
	cookieStore.delete("auth-token");

	return Response.json({ success: true });
}
```

#### 7. Login Page — Redirect Already-Authenticated Users

If the visitor already has a valid JWT, redirect them away from the login page.

```tsx
// app/(auth)/login/page.tsx
import { redirect } from "next/navigation";
import { getAuthenticatedUserId } from "@/lib/auth/get-user";
import LoginForm from "@/components/auth/login-form";

export default async function LoginPage() {
	const userId = await getAuthenticatedUserId();

	if (userId) {
		redirect("/dashboard");
	}

	return <LoginForm />;
}
```

#### 8. Protect Route Handlers and Server Actions

A protected page does not automatically protect its Route Handler or Server Action. Use the authentication helper inside each sensitive operation.

Route Handler example:

```ts
// app/api/orders/route.ts
import { getAuthenticatedUserId } from "@/lib/auth/get-user";

export async function GET() {
	const userId = await getAuthenticatedUserId();

	if (!userId) {
		return Response.json({ error: "Unauthorized" }, { status: 401 });
	}

	// Fetch only the orders belonging to this user.
	return Response.json({ message: "Authorized request" });
}
```

Server Action example:

```ts
// app/orders/actions.ts
"use server";

import { getAuthenticatedUserId } from "@/lib/auth/get-user";

export async function createOrder() {
	const userId = await getAuthenticatedUserId();

	if (!userId) {
		throw new Error("Unauthorized");
	}

	// Create the order for the authenticated user.
}
```

Always derive the user ID from the verified token, not from a user ID sent by the client. Perform authorization and ownership checks before accessing or modifying protected resources.

### 2.3 Session vs JWT

| Session-Based                                    | JWT-Based                                 |
| ------------------------------------------------ | ----------------------------------------- |
| Server stores session data                       | Token carries signed claims               |
| Browser commonly stores a session ID in a cookie | Client sends the token with requests      |
| Session can be invalidated centrally             | Revocation may require additional design  |
| Common for traditional web applications          | Common for APIs and multiple client types |

Both approaches can be secure when implemented correctly. The choice depends on the application's clients and requirements.

**Important:** Avoid storing authentication tokens in `localStorage` for a browser-based application. JavaScript running on the page can read them, including scripts injected through an XSS vulnerability. For browser authentication, secure `HttpOnly` cookies are generally a safer default. Native mobile applications should use platform-secure storage for tokens.

## 2. Cookies and Secure Cookie Options

Cookies are values managed by the browser and associated with a website. They are commonly used to carry a session identifier or an authentication token.

A server sends a cookie using the `Set-Cookie` response header. The browser sends it back in the `Cookie` request header.

Important cookie attributes:

| Attribute             | Purpose                                                 |
| --------------------- | ------------------------------------------------------- |
| `HttpOnly`            | Prevents client-side JavaScript from reading the cookie |
| `Secure`              | Sends the cookie only over HTTPS                        |
| `SameSite`            | Controls when cookies are sent with cross-site requests |
| `Path`                | Specifies which URL paths receive the cookie            |
| `Max-Age` / `Expires` | Controls the cookie's lifetime                          |

For authentication cookies, `HttpOnly`, `Secure` in production, an appropriate `SameSite` setting, and a suitable expiration are important.

Cookies help transport authentication information, but a cookie by itself does not prove that a user is authorized to perform an operation. The server must validate the authentication state.

## 3. Auth.js (NextAuth)

**Auth.js**, previously known as NextAuth.js, is a library that handles common authentication workflows in Next.js.

It provides features such as:

- Sign in and sign out
- Credentials and OAuth providers
- Session handling
- Authentication callbacks
- Integration with the Next.js App Router

Instead of implementing the complete authentication flow manually, an application configures Auth.js and the providers it needs.

### 3.1 Authentication Providers

A provider defines how a user authenticates.

Common provider types include:

| Provider              | Description                                                                     |
| --------------------- | ------------------------------------------------------------------------------- |
| Credentials           | Authenticates using application-managed credentials, such as email and password |
| Google                | Allows users to sign in with their Google account                               |
| GitHub                | Allows users to sign in with their GitHub account                               |
| Other OAuth providers | Connects authentication to supported external identity providers                |

With the Credentials provider, the application is responsible for verifying the submitted credentials. For password-based accounts, passwords must be hashed before storage and verified using a suitable password-hashing library.

OAuth providers delegate identity verification to an external provider. The application still needs to decide what user information to store and what access the user receives.

### 3.2 Basic Auth.js Configuration

Install `"next-auth": "^4.24.15"`

A typical App Router project can keep its Auth.js configuration in `auth.ts` at the project root.

```ts
// auth.ts
import { getServerSession, type NextAuthOptions } from "next-auth";
import CredentialsProvider from "next-auth/providers/credentials";
import { verifyCredentials } from "./lib/auth/verify-credentials";

export const authOptions: NextAuthOptions = {
	secret: process.env.JWT_SECRET,
	providers: [
		CredentialsProvider({
			name: "Credentials",
			credentials: {
				email: { label: "Email", type: "email" },
				password: { label: "Password", type: "password" },
			},
			async authorize(credentials) {
				const user = verifyCredentials({
					email: credentials?.email ?? "",
					password: credentials?.password ?? "",
				});

				return user;
			},
		}),
	],
	session: {
		strategy: "jwt",
	},
	pages: {
		signIn: "/login",
	},
};

export const auth = () => getServerSession(authOptions);
```

The `verifyCredentials` function is application logic. It should validate the input, find the user in the database, and compare the submitted password with the stored password hash. It must never compare or store plain-text passwords.

For Google OAuth, configure the provider's credentials using environment variables.

```env
AUTH_SECRET="your-generated-secret"
AUTH_GOOGLE_ID="your-google-client-id"
AUTH_GOOGLE_SECRET="your-google-client-secret"
```

Keep secrets in environment variables. Never expose them through variables prefixed with `NEXT_PUBLIC_` or commit real secret values to source control.

### 3.3 Connect Auth.js to the App Router

Expose the Auth.js handlers through a Route Handler:

```ts
// app/api/auth/[...nextauth]/route.ts
import NextAuth from "next-auth";
import { authOptions } from "@/auth";

const handler = NextAuth(authOptions);

export { handler as GET, handler as POST };
```

```ts
// proxy.ts
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";
import { getToken } from "next-auth/jwt";

const protectedRoutes = ["/dashboard"]; // update this array based on requirement
const authRoutes = ["/login", "/signup"]; // update this array based on requirement

const matches = (pathname: string, routes: string[]) =>
	routes.some(
		(route) => pathname === route || pathname.startsWith(`${route}/`),
	);

export async function proxy(request: NextRequest) {
	const { pathname } = request.nextUrl;

	const token = await getToken({
		req: request,
		secret: process.env.NEXTAUTH_SECRET ?? process.env.JWT_SECRET,
	});
	const isLoggedIn = !!token;

	// Logged-in users shouldn't see login/signup
	if (isLoggedIn && matches(pathname, authRoutes)) {
		return NextResponse.redirect(new URL("/dashboard", request.url));
	}

	// Guests can't access protected routes
	if (!isLoggedIn && matches(pathname, protectedRoutes)) {
		const loginUrl = new URL("/login", request.url);
		loginUrl.searchParams.set("callbackUrl", pathname);
		return NextResponse.redirect(loginUrl);
	}

	return NextResponse.next();
}

export const config = {
	matcher: ["/dashboard/:path*", "/login", "/signup"],
};
```

This Route Handler allows Auth.js to process its authentication-related requests.

### 3.4 Sign In and Sign Out

Auth.js provides `signIn` and `signOut` functions. They can be called from server-side code, including Server Actions.

**Credentials login** — Server Action form:

```tsx
// app/login/page.tsx
import { signIn } from "next-auth/react";

export default function LoginPage() {
	const onSubmit = async (data: z.output<typeof loginSchema>) => {
		try {
			const result = await signIn("credentials", {
				email: data.email,
				password: data.password,
				redirect: false,
			});

			if (!result || result.error) {
				toast.error(
					result?.error === "CredentialsSignin"
						? "Invalid email or password."
						: "Something went wrong. Please try again.",
				);
				return;
			}

			toast.success("Signed in successfully");

			router.push("/dashboard");
			router.refresh();
		} catch (error) {
			console.error("Login Error:", error);
			toast.error("Something went wrong. Please try again.");
		}
	};

	return (
		<form onSubmit={handleSubmit(onSubmit)}>
			<input name='email' type='email' required />
			<input name='password' type='password' required />
			<button type='submit'>Sign in</button>
		</form>
	);
}
```

**Sign out / Logout**

```tsx
"use client";

import { LogOut } from "lucide-react";
import { signOut } from "next-auth/react";
import { useState } from "react";

export default function LogoutButton() {
	const [loading, setLoading] = useState(false);

	return (
		<button
			type='button'
			disabled={loading}
			onClick={() => {
				setLoading(true);
				signOut({ callbackUrl: "/login" });
			}}
			className='flex items-center gap-2 rounded-lg border px-3 py-2 text-sm font-medium text-gray-600 hover:bg-red-50 hover:text-red-600 disabled:opacity-60'
		>
			<LogOut size={18} />
			<span className='hidden sm:inline'>
				{loading ? "Logging out..." : "Logout"}
			</span>
		</button>
	);
}
```

For a Credentials provider, the application still implements the credential verification logic. Auth.js manages the surrounding authentication workflow.

### 3.5 Read the Current Session

Use the `auth()` function on the server to read the current session.

```ts
import { auth } from "@/auth";

const session = await auth();

if (!session?.user) {
	// No authenticated user
}
```

The session can be checked in Server Components, Route Handlers, and Server Actions. Sensitive operations must perform their own server-side checks rather than relying only on whether a page is visible.

## 4. User Data and MongoDB

A typical application stores user information in MongoDB using a Mongoose model.

A user record may contain:

| Field          | Purpose                                        |
| -------------- | ---------------------------------------------- |
| `name`         | User's display name                            |
| `email`        | Unique account email                           |
| `passwordHash` | Hashed password for credentials-based accounts |
| `role`         | User role, such as `USER` or `ADMIN`           |

The exact fields depend on the authentication providers and application requirements. OAuth-only users may not have a password hash.

Important practices:

- Store a password hash, never a plain-text password.
- Enforce unique email addresses at the database level.
- Do not return `passwordHash` in API responses or expose it in client components.
- Validate user input on the server.
- Use a suitable password-hashing library; do not create your own hashing algorithm.

Auth.js can be configured with different session strategies and database integrations. The session strategy and persistence setup should be chosen deliberately for the application.

## 5. Protecting Pages and Server-Side Operations

A user interface can show different content depending on whether a user is signed in. However, hiding a button or page link is only a user-experience decision, not a security check.

### 5.1 Protect a Page

In an App Router Server Component, check the session and redirect unauthenticated users.

```tsx
// app/dashboard/page.tsx
import { auth } from "@/auth";
import { redirect } from "next/navigation";

export default async function DashboardPage() {
	const session = await auth();

	if (!session?.user) {
		redirect("/login");
	}

	return <h1>Dashboard</h1>;
}
```

### 5.2 Protect pages using a layout

```tsx
// app/dashboard/layout.tsx

import { auth } from "@/auth";
import { redirect } from "next/navigation";

export default async function DashboardLayout({
	children,
}: {
	children: React.ReactNode;
}) {
	const session = await auth();

	if (!session?.user) {
		redirect("/login");
	}

	return <>{children}</>;
}
```

### 5.3 Protect a Route Handler

A protected page does not automatically protect its API. A Route Handler must check authentication independently.

```ts
// app/api/orders/route.ts
import { auth } from "@/auth";

export async function GET() {
	const session = await auth();
	if (!session?.user) {
		return Response.json(
			{
				success: false,
				data: null,
				message: "Unauthenticated",
			},
			{ status: 401 },
		);
	}

	// Fetch only the orders the current user is allowed to access.
	return Response.json({ message: "Authorized request" });
}
```

### 5.4 Protect a Server Action

Server Actions run on the server, but they are not automatically restricted to authorized users. Check the current session inside every sensitive action.

```ts
"use server";

import { auth } from "@/auth";

export async function createOrder() {
	const session = await auth();

	if (!session?.user) {
		throw new Error("Unauthorized");
	}

	// Perform the operation for the authenticated user.
}
```

The same principle applies to update and delete operations. Do not trust user IDs, roles, or permissions supplied by the browser. Derive the current user's identity from the verified server-side session.

### 5.6 Middleware / Proxy

Next.js provides request-level Middleware (called Proxy in newer Next.js versions) that can perform early checks and redirect users away from groups of routes.

It can improve navigation and avoid unnecessary page work, but it must not be the only security layer. Always check authentication and authorization again inside sensitive Route Handlers and Server Actions.

## 6. Authorization

Authorization determines what an authenticated user is allowed to do.

Authentication answers **who the user is**. Authorization answers **what the user can access**.

### 6.1 Role-Based Access Control (RBAC)

Role-Based Access Control assigns roles to users. Each role has a set of allowed actions.

Example:

| Role    | Permissions                                  |
| ------- | -------------------------------------------- |
| `USER`  | View and manage their own profile and orders |
| `ADMIN` | Manage users, products, and orders           |

A user record may contain a role field:

```ts
type UserRole = "USER" | "ADMIN";
```

The server reads the role from trusted user/session data and checks it before performing a protected operation.

```ts
if (session.user.role !== "ADMIN") {
	return Response.json({ error: "Forbidden" }, { status: 403 });
}
```

Never accept a role sent by the client as proof of permission.

### 6.2 Permissions

For applications with more detailed access rules, permissions can be used instead of relying only on broad roles.

Examples:

```text
users:read
users:delete
products:create
products:update
orders:refund
```

A role can be associated with multiple permissions. For a small application, simple roles may be enough. Introduce permissions when role-based checks become difficult to manage.

### 6.3 Resource Ownership

A user may be allowed to access only resources they own, even when multiple users have the same role.

For example:

- A customer can view their own orders.
- A customer cannot view another customer's orders.
- An admin may be allowed to view all orders.

The server should use the authenticated user's ID when querying user-owned data.

```ts
const session = await auth();

if (!session?.user) {
	return Response.json({ error: "Unauthorized" }, { status: 401 });
}

// Query using the authenticated user's ID,
// rather than trusting a userId supplied by the client.
```

Role checks and ownership checks can be combined when the application requires both.

## 7. Where Authorization Must Be Enforced

Authorization must be checked where the protected operation is executed.

| Application area           | Required check                                                         |
| -------------------------- | ---------------------------------------------------------------------- |
| Server Component page      | Check access before rendering protected data                           |
| Route Handler              | Check access before returning or modifying data                        |
| Server Action              | Check access before performing the action                              |
| Database/service operation | Ensure the operation uses the correct user's identity and access rules |

A route group or folder name such as `(admin)` does not enforce access by itself. Hiding an admin button in a Client Component does not prevent a user from calling the underlying action or endpoint.

A useful request flow is:

```text
Request
   |
   v
Authentication
   |
   v
Authorization
   |
   +---- Role check
   |
   +---- Ownership check
   |
   v
Service / Business Logic
   |
   v
Database
```

## 8. Common Security Practices

- Hash passwords before storing them.
- Never expose passwords, password hashes, or authentication secrets.
- Keep provider secrets and Auth.js secrets in environment variables.
- Use secure cookie settings for browser authentication.
- Protect pages, Route Handlers, and Server Actions independently.
- Read the user's identity and role from trusted server-side session data.
- Check resource ownership before returning or modifying user-specific data.
- Rate-limit login and password-reset endpoints to reduce brute-force attempts.
- Use generic login errors where appropriate; avoid revealing whether an email is registered.
- Validate input on the server, even if the client also validates it.
- Do not rely on client-side state, hidden buttons, or Middleware/Proxy as the only security boundary.
