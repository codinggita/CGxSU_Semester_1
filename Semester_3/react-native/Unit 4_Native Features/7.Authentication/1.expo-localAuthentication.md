
# Local Authentication (`expo-local-authentication`)

---

# What is `expo-local-authentication`?

`expo-local-authentication` is an Expo SDK module that allows a React Native application to use the authentication mechanisms provided by the user's device.

Depending on the device and platform, this can include:

* Fingerprint
* Face authentication
* Touch ID
* Other biometric authentication methods supported by the device

For example, imagine that your application has a screen containing private information.

You may want to prevent someone from opening that screen simply by tapping a button.

Instead, your application can ask the device:

```text
"Please verify that the person using this app
is the device's authorized user."
```

The device can then display its native authentication UI.

For example:

```text
        ┌─────────────────────────┐
        │                         │
        │     Authenticate        │
        │                         │
        │      [ Face ]           │
        │                         │
        │   Look at your phone    │
        │                         │
        └─────────────────────────┘
```

After the device finishes authentication, your application receives a result.

The result can indicate that authentication:

```text
Succeeded
```

or

```text
Failed
```

or

```text
Was cancelled
```

or another supported result.

---

# Why Do We Need Local Authentication?

Normal application authentication and local device authentication solve different problems.

For example, suppose a user logs into your application using:

```text
Email
+
Password
```

The server verifies the credentials and creates an authenticated session.

However, after the user closes the app and opens it again, you may want an additional protection layer.

Instead of asking the user to type their password every time:

```text
Open App
   ↓
Enter Password
   ↓
Open Private Data
```

you can use local authentication:

```text
Open App
   ↓
Biometric Authentication
   ↓
Open Private Data
```

This can make accessing protected parts of an application both faster and more convenient.

# How Does Local Authentication Work?

The important thing to understand is that your React Native application does **not directly read the user's fingerprint or face**.

Instead, the application asks the operating system to perform authentication.

The simplified flow is:

```text
React Native Application

        ↓

expo-local-authentication

        ↓

Device Operating System

        ↓

Biometric System

        ↓

Fingerprint / Face / Other Method

        ↓

Authentication Result

        ↓

React Native Application
```

For example:

```js
const result = await LocalAuthentication.authenticateAsync();
```

Your application asks the device to authenticate the user.

The device displays the appropriate authentication interface.

After the authentication process completes, the application receives the result.

---

# Important Security Concept

Your application generally does **not** receive:

```text
 User's fingerprint image
 User's face image
 Fingerprint template
 Face biometric data
```

Instead, the application receives an authentication result.

Conceptually:

```text
Biometric Data
      ↓
Device OS handles it
      ↓
Authentication Result
      ↓
Your Application
```

This is an important distinction.

Your application is requesting:

> "Authenticate the user."

It is not asking:

> "Give me the user's fingerprint."

# Hardware vs Enrollment

One of the most important concepts in local authentication is understanding the difference between:

1. Biometric hardware
2. Biometric enrollment

These are **not the same thing**.

---

# 1. Biometric Hardware

First ask:

> Does this device have biometric hardware?

Use:

```js
const hasHardware =
  await LocalAuthentication.hasHardwareAsync();
```

The result is a boolean:

```js
true
```

or

```js
false
```

### Example

```js
const hasHardware =
  await LocalAuthentication.hasHardwareAsync();

console.log(hasHardware);
```

Possible output:

```text
true
```

This means the device reports that biometric hardware is available.

---

# What Does Hardware Mean?

Examples of biometric hardware include:

```text
Fingerprint sensor
Face authentication hardware
Other supported biometric hardware
```

For example, imagine a phone that has a fingerprint sensor.

Then:

```js
await LocalAuthentication.hasHardwareAsync();
```

may return:

```js
true
```

But this does **not** automatically mean that the user has configured a fingerprint.

That brings us to enrollment.

---

# 2. Biometric Enrollment

The next question is:

> Has the user actually enrolled a biometric credential on the device?

Use:

```js
const isEnrolled =
  await LocalAuthentication.isEnrolledAsync();
```

Again, the result is:

```js
true
```

or

```js
false
```

---

# Hardware Available Does Not Mean Enrollment Exists

Consider this situation:

```text
Biometric Hardware
       ↓
      YES

Biometric Credential Enrolled
       ↓
       NO
```

This means:

```js
hasHardwareAsync()
```

returns:

```js
true
```

but:

```js
isEnrolledAsync()
```

returns:

```js
false
```

The device supports biometric authentication, but the user has not configured an eligible biometric credential.

---

# Example

```js
const hasHardware =
  await LocalAuthentication.hasHardwareAsync();

const isEnrolled =
  await LocalAuthentication.isEnrolledAsync();

console.log("Hardware:", hasHardware);
console.log("Enrolled:", isEnrolled);
```

Possible output:

```text
Hardware: true
Enrolled: false
```

This is a perfectly possible state.

---

# Think of It Like a Lock

A useful analogy is a door lock.

```text
Hardware
=
Does the door have a lock?

Enrollment
=
Has someone configured a key for that lock?
```

You can have:

```text
Lock exists
+
No key configured
```

Similarly:

```text
Biometric hardware exists
+
No biometric credential enrolled
```

Therefore, checking only hardware is not enough.

# Authentication Types vs Security Level

Another important distinction is between:

```text
Authentication Type
```

and:

```text
Security Level
```

These answer different questions.

---

# Authentication Type

Authentication type asks:

> What biometric authentication types are supported by the device?

Use:

```js
const types =
  await LocalAuthentication.supportedAuthenticationTypesAsync();
```

The method returns an array of authentication type values.

For example, conceptually:

```text
[
  Fingerprint
]
```

or:

```text
[
  Face
]
```

or potentially multiple supported types.

---

# Why Is This Useful?

Suppose your application wants to display information such as:

```text
Biometric authentication available:
Fingerprint
```

or:

```text
Biometric authentication available:
Face
```

You can inspect the supported authentication types.

Example:

```js
const types =
  await LocalAuthentication.supportedAuthenticationTypesAsync();

console.log(types);
```

You can then determine which authentication mechanisms the device supports according to the values returned by the API.

---

# Authentication Type Does Not Mean Authentication Success

This is very important.

Suppose:

```js
supportedAuthenticationTypesAsync()
```

returns a fingerprint-related type.

That means:

```text
Fingerprint authentication is supported.
```

It does **not** mean:

```text
The user has successfully authenticated.
```

These are completely different concepts.

---

# Compare the Two

### Capability

```js
supportedAuthenticationTypesAsync()
```

asks:

> What authentication methods are supported?

### Authentication

```js
authenticateAsync()
```

asks:

> Can the user successfully authenticate right now?

So:

```text
supportedAuthenticationTypesAsync()
        ↓
"What can this device support?"

authenticateAsync()
        ↓
"Can this user authenticate?"
```

---

# Security Level

The next concept is the enrolled authentication security level.

Use:

```js
const level =
  await LocalAuthentication.getEnrolledLevelAsync();
```

This tells you about the security level of the authentication mechanism enrolled on the device.

The API returns a value from the module's `SecurityLevel` enum.

For example:

```js
LocalAuthentication.SecurityLevel.NONE
```

Other possible enum values include stronger authentication categories supported by the platform.

You should use the enum values rather than assuming numeric values.

---

# Why Do We Need Security Level?

Suppose your application has a highly sensitive feature.

You may want to know not only:

```text
Is some biometric capability available?
```

but also:

```text
What level of authentication is enrolled?
```

This can be useful when your application has security requirements.

For example:

```text
Normal Feature
      ↓
Basic local authentication may be enough

Highly Sensitive Feature
      ↓
Require an appropriate device authentication level
```

The exact security semantics depend on the platform.

Therefore, don't assume that every authentication method provides the same security characteristics.

# Main APIs

| API                                   | Question It Answers                                        | Return                               |
| ------------------------------------- | ---------------------------------------------------------- | ------------------------------------ |
| `hasHardwareAsync()`                  | Does the device have biometric hardware?                   | `Promise<boolean>`                   |
| `isEnrolledAsync()`                   | Is a biometric credential enrolled?                        | `Promise<boolean>`                   |
| `supportedAuthenticationTypesAsync()` | What biometric types are supported?                        | `Promise<AuthenticationType[]>`      |
| `getEnrolledLevelAsync()`             | What security level is enrolled?                           | `Promise<SecurityLevel>`             |
| `authenticateAsync()`                 | Can the user authenticate?                                 | `Promise<LocalAuthenticationResult>` |
| `cancelAuthenticate()`                | Can an active Android authentication request be cancelled? | `void`                               |

Notice that most methods are asynchronous.

That is why we normally use:

```js
await
```

with them.

We can use the results to decide what the application should do.

```js
    console.log("Biometric hardware is not available.");

    await LocalAuthentication.isEnrolledAsync();
```

# Part 2 — Understanding Local Authentication

Before writing authentication code, we need to understand what **local authentication** actually means and how it fits into a real application.

## What Does Local Authentication Mean?

Local authentication means asking the device's operating system to verify the person using the device with an authentication method already configured on that device.

Depending on the device and platform, this may involve:

```text
Fingerprint
Face authentication
Touch ID
Other supported biometric methods
```

The important point is that your React Native application does not directly inspect or process the user's biometric data. The operating system performs the authentication and your application receives the result.

---

## The Basic Mental Model

Think of the process as a conversation between your app and the device:

```text
Your Application
      ↓
"Device, authenticate this user"
      ↓
Operating System
      ↓
Fingerprint / Face / Other Method
      ↓
Authentication Result
      ↓
Your Application
```

Your application is therefore responsible for **requesting authentication and reacting to the result**. The device is responsible for performing the actual local verification.

For example:

```js
const result =
  await LocalAuthentication.authenticateAsync();
```

This does not mean that your JavaScript code is reading a fingerprint. It means that your application has requested the device's authentication system to authenticate the user.

---

## Local Authentication vs Application Login

This distinction is extremely important.

Suppose a user logs into your application with:

```text
Email
+
Password
```

Your backend may verify those credentials and create an authenticated session.

That is **application/server authentication**.

Local authentication is different. It can be used as an additional protection layer after the user has already established an application session.

For example:

```text
First Login
    ↓
Email + Password
    ↓
Backend Authentication
    ↓
Authenticated Session
    ↓
User closes app
    ↓
User opens app again
    ↓
Local Authentication
    ↓
Unlock Sensitive Features
```

So local authentication does not automatically replace your backend authentication system.

---

## Why Would We Use Local Authentication?

Imagine a banking application. Asking for a full password every time the user opens a sensitive screen may be inconvenient.

Instead, the application could use the device's local authentication system:

```text
Open Banking App
      ↓
Authenticate with device
      ↓
Authentication successful
      ↓
Show protected information
```

The same idea can be used for:

- Private notes
- Password managers
- Payment confirmation
- Sensitive documents
- Admin settings
- Protected screens
- Secure application settings

---

## Hardware, Enrollment, and Authentication Are Different

Beginners often mix these three concepts together. They are separate.

### 1. Hardware

Question:

> Does the device have biometric hardware?

API:

```js
LocalAuthentication.hasHardwareAsync();
```

---

### 2. Enrollment

Question:

> Has the user enrolled an eligible authentication credential?

API:

```js
LocalAuthentication.isEnrolledAsync();
```

---

### 3. Authentication

Question:

> Can the user successfully authenticate now?

API:

```js
LocalAuthentication.authenticateAsync();
```

These can be visualized as:

```text
Hardware
   ↓
Does the device have the required capability?

Enrollment
   ↓
Has the user configured a credential?

Authentication
   ↓
Can the user prove access right now?
```

---

## Example: Hardware Exists but Nothing Is Enrolled

Consider a new phone with a fingerprint sensor.

The device may report:

```text
Hardware = true
```

but the user has never registered a fingerprint:

```text
Enrollment = false
```

That means:

```text
Fingerprint sensor exists
        +
No biometric credential configured
```

So the application should not interpret `hasHardwareAsync() === true` as proof that authentication is ready.

---

## Authentication Type vs Security Level

These concepts are also different.

### Authentication Type

Authentication type answers:

> What kind of biometric authentication does the device support?

API:

```js
LocalAuthentication.supportedAuthenticationTypesAsync();
```

The result is an array of supported authentication type values.

For example, a device may expose fingerprint or facial recognition.

### Security Level

Security level answers:

> What security level is represented by the enrolled authentication?

API:

```js
LocalAuthentication.getEnrolledLevelAsync();
```

These answer different questions:

```text
Authentication Type
        ↓
"What authentication method/type is supported?"

Security Level
        ↓
"What security level is enrolled?"
```

---

## Capability vs Authentication Result

Another common mistake is confusing capability with successful authentication.

If this method returns a fingerprint type:

```js
await LocalAuthentication.supportedAuthenticationTypesAsync();
```

it means that the device reports support for that authentication type.

It does **not** mean the user has successfully authenticated.

Actual authentication happens through:

```js
await LocalAuthentication.authenticateAsync();
```

Think of it as:

```text
supportedAuthenticationTypesAsync()
        ↓
"What can this device support?"

                VS

authenticateAsync()
        ↓
"Did the user authenticate successfully?"
```

---

## The Device Controls the Authentication UI

When you call:

```js
await LocalAuthentication.authenticateAsync();
```

your application requests authentication, but the native operating system controls the actual authentication prompt.

Conceptually:

```text
React Native App
       ↓
Expo Local Authentication
       ↓
Native Authentication System
       ↓
Authentication Prompt
       ↓
User Interaction
       ↓
Result
```

This is why your application does not need to create its own fingerprint scanner UI.

---

## What Does the Application Receive?

The application receives an authentication result.

A successful operation can be represented conceptually as:

```js
{
  success: true
}
```

A failed operation can contain an error identifier:

```js
{
  success: false,
  error: "authentication_failed"
}
```

The application can then decide what to do.

For example:

```text
Authentication successful
        ↓
Allow protected action
```

while:

```text
Authentication unsuccessful
        ↓
Keep protected action locked
```

---

## Local Authentication Is Usually an Authorization Gate

A useful way to think about local authentication is as a gate around a sensitive operation.

For example:

```text
User wants to open private notes
             ↓
      Local authentication
             ↓
       success === true?
          /          \
        Yes           No
         ↓             ↓
   Show notes       Keep locked
```

The same pattern works for a payment:

```text
User presses Pay
      ↓
Authenticate
      ↓
success === true?
      ↓
Continue payment
```

The protected action should be behind the successful result.

## Example: Opening a Private Screen

Suppose we have:

```text
Home
  ↓
Private Data
```

We want authentication before opening the private screen.

A conceptual implementation is:

```js
const openPrivateScreen = async () => {

  const result =
    await LocalAuthentication.authenticateAsync({
      promptMessage:
        "Authenticate to open private data",
    });

  if (result.success) {
    // Navigate to the protected screen
  }

```

The important part is not the button itself. The important rule is:

```text
Authenticate
    ↓
Wait for result
    ↓
Check success
    ↓
Only then allow protected access
```

## Example: Authentication Before Payment

A payment flow might look like:

```text
User presses Pay
       ↓
Authenticate user
       ↓
Authentication successful?
       /            \
     Yes             No
      ↓               ↓
Continue          Stop payment
with payment
```

Example:

```js
const confirmPayment = async () => {

  const result =
    await LocalAuthentication.authenticateAsync({
      promptMessage:
        "Authenticate to confirm payment",
    });

  if (!result.success) {
    return;
  }

  // Continue with the protected payment action
};
```

The authentication result acts as the gate.

---

## Example: Authentication Before Private Notes

```js
const openPrivateNotes = async () => {

  const result =
    await LocalAuthentication.authenticateAsync({
      promptMessage:
        "Authenticate to open private notes",
    });

  if (result.success) {
    // Show private notes
  }
};
```

If authentication fails or is cancelled, the application can keep the notes hidden.

---

## What Local Authentication Does Not Automatically Do

Calling:

```js
LocalAuthentication.authenticateAsync();
```

does not automatically:

- Log the user into your backend
- Create a server session
- Navigate to a protected screen
- Unlock your application data automatically
- Authorize a payment by itself
- Store the user's biometric information for you

Your application decides what to do after receiving the result.

For example:

```text
authenticateAsync()
       ↓
result.success
       ↓
Your application logic
       ↓
Protected action
```

---

## Important Security Principle

Never treat the authentication request itself as proof of successful authentication.

Incorrect mental model:

```text
Call authenticateAsync()
        ↓
Assume user is authenticated
```

Correct mental model:

```text
Call authenticateAsync()
        ↓
Wait for result
        ↓
Check result.success
        ↓
Only if true → allow protected action
```

This distinction becomes especially important when protecting payments, private information, or other sensitive operations.

# Part 3 — Checking Biometric Hardware

## `hasHardwareAsync()`

Before asking a user to authenticate with biometrics, an application should first understand whether the device provides the required biometric hardware.

Expo provides:

```js

```

This method checks whether the device has biometric hardware that can be used for local authentication.

---

# What Does `hasHardwareAsync()` Do?

`hasHardwareAsync()` answers a simple question:

> **Does this device have biometric hardware available?**

Example:

```js
const hasHardware =
  await LocalAuthentication.hasHardwareAsync();

console.log(hasHardware);
```

The method returns a boolean:

```js
true
```

or:

```js
false
```

So the result can be thought of as:

```text
true
 ↓
Biometric hardware is available

false
 ↓
Biometric hardware is not available
```

---

# Why Do We Check Hardware First?

Imagine that your application has a button:

```text
┌──────────────────────────┐
│                          │
│    Unlock Secure Data    │
│                          │
└──────────────────────────┘
```

When the user taps the button, your application wants to use biometric authentication.

But what if the device does not have biometric hardware?

For example:

```text
Device
  ↓
No biometric hardware
  ↓
Cannot provide biometric authentication
```

In this situation, your application should not blindly assume that biometric authentication is available.

Instead, it can check first:

```js
const hasHardware =
  await LocalAuthentication.hasHardwareAsync();
```

Then decide what to do.

---

# Basic Flow

The basic idea is:

```text
Application
     ↓

     ↓

     ↓
   ┌───────────────┐
   │               │
  true            false
   │               │
   ↓               ↓
Continue        Use another
checking        authentication
```

Notice that `true` does **not** immediately mean:

```text
"Authenticate the user"
```

It only means:

```text
"Biometric hardware is available."
```

There are additional checks that may be required.

does not give you the final:


or:


```js

```

waits for the asynchronous operation to complete:

```js

  await LocalAuthentication.hasHardwareAsync();
```

Now:

```js

```

contains the boolean result.

```text
       ↓
```

## `isEnrolledAsync()`

# What Does `isEnrolledAsync()` Do?

`isEnrolledAsync()` answers the question:

> **Has the user enrolled a biometric/local authentication credential on this device?**

```js
const enrolled =
```

```text
Device

isEnrolledAsync()

true
```

```text

        ↓

        ↓
false
```

* Use another authentication method
* Tell the user that biometric authentication is not configured
* Direct the user to the appropriate device settings
* Hide or disable a biometric-only option


The platform and API determine the actual values returned.

Your application should rely on the API rather than trying to infer device state from theoretical combinations.

# Example — Complete Capability Check

We can now combine the first three concepts:

```js
const checkBiometricCapability = async () => {

  const hasHardware =
    await LocalAuthentication.hasHardwareAsync();

    await LocalAuthentication.isEnrolledAsync();

    await LocalAuthentication
      .supportedAuthenticationTypesAsync();

    return false;
  }

  return true;
};
```

```text

   ↓
Supported authentication type?
   ↓
```

# Part 6 — Understanding Authentication Security Levels

## `getEnrolledLevelAsync()`

So far, we have learned that local authentication can answer questions such as:

```text

        ↓

        ↓
```

There is another important question:

> **What security level does the enrolled authentication have?**

Expo provides:

```js
LocalAuthentication.getEnrolledLevelAsync()
```

---

# Why Do We Need a Security Level?

Consider two devices.

### Device A

```text
Fingerprint
```

### Device B

```text
Face Authentication
```

Knowing the authentication type tells us:

```text
"What authentication mechanism is available?"
```

But it doesn't describe the security classification of that authentication.

The security-level API gives us another piece of information:

```text
"How is the enrolled authentication classified in terms of security?"
```

So:

```text
Authentication Type
        ↓
Fingerprint / Face / Iris

Security Level
        ↓
None / Secret / Weak / Strong
```

These are **different concepts**.

# `SecurityLevel`

```js
LocalAuthentication.SecurityLevel
```

```js
LocalAuthentication.SecurityLevel.NONE
```

```js
LocalAuthentication.SecurityLevel.SECRET
```

```js
LocalAuthentication.SecurityLevel.BIOMETRIC_WEAK
```

```js
LocalAuthentication.SecurityLevel.BIOMETRIC_STRONG
```

| Security Level     | Value | General Meaning                               |
| ------------------ | ----: | --------------------------------------------- |
| `NONE`             |   `0` | No enrolled authentication                    |
| `SECRET`           |   `1` | Non-biometric secret such as a PIN or pattern |
| `BIOMETRIC_WEAK`   |   `2` | Weaker biometric security class               |
| `BIOMETRIC_STRONG` |   `3` | Strong biometric security class               |

Use:

```js
LocalAuthentication.SecurityLevel.BIOMETRIC_STRONG
```

instead of:

```js

```

```text

Pattern
Passcode
```

```text
SECRET ≠ Biometric
```

It represents a secret-based authentication mechanism rather than a biometric classification.

```js
LocalAuthentication.authenticateAsync()
```

# What Does `authenticateAsync()` Do?

`authenticateAsync()` starts the device's local authentication process.

In simple words:

> **Ask the device to verify the user.**

Depending on the device and its configuration, the user may be asked to authenticate using:

```text
Fingerprint

Face

Other supported biometric authentication

Device authentication fallback
```

The exact authentication UI is controlled by the operating system.

Your React Native application does **not** implement the fingerprint scanner or face-recognition algorithm itself.

Instead:

```text
Your React Native App
        ↓
authenticateAsync()
        ↓
Operating System
        ↓
Authentication Prompt
        ↓
User Authenticates
        ↓
Result returned to App
```

---

# Basic Syntax

The simplest usage is:

```js
const result =
  await LocalAuthentication.authenticateAsync();
```

Because authentication requires user interaction, this function is asynchronous.

Therefore:

```js
await
```

is normally used inside an `async` function.

---

# Basic Example

```js
import * as LocalAuthentication
  from "expo-local-authentication";

const authenticateUser = async () => {
  const result =
    await LocalAuthentication.authenticateAsync();

  console.log(result);
};
```

Then you can call:

```js
authenticateUser();
```

This starts the authentication process.

---

# What Happens When This Code Runs?

Suppose the device has biometric authentication configured.

When:

```js
await LocalAuthentication.authenticateAsync();
```

runs, the operating system may show an authentication prompt.

Conceptually:

```text
User taps "Unlock"
        ↓

        ↓
Device authentication prompt
        ↓
┌─────────────────────────┐
│ Authenticate to continue│
│                         │
│                         │
│                         │
│      [Cancel]           │
└─────────────────────────┘
        ↓
User authenticates
        ↓
Result returned
```

Your application then uses that result.

---

# The Result Object

`authenticateAsync()` returns a result object.

The most important property is:

```js
result.success
```

This tells your application whether authentication succeeded.

Example:

```js
const result =
  await LocalAuthentication.authenticateAsync();

if (result.success) {
  console.log("Authentication successful");
} else {
  console.log("Authentication failed");
}
```

The basic mental model is:

```text
authenticateAsync()
        ↓
     result
      /   \
 success  failure
   ↓        ↓
 true     false
```

---

# When `success` Is `true`

If:

```js
result.success === true
```

the authentication attempt succeeded.

Example:

```js
const result =
  await LocalAuthentication.authenticateAsync();

if (result.success) {
  console.log("User authenticated");
}
```

At this point, your application can perform whatever protected action is appropriate.

For example:

```text
Authentication successful
        ↓
Open protected screen
```

or:

```text
Authentication successful
        ↓
Show sensitive information
```

or:

```text
Authentication successful
        ↓
Continue sensitive operation
```

---

# When `success` Is `false`

If:

```js
result.success === false
```

the authentication attempt did not succeed.

For example:

```js
const result =
  await LocalAuthentication.authenticateAsync();

if (result.success) {
  console.log("Authentication successful");
} else {
  console.log("Authentication unsuccessful");
  console.log(result.error);
}
```

The result can also contain an error describing what happened.

---

# Why Should We Check `success`?

Do not simply write:

```js
await LocalAuthentication.authenticateAsync();

navigate("/home");
```

This would be a bad authentication flow because you are not checking whether authentication actually succeeded.

Instead:

```js
const result =
  await LocalAuthentication.authenticateAsync();

if (result.success) {
  navigate("/home");
}
```

Now the protected screen is opened only after successful authentication.

The important rule is:

> **Never treat calling `authenticateAsync()` as proof that authentication succeeded. Check the returned result.**

---

# Authentication Is Not the Same as Calling the API

This distinction is extremely important.

Calling:

```js
LocalAuthentication.authenticateAsync();
```

means:

```text
"Start authentication."
```

It does **not** mean:

```text
"The user has authenticated successfully."
```

The correct sequence is:

```text
Call authenticateAsync()
        ↓
Wait for result
        ↓
Check result.success
        ↓
If true → authenticated
If false → not authenticated
```

```text
                        ↓           ↓
```

# Do We Always Need These Pre-Checks?

Not necessarily.

* Decide whether to offer biometric login
* Explain why authentication cannot be used
* Build a more controlled authentication flow

For a simple application, you may choose to call `authenticateAsync()` and handle its result/error.

For a more polished application, capability checks can improve the user experience.

# Why Is Device Fallback Important?

Suppose the device supports biometric authentication but the user cannot successfully use it.

Depending on platform behavior and configuration, the authentication system may offer another device authentication method.

For example:

```text
Biometric
   ↓
Unable to authenticate
   ↓
Device passcode / PIN / other fallback
```

Whether and how this happens is controlled by the underlying operating system.

# Example — Complete Practical Function

Here is a more realistic reusable function:

```js
import * as LocalAuthentication
  from "expo-local-authentication";

const authenticateUser = async () => {

  try {

    // Check hardware
    const hasHardware =
      await LocalAuthentication.hasHardwareAsync();

    if (!hasHardware) {
      return {
        success: false,
        reason: "NO_HARDWARE",
      };
    }

    // Check enrollment
    const enrolled =
      await LocalAuthentication.isEnrolledAsync();

    if (!enrolled) {
      return {
        success: false,
        reason: "NOT_ENROLLED",
      };
    }

    // Start authentication
    const result =
      await LocalAuthentication.authenticateAsync({
        promptMessage:
          "Authenticate to continue",
        cancelLabel: "Cancel",
      });

    // Check authentication result
    if (result.success) {
      return {
        success: true,
      };
    }

    return {
      success: false,
      reason: result.error,
    };

  } catch (error) {

    console.error(
      "Authentication error:",
      error
    );

    return {
      success: false,
      reason: "UNKNOWN_ERROR",
    };
  }
};
```

This gives the rest of your application a simple result:

```js
const result =
  await authenticateUser();

if (result.success) {
  console.log("Access granted");
} else {
  console.log(
    "Access denied:",
    result.reason
  );
}
```

# Why Use `try...catch`?

Authentication APIs are asynchronous.

Unexpected errors can occur while interacting with the native authentication system.

Therefore, application code can use:

```js
try {
  // authentication
} catch (error) {
  // unexpected error
}
```

For example:

```js
try {

  const result =
    await LocalAuthentication.authenticateAsync();

  console.log(result);

} catch (error) {

  console.error(
    "Unexpected authentication error:",
    error
  );
}
```

Remember:

```text
Normal authentication failure
        ≠
Unexpected JavaScript/native error
```

Your application can choose to handle these separately.

# Part 8 — Authentication Options

In Part 7, we learned how to start authentication:

```js
const result =
  await LocalAuthentication.authenticateAsync();
```

This works, but sometimes an application needs more control over the authentication request.

For example, we may want to:

* Show a meaningful authentication message
* Customize the cancel button
* Control device fallback behavior
* Customize Android authentication text
* Customize the iOS fallback button
* Require stronger biometric authentication on Android
* Control confirmation behavior on Android

For this purpose, `authenticateAsync()` accepts an **options object**.

---

# Basic Syntax

The general syntax is:

```js
const result =
  await LocalAuthentication.authenticateAsync({
    option1: value,
    option2: value,
  });
```

For example:

```js
const result =
  await LocalAuthentication.authenticateAsync({
    promptMessage: "Authenticate to continue",
  });
```

The options object is optional.

Therefore, both are valid:

```js
await LocalAuthentication.authenticateAsync();
```

and:

```js
await LocalAuthentication.authenticateAsync({
  promptMessage: "Authenticate to continue",
});
```

---

# Why Do We Need Options?

Without options:

```js
await LocalAuthentication.authenticateAsync();
```

the operating system uses its normal/default authentication behavior.

With options:

```js
await LocalAuthentication.authenticateAsync({
  promptMessage: "Authenticate to open private notes",
});
```

we can provide additional instructions to the authentication system.

Think of it as:

```text
authenticateAsync()
        ↓
"Start authentication"

authenticateAsync(options)
        ↓
"Start authentication
 with these additional settings"
```

---

# Available Authentication Options

The commonly used options are:

| Option                    | Platform      | Purpose                              |
| ------------------------- | ------------- | ------------------------------------ |
| `promptMessage`           | Android + iOS | Main authentication message          |
| `cancelLabel`             | Android + iOS | Cancel button label                  |
| `disableDeviceFallback`   | Android + iOS | Controls device fallback             |
| `fallbackLabel`           | iOS           | Customizes iOS fallback button       |
| `promptDescription`       | Android       | Android prompt description           |
| `promptSubtitle`          | Android       | Android prompt subtitle              |
| `requireConfirmation`     | Android       | Controls confirmation behavior       |
| `biometricsSecurityLevel` | Android       | Controls accepted biometric strength |

Not every option applies to every platform.

# Default Behavior vs Explicit Configuration

It is useful to distinguish between:

```js
authenticateAsync()
```

and:

```js
authenticateAsync({
  promptMessage: "...",
  ...
})
```

The first asks the platform to authenticate using its normal/default configuration.

The second provides explicit instructions.

For example:

```js
await LocalAuthentication.authenticateAsync();
```

versus:

```js
await LocalAuthentication.authenticateAsync({
  promptMessage:
    "Authenticate to open private notes",
});
```

The authentication mechanism is still provided by the operating system.

The options mainly customize/configure the request.

---

# Important: Options Do Not Replace Authentication Checks

Adding:

```js
promptMessage: "Authenticate"
```

does not mean the device has biometric hardware.

Adding:

```js
biometricsSecurityLevel: "strong"
```

does not mean strong biometrics are enrolled.

Options configure the authentication request.

The earlier APIs answer different questions:

```text
hasHardwareAsync()
→ Is biometric hardware available?

isEnrolledAsync()
→ Is an authentication credential enrolled?

supportedAuthenticationTypesAsync()
→ What biometric types are supported?

getEnrolledLevelAsync()
→ What security level is enrolled?

authenticateAsync()
→ Ask the user to authenticate.
```

---

# Recommended Mental Model

Think of `authenticateAsync()` as having two parts:

```text
authenticateAsync()
        │
        ├── Options
        │      ↓
        │   How should the request behave?
        │
        └── Result
               ↓
          Did authentication succeed?
```

For example:

```js
const result =
  await LocalAuthentication.authenticateAsync({
    promptMessage:
      "Authenticate to continue",
  });
```

The option:

```js
promptMessage
```

controls part of the request.

The returned:

```js
result.success
```

tells us what happened.

# Complete Example

Here is a practical example combining the concepts:

```js
import * as LocalAuthentication
  from "expo-local-authentication";

const unlockPrivateData = async () => {

  try {

    // 1. Check hardware
    const hasHardware =
      await LocalAuthentication.hasHardwareAsync();

    if (!hasHardware) {
      console.log(
        "Biometric hardware is unavailable."
      );
      return;
    }

    // 2. Check enrollment
    const enrolled =
      await LocalAuthentication.isEnrolledAsync();

    if (!enrolled) {
      console.log(
        "No biometric credentials are enrolled."
      );
      return;
    }

    // 3. Authenticate
    const result =
      await LocalAuthentication.authenticateAsync({
        promptMessage:
          "Authenticate to view private data",

        cancelLabel:
          "Cancel",

        disableDeviceFallback:
          false,
      });

    // 4. Handle result
    if (result.success) {

      console.log(
        "Authentication successful."
      );

      // Show protected content here

    } else {

      console.log(
        "Authentication was not successful."
      );

      console.log(
        "Error:",
        result.error
      );
    }

  } catch (error) {

    console.error(
      "Unexpected authentication error:",
      error
    );
  }
};
```

# Part 9 — Authentication Results and Errors

In the previous parts, we learned how to start authentication:

```js
const result =
  await LocalAuthentication.authenticateAsync();
```

Calling this function starts the authentication process, but it does not tell us whether the user successfully authenticated.

For that, we need to inspect the returned **result object**.

---

# Understanding the Result

When `authenticateAsync()` finishes, it returns an object describing what happened.

The most important property is:

```js
result.success
```

The basic possibilities are:

```text
success = true
        ↓
Authentication succeeded
```

or:

```text
success = false
        ↓
Authentication did not succeed
```

---

# Successful Authentication

When authentication succeeds, the result contains:

```js
{
  success: true
}
```

Example:

```js
const result =
  await LocalAuthentication.authenticateAsync();

if (result.success) {
  console.log("Authentication successful");
}
```

At this point, the application can perform the protected operation.

For example:

```js
if (result.success) {
  router.push("/private");
}
```

The important rule is:

> **Only grant access after `result.success` is `true`.**

---

# Failed Authentication

When authentication does not succeed, the result contains:

```js
{
  success: false,
  error: "authentication_failed"
}
```

The result may also contain a warning.

Example:

```js
const result =
  await LocalAuthentication.authenticateAsync();

if (!result.success) {
  console.log("Authentication failed");
  console.log("Error:", result.error);
}
```

---

# `success` Is the First Thing to Check

A good pattern is:

```js
const result =
  await LocalAuthentication.authenticateAsync();

if (result.success) {
  // Authentication succeeded
  return;
}

// Authentication did not succeed
console.log(result.error);
```

This is better than immediately assuming that authentication succeeded.

---

# Result Object Mental Model

Think of the result as:

```text
authenticateAsync()
        ↓
      Result
        ↓
 ┌───────────────┐
 │ success       │
 └───────┬───────┘
         │
     ┌───┴───┐
     ↓       ↓
   true     false
     ↓       ↓
 Success   Check error
```

So the application should first ask:

```js
result.success
```

and only when it is `false` should it inspect:

```js
result.error
```

---

# Authentication Errors

Expo provides documented authentication error values.

The documented values include:

```text
not_enrolled
user_cancel
app_cancel
not_available
lockout
no_space
timeout
unable_to_process
unknown
system_cancel
user_fallback
invalid_context
passcode_not_set
authentication_failed
```

These values help your application understand **why authentication did not complete successfully**.

---

# Why Do We Need Error Values?

Consider this:

```js
if (!result.success) {
  console.log("Authentication failed");
}
```

This tells us that authentication did not succeed.

But it does not tell us **why**.

For example:

```text
User cancelled
        ↓
Authentication unsuccessful

Fingerprint did not match
        ↓
Authentication unsuccessful

Too many failed attempts
        ↓
Authentication unsuccessful
```

All of these can result in:

```js
success: false
```

But the application may want to respond differently.

That's why:

```js
result.error
```

is useful.

---

# 1. `not_enrolled`

This indicates that no biometric credentials are enrolled.

Conceptually:

```text
Device supports biometric authentication
        ↓
No biometric credential enrolled
        ↓
not_enrolled
```

Example:

```js
if (result.error === "not_enrolled") {
  console.log(
    "No biometric credentials are enrolled."
  );
}
```

---

# What Should the UI Do?

If the user hasn't enrolled biometrics, you could show:

```text
Biometric authentication isn't set up.

Please configure biometrics
in your device settings.
```

However, the exact message and available settings flow depend on the platform.

---

# Important Difference

Remember:

```js
hasHardwareAsync()
```

and:

```js
isEnrolledAsync()
```

already allow you to check this situation before authentication.

Therefore, a production application can often detect this earlier.

Still, you should understand:

```text
not_enrolled
```

because authentication can return documented errors describing the authentication state.

---

# 2. `user_cancel`

This means the user cancelled the authentication prompt.

Conceptually:

```text
Authentication prompt
        ↓
User presses Cancel
        ↓
user_cancel
```

Example:

```js
if (result.error === "user_cancel") {
  console.log(
    "User cancelled authentication."
  );
}
```

---

# What Should the App Do?

Usually, simply keep the protected content protected.

For example:

```js
if (result.error === "user_cancel") {
  console.log("Authentication cancelled");
  return;
}
```

There is normally no reason to show a serious error message for an intentional cancellation.

A user may simply have changed their mind.

---

# 3. `app_cancel`

`app_cancel` indicates that the application cancelled the authentication operation.

Conceptually:

```text
Authentication running
        ↓
Application cancels request
        ↓
app_cancel
```

This is different from:

```text
user_cancel
```

because the cancellation originated from the application rather than directly from the user.

---

# Example

```js
if (result.error === "app_cancel") {
  console.log(
    "Authentication was cancelled by the app."
  );
}
```

This distinction can be useful when debugging authentication flows.

---

# 4. `not_available`

`not_available` indicates that authentication is not available in the current situation.

Example:

```js
if (result.error === "not_available") {
  console.log(
    "Local authentication is not available."
  );
}
```

This can represent a device/platform state where the requested authentication mechanism cannot currently be used.

---

# 5. `lockout`

`lockout` indicates that the authentication system has been locked.

This can happen because of repeated failed authentication attempts or platform security rules.

Conceptually:

```text
Authentication attempt
        ↓
Failed
        ↓
Failed
        ↓
Failed
        ↓
Security threshold reached
        ↓
lockout
```

Example:

```js
if (result.error === "lockout") {
  console.log(
    "Authentication is temporarily locked."
  );
}
```

---

# Why Is `lockout` Different?

This is not simply:

```text
"The user's fingerprint didn't match."
```

It indicates a security state imposed by the authentication system.

Therefore, your UI may want to tell the user:

```text
Authentication is temporarily unavailable.

Please use your device's supported authentication
method or try again later.
```

The exact recovery behavior depends on the platform.

---

# 6. `timeout`

`timeout` indicates that the authentication operation timed out.

Example:

```js
if (result.error === "timeout") {
  console.log(
    "Authentication timed out."
  );
}
```

The application can allow the user to try again if appropriate.

# 9. `authentication_failed`

This is one of the most common errors.

It means the authentication attempt was unsuccessful.

For example:

```js
if (result.error === "authentication_failed") {
  console.log(
    "The authentication attempt failed."
  );
}
```

Conceptually:

```text
User attempts authentication
        ↓
Authentication does not match
        ↓
authentication_failed
```

---

# Important Difference: Failure vs Cancellation

These are not the same:

```text
authentication_failed
```

means the authentication attempt failed.

While:

```text
user_cancel
```

means the user cancelled the authentication prompt.

For example:

```text
User scans fingerprint
        ↓
Fingerprint doesn't match
        ↓
authentication_failed
```

versus:

```text
Authentication prompt appears
        ↓
User taps Cancel
        ↓
user_cancel
```

Your UI can respond differently.

# 10. `system_cancel`

`system_cancel` indicates that the authentication operation was cancelled by the system.

Example:

```js
if (result.error === "system_cancel") {
  console.log(
    "Authentication was cancelled by the system."
  );
}
```

This is different from:

```text
user_cancel
```

and:

```text
app_cancel
```

because the cancellation source is different.

Think of the three as:

```text
user_cancel
    ↓
User cancelled

app_cancel
    ↓
Application cancelled

system_cancel
    ↓
System cancelled
```

# 11. `no_space`

`no_space` is a documented authentication error value indicating that the authentication operation cannot proceed because the required system resources/storage space are unavailable.

Example:

```js
if (result.error === "no_space") {
  console.log(
    "Authentication cannot proceed because of a space/resource issue."
  );
}
```

This is a less common case, but it is part of the documented error set.

---

# 12. `unable_to_process`

This indicates that the authentication system was unable to process the authentication request.

Example:

```js
if (result.error === "unable_to_process") {
  console.log(
    "The authentication request could not be processed."
  );
}
```

This is different from a normal authentication mismatch.

Conceptually:

```text
Authentication request
        ↓
System attempts to process it
        ↓
Unable to process
        ↓
unable_to_process
```

---

# 13. `invalid_context`

`invalid_context` indicates that the authentication request was made with an invalid authentication context.

Example:

```js
if (result.error === "invalid_context") {
  console.log(
    "The authentication context is invalid."
  );
}
```

This is generally a lower-level/platform-related condition rather than a normal user mistake.

---

# 14. `unknown`

`unknown` represents an unspecified or otherwise unclassified authentication error.

Example:

```js
if (result.error === "unknown") {
  console.log(
    "An unknown authentication error occurred."
  );
}
```

When handling this case, a generic message is usually appropriate.

# Handling Errors With `switch`

A `switch` statement is a clean way to handle multiple documented errors.

```js
const result =
  await LocalAuthentication.authenticateAsync();

if (result.success) {

  console.log(
    "Authentication successful"
  );

  return;
}

switch (result.error) {

  case "user_cancel":
    console.log(
      "You cancelled authentication."
    );
    break;

  case "authentication_failed":
    console.log(
      "Authentication failed."
    );
    break;

  case "not_enrolled":
    console.log(
      "No biometric credentials are enrolled."
    );
    break;

  case "lockout":
    console.log(
      "Authentication is locked."
    );
    break;

  case "timeout":
    console.log(
      "Authentication timed out."
    );
    break;

  case "user_fallback":
    console.log(
      "User selected the fallback option."
    );
    break;

  case "passcode_not_set":
    console.log(
      "Device passcode is not configured."
    );
    break;

  default:
    console.log(
      "Authentication error:",
      result.error
    );
}
```

# A Better Production Pattern

Instead of only printing messages, your application can return a meaningful result.

```js
const authenticateUser = async () => {

  const result =
    await LocalAuthentication.authenticateAsync({
      promptMessage:
        "Authenticate to continue",
    });

  if (result.success) {
    return {
      success: true,
    };
  }

  return {
    success: false,
    error: result.error,
  };
};
```

Then:

```js
const result =
  await authenticateUser();

if (result.success) {

  console.log(
    "Access granted"
  );

} else {

  console.log(
    "Access denied:",
    result.error
  );
}
```

This keeps authentication logic separate from UI logic.

This is an important production concept.

For example:

```text

```



may require different handling.

Similarly:

```text
not_enrolled
```

doesn't make much sense to solve by repeatedly calling:


```text

  ↓

  ↓
```

# Example of Smart Error Handling

```js
const handleAuthentication = async () => {

  const result =
    await LocalAuthentication.authenticateAsync({
      promptMessage:
        "Authenticate to continue",

    return {
      status: "success",
    };

    case "user_cancel":
      return {

      };

    case "authentication_failed":
      return {
        status: "retry",
      };

    case "lockout":
      return {
        status: "locked",
      };

    case "not_enrolled":
      return {
        status: "not_enrolled",
      };

    default:
      return {
        status: "error",
```


This is a much cleaner architecture for a larger application.

```text
because the authentication system is locked.
```

And:

```text
success: false
```

means:

```text
Authentication unsuccessful
because the authentication attempt failed.
```

# Part 10 — Platform Differences and Configuration

So far, we have learned the common APIs provided by:

```js
expo-local-authentication
```

For example:

```js
LocalAuthentication.hasHardwareAsync();

LocalAuthentication.isEnrolledAsync();

LocalAuthentication.supportedAuthenticationTypesAsync();

LocalAuthentication.getEnrolledLevelAsync();

LocalAuthentication.authenticateAsync();
```

These APIs provide a common JavaScript interface.

However, the actual authentication system is provided by the operating system.

That means:

```text
React Native / Expo App
        ↓
expo-local-authentication
        ↓
 ┌───────────────┐
 ↓               ↓
Android         iOS
 ↓               ↓
Android         Apple
Biometric       Local
System          Authentication
```

Because Android and iOS have different authentication systems, some behavior and options are platform-specific.

---

# Why Does Platform Difference Matter?

Suppose you write:

```js
await LocalAuthentication.authenticateAsync({
  promptMessage: "Authenticate to continue",
});
```

The JavaScript code is almost the same on both platforms.

But internally:

```text
Android
   ↓
Android biometric authentication system

iOS
   ↓
Apple Local Authentication framework
```

So the actual UI, available biometric methods, fallback behavior, security classifications, and configuration requirements can differ.

---

# Android vs iOS

A simple comparison:

| Feature                   | Android                         | iOS                                  |
| ------------------------- | ------------------------------- | ------------------------------------ |
| Fingerprint               | Supported on compatible devices | Touch ID on compatible devices       |
| Face authentication       | Supported on compatible devices | Face ID on compatible devices        |
| Iris                      | Some devices/platforms          | Not generally applicable             |
| Security levels           | Android biometric classes       | Different Apple authentication model |
| `biometricsSecurityLevel` | Yes                             | No                                   |
| `requireConfirmation`     | Yes                             | No                                   |
| `promptDescription`       | Yes                             | No                                   |
| `promptSubtitle`          | Yes                             | No                                   |
| `fallbackLabel`           | No                              | Yes                                  |
| `cancelAuthenticate()`    | Yes                             | No                                   |
| Face ID usage description | No                              | Required when using Face ID          |

The important lesson is:

> **The Expo API is shared, but not every option is available on every platform.**

Depending on the device, Android may provide:

```text

Other supported biometric modalities
```

The exact authentication method depends on the hardware and Android device.

Your application normally does not implement fingerprint scanning or face recognition itself.

Instead:

```text

Android biometric system
   ↓
User authenticates

Result returned to App
```

Conceptually:



This tells the native iOS configuration what message should explain the application's use of Face ID.

```text
     ↓

     ↓
Appropriate native configuration
     ↓
```

A common beginner misconception is:

> "Face authentication uses the camera, so I need camera permission."

Your application does not receive the user's Face ID camera/sensor data.

```text
   ↓

   ↓
iOS / Android system
   ↓
Biometric verification
   ↓
Success / failure
   ↓
Your App
```

Your application receives the authentication result, not the underlying biometric data.

```js
export async function authenticateUser() {
  try {
    const hasHardware =
      await LocalAuthentication.hasHardwareAsync();

    if (!hasHardware) {
      return {
        success: false,
        error: "hardware_unavailable",
      };
    }

    const enrolled =
      await LocalAuthentication.isEnrolledAsync();

    if (!enrolled) {
      return {
        success: false,
        error: "not_enrolled",
      };
    }

    return await LocalAuthentication.authenticateAsync({
      promptMessage: "Authenticate to continue",
    });
  } catch (error) {
    console.error(error);

    return {
      success: false,
      error: "unknown",
    };
  }
}
```

Now a screen can simply call:

```js
const result =
  await authenticateUser();

if (result.success) {
  // Continue
}
```

---

# Why Create a Utility?

Without a utility, multiple screens may contain:

```text
hardware check
        +
enrollment check
        +
authentication
        +
error handling
```

A utility centralizes that behavior:

```text
                 authenticateUser()
                  /       |       \
                 /        |        \
             Payment   Private   Settings
```

This reduces duplication and makes future changes easier.

---

# Important Utility Design Principle

A utility should return enough information for the screen to decide what to do.

For example:

```js
{
  success: false,
  error: "not_enrolled"
}
```

The utility should not automatically navigate to a screen or display UI unless that behavior is intentionally part of its design.

A clean separation is:

```text
Authentication Utility
        ↓
Returns Result
        ↓
Screen / Feature
        ↓
Decides UI and Navigation
```
