# Expo Network (`expo-network`) 

---

# What is `expo-network`?

`expo-network` is an Expo SDK library for reading information about the device's network.

It can tell an application things such as:

-   whether an active network connection exists

-   whether internet connectivity is reachable

-   what type of network is active

-   the current IPv4 address

-   whether airplane mode is enabled on supported platforms

-   when network state changes

The main import is:

``` js

import * as Network from "expo-network";

```

The documented API surface includes:

``` text

useNetworkState()

getNetworkStateAsync()

getIpAddressAsync()

isAirplaneModeEnabledAsync()

addNetworkStateListener()

NetworkState

NetworkStateEvent

NetworkStateType

```

## Simple meaning

Think of `expo-network` as a ****network information assistant**** inside your application.

Your app can ask questions such as:

``` text

"Is the device connected to a network?"

"Is the internet reachable?"

"Is the user on Wi-Fi or mobile data?"

"What is the current IPv4 address?"

"Did the network connection change?"

"Is airplane mode enabled?"

```

It does ****not**** mean that `expo-network` itself performs your API requests.

For example:

``` js

fetch("https://example.com/api/products");

```

is still responsible for making an HTTP request.

`expo-network` gives your application useful information **about the current network situation**.

---

# Why do we need network information?

Modern mobile applications frequently depend on a network.

Examples:

-   Login

-   Fetching products

-   Loading user profiles

-   Sending messages

-   Uploading images

-   Downloading files

-   Synchronizing data

-   Calling REST APIs

-   Calling GraphQL APIs

-   Loading remote configuration

Suppose your application does:

``` js

fetch("https://example.com/api/products");

```

If the phone is offline, the request may fail.

A better application can first understand the network situation:

``` text

Is there an active connection?

        ↓

Is internet reachable?

        ↓

What type of connection is active?

        ↓

Perform the network-dependent operation

```

This allows us to build:

-   offline banners

-   retry systems

-   network status screens

-   connection indicators

-   Wi-Fi/mobile-data indicators

-   better error messages

-   network debugging tools

-   conditional downloads

-   synchronization systems

-   offline-first experiences

## Real-world example

Imagine a food delivery application.

The user opens the app without internet.

A poor experience might show:

``` text

Something went wrong.

```

The user does not know why.

A better experience can show:

``` text

You are offline.

Please connect to the internet and try again.

```

Even better:

``` text

You're offline.

Your previously loaded restaurants are still available.

We'll sync when you're back online.

```

Network awareness helps create this kind of experience.

# Part 1 - Installation and Setup

## 1.1 Create an Expo project

If you are starting from a new application:

``` bash

npx create-expo-app@latest network-demo

cd network-demo

npx expo start

```

You can then run the application using your normal Expo development

workflow.

---

## 1.2 Install `expo-network`

Install the package using:

``` bash

npx expo install expo-network

```

Other supported package-manager forms include:

``` bash

yarn expo install expo-network

```

``` bash

pnpm expo install expo-network

```

``` bash

bun expo install expo-network

```

### Why prefer `expo install`?

Expo projects contain a particular Expo SDK version.

Using:

``` bash

npx expo install expo-network

```

allows Expo to select a package version compatible with the project's SDK.

Instead of manually guessing:

``` bash

npm install expo-network@some-version

```

prefer the Expo installation command for Expo projects.

---

## 1.3 Import the module

After installation:

``` js

import * as Network from "expo-network";

```

The `* as Network` syntax gives us an object containing the APIs provided by the package.

For example:

``` js

Network.useNetworkState()

Network.getNetworkStateAsync()

Network.getIpAddressAsync()

```

---

## 1.4 Android permissions

Expo documents that Android requires access to network and Wi-Fi state.

The following permissions are added automatically:

``` text

ACCESS_NETWORK_STATE

ACCESS_WIFI_STATE

```

Normally, an Expo application using the package does not need to manually add these permissions.

## 1.5 First example

Let's start with the smallest useful example:

``` jsx

import { View, Text, Button } from "react-native";

import * as Network from "expo-network";

export default function App() {

        title="Check Network"

    </View>

```

``` text
      ↓

console.log()

```

The returned object contains network information.

For example, conceptually:

``` js

  type: "WIFI",

  isConnected: true,

  isInternetReachable: true
```

# Part 2 - Understanding Network Concepts

Before writing more code, we need to understand what a network actually means.

---

## 2.1 What is a network?

A network allows a device to communicate with another device or service.

A common flow is:

``` text

Phone

  ↓

Wi-Fi Router

  ↓

Internet

  ↓

API Server

```

For example, when a mobile app requests products:

``` text

React Native App

       ↓

     Router

       ↓

    Internet

       ↓

   Backend API

       ↓

    Database

```

The database is usually not directly accessed by the mobile application.

A backend server sits between the app and the database.

---

## 2.2 Network vs Internet

These terms are related, but they are not exactly the same.

### Network

A network is a communication system connecting devices.

For example:

``` text

Phone

  ↓

Wi-Fi Router

```

The phone can be connected to the router.

### Internet

The internet is a huge global network connecting many networks and services.

For example:

``` text

Phone

  ↓

Wi-Fi Router

  ↓

Internet

  ↓

Google / API / Server

```

### Important

A device can be connected to a network without having working internet access.

---

## 2.3 Wi-Fi does not automatically mean internet

Consider this situation:

``` text

Phone

  ↓

Wi-Fi Router

  X

Internet

```

The phone may still display:

``` text

Wi-Fi connected

```

but internet access may not work.

This is one of the most important concepts when learning `expo-network`.

---

## 2.4 `isConnected`

`isConnected` represents whether an active network connection exists.

Conceptually:

``` text

true

↓

An active network connection exists.

false

↓

No active network connection detected.

```

Expo documents that this value is false when the network type is `NONE` or `UNKNOWN`, and true otherwise.

### Example

``` js

const state = await Network.getNetworkStateAsync();

console.log(state.isConnected);

```

Possible result:

``` text

true

```

or:

``` text

false

```

---

## 2.5 `isInternetReachable`

`isInternetReachable` represents whether the internet is reachable through the currently active network connection.

For example:

``` js

{

  isConnected: true,

  isInternetReachable: false

}

```

means conceptually:

``` text

Device

  ↓

Connected to a network 

Internet

  ↓

Not currently reachable 

```

This can happen when a Wi-Fi network is available but the router has lost internet connectivity.

---

## 2.6 `type`

`type` represents the current network type.

Examples include:

``` text

WIFI

CELLULAR

ETHERNET

VPN

NONE

UNKNOWN

```

You can read it with:

``` js

const state = await Network.getNetworkStateAsync();

console.log(state.type);

```

---

## 2.7 The three-field mental model

Remember:

``` text

NetworkState

│

├── isConnected

│   └── Does an active network connection exist?

│

├── isInternetReachable

│   └── Is internet connectivity reachable?

│

└── type

    └── What kind of network is active?

```

Whenever students see a `NetworkState` object, they should immediately think:

``` text

CONNECTED?

INTERNET?

TYPE?

```

---

## 2.8 Four common scenarios

### Scenario 1 - Wi-Fi with internet

``` text

type = WIFI

isConnected = true

isInternetReachable = true

```

Meaning:

``` text

Wi-Fi connected

Internet reachable

```

---

### Scenario 2 - Wi-Fi without internet

``` text

type = WIFI

isConnected = true

isInternetReachable = false

```

Meaning:

``` text

Connected to Wi-Fi

But internet is unavailable

```

---

### Scenario 3 - No network

``` text

type = NONE

isConnected = false

```

Meaning:

``` text

No active network connection

```

---

### Scenario 4 - Mobile data

``` text

type = CELLULAR

isConnected = true

```

Meaning:

``` text

Device is connected through cellular/mobile data.

```

The exact value of `isInternetReachable` should be treated according to

the platform and current network conditions.

---

## 2.9 Network status is not API success

This is extremely important.

Even if:

``` js

isConnected === true

```

your API request can still fail.

Possible reasons:

-   server is down

-   DNS fails

-   request times out

-   authentication fails

-   backend returns an error

-   TLS/network problems occur

-   endpoint does not exist

-   request is rejected

-   server returns `500`

-   server returns `401`

-   server returns `403`

Therefore:

``` text

Network state

```

and:

``` text

Request success

```

are different things.

### Example

``` text

isConnected = true

       ↓

fetch("/products")

       ↓

Server returns 500

       ↓

API request failed

```

So:

> Network information is a useful signal, not a guarantee that every API

> request will succeed.

---

## 2.10 Network check vs API check

Think of these as two different questions.

### Network check

``` text

Can the device currently access a network?

```

### API check

``` text

Did my particular request succeed?

```

A good application may use both.

``` text

Network State

     ↓

Should we attempt the request?

     ↓

API Request

     ↓

Did the server respond successfully?

```

# Part 3 - `useNetworkState()`

## 3.1 What is the hook?

`useNetworkState()` is a React hook that returns the current network state.

Expo documents that it initiates a listener for network changes and cleans it up when the component unmounts.

This makes it especially useful for UI.

---

## 3.2 Basic example

``` jsx

import { View, Text } from "react-native";

import * as Network from "expo-network";

export default function App() {

  const state = Network.useNetworkState();

  return (

    <View>

      <Text>Type: {state.type}</Text>

      <Text>

        Connected: {String(state.isConnected)}

      </Text>

      <Text>

        Internet Reachable:

        {String(state.isInternetReachable)}

      </Text>

    </View>

  );

}

```

---

## 3.3 Why is it called a hook?

Because it follows React's hook model.

It can be used inside a React component:

``` js

const state = Network.useNetworkState();

```

The hook gives the component network information.

When the network changes, the hook can provide updated state so React can render the updated UI.

---

## 3.4 Mental model

``` text

Component mounts

      ↓

useNetworkState()

      ↓

Current network state

      ↓

Network changes

      ↓

Hook receives updated state

      ↓

React UI updates

```

This is why the hook is useful for screens that need to **continuously display network status**.

---

## 3.5 Show online/offline UI

``` jsx

const state = Network.useNetworkState();

const online =

  state.isConnected === true &&

  state.isInternetReachable === true;

return (

  <Text>

    {online ? "You are online" : "You are offline"}

  </Text>

);

```

### Why use both?

Because:

``` js

isConnected === true

```

does not necessarily mean:

``` js

isInternetReachable === true

```

---

## 3.6 A more user-friendly status

``` jsx

const state = Network.useNetworkState();

let message = "Checking network...";

if (

  state.isConnected === true &&

  state.isInternetReachable === true

) {

  message = "You are online";

} else if (state.isConnected === true) {

  message = "Connected, but internet may be unavailable";

} else {

  message = "You are offline";

}

return <Text>{message}</Text>;

```

This gives the user more useful information than simply showing `"Offline"`.

---

## 3.7 Show network type

``` jsx

<Text>

  Network Type: {state.type ?? "Unknown"}

</Text>

```

Possible display:

``` text

Network Type: WIFI

```

or:

``` text

Network Type: CELLULAR

```

---

## 3.8 Wi-Fi detection

``` js

if (state.type === "WIFI") {

  console.log("Using Wi-Fi");

}

```

---

## 3.9 Cellular detection

``` js

if (state.type === "CELLULAR") {

  console.log("Using mobile data");

}

```

---

## 3.10 Conditional UI based on network

``` jsx

if (state.type === "CELLULAR") {

  return <Text>You are using mobile data.</Text>;

}

if (state.type === "WIFI") {

  return <Text>You are using Wi-Fi.</Text>;

}

return <Text>Network type is unknown.</Text>;

```

---

## 3.11 When should we use the hook?

Use `useNetworkState()` when the **React UI needs to react to network

changes**.

Good use cases:

-   online/offline banner

-   network status screen

-   disabling/enabling UI

-   displaying Wi-Fi/mobile data

-   showing connection state

-   reacting immediately when connectivity changes

# Part 4 - `getNetworkStateAsync()`

## 4.1 What does it do?

It gets the current network connection state.

Return type:

``` text

Promise<NetworkState>

```

Because it is asynchronous, use:

``` js

await

```

inside an async function.

---

## 4.2 Basic example

``` js

const state = await Network.getNetworkStateAsync();

console.log(state);

```

---

## 4.3 Complete example

``` jsx

import { useState } from "react";

import { View, Text, Button } from "react-native";

import * as Network from "expo-network";

export default function App() {

  const [state, setState] = useState(null);

  const checkNetwork = async () => {

    try {

      const result = await Network.getNetworkStateAsync();

      setState(result);

    } catch (error) {

      console.error("Network error:", error);

    }

  };

  return (

    <View>

      <Button

        title="Check Network"

        onPress={checkNetwork}

      />

      {state && (

        <>

          <Text>Type: {state.type}</Text>

          <Text>

            Connected: {String(state.isConnected)}

          </Text>

          <Text>

            Internet Reachable:

            {String(state.isInternetReachable)}

          </Text>

        </>

      )}

    </View>

  );

}

```

---

## 4.4 When should we use it?

Use `getNetworkStateAsync()` when you need a ****current snapshot****.

For example:

``` text

Button pressed

      ↓

Get current network state

      ↓

Make a decision

```

For continuously updating React UI, `useNetworkState()` is often more convenient.

---

## 4.5 Hook vs async function

### `useNetworkState()`

Think:

``` text

"Keep my UI informed about network changes."

```

### `getNetworkStateAsync()`

Think:

``` text

"Tell me the network state right now."

```

# Part 5 - `getIpAddressAsync()`

## 5.1 What is an IP address?

An IP address is a network address associated with a network interface.

Example IPv4:

``` text

192.168.1.20

```

You can think of it as an address used in network communication.

### Important

An IP address is ****not the same thing as your device name****.

For example:

``` text

Device name:

Rajesh's iPhone

IP address:

192.168.1.20

```

These represent different concepts.

---

## 5.2 Basic example

``` js

const ip = await Network.getIpAddressAsync();

console.log(ip);

```

Return type:

``` text

Promise<string>

```

---

## 5.3 Example component

``` jsx

import { useState } from "react";

import { View, Text, Button } from "react-native";

import * as Network from "expo-network";

export default function App() {

  const [ip, setIp] = useState("");

  const loadIp = async () => {

    try {

      const result = await Network.getIpAddressAsync();

      setIp(result);

    } catch (error) {

      console.error(error);

    }

  };

  return (

    <View>

      <Button

        title="Get IP"

        onPress={loadIp}

      />

      <Text>

        IP: {ip || "Not loaded"}

      </Text>

    </View>

  );

}

```

---

## 5.4 Failed retrieval

Expo documents:

``` text

0.0.0.0

```

when the IP address cannot be retrieved.

Therefore, do not assume every returned value represents a useful device address.

For example:

``` js

const ip = await Network.getIpAddressAsync();

if (ip === "0.0.0.0") {

  console.log("Could not retrieve a useful IP address");

}

```

---

## 5.5 Native behavior vs web behavior

On web, Expo documents that this method uses the third-party `ipify` service to obtain the public IP address of the current device.

This is important:

``` text

Native behavior

      ≠

Web behavior

```

A developer should always check platform-specific behavior before

building logic around network information.

---

## 5.6 Is IP address the same as internet?

No.

A device can have an IP address and still have problems reaching a particular internet service.

For example:

``` text

Device has IP

      ↓

Network exists

      ↓

API server unavailable

      ↓

Request fails

```

So:

``` text

IP address

```

does not automatically mean:

``` text

Internet is working perfectly

```

# Part 6 - `isAirplaneModeEnabledAsync()`

## 6.1 What does it do?

It checks whether the device is in airplane mode.

``` js

const enabled =

  await Network.isAirplaneModeEnabledAsync();

```

Return type:

``` text

Promise<boolean>

```

Possible results:

``` text

true

false

```

---

## 6.2 Example

``` jsx

import { useState } from "react";

import { View, Text, Button } from "react-native";

import * as Network from "expo-network";

export default function App() {

  const [enabled, setEnabled] = useState(null);

  const check = async () => {

    const result =

      await Network.isAirplaneModeEnabledAsync();

    setEnabled(result);

  };

  return (

    <View>

      <Button

        title="Check Airplane Mode"

        onPress={check}

      />

      <Text>

        Airplane Mode:

        {enabled === null

          ? "Unknown"

          : String(enabled)}

      </Text>

    </View>

  );

}

```

---

## 6.3 Understanding the boolean

If:

``` js

enabled === true

```

then:

``` text

Airplane mode is enabled.

```

If:

``` js

enabled === false

```

then:

``` text

Airplane mode is not enabled.

```

---

## 6.4 Platform note

The Expo API documentation marks this method as Android-only.

Do not assume it has identical support on all platforms.

### Classroom rule

Whenever an API has platform restrictions, students should check:

``` text

Android

iOS

Web

tvOS

```

before depending on it in production code.

# Part 7 - Network State Listener

## 7.1 What is an event listener?

An event listener waits for something to change.

For network state:

``` text

Network changes

      ↓

Listener receives event

      ↓

Callback executes

```

Instead of repeatedly asking:

``` text

"Did the network change?"

"Did the network change?"

"Did the network change?"

```

we subscribe to changes.

---

## 7.2 `addNetworkStateListener()`

``` js

const subscription =

  Network.addNetworkStateListener((state) => {

    console.log(state);

  });

```

The callback receives updated network information.

---

## 7.3 Read event properties

``` js

const subscription =

  Network.addNetworkStateListener(

    ({ type, isConnected, isInternetReachable }) => {

      console.log("Type:", type);

      console.log("Connected:", isConnected);

      console.log("Internet:", isInternetReachable);

    }

  );

```

---

## 7.4 Subscription cleanup

The returned object has a `remove()` method:

``` js

subscription.remove();

```

This is important because a subscription should not remain active after the component no longer needs it.

---

## 7.5 React `useEffect`

``` jsx

import { useEffect } from "react";

import * as Network from "expo-network";

export default function App() {

  useEffect(() => {

    const subscription =

      Network.addNetworkStateListener((state) => {

        console.log("Network changed:", state);

      });

    return () => {

      subscription.remove();

    };

  }, []);

  return null;

}

```

---

## 7.6 Why cleanup matters

Without cleanup, you can accidentally keep old listeners alive.

Conceptually:

``` text

Listener 1

Listener 2

Listener 3

...

```

One network change could then trigger multiple callbacks.

The correct lifecycle is:

``` text

Mount

  ↓

Subscribe

  ↓

Receive changes

  ↓

Unmount

  ↓

Remove subscription

```

---

## 7.7 Listener vs hook

Both can respond to network changes.

### Hook

``` js

const state = Network.useNetworkState();

```

Best when:

``` text

Network state

     ↓

React UI

```

### Listener

``` js

Network.addNetworkStateListener(...)

```

Useful when:

``` text

Network change

     ↓

Run custom logic

```

For example:

``` text

Network becomes available

        ↓

Start synchronization

```

or:

``` text

Network becomes unavailable

        ↓

Pause upload

```

---

## 7.8 Example: logging network changes

``` jsx

useEffect(() => {

  const subscription =

    Network.addNetworkStateListener((state) => {

      console.log("Network type:", state.type);

      console.log("Connected:", state.isConnected);

      console.log(

        "Internet:",

        state.isInternetReachable

      );

    });

  return () => subscription.remove();

}, []);

```

# Part 8 - `NetworkState`

`NetworkState` is the object representing current network state.

Its documented properties are:

``` text

isConnected

isInternetReachable

type

```

---

## 8.1 `isConnected`

Type:

``` ts

boolean

```

Meaning:

``` text

An active network connection exists.

```

Important:

``` text

connected != guaranteed internet access

```

---

## 8.2 `isInternetReachable`

Type:

``` ts

boolean

```

Meaning:

``` text

Internet is reachable through the currently active connection.

```

Expo documents platform-specific implementation details for this value.

On iOS, Expo documents that this value is always the same as `isConnected`.

---

## 8.3 `type`

Type:

``` ts

NetworkStateType

```

It describes the current network connection type.

Example:

``` js

{

  type: "WIFI",

  isConnected: true,

  isInternetReachable: true

}

```

---

## 8.4 Safe UI handling

Network information can sometimes be unavailable or unknown.

Therefore, UI code should avoid assuming every value is always a perfect string/boolean.

For example:

``` jsx

<Text>

  Type: {state.type ?? "Unknown"}

</Text>

```

For boolean-like values:

``` jsx

<Text>

  Connected: {String(state.isConnected)}

</Text>

```

# Part 9 - `NetworkStateEvent`

`NetworkStateEvent` represents the updated network state supplied when a network-state event occurs.

It is passed to:

``` js

Network.addNetworkStateListener(...)

```

Example:

``` js

Network.addNetworkStateListener((event) => {

  console.log(event.type);

  console.log(event.isConnected);

  console.log(event.isInternetReachable);

});

```

Think:

``` text

Network change

      ↓

NetworkStateEvent

      ↓

Listener callback

```

---

## 9.1 Why have an event object?

Instead of sending three separate values:

``` text

type

isConnected

isInternetReachable

```

the event gives us a structured object.

That makes it easier to pass around and destructure:

``` js

({ type, isConnected, isInternetReachable }) => {

  // ...

}

```

---

## 9.2 Destructuring example

# Part 11 - Platform Differences

Cross-platform does not mean identical behavior on every platform.

Always consider:

``` text

Android

iOS

tvOS

Web

```

---

## Android

The package supports Android and provides Android-specific network behavior.

Android automatically receives the documented network/Wi-Fi state permissions.

---

## iOS

Network state is supported.

Expo documents an important detail:

``` text

isInternetReachable

```

is always the same as:

``` text

isConnected

```

on iOS.

Therefore, do not build platform-independent assumptions that depend on those two values being meaningfully different on iOS.

---

## tvOS

Network-state APIs are documented as supported where indicated by the Expo platform badges.

---

## Web

Web has additional limitations.

For `getNetworkStateAsync()`, Expo documents:

``` text

active network connection → type = UNKNOWN

no active network connection → type = NONE

```

because:

``` text

navigator.connection.type

```

is not available in browsers in the same way native platforms expose network types.

For `getIpAddressAsync()`, Expo documents use of the third-party `ipify` service to obtain the public IP.

The lesson:

``` text

Cross-platform API

       does not mean

identical native behavior.

```

---

## 11.1 Why platform differences matter

Imagine your code says:

``` js

  downloadLargeFile();

}

```

This may work differently across platforms because the available network type information can differ.

Therefore:

> Network-dependent logic should be designed with platform behavior in

> mind.

## 23. API Contract Sheet — Learn Every API the Same Way

### `useNetworkState()`

**What it does:** React hook that keeps the component informed about current network state.
**Return:** Returns `NetworkState`.
**When to use:** Use for UI that should react automatically to network changes.
**What it does NOT do:** It does not make API requests and does not guarantee your backend will respond.

**Teaching rule:** Always identify whether you need a **snapshot**, a **reactive value**, or a **change event** before choosing the API.

### `getNetworkStateAsync()`

**What it does:** Reads the current network state once.
**Return:** Returns `Promise<NetworkState>`.
**When to use:** Use for a one-time check or manual refresh.
**What it does NOT do:** It does not continuously watch changes.

**Teaching rule:** Always identify whether you need a **snapshot**, a **reactive value**, or a **change event** before choosing the API.

### `getIpAddressAsync()`

**What it does:** Reads the current IPv4 address according to the platform implementation.
**Return:** Returns `Promise<string>`.
**When to use:** Use when your feature genuinely needs an IP value.
**What it does NOT do:** It does not prove internet access and is not an API request mechanism.

**Teaching rule:** Always identify whether you need a **snapshot**, a **reactive value**, or a **change event** before choosing the API.

### `isAirplaneModeEnabledAsync()`

**What it does:** Checks airplane mode on supported Android behavior.
**Return:** Returns `Promise<boolean>`.
**When to use:** Use for platform-aware status/debug UI.
**What it does NOT do:** It is not a replacement for checking actual connectivity.

**Teaching rule:** Always identify whether you need a **snapshot**, a **reactive value**, or a **change event** before choosing the API.

### `addNetworkStateListener()`

**What it does:** Subscribes to network-state changes.
**Return:** Returns an event subscription with `remove()`.
**When to use:** Use when a non-hook architecture needs event-driven updates.
**What it does NOT do:** It must be removed when the owner is disposed.

**Teaching rule:** Always identify whether you need a **snapshot**, a **reactive value**, or a **change event** before choosing the API.

## 24. Deep Dive — `NetworkState` Is the Core Data Model

A useful way to teach `expo-network` is to treat `NetworkState` as the central object and the other APIs as different ways of obtaining it.

```text
NetworkState
   │
   ├── isConnected
   │      └── Is there an active network connection?
   │
   ├── isInternetReachable
   │      └── Does the platform report internet reachability?
   │
   └── type
          └── What network type is active?
```

The hook, one-time method, and event listener should therefore be taught as three different access patterns for network state:

| Access pattern | API | Mental model |
|---|---|---|
| Reactive UI | `useNetworkState()` | “Keep me updated.” |
| One-time read | `getNetworkStateAsync()` | “Tell me now.” |
| Event-driven | `addNetworkStateListener()` | “Tell me when it changes.” |

### 24.1 Snapshot vs stream vs reactive render

```text
getNetworkStateAsync()
        │
        └── one value ──> function continues

addNetworkStateListener()
        │
        ├── event
        ├── event
        ├── event
        └── remove()

useNetworkState()
        │
        ├── render with current state
        ├── network changes
        ├── hook updates
        └── component re-renders
```

## 25. Safe Handling of `NetworkState` Values

Network-related values should be treated as runtime state, not as constants you can safely assume from your development phone.

### 25.1 Safe display helper

```js
const getNetworkLabel = (state) => {
  if (!state) return "Checking network...";
  if (state.type === Network.NetworkStateType.NONE) return "No network";
  if (state.type === Network.NetworkStateType.UNKNOWN) return "Network type unknown";
  if (state.isInternetReachable === false) return "Connected, but internet unavailable";
  if (state.isConnected) return `Connected via ${state.type}`;
  return "Network status unavailable";
};
```

### 25.2 Why not simply use `isConnected`?

Because a connected transport can exist while internet access is unavailable. The official documentation explicitly warns that `isConnected` does not mean internet is reachable. citeturn0search0

### 25.3 Why not simply use `type === WIFI`?

Because `WIFI` answers a different question: what type of active connection is reported? It does not by itself prove that your API endpoint is healthy.

## 26. Error Codes and Troubleshooting

This section closes the major gap identified in the original README. The official documentation lists error codes associated with network-information operations. citeturn0search0

### `ERR_NETWORK_IP_ADDRESS`

**Meaning:** On Android, an unknown Wi-Fi host may be encountered while accessing `WifiManager` in `getIpAddressAsync()`. On iOS, no network interfaces could be retrieved.
**Troubleshooting:** Catch the error, log the platform and operation, and provide a fallback such as “IP unavailable”. Do not treat this as proof that the entire app is offline.

Example defensive pattern:
```js
try {
  const state = await Network.getNetworkStateAsync();
  console.log("Network state:", state);
} catch (error) {
  console.error("Network information failed:", error);
  // Show a safe fallback in the UI.
}
```

### `ERR_NETWORK_UNDEFINED_INTERFACE`

**Meaning:** The documentation associates this with an undefined `interfaceName` passed to `getMacAddressAsync()`.
**Troubleshooting:** If working with a version that exposes such an API, validate the interface argument and verify that the method is actually supported by the installed SDK.

Example defensive pattern:
```js
try {
  const state = await Network.getNetworkStateAsync();
  console.log("Network state:", state);
} catch (error) {
  console.error("Network information failed:", error);
  // Show a safe fallback in the UI.
}
```

### `ERR_NETWORK_SOCKET_EXCEPTION`

**Meaning:** The documentation associates this with socket creation/access errors in `getMacAddressAsync()`.
**Troubleshooting:** Treat it as a low-level network-information failure; do not automatically conclude that HTTP connectivity is unavailable.

Example defensive pattern:
```js
try {
  const state = await Network.getNetworkStateAsync();
  console.log("Network state:", state);
} catch (error) {
  console.error("Network information failed:", error);
  // Show a safe fallback in the UI.
}
```

### `ERR_NETWORK_INVALID_PERMISSION_INTERNET`

**Meaning:** The documentation associates this with invalid `ACCESS_WIFI_STATE` permission handling in `getMacAddressAsync()`.
**Troubleshooting:** Verify the installed Expo SDK, native permissions, and whether the referenced API is actually available in that SDK.

Example defensive pattern:
```js
try {
  const state = await Network.getNetworkStateAsync();
  console.log("Network state:", state);
} catch (error) {
  console.error("Network information failed:", error);
  // Show a safe fallback in the UI.
}
```

### `ERR_NETWORK_NO_ACCESS_NETWORKINFO`

**Meaning:** Unable to access network information.
**Troubleshooting:** Catch the error, record diagnostic context, and show a safe fallback instead of crashing the UI.

Example defensive pattern:
```js
try {
  const state = await Network.getNetworkStateAsync();
  console.log("Network state:", state);
} catch (error) {
  console.error("Network information failed:", error);
  // Show a safe fallback in the UI.
}
```

### 26.1 General error-handling rule

```text
Network API throws?
      ↓
Catch the error
      ↓
Identify which operation failed
      ↓
Show a safe fallback
      ↓
Do not automatically label the whole app “offline”
```

A failure to read **network metadata** and a failure to perform an **HTTP request** are different classes of failure.

## 31. Event Listener Masterclass

`addNetworkStateListener()` is useful when you want a callback whenever the network state changes. The official docs describe the listener callback as receiving a `NetworkState` object and the subscription as exposing `remove()`. citeturn0search0

### 31.1 Minimal listener

```js
const subscription = Network.addNetworkStateListener((state) => {
  console.log("Network changed:", state);

```

### 31.2 React lifecycle listener

```jsx
useEffect(() => {
  const subscription = Network.addNetworkStateListener((state) => {
    setNetworkState(state);
  });

  return () => subscription.remove();
}, []);
```

### 31.3 Why cleanup matters

Without cleanup, a component can leave a listener behind after unmounting. Repeated mounting can then create duplicate callbacks and confusing logs.

```text
Mount → add listener
Unmount → remove listener
Mount → add listener
Unmount → remove listener
```

## 33. Platform Behavior Deep Dive

The official documentation marks APIs by platform. `useNetworkState`, `getIpAddressAsync`, `getNetworkStateAsync`, and `addNetworkStateListener` are documented for Android, iOS, tvOS, and Web, while `isAirplaneModeEnabledAsync` is Android-only. citeturn0search0

### 33.1 Android

Teach students to remember: Android exposes several network types and has Android-specific airplane-mode behavior. The documentation also notes Android-specific implementation details for internet reachability.

### 33.2 iOS

The official docs state that `isInternetReachable` on iOS is always the same as `isConnected`. This is an important cross-platform teaching point: the same property name does not necessarily imply identical implementation semantics. citeturn0search0

### 33.3 Web

The official docs state that browsers do not provide the same `navigator.connection.type` information used for native network type reporting. When there is an active network connection, `getNetworkStateAsync()` reports `UNKNOWN`; without an active connection it reports `NONE`. `getIpAddressAsync()` uses ipify on web. citeturn0search0

### 33.4 tvOS

When teaching tvOS, focus on the APIs documented for that platform and avoid assuming mobile-specific concepts such as cellular data are meaningful there.

## 34. Network Type Master Reference

| Enum | Platforms documented | Meaning |
|---|---|---|
| `BLUETOOTH` | Android | Bluetooth-based active connection. |
| `CELLULAR` | Android, iOS | Mobile data or documented tethering-related cellular connection. |
| `ETHERNET` | Android, iOS | Ethernet connection. |
| `NONE` | All documented platforms | No active network connection detected. |
| `OTHER` | Android | Other active network type. |
| `UNKNOWN` | All documented platforms | Connection type could not be determined. |
| `VPN` | Android | VPN connection. |
| `WIFI` | Android, iOS | Wi-Fi connection. |
| `WIMAX` | Android | WiMAX connection. |

### 34.1 Never assume only Wi-Fi and cellular exist

A beginner app often writes:

```js
if (state.type === Network.NetworkStateType.WIFI) {
  // Wi-Fi
} else {
  // cellular
}
```

That `else` assumption is unsafe. A state can be `NONE`, `UNKNOWN`, `VPN`, `ETHERNET`, or another supported value depending on platform.

Prefer an explicit switch:

```js
switch (state.type) {
  case Network.NetworkStateType.WIFI:
    return "Wi-Fi";
  case Network.NetworkStateType.CELLULAR:
    return "Mobile data";
  case Network.NetworkStateType.ETHERNET:
    return "Ethernet";
  case Network.NetworkStateType.VPN:
    return "VPN";
  case Network.NetworkStateType.NONE:
    return "Offline";
  case Network.NetworkStateType.UNKNOWN:
    return "Unknown";
  default:
    return String(state.type);
}
```

## 36. Example — A Production-Friendly Network Status Component

```jsx
import { Text, View } from "react-native";
import * as Network from "expo-network";

export default function NetworkStatus() {
  const state = Network.useNetworkState();

  let title = "Checking network";
  let detail = "Please wait...";

  if (state.type === Network.NetworkStateType.NONE) {
    title = "Offline";
    detail = "No active network connection.";
  } else if (state.isInternetReachable === false) {
    title = "Limited connectivity";
    detail = "The device is connected, but internet may be unavailable.";
  } else if (state.isConnected) {
    title = "Online";
    detail = `Connection: ${state.type}`;
  }

  return (
    <View>
      <Text>{title}</Text>
      <Text>{detail}</Text>
    </View>
  );
}
```

### Teaching point

This component is a **network-information UI**. It is not an API-health monitor. A production application should still handle request errors, HTTP status codes, timeouts, authentication failures, and server failures separately.

## 43. Practical Architecture — Where Network State Belongs

A small app can read `useNetworkState()` directly in a screen. A larger application may centralize network-aware UI decisions in a provider, shared hook, or service layer. The goal is not to create unnecessary abstraction; the goal is to avoid duplicating inconsistent logic.

```text
                Network State
                      │
        ┌─────────────┼─────────────┐
        │             │             │
      UI Banner    Sync Logic    Download Guard
        │             │             │
        └─────────────┼─────────────┘
                      │
                HTTP / API layer
```

### 43.1 Separation of responsibilities

| Layer | Responsibility |
|---|---|
| `expo-network` | Device/network metadata |
| API client | HTTP requests and response handling |
| Cache | Previously fetched data |
| Sync layer | Decides what to upload/download |
| UI | Communicates current state to users |
| Backend | Authentication, business logic, persistence |

## 44. Offline-First Thinking

A network-aware application should not always think in only two states: online and offline.

A more useful product model is:

```text
ONLINE
  ↓
CONNECTED BUT LIMITED
  ↓
OFFLINE
  ↓
RECOVERING
  ↓
ONLINE AGAIN
```

### 44.1 Example product behavior

**Online:** Load fresh data and allow sync.
**Connected but limited:** Allow lightweight operations and show a warning when appropriate.
**Offline:** Show cached data, queue supported changes, disable only operations that truly require connectivity.
**Recovering:** Attempt synchronization and communicate progress.
**Online again:** Flush queued work carefully and refresh stale data.

`expo-network` can provide the network-state signal, but the queue/cache/sync behavior is application architecture that you build separately.

## 45. Retry Strategy — Network State Is Only One Input

A robust retry decision should consider at least:
- current network state
- whether the previous failure was transport-level
- HTTP status
- request idempotency
- number of previous attempts
- backoff delay
- user intent
- whether the operation is safe to repeat

### Example

```text
Request fails
    ↓
Was there a network connection?
    ↓
Was it a transient transport failure?
    ↓
Is the operation safe to retry?
    ↓
Apply bounded backoff
    ↓
Retry or surface the error
```

Do not build a retry loop that blindly retries every `500`, `401`, validation error, or user-cancelled operation.

## 48. Interview Questions — Advanced Set

### Q1. Why is `isConnected` not enough?

**Answer:** Because an active network connection does not necessarily mean internet connectivity is reachable.

**Follow-up:** Explain the answer with a real device scenario, not only a definition.

### Q2. Why can `type` be `UNKNOWN` on web?

**Answer:** The official docs explain that the browser does not provide the same connection-type information, so active web connections can be reported as `UNKNOWN`.

**Follow-up:** Explain the answer with a real device scenario, not only a definition.

### Q3. What is the difference between a hook and an event listener?

**Answer:** A hook integrates reactive network state with React rendering; a listener gives an imperative callback whenever network state changes.

**Follow-up:** Explain the answer with a real device scenario, not only a definition.

### Q4. Why remove a listener?

**Answer:** To stop receiving events after the owner is disposed and avoid duplicate callbacks/lifecycle problems.

**Follow-up:** Explain the answer with a real device scenario, not only a definition.

### Q5. Does Wi-Fi mean internet?

**Answer:** No. Wi-Fi can connect the device to a local router while the router has no usable internet path.

**Follow-up:** Explain the answer with a real device scenario, not only a definition.

### Q6. Does `expo-network` make HTTP requests?

**Answer:** No. It reports network information; HTTP requests are handled by request mechanisms such as `fetch` or another API client.

**Follow-up:** Explain the answer with a real device scenario, not only a definition.

### Q7. Does a successful network-state read prove your API is healthy?

**Answer:** No. It only provides network metadata; the backend can still be down or return an error.

**Follow-up:** Explain the answer with a real device scenario, not only a definition.

# Chapter 1 - Network Fundamentals

Before writing network code, we need to understand the problem that `expo-network` solves.

---

# What is a Network?

A network is a communication path between devices or services.

A simplified mobile-app flow looks like:

```text
Mobile App
    ↓
Wi-Fi / Mobile Network
    ↓
Internet
    ↓
Backend Server
    ↓
Database
```

For a product screen:

```text
React Native App
       ↓
fetch()
       ↓
HTTPS
       ↓
API Server
       ↓
Database
```

`expo-network` does not replace `fetch()`.

Instead, it helps answer questions about the device's current network environment.

---

# Real-Life Example

Imagine a shopping application.

The user taps:

```text
Load Products
```

If the phone has no connection, showing:

```text
Something went wrong.
```

is not very helpful.

A better app can detect the situation and show:

```text
You are offline.

Please reconnect to the internet and try again.
```

The network information can also help the app decide whether a large download should happen over Wi-Fi.

---

# Three Questions Every Student Should Ask

Whenever you receive a `NetworkState`, ask:

```text
1. Is there an active connection?
2. Is internet connectivity reachable?
3. What type of network is active?
```

These correspond to:

```js
state.isConnected
state.isInternetReachable
state.type
```

---

# Network vs Internet

These are related but different.

```text
Network
   ↓
A communication connection exists.

Internet
   ↓
That connection can reach the wider internet.
```

A device may have:

```text
Wi-Fi connected
Internet unavailable
```

So:

```js
isConnected === true
```

does not necessarily mean:

```js
isInternetReachable === true
```

---

# Example

```js
const state = await Network.getNetworkStateAsync();

console.log("Connected:", state.isConnected);
console.log("Internet:", state.isInternetReachable);
console.log("Type:", state.type);
```

Possible output:

```text
Connected: true
Internet: true
Type: WIFI
```

Another possible situation:

```text
Connected: true
Internet: false
Type: WIFI
```

Another:

```text
Connected: false
Internet: false
Type: NONE
```

# Chapter 3 - `getNetworkStateAsync()`

Now we will study the first major API deeply.

```js
Network.getNetworkStateAsync()
```

---

# What Does It Do?

It returns the current network state as a snapshot.

Think:

```text
"Tell me the network status right now."
```

It does not mean:

```text
"Keep watching forever."
```

For continuous changes, use a listener or the network-state hook.

---

# Syntax

```js
const state = await Network.getNetworkStateAsync();
```

The function is asynchronous.

Therefore:

```js
await
```

is normally used inside an `async` function.

---

# Return Value

Conceptually:

```js
NetworkState
```

The useful properties are:

```js
state.isConnected
state.isInternetReachable
state.type
```

---

# First Example

```jsx
const checkNetwork = async () => {
  try {
    const state = await Network.getNetworkStateAsync();

    console.log("Connected:", state.isConnected);
    console.log(
      "Internet:",
      state.isInternetReachable
    );
    console.log("Type:", state.type);
  } catch (error) {
    console.log("Network check failed:", error);
  }
};
```

# Example Output

```text

Internet: true
Type: WIFI
```

# Chapter 5 - Understanding `isInternetReachable`

---

# What Does It Mean?

`isInternetReachable` answers a more specific question:

```text
"Is internet connectivity reachable through the current network?"
```

Example:

```js
console.log(state.isInternetReachable);
```

---

# Why Is This Useful?

Consider:

```text
Phone
  ↓
Wi-Fi Router
  ↓
Internet X
```

The phone is connected to Wi-Fi.

So:

```text
isConnected = true
```

But internet access may not be available:

```text
isInternetReachable = false
```

---

# UI Example

```jsx
const getMessage = (state) => {
  if (!state.isConnected) {
    return "No network connection";
  }

  if (state.isInternetReachable === false) {
    return "Network connected, but internet is unavailable";
  }

  return "Internet available";
};
```

---

# Important Nullability Concept

When a value can be unavailable or unknown, do not assume it is always a simple boolean.

A safe check can distinguish:

```text
true
false
unknown / unavailable
```

For example:

```js
if (state.isInternetReachable === true) {
  console.log("Internet reachable");
} else if (state.isInternetReachable === false) {
  console.log("Internet not reachable");
} else {
  console.log("Internet reachability is unknown");
}
```

This is more robust than blindly treating every non-true value as offline.

```text
  ↓

  ↓

  ↓
Wait for connection
```

# Chapter 9 - `useNetworkState()`

# What is the Hook?

`useNetworkState()` is useful when a React component needs network state and should react to changes.

Think:

```text

    ↓
Give me one snapshot.

useNetworkState()
    ↓
Give me state that updates as network conditions change.
```

---

# Basic Example

```jsx

import * as Network from "expo-network";

export default function App() {
  const state = Network.useNetworkState();

  return (
    <View
      style={{
        flex: 1,
        justifyContent: "center",
        alignItems: "center",
      }}
    >
      <Text>
        Connected: {String(state.isConnected)}
      </Text>

      <Text>
        Internet: {String(state.isInternetReachable)}
      </Text>

      <Text>
        Type: {state.type}
      </Text>
    </View>
  );
}
```

# What Happens?

```text
Component renders
      ↓
useNetworkState()
      ↓
Network state available
      ↓
Network changes
      ↓
Hook state updates
      ↓
Component renders again
```

# Real-Life Example

Imagine an application with an offline banner.

```text
|        App Content            |
|                              |
--------------------------------
```

When the device reconnects:


# Chapter 11 - Network State Listener

---

# What is a Listener?

A listener lets your code react when the network state changes.

Function:

```js
Network.addNetworkStateListener()
```

Conceptually:

```text
Start listening
      ↓
Network changes
      ↓
Callback runs
      ↓
Your code reacts
```

---

# Basic Example

```jsx
import { useEffect } from "react";
import * as Network from "expo-network";

export default function App() {
  useEffect(() => {
    const subscription =
      Network.addNetworkStateListener((state) => {
        console.log("Network changed");
        console.log(state);
      });

    return () => {
      subscription.remove();
    };
  }, []);

  return null;
}
```

---

# Why `remove()`?

This is critical.

When a component is no longer active, the listener should be removed.

```js
subscription.remove();
```

Without cleanup, long-lived listeners can produce:

```text
duplicate callbacks
unexpected updates
unnecessary work
memory/lifecycle problems
```

---

# Listener Lifecycle

```text
Component Mounts
      ↓
Listener Added
      ↓
Network Changes
      ↓
Callback Runs
      ↓
Component Unmounts
      ↓
Listener Removed
```

---

# Common Mistake

Bad pattern:

```js
useEffect(() => {
  Network.addNetworkStateListener((state) => {
    console.log(state);
  });
}, []);
```

Better:

```js
useEffect(() => {
  const subscription =
    Network.addNetworkStateListener((state) => {
      console.log(state);
    });

  return () => {
    subscription.remove();
  };
}, []);
```

```js
  console.log(state);

```

You can read:


# Destructuring Example

Instead of:

```js

  console.log(state.isConnected);
```

you can write:

# Chapter 15 - Complete Network Status Dashboard

Now we combine the main APIs.

The screen should show:

```text
Network Status
-------------------------
Connected: Yes
Internet: Yes
Type: WIFI
IP: 192.168.1.24
Airplane Mode: OFF
-------------------------
[Refresh]
```

---

# Full Example

```jsx
import { useState } from "react";
import {
  Button,
  Text,
  View,
} from "react-native";
import * as Network from "expo-network";

export default function App() {
  const [network, setNetwork] = useState(null);
  const [ip, setIp] = useState(null);
  const [airplaneMode, setAirplaneMode] =
    useState(null);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState(null);

  const refresh = async () => {
    try {
      setLoading(true);
      setError(null);

      const networkState =
        await Network.getNetworkStateAsync();

      const ipAddress =
        await Network.getIpAddressAsync();

      const airplane =
        await Network.isAirplaneModeEnabledAsync();

      setNetwork(networkState);
      setIp(ipAddress);
      setAirplaneMode(airplane);
    } catch (err) {
      console.log(err);
      setError("Unable to read network information.");
    } finally {
      setLoading(false);
    }
  };

  return (
    <View
      style={{
        flex: 1,
        justifyContent: "center",
        alignItems: "center",
        gap: 10,
        padding: 20,
      }}
    >
      <Text>
        Network Status Dashboard
      </Text>

      <Button
        title={
          loading
            ? "Refreshing..."
            : "Refresh"
        }
        onPress={refresh}
        disabled={loading}
      />

      {error && (
        <Text>{error}</Text>
      )}

      {network && (
        <>
          <Text>
            Connected:
            {" "}
            {String(network.isConnected)}
          </Text>

          <Text>
            Internet:
            {" "}
            {String(network.isInternetReachable)}
          </Text>

          <Text>
            Type: {network.type}
          </Text>
        </>
      )}

      {ip && (
        <Text>
          IPv4: {ip}
        </Text>
      )}

      {airplaneMode !== null && (
        <Text>
          Airplane Mode:
          {" "}
          {airplaneMode ? "ON" : "OFF"}
        </Text>
      )}
    </View>
  );
}
```

# Chapter 17 - Network-Aware API Calls

A network check can improve UX before an expensive operation.

Example:

```js
const state =
  await Network.getNetworkStateAsync();

if (state.isConnected === false) {
  console.log("No network.");
  return;
}

const response =
  await fetch("https://example.com/api/products");
```

---

# But Is This a Guarantee?

No.

The network can disappear immediately after the check.

```text
Check network
     ↓
Connected
     ↓
Network disappears
     ↓
fetch()
     ↓
Request fails
```

Therefore you still need proper request error handling.

---

# Correct Production Pattern

```js
const state =
  await Network.getNetworkStateAsync();

if (state.isConnected === false) {
  showOfflineMessage();
  return;
}

try {
  const response =
    await fetch(url);

  if (!response.ok) {
    throw new Error(
      `HTTP ${response.status}`
    );
  }

  const data = await response.json();

  return data;
} catch (error) {
  showRequestError(error);
}
```

# Chapter 24 - Error Codes & Troubleshooting

The official Expo documentation includes network-related error codes. These are important when debugging.

---

# `ERR_NETWORK_IP_ADDRESS`

This error is associated with inability to obtain an expected IP-address value under documented native conditions.

Treat it as an API/native-network-information problem, not as proof that your backend is down.

---

# `ERR_NETWORK_UNDEFINED_INTERFACE`

This is associated with an undefined interface name in the documented low-level MAC-address path.

If your installed Expo SDK does not expose that API, do not invent or call it.

The error-code documentation may contain references to APIs that differ across documentation/version surfaces.

---

# `ERR_NETWORK_SOCKET_EXCEPTION`

This indicates a socket-level problem in the documented low-level network-information path.

Again, this is different from:

```text
HTTP 500
```

because an HTTP 500 means a server successfully responded with a server error.

---

# `ERR_NETWORK_INVALID_PERMISSION_INTERNET`

This represents a network-information permission/configuration problem described by Expo's documentation.

Do not confuse this with:

```text
User denied location permission
```

or another unrelated runtime permission.

---

# `ERR_NETWORK_NO_ACCESS_NETWORKINFO`

This means the module could not access the required network information.

When debugging:

```text
1. Check platform.
2. Check SDK/package version.
3. Check native build.
4. Check permissions/configuration.
5. Reproduce on a physical device.
6. Inspect the actual error object.
```

---

# Chapter 25 - Error Handling Pattern

Do not write:

```js
const state =
  await Network.getNetworkStateAsync();
```

and assume it can never fail.

Use:

```js
try {
  const state =
    await Network.getNetworkStateAsync();

  console.log(state);
} catch (error) {
  console.log(
    "Unable to read network state:",
    error
  );
}
```

# Mistake 1 - Treating `isConnected` as API Success

Wrong mental model:

```text
isConnected === true
        ↓
API must work
```

Correct:

```text
isConnected === true
        ↓
A network connection is detected
        ↓
API may still fail
```

---

# Mistake 2 - Treating Wi-Fi as Internet

Wrong:

```text
type === WIFI
        ↓
Internet definitely works
```

Correct:

```text
type === WIFI
        ↓
Wi-Fi is the reported network type
```

Use reachability and actual request handling as separate signals.

---

# Mistake 3 - Treating `UNKNOWN` as `NONE`

Wrong:

```js
if (
  state.type === Network.NetworkStateType.UNKNOWN

  // definitely offline
}
```

Correct:

```text
UNKNOWN
=
Type cannot be determined

NONE
=
No active network
```

# Mistake 4 - Forgetting Listener Cleanup

Wrong:

```js
useEffect(() => {
  Network.addNetworkStateListener(callback);
}, []);
```

Better:

```js
useEffect(() => {
  const subscription =
    Network.addNetworkStateListener(callback);

    subscription.remove();
```

If a screen needs to react to changes, this:

Prefer:

This is incorrect:

An IP address and internet reachability answer different questions.

# Chapter 32 - Interview Questions

---

# Beginner Question 1

### What is `expo-network`?

Answer:

`expo-network` is an Expo SDK module for reading information about the device's network state, such as connection state, reachability, network type, IP information, and network changes.

---

# Beginner Question 2

### Does `expo-network` make API requests?

Answer:

No.

HTTP requests are made using mechanisms such as:

```js
fetch()
```

or an HTTP client.

`expo-network` provides network information.

---

# Beginner Question 3

### What is `isConnected`?

Answer:

It indicates whether an active network connection exists.

---

# Beginner Question 4

### What is `isInternetReachable`?

Answer:

It indicates whether internet connectivity is reachable through the current network, subject to platform behavior.

---

# Beginner Question 5

### What does `type` represent?

Answer:

It represents the current network type, such as Wi-Fi, cellular, Ethernet, VPN, none, or unknown.

---

# Intermediate Question 6

### What is the difference between `useNetworkState()` and `getNetworkStateAsync()`?

Answer:

`getNetworkStateAsync()` gives a current snapshot when called.

`useNetworkState()` is designed for React components that need network state updates as the network changes.

---

# Intermediate Question 7

### Can `isConnected` be true while an API request fails?

Answer:

Yes.

The server may be unavailable, DNS may fail, the request may time out, authentication may fail, or the backend may return an HTTP error.

---

# Intermediate Question 8

### Why should listeners be removed?

Answer:

To prevent stale subscriptions, duplicate callbacks, unnecessary work, and lifecycle-related problems.

---

# Intermediate Question 9

### Is Wi-Fi the same as internet?

Answer:

No.

Wi-Fi indicates a network type. Internet reachability is a separate concept.

---

# Advanced Question 10

### Does a network check guarantee that the next request will succeed?

Answer:

No.

Network state can change between the check and the request.
