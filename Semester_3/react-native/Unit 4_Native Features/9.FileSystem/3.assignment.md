
# Assignment 2: Offline Notes Manager Pro

## Overview

Build an **Offline Notes Manager Pro** application using React Native and Expo's modern `expo-file-system` API.

The application must allow users to create, save, list, read, edit, rename, duplicate, search, and delete notes stored as `.txt` files in the application's document directory.

The app should behave like a practical offline notes tool: notes remain available after navigating away from the screen or restarting the application, provided the app's document data has not been removed.

This assignment combines file-system operations with React state management, form validation, list filtering, file metadata, and safe user workflows.

---

## Scenario

You are building an offline notes application for students. Users should be able to save class notes, reopen them later, edit existing notes, and organize their notes without requiring an internet connection.

Suggested storage structure:

```text
Document Directory/
└── notes/
    ├── note-<unique-id>.txt
    ├── note-<unique-id>.txt
    └── note-<unique-id>.txt
```

The exact filename format is up to the student. Filenames must be safe and unique.

---

# Required Features

## 1. Initialize the Notes Directory

Create a `notes` directory inside `Paths.document`.

### Requirements

- Ensure the directory exists before listing or saving notes.
- Create it if it does not exist.
- Use suitable creation options so initialization can safely run more than once.
- Keep the directory reference in a reusable place rather than rebuilding it throughout the UI.
- Display the notes directory URI in an About or Storage section.

**Important:** Constructing a `Directory` or `File` reference does not, by itself, guarantee that the physical directory or file exists.

---

## 2. Create a Note

Provide a form with:

- Note title input.
- Multiline note content input.
- **Save Note** button.
- **Clear Form** button.

### Validation

- Title must not be empty.
- Content must not be empty after trimming whitespace.
- Trim leading and trailing whitespace from the title.
- Reject titles containing unsafe path separators or invalid filename characters.
- Generate a safe, unique filename using an ID or timestamp-based approach.
- Save notes as `.txt` files.
- Avoid overwriting an existing note accidentally.

### After Successful Creation

- Show a success message.
- Clear the create form.
- Refresh the saved notes list.
- Optionally open the newly created note in the editor.

### Error Handling

If the save operation fails:

- Keep the user's input available.
- Display a friendly error message.
- Do not crash the application.

---

## 3. List Saved Notes

Read the contents of the notes directory and display saved notes.

For each note, show:

- Friendly title or filename.
- File size in a readable format.
- Last modified date, if available.
- An **Open** action.
- A **Rename** action.
- A **Duplicate** action.
- A **Delete** action.

### Requirements

- Include a Refresh button.
- Display the number of saved notes.
- Show an empty state when no notes exist.
- Show a loading state while reading the directory.
- Handle missing or unreadable files gracefully.

If the implementation stores only the title inside the text file, students may use a simple filename-to-title display or derive a friendly title from the filename. The chosen approach should be explained in the README.

---

## 4. Open and Read a Note

When a user selects a note:

- Read the latest text content from the physical file.
- Display the selected note's title and content in the editor.
- Display its filename and URI.
- Show file size and modification time where supported.
- Indicate which note is currently selected.

### Reload Content

Add a **Reload** action that reads the file again from disk and updates the editor.

### Missing File Handling

If the selected file no longer exists or cannot be read:

- Display a friendly message.
- Do not leave the UI pretending that stale content is current.
- Provide a way to refresh the list or clear the selection.

---

## 5. Update a Note

Allow users to edit the selected note's title and content.

### Requirements

- Display the selected note's current title and content.
- Allow content editing.
- Validate that the title and content are not empty.
- Save changes to the appropriate file.
- Show a success or error message.
- Refresh the list and metadata after a successful update.
- Keep the selected note synchronized with the updated file.

### Unsaved Changes

If the user edits the note and then selects another note or clears the editor, warn them that unsaved changes may be lost.

Students may implement a simple confirmation dialog or a clear discard-changes workflow.

---

## 6. Delete a Note

Allow users to delete a saved note.

### Requirements

- Provide a Delete action in the list and/or editor.
- Ask for confirmation before deletion.
- Delete only the selected note.
- Refresh the notes list after successful deletion.
- Clear the editor if the deleted note was open.
- Display a success or error message.

If deletion fails, keep the note visible where appropriate and allow the user to retry.

---

## 7. Search Notes

Add a search input that allows users to search notes.

### Requirements

- Search by note title or filename.
- Search by note content, if the implementation loads or indexes content for searching.
- Update visible results as the query changes.
- Display the number of matching notes.
- Show a helpful empty state when no results match.
- Add a Clear Search action.

Searching must not change the actual file contents.

**Note:** Searching note content may require reading file contents. Avoid repeatedly reading every file on every keystroke if a more efficient in-memory approach is practical.

---

## 8. Sort Notes

Provide sorting options:

- Title or filename: A–Z.
- Title or filename: Z–A.
- Recently modified, if modification metadata is available.
- Oldest modified, if modification metadata is available.

### Requirements

- Sorting should update the visible list only.
- Do not rename or rewrite files just to change their display order.
- Handle missing modification dates with a consistent fallback.

---

## 9. Rename a Note

Allow users to rename an existing note.

### Requirements

- Provide a Rename action.
- Pre-fill the rename input with the current title or filename.
- Reject an empty new name.
- Validate unsafe filename characters.
- Preserve the `.txt` extension.
- Prevent accidental collisions with another existing file.
- Keep the note content unchanged.
- Refresh the list and selected-note details after a successful rename.

The application should clearly distinguish between the friendly title shown to the user and the physical filename if they are stored separately.

---

## 10. Duplicate a Note

Allow users to create a copy of an existing note.

### Requirements

- Provide a Duplicate action.
- Create a new file with a unique filename.
- Copy the source note's content.
- Do not overwrite the original or another existing note.
- Refresh the list after duplication.
- Display a success or error message.

Suggested display name:

```text
Biology Notes (Copy)
```

Students may choose another naming convention, as long as duplicates remain unique and safe.

---

## 11. File Metadata and Storage Information

Add a small **Storage Details** section showing:

- Notes directory URI.
- Total number of notes.
- Combined size of notes, where file sizes are available.
- Selected note's URI.
- Selected note's size.
- Selected note's last-modified date, if available.

Use documented metadata properties supported by the installed Expo SDK.

If a value is unavailable, display `Not available` rather than crashing or inventing a value.

---

## 12. Refresh and State Synchronization

Provide a Refresh button that reloads the notes directory.

Refresh after successful:

- Create.
- Update, if displayed metadata may change.
- Rename.
- Duplicate.
- Delete.

### Requirements

- Show a loading or refreshing indicator.
- Avoid conflicting duplicate refresh operations.
- Update the list from the actual directory contents.
- Keep the selected note valid after refresh.
- If the selected file is no longer present, clear the selection or display a missing-file state.

# Bonus Challenges

## Bonus 1: Pin Important Notes

Allow users to pin and unpin notes.

Persist pin state either in a suitable local metadata file or another documented approach. Explain how the pin state remains associated with the correct note.

## Bonus 2: Note Categories

Allow users to assign categories such as:

- College
- Personal
- Work
- Other

Add category filtering. Students should explain how category information is stored and kept synchronized with notes.

## Bonus 3: Word and Character Count

Display:

- Character count.
- Word count.
- Optional reading-time estimate.

Update the counts as the user types.

## Bonus 4: Export a Note

Use an appropriate sharing or file-sharing API covered in the course to let users share or export a note.

## Bonus 5: Recently Opened Notes

Track recently opened notes during the current app session and display a small recent-notes section.

## Bonus 6: Recover from a Missing File

If a note disappears while selected, provide a clear recovery flow that refreshes the directory and clears or updates the selection safely.
