# Part 1 — Understanding Splash Screens

## 1. What Is a Splash Screen?

A **splash screen**, also called a *launch screen*, is the initial visual screen displayed when a user opens a mobile application.

When a user taps an application's icon, the operating system begins launching the application. During this process, the native splash screen provides the first visual experience before the application's main interface becomes available.

A splash screen commonly contains:

- **Application logo:** Identifies the application.
- **Background color:** Matches the application's branding.
- **Brand artwork:** Optional graphics or illustrations.
- **Simple layout:** Keeps the initial screen clean and recognizable.

### Example

Imagine that you are developing an educational application called **LearnHub**.

When a user opens LearnHub:

1. The user taps the application icon.
2. The operating system starts launching the application.
3. The native splash screen displays the LearnHub logo.
4. React Native starts preparing the application interface.
5. The splash screen disappears when the application is ready to display its initial interface.

**Important:** A native splash screen is not an ordinary React Native screen. It can appear before JavaScript has started rendering React components.

## 2. Why Do We Need a Splash Screen?

A splash screen provides a consistent visual experience during the initial application launch.

### 1. Brand Identity

The application logo and background color help users recognize the application.

For example, a banking application may display its logo on a white background, while a gaming application may use a dark background.

### 2. Smooth Startup Experience

Applications need time to initialize their native components and prepare their interface.

The native splash screen provides a visual transition while this process occurs.

However, **a splash screen does not make an application launch faster**. It improves the visual experience during startup.

### 3. Preparation of Essential Resources

Some applications need to prepare essential resources before displaying their first screen.

Examples include:

- Loading custom fonts.
- Reading local configuration.
- Restoring an authentication session.
- Initializing required application services.

Expo allows developers to keep the splash screen visible while these tasks are completed.

### 4. Consistent Appearance

A properly configured splash screen helps maintain a consistent appearance across supported devices.

However, its exact rendering can differ between operating systems and device configurations.

### 5. Better Perceived Experience

A simple, recognizable splash screen can make an application feel more polished.

The objective is to provide a clean transition rather than keep users waiting unnecessarily.

**Remember:** The splash screen does not automatically fetch API data, load fonts, or restore authentication. Developers must implement these operations separately when required.

## 3. Splash Screen vs. Loading Screen

Although native splash screens and loading screens may look similar, they serve different purposes.

### Native Splash Screen

A native splash screen is displayed during the initial application launch.

It is configured through native application resources, which Expo can generate using project configuration.

It can appear before JavaScript is ready to render React Native components.

### React Native Loading Screen

A loading screen is an interface created using React Native components.

It is useful when the application needs to perform an operation such as fetching products, loading a dashboard, or submitting a request.

### Example: Loading Screen

```jsx
import {
  View,
  Text,
  ActivityIndicator,
} from "react-native";

export default function LoadingScreen() {
  return (
    <View
      style={{
        flex: 1,
        justifyContent: "center",
        alignItems: "center",
      }}
    >
      <ActivityIndicator
        size="large"
        color="#2563eb"
      />

      <Text style={{ marginTop: 12 }}>
        Loading your dashboard...
      </Text>
    </View>
  );
}
```

### Understanding the Code

- `View` provides the container.
- `ActivityIndicator` displays a loading spinner.
- `Text` displays a message.
- `justifyContent: "center"` centers the content vertically.
- `alignItems: "center"` centers the content horizontally.

### Comparison Table

| Native Splash Screen | React Native Loading Screen |
|---|---|
| Appears during native application launch. | Appears when React Native renders a loading interface. |
| Can appear before JavaScript is ready. | Requires React Native to render its components. |
| Configured through native resources and Expo configuration. | Built using components such as `View` and `ActivityIndicator`. |
| Handles the initial launch experience. | Handles operations that continue after the interface starts. |
| Commonly displays a logo and background. | Can display progress indicators, messages, and other UI. |

**Remember:** The splash screen handles the initial launch, while a loading screen handles operations within the running application.

## 4. How Does a Splash Screen Work?

The basic application startup process looks like this:

```text
User opens the application
          |
          v
Operating system launches the app
          |
          v
Native splash screen appears
          |
          v
React Native application starts
          |
          v
Essential resources load, if required
          |
          v
Splash screen disappears
          |
          v
Application interface becomes visible
```

Let's understand each stage.

### Stage 1 — Application Launch

The user taps the application icon, and the operating system begins launching the application.

### Stage 2 — Native Splash Screen

The operating system displays the configured splash screen while the application starts.

### Stage 3 — React Native Initialization

The JavaScript runtime starts preparing the application interface.

If the project uses Expo Router, its root layout and route hierarchy are prepared during this process.

### Stage 4 — Essential Initialization

The application may need to load fonts, read local settings, or restore an authentication session.

Developers can use the Splash Screen API to coordinate these tasks with splash screen visibility.

### Stage 5 — Splash Screen Hiding

Once the initial interface is ready, the splash screen is hidden.

### Stage 6 — Application Interface

The user sees the application's first React Native screen.

This might be a login screen, home screen, dashboard, or onboarding screen.

Additional operations can continue using normal loading indicators after the first interface appears.

## 5. What Is `expo-splash-screen`?

`expo-splash-screen` is an Expo library that allows developers to configure the native splash screen and control its visibility.

It provides two main capabilities.

### 1. Configure the Appearance

You can configure:

- Background color.
- Splash screen image.
- Image width.
- Image resizing behavior.
- Dark appearance options.
- Supported platform-specific settings.

These settings are generally applied when the native application is built.

### 2. Control Visibility

The library provides methods for controlling when the splash screen disappears.

```jsx
import * as SplashScreen from "expo-splash-screen";

SplashScreen.preventAutoHideAsync().catch(
  console.warn
);
```

When the application is ready:

```jsx
SplashScreen.hide();
```

The first method requests manual control over splash screen visibility. The second hides the splash screen.

## 6. Automatic vs. Manual Control

### Automatic Control

With automatic behavior, Expo handles the normal splash screen visibility lifecycle.

This is suitable when the application does not need custom initialization logic before displaying its first screen.

### Manual Control

With manual control, the developer requests that the splash screen remain visible and hides it when the application is ready.

```text
Application opens
       |
       v
preventAutoHideAsync()
       |
       v
Initialize essential resources
       |
       v
Check application readiness
       |
       v
hide()
       |
       v
Display application interface
```

Manual control is useful when the initial interface depends on essential resources, such as custom fonts.

However, it requires proper error handling to avoid leaving the splash screen visible indefinitely.

## 7. When Should You Use Manual Control?

Manual control is useful when:

- A custom font must load before the first screen appears.
- Essential local configuration must be read.
- Authentication must be restored before selecting the initial route.
- Required application initialization must finish before rendering the interface.

Not every operation should block startup.

For example, fetching an entire product catalog or loading optional recommendations can generally happen after the first screen appears.

**Best practice:** Keep startup work limited to what is genuinely required for the initial interface.

# Part 2 — Installation and Project Setup

## 1. Install the Package

Open your terminal in the root directory of your Expo project and run:

```bash
npx expo install expo-splash-screen
```

### Understand the Command

- `npx` executes a package command without requiring a global installation of the Expo CLI.
- `expo` runs the Expo CLI.
- `install` installs a package using a version compatible with your Expo SDK.
- `expo-splash-screen` is the package being installed.

Using `npx expo install` helps select a compatible version of an Expo library.

### What Happens After Installation?

1. The package is added to your project dependencies if needed.
2. Your `package.json` records the dependency.
3. Your package manager updates the lockfile.
4. You can import the library into your JavaScript files.

```jsx
import * as SplashScreen from "expo-splash-screen";
```

### What If It Is Already Installed?

Many Expo templates already include `expo-splash-screen`.

Check your `package.json` for an entry similar to:

```json
{
  "dependencies": {
    "expo-splash-screen": "..."
  }
}
```

The version depends on your Expo SDK.

**Important:** Do not copy an arbitrary package version from an example. Use Expo's installation command.

## 2. Understand the Project Structure

For an Expo Router application, your project might look like this:

```text
my-app/
├── app/
│   ├── _layout.js
│   └── index.js
├── assets/
│   ├── images/
│   │   ├── splash-icon.png
│   │   └── splash-icon-dark.png
│   └── fonts/
│       └── Inter-Regular.ttf
├── app.json
├── package.json
└── package-lock.json
```

Your project may contain additional files and folders.

### What Is `app/_layout.js`?

In Expo Router, `_layout.js` defines how routes are organized and displayed.

Example:

```jsx
import { Stack } from "expo-router";

export default function RootLayout() {
  return <Stack />;
}
```

Here, `Stack` provides stack-based navigation.

Later, we will use the root layout to coordinate splash screen visibility with essential startup tasks.

**Important:** The root layout does not configure native splash screen artwork. The artwork is configured through Expo project configuration.

### What Is `app.json`?

The `app.json` file contains configuration settings used by Expo to prepare your application.

It can specify application details, platform settings, assets, and config plugins.

Example:

```json
{
  "expo": {
    "name": "my-app",
    "slug": "my-app",
    "plugins": []
  }
}
```

We will configure the splash screen plugin in Part 3.

### What Is the `assets/images/` Folder?

This folder stores images used by your application.

For example:

```text
assets/
└── images/
    ├── splash-icon.png
    └── splash-icon-dark.png
```

The filenames are examples. You can use different names as long as your configuration points to the correct files.

### What If Your Project Uses `src/app/`?

Some Expo Router projects use this structure:

```text
my-app/
├── src/
│   └── app/
│       ├── _layout.js
│       └── index.js
├── assets/
│   └── images/
│       └── splash-icon.png
└── app.json
```

This is also a valid project organization.

The image path in `app.json` is relative to the project configuration file, not relative to `_layout.js`.

For example:

```json
"image": "./assets/images/splash-icon.png"
```

## 3. Start the Development Server

Run the following command from your project's root directory:

```bash
npx expo start
```

This starts the Expo development server.

Depending on your setup, you can run the application in:

- Expo Go.
- An Android emulator.
- An iOS simulator where supported.
- A compatible development build.

### Does This Show the Final Splash Screen?

Not necessarily.

Expo Go has its own native application shell and does not reliably reproduce your application's configured splash screen.

Development builds also do not fully reproduce the standalone splash screen experience in the same way as a release build.

**For accurate testing, create and install a release build on your target device or simulator.**

# Part 3 — Configure and Customize the Splash Screen

## 1. Configure `app.json`

Expo provides a config plugin called `expo-splash-screen`.

It allows you to customize the native splash screen through your Expo project configuration.

Open `app.json` and add the plugin under `expo.plugins`.

```json
{
  "expo": {
    "plugins": [
      [
        "expo-splash-screen",
        {
          "backgroundColor": "#2563eb",
          "image": "./assets/images/splash-icon.png",
          "imageWidth": 200,
          "resizeMode": "contain"
        }
      ]
    ]
  }
}
```

### Understand the Configuration

**`plugins`**

The `plugins` array tells Expo which configuration plugins should be applied when preparing the native application.

**`backgroundColor`**

Defines the splash screen background color.

**`image`**

Specifies the splash screen artwork file.

**`imageWidth`**

Configures the image width.

**`resizeMode`**

Determines how the image is scaled.

### Preserve Existing Plugins

If your project already contains other plugins, add `expo-splash-screen` to the existing array.

Do not remove plugins required by other libraries.

For example:

```json
{
  "expo": {
    "plugins": [
      "expo-router",
      [
        "expo-splash-screen",
        {
          "backgroundColor": "#2563eb",
          "image": "./assets/images/splash-icon.png",
          "imageWidth": 200,
          "resizeMode": "contain"
        }
      ]
    ]
  }
}
```

This is an illustrative configuration. Keep the plugins that your actual project requires.

### Important Properties

| Property | Purpose |
|---|---|
| `backgroundColor` | Defines the background color. |
| `image` | Specifies the splash screen image. |
| `imageWidth` | Configures the image width. |
| `resizeMode` | Determines how the image is scaled. |
| `dark` | Configures a dark appearance. |
| `android` | Allows Android-specific overrides. |
| `ios` | Allows iOS-specific overrides. |

**Important:** Native configuration changes generally require a new native build.

## 2. Customize the Background Color

The `backgroundColor` property defines the background behind the splash screen image.

Example:

```json
"backgroundColor": "#ffffff"
```

This specifies a white background.

```json
"backgroundColor": "#000000"
```

This specifies a black background.

```json
"backgroundColor": "#2563eb"
```

This specifies a blue background.

### Understand Hexadecimal Colors

Hexadecimal colors are commonly written in the format `#RRGGBB`.

- `RR` represents red.
- `GG` represents green.
- `BB` represents blue.

Examples:

```text
#000000 → Black
#ffffff → White
#ff0000 → Red
#00ff00 → Green
#0000ff → Blue
```

### Best Practice

Choose a background color that provides enough contrast with the logo.

For example, a white logo may be difficult to see against a white background.

## 3. Configure the Splash Screen Image

The `image` property specifies the artwork displayed on the splash screen.

```json
"image": "./assets/images/splash-icon.png"
```

Consider this structure:

```text
my-app/
├── assets/
│   └── images/
│       └── splash-icon.png
├── app.json
└── package.json
```

Because `app.json` is located in the project root, the relative image path begins from that location.

### Image Preparation Tips

- Use PNG artwork for the configured image.
- Start with a sufficiently large source image, such as a 1024 × 1024 pixel square logo.
- Keep important artwork centered.
- Leave transparent space around the logo when appropriate.
- Ensure that the logo contrasts with the background.
- Avoid unnecessary text and overly detailed illustrations.

A square image is a useful starting point for a logo, but it is not a strict requirement for every design.

### What If the Image Path Is Incorrect?

Suppose the actual file is:

```text
assets/images/splash-icon.png
```

But the configuration contains:

```json
"image": "./assets/images/logo.png"
```

The configured path does not match the actual filename.

Verify the filename, extension, and directory.

**Remember:** The filename is your choice. The configured path must match the actual asset.

## 4. Control the Image Width

The `imageWidth` property controls the configured width of the splash screen image.

```json
"imageWidth": 100
```

This configures a relatively small width.

```json
"imageWidth": 200
```

This configures a larger width.

```json
"imageWidth": 250
```

This configures an even larger width.

### How Does Image Width Affect the Design?

If the logo appears too small, increasing `imageWidth` can make it more prominent.

If the logo dominates the screen, reducing `imageWidth` can create a cleaner layout.

The displayed height depends on the image's aspect ratio.

### Understand the Units

The configured width uses layout units rather than necessarily representing physical screen pixels.

A value of `200` does not mean the image always occupies exactly 200 physical pixels on every device.

Screen density and platform rendering affect the relationship between layout units and physical pixels.

**Best practice:** Start with a moderate width and verify the result in a native release build.

## 5. Understand `resizeMode`

The `resizeMode` property determines how the splash screen image is scaled.

### Option 1 — `contain`

```json
"resizeMode": "contain"
```

The complete image remains visible without cropping.

The image preserves its aspect ratio, so empty space may remain around it.

**Best suited for:** Logos and brand marks that must remain fully visible.

### Option 2 — `cover`

```json
"resizeMode": "cover"
```

The image is scaled to cover the available area while preserving its aspect ratio.

Some parts of the image may be cropped.

**Best suited for:** Artwork designed to fill an area where cropping is acceptable.

### Option 3 — `native`

```json
"resizeMode": "native"
```

This option uses native image resizing behavior. The resulting appearance depends on the platform and native resources.

Use it when native sizing behavior matches your intended design.

### Comparison Table

| Value | Behavior | Suitable Use |
|---|---|---|
| `contain` | Displays the complete image without cropping. | Logos and brand marks. |
| `cover` | Fills the available area; cropping may occur. | Artwork intended to fill an area. |
| `native` | Uses native image resizing behavior. | Designs requiring native sizing behavior. |

For most logo-based splash screens, `contain` is a good starting point.

## 6. Configure Dark Mode

Some applications use different backgrounds and logos for light and dark appearances.

The `dark` option lets you define an alternative splash screen configuration.

```json
{
  "expo": {
    "plugins": [
      [
        "expo-splash-screen",
        {
          "backgroundColor": "#ffffff",
          "image": "./assets/images/splash-icon.png",
          "imageWidth": 200,
          "resizeMode": "contain",
          "dark": {
            "backgroundColor": "#000000",
            "image": "./assets/images/splash-icon-dark.png"
          }
        }
      ]
    ]
  }
}
```

### Understand the Configuration

In the regular configuration:

- The background is white.
- The regular logo is displayed.

In the dark configuration:

- The background is black.
- The dark logo is displayed.

Example asset structure:

```text
assets/
└── images/
    ├── splash-icon.png
    └── splash-icon-dark.png
```

Make sure both files exist and are suitable for their respective backgrounds.

**Important:** Dark appearance behavior depends on platform support and the native configuration. Test both appearances in a release build.

## 7. Configure Platform-Specific Appearance

Sometimes Android and iOS need different splash screen artwork or backgrounds.

The config plugin supports platform-specific overrides.

For example, the configuration can be organized like this:

```json

      [

          "resizeMode": "contain",
          "android": {
            "backgroundColor": "#2563eb",
            "image": "./assets/images/splash-icon-android.png"

          "ios": {
            "backgroundColor": "#ffffff",
            "image": "./assets/images/splash-icon-ios.png"

        }
```

### Understand the Example

- The general configuration defines the default appearance.
- The Android override specifies Android-specific values.
- The iOS override specifies iOS-specific values.

The example illustrates the configuration structure. Check the current Expo config plugin reference for the supported properties of your installed SDK before using additional platform-specific options.

**Best practice:** Use platform overrides only when the design genuinely needs to differ between platforms.

# Part 4 — Understand the Splash Screen API and Animation

## 1. Import the Library

Import the Splash Screen API into your JavaScript file.

```jsx
import * as SplashScreen from "expo-splash-screen";
```

### Understand the Import

- `import` allows us to use functionality exported by another module.
- `* as SplashScreen` imports the module's exported members under the `SplashScreen` namespace.
- `"expo-splash-screen"` identifies the Expo package.

You can now access the methods through `SplashScreen`.

```jsx
SplashScreen.preventAutoHideAsync();
```

```jsx
SplashScreen.hide();
```

```jsx
SplashScreen.setOptions({
  duration: 1000,
  fade: true,
});
```

You do not need to use every method in every application.

## 2. Understand the Important Methods

| Method | Purpose | Return Value |
|---|---|---|
| `preventAutoHideAsync()` | Requests manual control over visibility. | `Promise<boolean>` |
| `hide()` | Hides the native splash screen. | `void` |
| `hideAsync()` | Backward-compatible asynchronous hiding method. | `Promise<void>` |
| `setOptions()` | Configures the supported fade-out animation. | `void` |

### Which Methods Should You Use?

For a simple application, the default splash screen behavior may be sufficient.

For an application that needs manual control, the most important methods are:

- `preventAutoHideAsync()`
- `hide()`

`setOptions()` is optional.

`hideAsync()` is primarily useful for maintaining compatibility with older code.

## 3. Understand `preventAutoHideAsync()`

### What Does It Do?

The `preventAutoHideAsync()` method requests that the native splash screen remain visible rather than being hidden automatically.

This allows the developer to coordinate splash screen visibility with essential initialization tasks.

### Syntax

```jsx
SplashScreen.preventAutoHideAsync().catch(
  console.warn
);
```

The `.catch(console.warn)` part logs a warning if the promise rejects.

### Where Should We Call It?

Call the method at the module's top level, outside the React component.

Example:

```jsx
import { Stack } from "expo-router";
import * as SplashScreen from "expo-splash-screen";

SplashScreen.preventAutoHideAsync().catch(
  console.warn
);

export default function RootLayout() {
  return <Stack />;
}
```

The request is made when the module is evaluated, giving it an opportunity to run before the root component mounts.

### Why Not Call It Inside `useEffect()`?

Consider this example:

```jsx
useEffect(() => {
  SplashScreen.preventAutoHideAsync();
}, []);
```

An effect runs after React commits the component's initial render.

The request may therefore happen later than intended.

Calling the method at module scope is the recommended pattern when manual splash screen control is required.

### When Should We Use It?

Use manual control when essential resources must be prepared before the first interface appears.

Do not use it merely to keep a logo visible for an arbitrary duration.

**Remember:** This method controls visibility. It does not load fonts, fetch data, or initialize services.

## 4. Understand `hide()`

### What Does It Do?

The `hide()` method hides the native splash screen.

It is generally called when the application has prepared everything required to display its initial interface.

### Syntax

```jsx
SplashScreen.hide();
```

This is a synchronous method call. You do not need `await`.

### Example

```jsx
if (isReady) {
  SplashScreen.hide();
}
```

Here, `isReady` represents whether the required initialization has completed.

The condition prevents the splash screen from being hidden before the application is ready.

### Startup Flow

```text
Application starts
       |
       v
Essential resources load
       |
       v
isReady becomes true
       |
       v
SplashScreen.hide()
       |
       v
Application interface appears
```

### Important Considerations

- Hide the splash screen when the initial interface is ready.
- Avoid hiding it before essential initialization finishes.
- Handle initialization failures so the application does not remain stuck.
- If an animation is configured, the transition may continue according to the supported platform behavior.

**Remember:** `hide()` hides the native splash screen. It does not navigate to another route or render a React component.

## 5. Understand `hideAsync()`

### What Does It Do?

`hideAsync()` is a backward-compatible asynchronous method for hiding the splash screen.

Older examples and existing applications may use it.

### Syntax

```jsx
await SplashScreen.hideAsync();
```

Because it returns a promise, it can be used with `await` inside an asynchronous function.

### Example

```jsx
async function finishStartup() {
  // Assume initialization has completed.

  await SplashScreen.hideAsync();

  console.log("Splash screen hide request completed");
}
```

### `hide()` vs. `hideAsync()`

| `hide()` | `hideAsync()` |
|---|---|
| Synchronous method call. | Returns a promise. |
| Does not require `await`. | Can be used with `await`. |
| Preferred for straightforward new code. | Useful for backward compatibility. |

For new implementations, prefer `hide()` when you simply need to hide the splash screen.

## 6. Understand `setOptions()`

### What Does It Do?

The `setOptions()` method configures the supported splash screen fade-out animation.

It allows you to specify the animation duration and whether the fade effect is enabled.

### Syntax

```jsx
SplashScreen.setOptions({
  duration: 1000,
  fade: true,
});
```

This configures a fade-out duration of 1000 milliseconds, or one second.

### Understand the Options

| Option | Description |
|---|---|
| `duration` | Specifies the fade-out animation duration in milliseconds. |
| `fade` | Enables the built-in fade-out animation on iOS. |

### Option 1 — `duration`

```jsx
duration: 1000
```

This specifies a duration of one second.

For a shorter animation:

```jsx
duration: 300
```

For a longer animation:

```jsx
duration: 1500
```

These values configure the animation duration. They are not instructions to wait before starting the application.

### Option 2 — `fade`

```jsx
fade: true
```

This enables the built-in fade-out animation on iOS.

**Platform note:** Do not assume that setting `fade: true` produces the same animation on Android. The built-in fade option has platform-specific behavior.

## 7. Complete Fade Animation Example

**File:** `app/_layout.js`

```jsx
import { Stack } from "expo-router";
import * as SplashScreen from "expo-splash-screen";

SplashScreen.setOptions({
  duration: 1000,
  fade: true,
});

export default function RootLayout() {
  return <Stack />;
}
```

### How Does It Work?

1. The Splash Screen library is imported.
2. `setOptions()` configures the supported fade animation.
3. Expo handles the normal splash screen visibility lifecycle.
4. When the splash screen hides, the configured animation is used where supported.
5. The application interface becomes visible.

This example does not require `preventAutoHideAsync()` because it does not manually delay hiding the splash screen.

## 8. How Do the Methods Work Together?

Imagine that LearnHub needs to load a custom font before displaying its dashboard.

The startup process would be:

```text
Application opens
       |
       v
preventAutoHideAsync()
       |
       v
Load essential resources
       |
       v
Check whether resources are ready
       |
       v
hide()
       |
       v
Display the application interface
```

Each method has a specific responsibility.

- `preventAutoHideAsync()` requests that the splash screen remain visible.
- Resource-loading logic prepares the required resources.
- `hide()` hides the splash screen.
- `setOptions()` optionally configures the fade-out animation.

**Do we need all four methods?**

No. Many applications need only the default behavior. Manual control generally requires `preventAutoHideAsync()` and `hide()`, while the other methods serve different purposes.

# Part 5 — Control the Splash Screen Manually

## 1. When Is Manual Control Needed?

Imagine that LearnHub must load an essential local configuration before displaying its dashboard.

We want to keep the splash screen visible until initialization finishes.

```text
Application opens
       |
       v
Splash screen stays visible
       |
       v
Essential resources load
       |
       v
isReady becomes true
       |
       v
Splash screen hides
       |
       v
Application interface appears
```

We will use:

- `preventAutoHideAsync()`
- `useState()`
- `useEffect()`
- `hide()`

## 2. Complete Example

**File:** `app/_layout.js`

```jsx
import { Stack } from "expo-router";
import * as SplashScreen from "expo-splash-screen";
import { useEffect, useState } from "react";

// Request manual control before the root layout mounts.
SplashScreen.preventAutoHideAsync().catch(
  console.warn
);

export default function RootLayout() {
  const [isReady, setIsReady] = useState(false);

  useEffect(() => {
    async function prepareApp() {
      try {
        // Teaching example: simulate initialization.
        await new Promise((resolve) => {
          setTimeout(resolve, 2000);
        });
      } catch (error) {
        console.warn("Startup error:", error);
      } finally {
        setIsReady(true);
      }
    }

    prepareApp();
  }, []);

  useEffect(() => {
    if (isReady) {
      SplashScreen.hide();
    }
  }, [isReady]);

  if (!isReady) {
    return null;
  }

  return <Stack />;
}
```

## 3. Understand the Code

### Step 1 — Request Manual Control

```jsx
SplashScreen.preventAutoHideAsync().catch(
  console.warn
);
```

This requests that the native splash screen remain visible until the application hides it.

### Step 2 — Create a Readiness State

```jsx
const [isReady, setIsReady] = useState(false);
```

Initially, `isReady` is `false`, meaning initialization has not finished.

### Step 3 — Start Initialization

```jsx
useEffect(() => {
  async function prepareApp() {
    // Initialization work
  }

  prepareApp();
}, []);
```

The effect starts the asynchronous preparation process when the root layout mounts.

### Step 4 — Simulate an Asynchronous Operation

```jsx
await new Promise((resolve) => {
  setTimeout(resolve, 2000);
});
```

This waits approximately two seconds.

It is only a teaching example. It does not load actual resources.

### Step 5 — Update the Readiness State

```jsx
finally {
  setIsReady(true);
}
```

The `finally` block executes whether the simulated operation succeeds or fails.

### Step 6 — Hide the Splash Screen

```jsx
useEffect(() => {
  if (isReady) {
    SplashScreen.hide();
  }
}, [isReady]);
```

When `isReady` becomes `true`, the effect hides the splash screen.

### Step 7 — Render the Application

```jsx
if (!isReady) {
  return null;
}
```

This prevents the route navigator from rendering until initialization completes.

### Why Do We Need Both Methods?

| Method | Responsibility |
|---|---|
| `preventAutoHideAsync()` | Requests that the splash screen remain visible. |
| `hide()` | Hides the splash screen when the application is ready. |

**Production note:** Replace the simulated delay with actual initialization logic. Always decide what should happen if essential initialization fails.

## 4. Understand Error Handling

A production application should not remain stuck behind a splash screen indefinitely.

Consider these cases:

- A custom font fails to load.
- Local configuration cannot be read.
- An essential service fails to initialize.
- A network request times out.

The correct response depends on whether the resource is essential.

For an optional resource, the application might continue with a fallback.

For an essential resource, the application might display an error screen with a retry option.

The goal is to reach a deliberate application state rather than hide every error or block the interface forever.

## 1. Load Custom Fonts

### Step 2 — Prepare the Font File

```text
assets/

    └── Inter-Regular.ttf
```

### Step 3 — Load the Font

**File:** `app/_layout.js`

```jsx
import { Stack } from "expo-router";
import * as SplashScreen from "expo-splash-screen";
import { useEffect } from "react";
import { useFonts } from "expo-font";

SplashScreen.preventAutoHideAsync().catch(

export default function RootLayout() {

      SplashScreen.hide();

  }, [loaded, error]);

  }

  return <Stack />;
}
```

### Understand the Code

**Load the font**

```jsx

```

**Hide the splash screen**

## 2. Load Essential API Data

Sometimes an application needs essential configuration from an API before displaying its first screen.

The following example demonstrates the startup sequence.

```jsx
import { Stack } from "expo-router";
import * as SplashScreen from "expo-splash-screen";
import { useEffect, useState } from "react";

SplashScreen.preventAutoHideAsync().catch(
  console.warn
);

export default function RootLayout() {
  const [isReady, setIsReady] = useState(false);

  useEffect(() => {
    async function prepareApp() {
      try {
        const response = await fetch(
          "https://jsonplaceholder.typicode.com/posts/1"
        );

        if (!response.ok) {
          throw new Error(
            "Failed to load startup data"
          );
        }

        const data = await response.json();

        console.log("Startup data:", data);
      } catch (error) {
        console.warn(
          "Could not load startup data:",
          error
        );
      } finally {
        setIsReady(true);
      }
    }

    prepareApp();
  }, []);

  useEffect(() => {
    if (isReady) {
      SplashScreen.hide();
    }
  }, [isReady]);

  if (!isReady) {
    return null;
  }

  return <Stack />;
}
```

### Understand the Startup Sequence

1. Request manual control over splash screen visibility.
2. Fetch the sample API data.
3. Check whether the HTTP response was successful.
4. Parse the response as JSON.
5. Handle any errors.
6. Mark initialization as complete.
7. Hide the splash screen and render the navigator.

### Important Considerations

This example logs the response rather than storing it for the dashboard.

It also continues after a failed request. That is appropriate only when the data is optional or a fallback is acceptable.

For essential data, you may want to display an error screen or offer a retry action instead of continuing to the main interface.

### Should Every API Request Block the Splash Screen?

No.

Use manual splash screen control only when the data is genuinely required to display the initial interface.

For example:

| Operation | Should It Usually Block Startup? |
|---|---|
| Loading an essential local configuration | Possibly |
| Loading a required custom font | Yes, if the first screen depends on it |
| Restoring authentication needed to select the initial route | Possibly |
| Fetching an entire product catalog | Usually no |
| Loading optional recommendations | No |
| Fetching secondary dashboard statistics | Usually no |

**Best practice:** Display the initial interface promptly and load nonessential data afterward.
