# React Native – Notifications

This chapter is a structured, SDK-54-focused guide to **local notifications with `expo-notifications`** in React Native / Expo.

>  **Platform warning:** Expo gives you a common JavaScript API, but Android and iOS are not identical. Android uses **Notification Channels**; permission, presentation, trigger, and OS behavior can differ by platform. Read the platform notes before treating an example as cross-platform.

## Core Mental Model

```text
PERMISSION  →  Can the app notify?
CONTENT     →  What should the user see?
DATA        →  What context does the app need?
TRIGGER     →  When should it fire?
SCHEDULER   →  Create the scheduled request
ID          →  How do we manage that request later?
LISTENER    →  What does the app do when an event occurs?
RESPONSE    →  What happens when the user interacts?
CANCELLATION→  How does a reminder stop?
```

# Part 1 - Notification Fundamentals

Before writing notification code, understand what happens when a notification is created, scheduled, displayed, and interacted with.

The basic mental model is:

```text
Your React Native App
        ↓
expo-notifications
        ↓
Operating System
        ↓
Notification System
        ↓
User sees notification
```

Your React Native JavaScript code does not directly draw the notification banner. The operating system handles the notification UI.

For example:

```text
React Native App
      ↓
"Study reminder"
      ↓
expo-notifications
      ↓
Android / iOS notification system
      ↓
┌──────────────────────────────┐
│  Study Reminder              │
│ Time to study React Native!  │
└──────────────────────────────┘
```

---

## 1. What Is a Notification?

A notification is a message presented by the operating system to inform the user about something.

Example:

```text
┌──────────────────────────────────┐
│ WhatsApp                         │
│ Rajesh sent you a message        │
└──────────────────────────────────┘
```

Another example:

```text
┌──────────────────────────────────┐
│ Water Reminder                   │
│ Drink some water                 │
└──────────────────────────────────┘
```

A notification can contain information such as:

```text
Title
Body
Sound
Badge
Data
Actions
```

A simplified notification content object can look like:

```js
{
  title: 'Water Reminder',
  body: 'Drink some water',
}
```

---

## 2. Notification vs In-App UI

This is one of the first concepts to understand.

Normal React Native UI:

```jsx
<View>
  <Text>Hello</Text>
</View>
```

is rendered **inside your application**.

A notification is presented by the **operating system notification system**.

Therefore:

```text
React Native UI
      ↓
Inside App
```

while:

```text
Notification
      ↓
OS Notification System
      ↓
Outside / Above the App UI
```

For example, your application might currently display:

```text
┌─────────────────────────────┐
│       Your React Native App │
│                             │
│       Welcome!              │
│                             │
└─────────────────────────────┘
```

A notification can be presented separately by the operating system.

This is why notifications are different from simply showing another `<View>` or `<Alert>` inside the app.

---

## 3. Why Do Applications Use Notifications?

Users do not continuously keep every application open.

Imagine a reminder application.

Without notifications:

```text
User closes app
      ↓
App is no longer visible
      ↓
User may forget the task
```

With a scheduled notification:

```text
User closes app
      ↓
Notification scheduled
      ↓
Operating system waits
      ↓
Trigger time arrives
      ↓
Notification appears
```

Common notification use cases include:

- Reminders
- Alarms
- Chat messages
- Order updates
- Delivery updates
- Social interactions
- Calendar events
- Habit tracking
- Promotions
- Security alerts

## 5. Local Notifications

A **local notification** is created or scheduled locally by the application/device.

Example:

```text
User
  ↓
Sets reminder for 8:00 AM
  ↓
App schedules notification
  ↓
Device manages the scheduled notification
  ↓
8:00 AM
  ↓
Notification appears
```

A backend server is not required for the basic reminder scenario.

Typical use cases:

- Water reminders
- Study reminders
- Habit trackers
- To-do reminders
- Alarm applications
- Daily tips
- Local calendar-style reminders

Example content:

```js
{
  title: 'Study Reminder',
  body: 'Time to continue your React Native course.',
}
```

The important idea is:

```text
App
 ↓
Create/schedule
 ↓
Device
 ↓
Notification
```

---

## 6. Push Notifications

A **push notification** normally originates from a remote system/server.

The basic architecture is:

```text
Your Backend
     ↓
Push Service
     ↓
Device
     ↓
Operating System
     ↓
Notification
```

For example, consider a shopping application:

```text
Order placed
     ↓
Backend
     ↓
Order shipped
     ↓
Push notification
     ↓
User's device
```

The user might receive:

```text
Order Update

Your order has been shipped.
```

Push notifications are useful for:

- Chat messages
- Order status
- Delivery status
- Social notifications
- Account alerts
- Server-generated events
- Time-sensitive remote information

---

## 7. Local vs Push Notifications

This distinction is extremely important.

| Feature | Local Notification | Push Notification |
|---|---|---|
| Main source | Device/app | Remote server |
| Backend required | Not for basic scheduling | Usually yes |
| Internet required for basic scheduling | No | Yes for remote delivery |
| Example | Water reminder | New chat message |


Think about this question:

> Does the information already exist on the device and simply need to be shown later?

If yes, a local notification is often appropriate.

Example:

```text
"Remind me tomorrow at 8 AM."
```

The device can schedule that reminder.

But:

> Tell the user when their order status changes on the server.

requires remote communication, so push notifications are appropriate.

---

## 8. Scheduled Notifications

A scheduled notification is configured to appear at a future time or after a specified trigger.

Basic flow:

```text
Now
 ↓
Schedule notification
 ↓
Wait
 ↓
Trigger condition occurs
 ↓
Notification appears
```

Possible examples:

```text
After 10 minutes
Every day at 8 AM
At a particular date/time
At a recurring time
```

Expo provides:

```js
Notifications.scheduleNotificationAsync()
```

The important idea is that scheduling creates a notification request with:

```text
Content
+
Trigger
```

Conceptually:

```js
{
  content: {
    title: 'Reminder',
    body: 'Time to study!',
  },

  trigger: {
    // when the notification should fire
  },
}
```

---

## 9. Immediate vs Scheduled Notification

These are different concepts.

## Immediate

You want the notification now:

```text
Button pressed
     ↓
Create notification
     ↓
Display notification
```

## Scheduled

You want it later:

```text
Button pressed
     ↓
Create notification request
     ↓
Register trigger
     ↓
Wait
     ↓
Trigger occurs
     ↓
Notification appears
```

Both concepts are important when learning local notifications.

---

## 10. Foreground State

Foreground means:

```text
Application is currently open and active
```

For example:

```text
User
 ↓
Opens your app
 ↓
App is visible
 ↓
Notification arrives
```

When a notification arrives while the application is in the foreground, the notification presentation behavior can be controlled using the notification handler.

This is why:

```js
Notifications.setNotificationHandler()
```

is important.

---

## 11. Background State

Background means the application is not currently the active screen.

For example:

```text
User opens app
      ↓
Presses Home
      ↓
Another screen/app becomes visible
      ↓
Your app is in background
```

A scheduled notification is useful in this situation because the operating system can present the notification without your React Native screen being visible.

---

## 12. Terminated / Quit State

The user may completely close the application.

For example:

```text
User opens app
      ↓
Schedules reminder
      ↓
Closes app
      ↓
Time passes
      ↓
Trigger time arrives
      ↓
Operating system can present notification
```

This is one of the major benefits of local scheduled notifications.

However, actual behavior can depend on:

- Operating system
- Permission state
- Device settings
- Battery restrictions
- Notification configuration
- Type of notification

## 13. Notification Permission

After package setup, the next major concept is permission.

The user controls whether the application is allowed to send notifications.

The application should therefore check the current permission state.

The API is:

```js
Notifications.getPermissionsAsync()
```

---

## 14. Checking Permission

> **Normal permission flow:** First call `getPermissionsAsync()`. If the returned `status` is not `granted`, call `requestPermissionsAsync()`. Do not request permission repeatedly when it is already granted.

Basic example:

```js
const permission =
  await Notifications.getPermissionsAsync();

console.log(permission);
```

A simplified mental model is:

```text
Permission status
│
├── granted
├── denied
└── undetermined / not yet decided
```

The exact returned object can contain additional platform-specific fields. In normal Expo usage, check the returned `status` value and request permission only when it is not already `granted`.

The returned object can contain additional information, so logging it during development is useful:

```js
console.log(
  await Notifications.getPermissionsAsync()
);
```

---

## 15. Why Check Before Requesting?

Imagine requesting permission every time the application starts:

```js
await Notifications.requestPermissionsAsync();
```

A better flow is:

```text
Check permission
       ↓
Granted?
   /       \
 Yes       No
  |         |
Continue   Request
```

This avoids unnecessarily requesting permission when it is already granted.

---

## 16. Requesting Permission

If permission has not already been granted:

```js
const {
  status,
} =
  await Notifications.requestPermissionsAsync();
```

Then:

```js
if (status === 'granted') {

  console.log(
    'Permission granted'
  );

} else {

  console.log(
    'Permission denied'
  );

}
```

The flow is:

```text
requestPermissionsAsync()
        ↓
Operating System
        ↓
Permission prompt
        ↓
User decision
        ↓
Your application
        ↓
Permission status
```

---

## 17. Basic Permission Function

A reusable function is better than duplicating permission logic.

```js
const requestNotificationPermission =
  async () => {

    const {
      status,
    } =
      await Notifications
        .requestPermissionsAsync();

    if (status !== 'granted') {

      console.log(
        'Notification permission denied'
      );

      return false;
    }

    console.log(
      'Notification permission granted'
    );

    return true;
  };
```

Usage:

```js
const allowed =
  await requestNotificationPermission();

if (allowed) {

  console.log(
    'We can continue with notifications'
  );

}
```

## 18. Handling Permission Denial

Never assume the user will grant permission.

Handle:

```js
status !== 'granted'
```

Example:

```js
if (
  finalStatus !==
  'granted'
) {

  Alert.alert(
    'Notifications Disabled',
    'Please enable notifications in Settings.'
  );

  return false;
}
```

This is much better than silently failing.

## 21. Complete Permission Example

```jsx
import {
  Alert,
  Linking,
} from 'react-native';

import * as Notifications
  from 'expo-notifications';

const requestNotificationPermission =
  async () => {

    try {

      const {
        status: existingStatus
      } =
        await Notifications
          .getPermissionsAsync();

      let finalStatus =
        existingStatus;

      if (
        existingStatus !==
        'granted'
      ) {

        const {
          status,
        } =
          await Notifications
            .requestPermissionsAsync();

        finalStatus = status;
      }

      if (
        finalStatus !==
        'granted'
      ) {

        Alert.alert(

          'Notifications Disabled',

          'Please enable notifications in Settings for important updates.',

          [
            {
              text: 'Cancel',
            },

            {
              text: 'Open Settings',

              onPress: () =>
                Linking.openSettings(),
            },
          ]

        );

        return false;
      }

      return true;

    } catch (error) {

      console.error(
        'Permission error:',
        error
      );

      return false;
    }
  };
```

## 22. Notification vs `setTimeout()`

This is an important React Native concept.

You might think:

```js
setTimeout(() => {
  console.log('Reminder');
}, 10000);
```

could replace notifications.

It cannot provide the same behavior.

`setTimeout()` is a JavaScript timer.

A local notification is handled through the operating system's notification infrastructure.

Compare:

```text
setTimeout()
    ↓
JavaScript runtime
```

versus:

```text
scheduleNotificationAsync()
    ↓
Notification system / OS
```

A timer is therefore not a replacement for a scheduled local notification.

requires operating-system notification functionality.

# Part 4 - Notification Triggers & Scheduling with `expo-notifications`

In Part 3, we learned:

```text

        ↓

        ↓

        ↓

```

This part focuses specifically on the **trigger**.

The key question is:

> **When should the notification appear?**

---

## 1. What Is a Notification Trigger?

A notification trigger defines the condition that determines when a scheduled notification should fire.

Remember:

```text
content = WHAT
trigger = WHEN
```

Example:

```js
content: {
  title: 'Study Reminder',
  body: 'Time to study React Native!',
}
```

answers:

```text
WHAT should the user see?
```

while:

```js
trigger: {
  // timing configuration
}
```

answers:

```text
WHEN should the notification fire?
```

---

## 2. Why Is the Trigger Important?

Suppose the user creates:

```text
Reminder:
Drink Water
```

The application still needs to know:

```text
When?
```

Possible requirements:

```text
After 10 seconds
After 30 minutes
At 8:00 AM
Tomorrow at 10:00 AM
Every day at 8:00 AM
Every Monday at 9:00 AM
```

The trigger represents this timing requirement.

---

## 3. Notification Scheduling Model

A useful mental model is:

```text
User creates reminder
        ↓
Application creates content
        ↓
Application creates trigger
        ↓
scheduleNotificationAsync()
        ↓
Notification ID returned
        ↓
Operating system manages request
        ↓
Trigger condition occurs
        ↓
Notification appears
```

The trigger is therefore one of the most important parts of local notification scheduling.

For our learning, think about notification triggers in these categories:

# Part 5 - Managing Scheduled Notifications with `expo-notifications`

In Part 4, we learned how to decide **when** a notification should fire.

Now we move to an equally important question:

> **What do we do after a notification has already been scheduled?**

A real application should not only create notifications. It should also be able to:

```text
View scheduled notifications
        ↓
Identify notifications
        ↓
Cancel one notification
        ↓
Cancel all notifications
        ↓
Update a reminder
        ↓
Replace an old notification
        ↓
Keep application data synchronized
```

This is what notification management means.

---

## 1. Why Do We Need Notification Management?

Imagine a reminder application.

The user creates:

```text
Study React Native
Tomorrow at 8 AM
```

The application schedules a notification.

Later, the user changes it to:

```text
Study React Native
Tomorrow at 10 AM
```

Now the application has a problem.

If it simply creates another notification:

```text
Old notification
8 AM

New notification
10 AM
```

the user may receive **both**.

That is not what the user asked for.

A better flow is:

```text
Old reminder
     ↓
Find old notification ID
     ↓
Cancel old notification
     ↓
Create new notification
     ↓
Save new notification ID
```

This is why notification management is necessary.

```text

```

# Part 6 - Notification Listeners with `expo-notifications`

Until now, we learned how to:

```text
Request permission
      ↓
Create notification
      ↓
Schedule notification
      ↓
Get notification ID
      ↓
Cancel / manage notification
```

Now we need to understand another important part:

> **How does our React Native application know that a notification was received?**

This is where **notification listeners** become important.

---

## 1. What Is a Notification Listener?

A notification listener allows your application to react when a notification-related event occurs.

Think of it like:

```text
Notification event
       ↓
Listener is waiting
       ↓
Listener callback runs
       ↓
Application receives notification information
       ↓
Your code reacts
```

For example:

```text
Notification arrives
       ↓
Listener receives event
       ↓
Read title
       ↓
Read body
       ↓
Read data
       ↓
Update application state
```

---

## 2. Why Do We Need Listeners?

Suppose a notification is received while your application is running.

Your application might want to:

```text
Update UI
Show an in-app message
Refresh data
Log the notification
Read notification data
Update a badge
Trigger some application logic
```

A listener provides a way for JavaScript code to respond to the notification event.

---

## 3. The Main Listener API

For notifications received while the application is running, the important API is:

```js
Notifications.addNotificationReceivedListener()
```

Basic shape:

```js
const subscription =
  Notifications
    .addNotificationReceivedListener(
      notification => {

        console.log(
          'Notification received:',
          notification
        );

      }
    );
```

The callback runs when the listener receives a notification event.

---

## 4. Understanding the Callback

The callback:

```js
notification => {

  console.log(
    notification
  );

}
```

receives notification information.

You can inspect it:

```js
console.log(
  'Notification:',
  notification
);
```

During development, logging the complete object is useful because it lets you understand the structure of the notification.

---

## 5. Basic Listener Example

```jsx
import React, {
  useEffect,
} from 'react';

import {
  View,
  Text,
} from 'react-native';

import * as Notifications
  from 'expo-notifications';

export default function NotificationScreen() {

  useEffect(() => {

    const subscription =
      Notifications
        .addNotificationReceivedListener(
          notification => {

            console.log(
              ' Notification received'
            );

            console.log(
              notification
            );

          }
        );

    return () => {

      subscription.remove();

    };

  }, []);

  return (

    <View>

      <Text>
        Notification Listener Screen
      </Text>

    </View>
  );
}
```

This is the basic React pattern:

```text
Mount component
      ↓
Create listener
      ↓
Notification arrives
      ↓
Callback executes
      ↓
Unmount component
      ↓
Remove listener
```

---

## 6. Why Use `useEffect()`?

Listeners are subscriptions.

A subscription should generally be:

```text
Created
when needed
```

and:

```text
Removed
when no longer needed
```

React's:

```js
useEffect()
```

is a natural place to manage this lifecycle.

Example:

```js
useEffect(() => {

  const subscription =
    Notifications
      .addNotificationReceivedListener(
        ...
      );

  return () => {

    subscription.remove();

  };

}, []);
```

The empty dependency array:

```js
[]
```

means the effect is set up when the component mounts and cleaned up when it unmounts.

---

## 7. Why Is Cleanup Important?

Suppose you do this:

```js
useEffect(() => {

  Notifications
    .addNotificationReceivedListener(
      notification => {
        console.log(notification);
      }
    );

}, []);
```

but never remove the listener.

Depending on how the component is mounted and unmounted, you can end up with unwanted subscriptions.

The safer pattern is:

```js
const subscription =
  Notifications
    .addNotificationReceivedListener(
      callback
    );

return () => {

  subscription.remove();

};
```


This distinction is important.



```js
Notifications
  .addNotificationReceivedListener(...)
```

```text

    ↓
OBSERVE / RESPOND
```

## 19. Schedule vs Listen

| API | Purpose |
|---|---|
| `scheduleNotificationAsync()` | Schedule a notification |
| `addNotificationReceivedListener()` | Listen for a received notification |
| `getAllScheduledNotificationsAsync()` | Read scheduled notification requests |
| `cancelScheduledNotificationAsync()` | Cancel one scheduled notification |
| `cancelAllScheduledNotificationsAsync()` | Cancel all scheduled notifications |

This distinction is extremely important.

## 20. Listener and Foreground Notifications

When your application is running in the foreground, notification behavior is influenced by the notification handler configured earlier.

For example:

```js
Notifications.setNotificationHandler({

  handleNotification:
    async () => ({

      shouldShowBanner:
        true,

      shouldShowList:
        true,

      shouldPlaySound:
        true,

      shouldSetBadge:
        true,

    }),

});
```

The handler controls presentation behavior.

The listener allows your application code to react to the received notification event.

These are related but different responsibilities.

---

## 21. Handler vs Listener

This is one of the most important distinctions in this module.

### Notification Handler

```js
Notifications.setNotificationHandler(...)
```

answers:

> **How should the notification be presented while the app is in the foreground?**

### Notification Listener

```js
Notifications.addNotificationReceivedListener(...)
```

answers:

> **What should my JavaScript application do when the notification is received?**

Mental model:

```text
Notification received
        │
```

## 30. Why `subscription.remove()`?

The call:

```js

  .addNotificationReceivedListener(...)
```

returns a subscription object.

That object represents the active listener.

Calling:


Mental model:

```text

          ↓

          ↓
```

```text
        ↓

        ↓
```

> **What happens when the user interacts with the notification?**

```text
        ↓
```

## 1. Notification Received vs Notification Response

These are two different concepts.

### Notification received

Means:

```text
A notification was delivered/received.
```

The API we learned in Part 6 is:

```js
Notifications.addNotificationReceivedListener()
```

### Notification response

Means:

```text
The user interacted with the notification.
```

For example:

```text
User taps notification
```

The important API is:

```js
Notifications.addNotificationResponseReceivedListener()
```

Mental model:

```text
Notification
      │
      ├── Received
      │      ↓
      │   Received Listener
      │
      └── User Interaction
             ↓
       Response Listener
```

## 2. The Response Listener

The main API is:

```js
Notifications.addNotificationResponseReceivedListener()
```

Basic example:

```js

        console.log(
          'Notification response:',
          response
        );

      }
    );
```

The callback receives a **notification response object**.

## 6. Why Cleanup Is Important

A response listener is also a subscription.

```text

Listener 2
Listener 3
```

may all execute.

Correct pattern:

```js

  Notifications
    .addNotificationResponseReceivedListener(
      callback

  subscription.remove();

};
```

# Part 8 - Android Notification Channels with `expo-notifications`

This part is focused on an **Android-specific concept**:

> **Notification Channels**

---

## 1. What Is a Notification Channel?

Starting with **Android 8.0 (API level 26)**, notifications must belong to a notification channel. A channel defines the visual and auditory behavior for notifications assigned to it. Users can also control channel-level settings from Android's notification settings. citeturn0search0

Think of a channel as a **category of notifications**.

For example:

```text
My App
│
├── Messages
│
├── Orders
│
├── Reminders
│
└── Promotions
```

Each category can have its own notification behavior.

---

## 2. Why Were Channels Introduced?

Before notification channels, an application could largely control notification behavior directly.

Android introduced channels so that users have more control over notification categories.

For example:

```text
Messages
→ Important

Promotions
→ Less important

Reminders
→ Normal
```

The user can manage these categories from Android's notification settings.

Therefore:

```text
App Developer
      ↓
Creates notification channels
      ↓
User
      ↓
Controls channel behavior
```

---

## 3. Notification Channel Mental Model

Think:

```text
Notification
      ↓
Channel
      ↓
Android System
      ↓
User-visible notification
```

More specifically:

```text
Notification Content
        +
Channel ID
        ↓
Android Notification Channel
        ↓
Channel configuration
        ↓
Notification presentation
```

---

## 4. Android vs iOS

Notification channels are an **Android-specific** concept.

```text
Android
   ↓
Notification Channels
```

iOS does not use Android-style notification channels.

Therefore, channel code should usually be guarded:

```js
if (Platform.OS === 'android') {
  // Android channel logic
}
```

---

```text

```

The second argument is:

```text

```

## 33. Important Android Rule: Channels Are Persistent

Once an Android notification channel has been created, its settings are controlled by Android and the user.

Expo's SDK 54 documentation notes an important limitation:

> After a channel is created, only its name and description can be modified programmatically; other channel settings are controlled by Android. citeturn0search0

## 34. Why Can't We Freely Change Importance Later?

Suppose you create:




The OS owns those channel-level settings after creation.

## 1. What Is a Notification Category?


# Part 11 - Advanced Scheduling & Trigger Types with `expo-notifications`

This part continues from:

In the earlier scheduling parts, we learned the basic idea:

```text
Notification Content
        +
Trigger
        ↓
Scheduled Notification
```

Now we go much deeper into **triggers**.

The goal is to understand how to build real-world schedules such as:

```text
In 10 seconds
Tomorrow at 9:00 AM
Every 20 minutes
Every day at 8:00 PM
Every Monday at 9:00 AM
Every month on the 1st
Every year on a specific date
At a specific calendar date/time
```

Expo SDK 54 provides several schedulable trigger types, including:

```text
TIME_INTERVAL
DATE
DAILY
WEEKLY
MONTHLY
YEARLY
CALENDAR
```

The exact trigger availability differs by platform. For example, Expo documents dedicated daily/weekly/monthly/yearly trigger types for Android, while iOS uses calendar-based triggers for equivalent calendar scheduling. citeturn0search0

---

## 1. What Is a Notification Trigger?

A trigger answers one question:

> **When should this notification be delivered?**

For example:

```text
Content:
"Time to study"

Trigger:
10 seconds from now
```

or:

```text
Content:
"Daily standup"

Trigger:
Every day at 9:00 AM
```

Mental model:

```text
Notification
      │
      ├── Content
      │     ├── title
      │     ├── body
      │     └── data
      │
      └── Trigger
            └── when?
```

---

## 2. Content vs Trigger

This distinction is extremely important.

### Content

```js
content: {
  title: 'Study Reminder',
  body: 'Time to study React Native.',
}
```

means:

```text
WHAT should the user see?
```

### Trigger

```js
trigger: {
  type:
    Notifications
      .SchedulableTriggerInputTypes
      .TIME_INTERVAL,

  seconds: 10,
}
```

means:

```text
WHEN should it happen?
```

So:

```text
CONTENT
 ↓
What?

TRIGGER
 ↓
When?
```

---

## 3. `scheduleNotificationAsync()`

The main scheduling API is:

```js
Notifications.scheduleNotificationAsync()
```

It receives a notification request:

```js
await Notifications
  .scheduleNotificationAsync({

    content: {
      // notification content
    },

    trigger: {
      // scheduling rule
    },

  });
```

Expo documents this API as scheduling a notification to be triggered in the future. It returns a notification identifier that can later be used for cancellation or identification. citeturn0search0

---

## 4. Notification Identifier

When you schedule a notification:

```js
const identifier =
  await Notifications
    .scheduleNotificationAsync({
      // ...
    });
```

the API returns:

```text
notification identifier
```

Example:

```js
console.log(
  identifier
);
```

You can save this identifier.

Why?

Because later you can cancel the exact scheduled notification:

```js
await Notifications
  .cancelScheduledNotificationAsync(
    identifier
  );
```

This connects directly to Part 5.

---

## 5. Trigger Types Overview

The main trigger types are:

| Trigger | Meaning |
|---|---|
| `TIME_INTERVAL` | After a period of time |
| `DATE` | At one specific date/time |
| `DAILY` | Every day at a time |
| `WEEKLY` | Every week at a weekday/time |
| `MONTHLY` | Every month on a day/time |
| `YEARLY` | Every year on a date/time |
| `CALENDAR` | Match specified calendar date components, primarily iOS |

Expo SDK 54 exposes these through `SchedulableTriggerInputTypes`. citeturn0search0

## 6. `TIME_INTERVAL`

`TIME_INTERVAL` means:

> Trigger after a specified number of seconds has elapsed.


## 9. Important iOS Rule for Repeating Intervals

On iOS, when:

```js

```

the time interval must be at least:


Expo SDK 54 documents this requirement. citeturn0search0

Therefore, avoid:

```js

repeats: true,
```

for iOS repeating notifications.

Use:

```js

repeats: true,
```

or greater.

## 95. Advanced Scheduling Utility

```js
import * as Notifications
  from 'expo-notifications';

export async function
scheduleReminder({
  title,
  body,
  trigger,
}) {

  const next =
    await Notifications
      .getNextTriggerDateAsync(
        trigger
      );

  if (
    next === null
  ) {

    throw new Error(
      'Invalid or non-triggering schedule'
    );

  }

  const notificationId =
    await Notifications
      .scheduleNotificationAsync({

        content: {

          title,
          body,

        },

        trigger,

      });

  return {

    notificationId,

    nextTrigger:
      new Date(next),

  };

}
```

This gives your application:

```text

+

```

in one operation.

## 14. Step 5 - Permission Service

Example:

```js
import {
  Linking,
} from 'react-native';

import * as Notifications
  from 'expo-notifications';

export async function
getNotificationPermissions() {

  return Notifications
    .getPermissionsAsync();

}

export async function
requestNotificationPermissions() {

  return Notifications
    .requestPermissionsAsync();

}

export async function
ensureNotificationPermission() {

  const current =
    await Notifications
      .getPermissionsAsync();

  if (
    current.granted
  ) {

    return {
      status:
        'granted',

      permissions:
        current,
    };

  }

  if (
    !current.canAskAgain
  ) {

    return {
      status:
        'settings',

      permissions:
        current,
    };

  }

  const result =
    await Notifications
      .requestPermissionsAsync();

  if (
    result.granted
  ) {

    return {
      status:
        'granted',

      permissions:
        result,
    };

  }

  return {
    status:
      'denied',

    permissions:
      result,
  };

}

export async function
openNotificationSettings() {

  await Linking
    .openSettings();

}
```

## 16. Step 6 - Trigger Builder


Example:

```js
import * as Notifications
  from 'expo-notifications';

export function
buildTrigger(config) {

  switch (
    config.frequency
  ) {

    case 'interval':

      return {

        type:
          Notifications
            .SchedulableTriggerInputTypes
            .TIME_INTERVAL,

        seconds:
          config.seconds,

        repeats:
          config.repeats ??
          false,

      };

    case 'daily':

      return {

        type:
          Notifications
            .SchedulableTriggerInputTypes
            .DAILY,

        hour:
          config.hour,

        minute:
          config.minute,

      };

    case 'weekly':

      return {

        type:
          Notifications
            .SchedulableTriggerInputTypes
            .WEEKLY,

        weekday:
          config.weekday,

        hour:
          config.hour,

        minute:
          config.minute,

      };

    case 'monthly':

      return {

        type:
          Notifications
            .SchedulableTriggerInputTypes
            .MONTHLY,

        day:
          config.day,

        hour:
          config.hour,

        minute:
          config.minute,

      };

    case 'yearly':

      return {

        type:
          Notifications
            .SchedulableTriggerInputTypes
            .YEARLY,

        month:
          config.month,

        day:
          config.day,

        hour:
          config.hour,

        minute:
          config.minute,

      };

    case 'date':

      return {

        type:
          Notifications
            .SchedulableTriggerInputTypes
            .DATE,

        date:
          config.date,

      };

    default:

      throw new Error(
        `Unsupported frequency: ${config.frequency}`
      );

  }

}
```

## 19. Step 7 - Notification Scheduler

```text

```

Example:

```js
import * as Notifications
  from 'expo-notifications';

export async function
scheduleNotification({
  content,
  trigger,
}) {

  const next =
    await Notifications
      .getNextTriggerDateAsync(
        trigger
      );

  if (
    next === null
  ) {

    throw new Error(
      'Invalid or non-triggering notification trigger'
    );

  }

  const notificationId =
    await Notifications
      .scheduleNotificationAsync({

        content,

        trigger,

      });

  return {

    notificationId,

    nextTrigger:
      new Date(next),

  };

}
```

## 36. Step 13 - Create Reminder Service

Now combine everything.

```js
import {
  ensureNotificationPermission,
} from './notificationPermissions';

import {
  buildTrigger,
} from '../utils/triggerBuilder';

import {
  scheduleNotification,
} from './notificationScheduler';

export async function
createReminder(
  reminder
) {

  const permission =
    await ensureNotificationPermission();

  if (
    permission.status !==
    'granted'
  ) {

    return {
      success:
        false,

      reason:
        permission.status,

    };

  }

  const trigger =
    buildTrigger(
      reminder
    );

  const result =
    await scheduleNotification({

      content: {

        title:
          reminder.title,

        body:
          reminder.body,

        categoryIdentifier:
          'reminder',

      },

      trigger,

    });

  return {

    success:
      true,

    notificationId:
      result.notificationId,

    nextTrigger:
      result.nextTrigger,

  };

}
```

## 45. Edit Function

```js
export async function
updateReminder(
  reminder
) {

  if (
    reminder.notificationId
  ) {

    await cancelNotification(
      reminder.notificationId
    );

  const result =
    await createReminder(
      reminder
    );

    !result.success
  ) {

    return result;

    result.notificationId;

    true;

  return {

    success:
      true,

  };

}
```


## 75. Generic Response Handler

```js
function
handleNotificationResponse(
  response
) {

  const {
    actionIdentifier,
    notification,

  const data =
    notification
      .request
      .content
      .data;

  if (
    data?.type !==
    'REMINDER'

  }

  const reminderId =
    data.reminderId;

  switch (
    actionIdentifier
  ) {

      .DEFAULT_ACTION_IDENTIFIER:

      // Open reminder

      break;

    case 'COMPLETE':

      // Complete reminder

      break;

    case 'SNOOZE':

      // Snooze reminder

  }

}
```

## 32. Pending Notification Response

## 98. Local Notifications vs Push Notifications

This documentation has focused on:

```text
Local Notifications
```

A local notification is scheduled by the application/device.

Conceptually:

```text
App
 ↓
OS
 ↓
Notification
```

Push notifications involve a remote sender/service:

```text
Server
 ↓
Push service
 ↓
Device
 ↓
Notification
```

These are different architectures.

For the SDK 54 class material covered here, the focus is local notification functionality.

---

## 99. Local Notification Use Cases

Good examples:

```text
Reminders
Study schedules
Workout reminders
Medication reminders
Calendar events
Timers
Habits
Offline tasks
Local alarms
```

The exact product requirements determine whether local notifications are appropriate.

## 100. When Local Notifications Are Not Enough

If the requirement is:

```text
A server tells the device about a new event
```

then a local schedule alone is not enough.

For example:

```text
New chat message
 ↓
Server creates event
 ↓
Device receives push
```

This belongs to push notification architecture.

## 101. Final Comparison

| Feature | Local Notification | Push Notification |
|---|---|---|
| Scheduled on device | Yes | Usually server-driven |
| Requires backend | No | Usually yes |
| Works for local reminders | Excellent | Usually unnecessary |
| Server-triggered event | No | Yes |
| Offline scheduling | Yes | Depends on received push |
| Typical use | Reminders | Messages/events |
